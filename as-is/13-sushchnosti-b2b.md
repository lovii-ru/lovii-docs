# 13. Сущности b2b: юрлицо, магазин, точка — словарь и разбор «бардака» кабинета МСП

> Срез: 2026-09-17, цифры — живой staging (SQL этого дня). Рабочая заметка (класс W).
> Это главный док про «что есть что». Формат — [README](README.md).

## Четыре сущности — одна цепочка

| Как называем | Таблица | Что это | Пример (твои данные) |
|---|---|---|---|
| **Юрлицо** | `lovii_b2b.partners` | компания с ИНН, договор, рублёвый счёт; верификация = `verified_at` | 263 ООО «АТМОСФЕРА», 265 ООО «АКСИОМА» |
| **Магазин (витрина)** | `merchants` | вывеска для покупателя: имя, лого, тип, тариф; товары принадлежат ему | 280 «Пышки & Пончики» |
| **Точка (филиал)** | `merchant_branches` | адрес, часы, тумблеры доставки, min_order; заказы и товары привязаны к ней | 1024 «На Белы Куна» |
| **Пользователь кабинета** | `lovii_b2b.partner_users` + `partner_memberships` | твой аккаунт в b2b/app-кабинете (мост на users по `core_user_id`); роль и доступ к точкам | user 51 → owner |

```text
Юрлицо (partners, 263 «АТМОСФЕРА», ИНН 7842216839)
   │ partner_id                        ── рублёвый счёт: accounts owner_type=partner (52 587,00 ₽)
   ├──> Магазин (merchants, 280 «Пышки & Пончики», тариф Старт)
   │        │ merchant_id
   │        └──> Точка (merchant_branches, 1024 «На Белы Куна», 29 товаров)
   │                 └── /stores/1024 ← сюда ведёт витрина; заказы имеют branch_id=1024
   └──> членства (partner_memberships): ты = owner → видишь все точки юрлица
```

Ключевые следствия:
- **Один магазин может иметь несколько точек** (филиалов) — «Пончики» на локальном
  стенде это вторая точка с собственным merchant+branch.
- **Покупатель видит магазин** (вывеску), но география/часы/доставка — от точки.
  `/stores/{id}` = id **точки** (SZ-005).
- **Деньги капают на юрлицо** (90% на счёт ИНН), пул — по юрлицу точки.
- Мерчантов у юрлица может быть несколько (сети), и наоборот — один мерчант на юрлицо.

## Пятая сущность: заявка (путь подключения)

`partner_applications` — заявка «ЛОВИ Бизнес». При создании **одновременно
материализует**: юрлицо-черновик (partners, verified_at=NULL) + пользователя
кабинета + membership owner + магазин (pending_moderation) + филиал-черновик
(если был адрес). Дальше: апрув представителя → платёж 1 ₽ → (ручная) верификация.
Подробно — [05](05-rol-i-kabinety.md).

## Шестая: товары

- **Позиция МСП** = `merchant_offers` — создаётся в кабинете, привязана к магазину
  и точке (branch_id), цена в копейках. Фото/описание физически лежат в связанном
  `catalog_products` (media).
- **Kuper-каталог** = те же `catalog_products` + офферы импорта (`source_type` ≠
  manual) — второй, импортный контур (выключен, `INTEGRATIONS_ENABLED=false`).

## Что происходит в кабинете МСП (app) — и почему «бардак»

Кабинет строится цепочкой `MspAccess`: User → PartnerUser → активные memberships →
мерчанты этих юрлиц → их филиалы (MspAccess.php:36–67). Табы и заказы — по
выбранной точке (`branch_id`). Из этого следуют реальные источники путаницы:

1. **Партнёр без магазина = пустое место.** АКСИОМА (265) верифицирована, но
   мерчантов у неё нет → в кабинете от неё ничего не появляется («К профилю пока
   не привязана точка», если других нет).
2. **Магазины-черновики без точки и витрины.** На staging сейчас: Grand → merchant
   283 (pending_moderation, 0 филиалов), «Пекарня Статус-92» → 284 (то же),
   «Заветный хлеб» → 285 (то же). Они всплывают в обзоре как «пустые» карточки
   (полировка «прятать черновики без витрины» делалась на локальном стенде, до
   staging не доехала).
3. **Дубли юрлиц.** Grand (268) и «Статус-92» (269) — **один ИНН 970512345688**,
   два юрлица-черновика. Плюс исторически у АТМОСФЕРЫ были два пути подключения
   (ручная верификация 263 и заявка «Пончики» через старый SZ-007-путь на локальном
   стенде → второй partner). Каждая новая заявка создаёт **новое** юрлицо —
   склейки по ИНН нет.
4. **Имя магазина ≠ имя точки.** «Пышки & Пончики» — магазин; «На Белы Куна» —
   точка. В обзоре теперь показывается точка (карточки слиты с селектором,
   SZ-038), но заголовки/настройки берут `name` филиала, а у SQL-вставленных
   филиалов name бывает NULL → пустой заголовок.
5. **«Рабочая точка» глобальна** (localStorage `loviMspBranchId` без привязки к
   юзеру) — после тестов под другим аккаунтом можно унаследовать чужую точку
   (лечится валидацией 404 + сбросом, SZ-038). Селектор виден только при ≥2 филиалах.
6. **Тариф и комплаенс — на разных сущностях**: тариф точки — на мерчанте
   (`merchants.tariff`), верификация — на юрлице (`partners.verified_at`),
   апрув представителя — тоже на юрлице (`representative_approved_at`). Поэтому
   «точка есть, а витрина скрыта» = юрлицо не верифицировано (teaser).

## Чистая терминология (предлагаю придерживаться)

- **Юрлицо/партнёр** — `partners` (компания, ИНН, счёт). Не «мерчант».
- **Магазин/витрина** — `merchants` (вывеска, каталог). Не «точка».
- **Точка/филиал** — `merchant_branches` (адрес, часы, заказы). Слово «мерчант»
  в интерфейсах больше не показывать покупателю/МСП.
- **Позиция** — `merchant_offers` (не «товар каталога» — это другое: catalog_products).

## Кандидаты в «не хватает» (решает владелец)

1. Склейка дубликатов юрлиц по ИНН (Grand/Статус-92) + правило: заявка на
   существующий ИНН не создаёт второго партнёра, а привязывается к существующему.
2. Прятать в обзоре МСП магазины без филиалов/витрины (довести до staging).
3. Обязательное имя точки при создании (и дозаполнить NULL-имена).
4. Единый глоссарий в интерфейсах (вывеска/точка/юрлицо) — без слова «мерчант».
5. Показывать в кабинете статус юрлица (верифицировано?) рядом с точкой — чтобы
   было видно, почему витрина в «Скоро».
