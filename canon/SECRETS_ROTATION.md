## 2. Порядок ротации (утверждаемый план)

| Шаг | Что | Кто | Когда |
|:--|:--|:--|:--|
| 1 | GitHub PAT → fine-grained + обновить remotes/секреты | владелец | до прод-деплоев |
| 2 | Аудит authorized_keys + GitHub Actions-секреты | владелец + агент готовит команды | до прод-деплоев |
| 3 | Telegram/MAX/VK токены — ротация, актуализация .env, перезапуск воркеров | владелец (кнопки во внешних UI) + агент (env/рестарт) | перед прод-деплоем core |
| 4 | MAX-файл «Боты Макс.txt»: сверить подписи, зафиксировать bot_id ↔ токен | агент (по поручению) | с шагом 3 |
| 5 | Пароли БД прод (≠ staging), права app-юзера | владелец | при создании прод-БД |
| 6 | APP_KEY прод — сгенерировать НОВЫЙ при пустой БД (не ротировать после данных) | владелец | при инициализации прода |
| 7 | VAPID прод: `php artisan push:generate-vapid --force` → `.env` | агент + владелец подтверждает | при прод-деплое core |
| 8 | Т-Банк: тест-ключи не в прод-.env; бой — при подключении эквайринга | владелец | к деньгам (трек I) |
| 9 | Финальный прогон `restrictions:report`-подобных проверок не требуется; проверка: пуши/OTP/почта live на проде | владелец + агент | после прод-деплоя |

## 3. Инцидент-план (черновик: утечка секрета)

1. **Отключить источник утечки**: удалить/закрыть пост/файл/чат, отозвать токен
   у провайдера (BotFather / MAX / VK / GitHub → Settings → Tokens / провайдер почты).
2. **Сменить секрет** и внести в `.env` затронутого окружения (staging/prod).
3. **Рестарт** затронутых сервисов: core (воркеры Telegram/MAX поллеров,
   Horizon), b2b-стек при необходимости.
4. **Проверить следы использования**: логи ботов/провайдера на чужие вызовы за
   период компрометации; GitHub — Security log + recent CI runs.
5. **Записать инцидент** в `canon/FINDINGS.md` (дата, секрет, объём, действия).
6. **Особые случаи**: APP_KEY — не ротировать «в горячем режиме» (зашифрованные
   данные станут нечитаемы); утечка APP_KEY = рассматривать как утечку всех
   шифрованных полей → план ротации с миграцией данных обсуждается отдельно.
