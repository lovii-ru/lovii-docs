> Репо: `lovii-core` (ядро), `lovii-app` + `lovii-b2b`/`lovii-admin` (поверхности)

## Постановка (что должно получиться)

Единая система «тихого удаления» для пользовательских сущностей. Принцип
владельца: **удаление для системы — отметка; физическое удаление данных —
только системно, по времени, с высоким доступом**.

1. **Tombstone (мягкое удаление)**: при удалении сущность не исчезает из БД —
   ставится отметка (`deleted_at` + причина + кто удалил), сущность исчезает из
   всех витрин/выдач/API, но остаётся видимой для аудита и финконтурa
   (ledger-ноги не трогаем никогда).
2. **Отложенное физическое удаление** — отдельный процесс (очередь/команда в
   schedule), который спустя установленный срок (retention) зачищает ПИИ
   данных сущности; запускается только под высоким доступом (console-only,
   не из UI/API), с журналом.
3. **Запрет пересоздания с теми же данными**: уникальные ключи живых сущностей
   должны учитывать tombstone так, чтобы удалённый телефон/ИНН/промокод НЕ
   освобождался для повторной регистрации (анти-фрод; срок удержания = retention).
   Сейчас наоборот: partial unique-индексы пропускают soft-deleted строки.
4. **Покрытие сущностей**: профиль покупателя (user), юрлицо МСП (partner),
   мерчант (бренд), торговая точка (branch). Для точки/мерчанта — каскад
   по модели «мерчант=дефолт, точка=переопределение» (канон T-025): удаление
   мерчанта гасит его точки/витрины/правила лояльности.
5. **Surfaces**: UI удаления (подтверждение + честный текст «что исчезнет»)
   там, где сущность создаётся; для профиля — самообслуживание покупателя;
   для МСП/мерчанта/точки — кабинет b2b + admin.

## Что НЕ входит

- Физическое удаление по запросу пользователя из UI — только системный процесс.
- Удаление/правка ledger, заказов, платежей — финансовая история неприкосновенна
  (канон T-023: append-only).
- 152-ФЗ «право на забвение» как юртребование — отдельная юркарта (Б-серия).
