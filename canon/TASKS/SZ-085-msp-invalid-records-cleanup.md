# SZ-085 — Инструмент очистки невалидных МСП-записей (заявки/черновики юрлиц с неподтверждённым ИНН)

> Статус: **Открыта** · Приоритет: **P1, вне очереди** (постановка владельца
> 2026-09-30: «хочу инструмент удаления МСП для перерегистрации / реестров по
> ИНН — защита от невалидных записей, спама представителей, неподтверждённых ИНН»)
> Исполнитель: zcode · Репо: `lovii-core` (+ admin/b2b поверхности позже)
> Это **срез SZ-084** («тихое удаление») — можно и нужно сделать до общих фаз,
> механика (tombstone + высокая ступень доступа) — та же. Родитель: SZ-084,
> ресёрч: RES-012 (§1–6 код, §7 практики).

## Проблема (факты из RES-012-доресёрча 2026-09-30)

1. **При reject заявки ничего не удаляется**: `RejectPartnerApplicationAction`
   (lovii-core, `/approvals/{id}/reject`, только из `awaiting_rep_approval`)
   ставит `status=failed` — а черновик `lovii_b2b.partners` (+ PartnerUser +
   membership Owner) остаётся в БД навсегда. Удалить его некем и нечем.
2. **Спам-математика против нас**: лимит `MAX_UNVERIFIED_OWNED_PARTNERS = 5`
   (PartnerUser::47, «5 неверифицированных юрлиц на пользователя») считается
   по тем самым черновикам — мусорные/отклонённые записи **съедают слоты**,
   пользователь упирается в лимит, повторная регистрация с тем же ИНН
   переиспользует старую грязную заявку (`findOwnApplication` по identity_key,
   reopen для failed/expired).
3. **Реестр ИНН захламляется**: partial unique держит только verified-партнёров;
   неверифицированные черновики-дубли по одному ИНН держатся только кодом
   (`PartnerInnGuard`), исторические дубли заявок существуют (identity_key
   индекс пока НЕуникальный — миграция 2026_09_27_120000, «шесть отклонённых
   заявок» в комментарии).
4. Поверхностей очистки нет: в admin — Partners view-only, ресурса заявок
   нет; в b2b — PartnerResource не существует.

## Что должно получиться

1. **Команда/сервис удаления МСП-записи** в lovii-core (единая точка, не
   прямые DELETE из Filament):
   - вход: заявка (`partner_applications`) или юрлицо (`lovii_b2b.partners`);
   - разрешено только для **не-verified** записей (`verified_at IS NULL`);
   - tombstone (deleted_at/статус failed+archived) черновика, а для чистого
     мусора — удаление черновика-партнёра + PartnerUser + membership +
     обнуление partner_id у заявки; заявка остаётся (аудит) в failed/expired;
   - если у юрлица уже есть мерчанты/точки/счета с движением — отказ с
     перечнем (как `cannot_force_delete` каталога; прецедент
     `business:reconcile-inn-duplicates`: dry-run/`--apply`/снимок/`--undo`).
2. **Anti-спам-реестр ИНН**: при удалении невалидной записи ИНН попадает в
   реестр хэшей (HMAC, §7.3 RES-012) с TTL-политикой — повторная подача
   заявки с тем же ИНН возможна (перерегистрация — легитимный сценарий), но
   помечается/лимитируется; полностью «сгоревшие» (многократно отклонённые)
   ИНН — на ревью.
3. **Освобождение слота**: удалённые/заархивированные черновики перестают
   считаться в `MAX_UNVERIFIED_OWNED_PARTNERS` и
   `assertUnverifiedPartnerCap`.
4. **Поверхность**: минимум — artisan-команда (высокая ступень: dry-run по
   умолчанию, снимок, журнал); следующий шаг — кнопка в admin (Shield-политика
   отдельной роли). Для представителя — готовый «Отклонить» уже есть, его
   дообогатить: reject → зачистка черновика той же командой (queue).
5. **Разовая зачистка накопленного**: команда с `--dry`-отчётом «все
   не-verified черновики старше N дней / failed-заявки без активности» →
   прогон на staging локально, отчёт владельцу, потом --apply.

## Границы

- verified-юрлица, юрлица с мерчантами/движением по счетам — НЕ трогаем
  (это фазы SZ-084: каскад, retention).
- Существующий лимит 5 и throttle 5/мин не менять в этой карточке (только
  учесть зачистку в подсчёте).
