# SZ-020 — C-1: Адреса city_name → city_id + эндпоинт ближайших городов

> Статус: **На приёмке** (2026-09-11, core `85321dc` + app `bca0ac5` — приёмка zcode запрашивается). Постановка (2026-09-10, из BACKLOG Трек C-1)
> Приоритет: **P2** — фундамент гео-фич (доставка, «рядом со мной»,
> фильтры города); после SZ-004 (геокодинг) данные уже чистые — окно для
> нормализации схемы
> Исполнитель: Super Z · Репо: `lovii-core` + `lovii-app` · Гейт: composer + yarn
> Контекст: дубли городов слиты SZ-004, ручные адреса геокодируются; но
> пользовательские адреса и часть сущностей хранят city_name строкой

## 1. Что

1. **Схема**: везде, где адрес/сущность ссылается на город строкой
   (`city_name`), — переход на `city_id` (FK на `cities`) с миграцией данных
   (строку резолвить по справочнику; не найдено — создать по канонам
   дедупликации SZ-004 §2.3);
2. **API**: `GET /v1/cities/nearest?lat=&lon=` — список активных городов
   вокруг точки (уже есть внутренний `FindNearbyCitiesQuery` — обернуть в
   эндпоинт с кэшем), + эндпоинт поиска города по префиксу (для пикера);
3. **openapi.yaml**: контракты новых эндпоинтов;
4. **app**: пикер города на адресных экранах переключается на city_id
   (без изменения UX).

## 2. NB

- Не ломать `GET /v1/cities` (если существует) — контракты старые клиентские
  сборки; deprecation — позже;
- Тесты: миграция-бэкфилл (строка → id), nearest-эндпоинт (радиус, пустой
  результат), guard дедупликации при создании.

## 3. Приёмка

- Владелец: адресные экраны работают как раньше (визуально ничего не меняется).
- zcode: приёмка кода.

## 4. Отчёт исполнителя (Super Z, 2026-09-11)

### 4.1. Схема (§1.1)
- `user_addresses` уже `city_id` (FK) — здесь нормализация была завершена ранее.
- Попутный runtime-баг исправлен: Create/UpdateAddressAction содержали
  `b_strtolower($data->cityName])` (валидный для PHP 8.5 синтаксис, но
  undefined-функция → создание/обновление адреса падало при обращении).
- `partner_applications`: миграция `+city_id` (FK nullable) с бэкфиллом
  (CityNameNormalizer; не найдено + координаты — создать по канону дедупа
  SZ-004 §2.3); `CreatePartnerApplicationAction` резолвит city_id сразу при
  наличии координат; `city_name` остаётся в API (совместимость).

### 4.2. API (§1.2)
- `GET /v1/cities/nearest?lat=&lon=` — активные города в радиусе (30 км,
  конфиг), ближайший первым; пустой радиус → fallback единственный ближайший;
  reuse кэша FindNearbyCitiesQuery.
- `GET /v1/cities?search=префикс&limit` — пикер (ё/регистр-независимо);
  `GET /v1/cities` без параметров — как раньше (кэш 24 ч).
- Адреса: `city_id` в Create/UpdateAddress — приоритетнее `city_name` (фолбэк —
  резолв по имени, старые клиенты не ломаются).
- openapi.yaml: /cities/nearest + параметры /cities.

### 4.3. App (§1.4)
- `CitySearchInput`: подсказки из справочника (`/cities?search=`) первым блоком —
  выбор передаёт точный `city_id`; geoSuggest остаётся fallback. Форма/пayload:
  `city_id` опционально. UX не изменился.
- Существующие адресные экраны: без изменений (визуально ничего не меняется — §3).
