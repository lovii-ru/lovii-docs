## 1. Что делать

Систематический проход **всего** b2b-кабинета как реальный партнёр
(b2b-staging, роль owner точки), по каждому ресурсу — полный CRUD-цикл
с проверкой каждой формы, каждой кнопки, каждого состояния. Найденное:
мелкое — чинить сразу (коммит на баг с тестом), крупное — чинить в этой же
задаче, но отдельным коммитом. Ни один экран не считается проверенным, пока
не пройдён руками на staging.

## 3. Сквозные проверки (помимо CRUD)

- **Мульти-тенантность**: партнёр A не видит/не редактирует данные партнёра B
  (проверить под двумя аккаунтами) — это безопасность, приоритет в любом находке;
- **Пустые состояния**: новый партнёр без мерчантов/филиалов/позиций — что
  видит, нет ли голых 500/пустых экранов;
- **Русские тексты**: орфография, «сырые» ключи переводов (看到的 как
  `b2b.fields.…`), обрезанные лейблы;
- **Загрузки**: HEIC с iPhone, PNG без сжатия, большие файлы (после SZ-003
  лимит 64М — нормализатор обязан всё пережить);
- **Пагинации/сортировки** на больших списках (Kuper-данные: 275 мерчантов —
  но из b2b виден только свой; проверить на тестовом партнёре с данными).

## 6. Дополнение владельца (2026-09-10): автотесты + сверка с витриной

Владелец: «хотелось бы автоматизировать тестирование функционала данного
кабинета, чтобы всё что там есть работало согласно сценариям, а всё что
мешает или не работает было выписано. Обязательно сверять всё, что он
сделал, с публичной витриной — чтобы было понятно, что из функционала
точно работает».

**Каждый ресурс из карты §2 проверяется в ТРИ слоя:**

1. **UI-проход на staging** (уже требует §1) — как реальный партнёр.
2. **Автотест в `lovii-b2b` (Pest)** — не только регрессы к найденным багам:
   на каждый ресурс — CRUD-цикл через формы (Livewire/Filament test-helpers),
   валидации, мульти-тенантность (чужие данные не читаются и не пишутся),
   пустые состояния. Тесты остаются в репо — это будущий регресс-щит кабинета.
3. **Сверка с витриной через публичный API api-staging** — после каждого
   значимого действия b2b: что увидит покупатель на app-staging.
   Минимальная карта соответствий:
   - категория создана/активна → `/v1/storefront?branch_id=…` содержит её
     (учитывать кэш дерева — после F-6 инвалидируется автоматически);
   - позиция (is_active+is_available, branch привязан — SZ-013) → видна на
     витрине и находитcя `/v1/search/offers?q=…`;
   - часы филиала → `/v1/storefront/info` availability совпадает;
   - лого/cover/фото → URL отвечает 200 и рендерится в ресурсах витрины;
   - мерчант/тип → `/v1/stores`, `/v1/popular-stores`, поиск — в соответствии
     с решением владельца по SZ-005 (merchant_type = явные фильтры).

**Итоговый артефакт для владельца** — матрица покрытия в отчёте (§4):
«ресурс/функция → работает в b2b? → тест в репо? → видно на витрине? →
находка/фикс». Цель: владелец одним взглядом видит, что из функционала
**точно работает** end-to-end, а что — нет и почему.

Связанное: SZ-013 (привязка позиций к филиалу) — входит в слой b2b по
Position; журнал SZ-006 §2 (F-1…F-8) — стартовый список, перенести строки
в общий журнал этой задачи при завершении SZ-006 §2.
