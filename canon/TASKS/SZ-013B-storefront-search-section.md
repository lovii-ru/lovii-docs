> Статус: **На приёмке** (2026-09-10, Super Z — отчёт §5; приёмка zcode ЗАПРОШАЕТСЯ). Контекст исходной постановки (2026-09-10, владелец: «поиск в разделе ПОИСК не работает

> Приоритет: **P1** — поиск = главный путь клиента к товару
> Исполнитель: Super Z · Репо: `lovii-core` + `lovii-app` · Гейт: composer + yarn
> Диагностика zcode: живые пробы API 2026-09-10 (см. §1)

## 1. Факты (проверено zcode на staging 2026-09-10)

- `/v1/search/merchants` — 200, релевантность ок («Дикси», «дикс» (префикс),
  «Пятерочка», «Пышки» находятся; пустой q = 24 магазина). После фикса
  SZ-005 результаты содержат `branch_id`, ссылки работают.
- `/v1/search/offers` — 200 после ops-фикса F-1 (SZ-006: `search:sync` +
  `scout:sync-index-settings`; до этого — 500 «branch_id not filterable»).
- **Вероятная причина жалобы:** ответ `/v1/search/offers` — это «сырые»
  документы Meilisearch-индекса `offers` (`id, title, price, old_price,
  unit_type…`), в которых **нет полей `image_url` и `requirements`** — а
  карточка товара в app типизирована как `StorefrontOfferCard`
  (`lovii-app/src/package/global-types/api/catalog.ts` §143), где `image_url`
  и `requirements` обязательны. Результат: в разделе «Поиск» карточки товаров
  без фото и/или ошибка отрисовки → «не работает».
- «На главной вроде работал»: главная ищет **магазины** (`search/merchants`) —
  контракт совпал, плюс фикс ссылки SZ-005. Раздел «Поиск» ищет **товары** —
  контракт разъехался.

## 2. Задачи

### 2.1. Свести контракты поиска товаров

- Сравнить `SearchOffersController` (поиск) с рабочей витриной магазина
  (`/v1/storefront`): тот же ресурс/шейп ответа (StorefrontOfferCard:
  `image_url` из media позиции, `requirements`, `is_available`,
  `branch_id`/`merchant_id` для перехода, цена в копейках).
- Переход из результата поиска в карточку товара
  (`/stores/{branchId}/product/{offerId}`) — проверить все id в payload.
- Feature-тест на шейп ответа `search/offers` (регресс контракта).

### 2.2. Полный UI-прогон раздела «Поиск» (app, staging)

- Ввод запроса (полный/пустой/опечатки/латиница), empty state, пагинация/скролл;
- карточки: фото, цена (копейки → формат рублей), старая цена;
- клик по товару → карточка товара в магазине → добавить в корзину;
- поиск МАГАЗИНОВ тем же прогоном (не сломать фикс SZ-005);
- консоль/сеть чистые, 500-ки в `lovii-core-staging` логах — ноль новых.

### 2.3. Нижняя навигация перекрывает кнопки действий (жалоба владельца)

- На экранах клиентского интерфейса, где внизу есть кнопка действия
  («Создать заказ», «Оплатить», корзина и т.п.), нижняя навигация (таббар)
  **закрывает кнопку** — нажать нельзя/видно не полностью.
- Фикс: контент и/или панель кнопки должны иметь нижний отступ = высота
  таббара (+ safe-area-inset-bottom на iPhone с «чёлкой»), либо кнопка
  закрепляется НАД таббаром. Паттерн один на все экраны (компонент/класс),
  не точечные костыли.
- Прогнать ВСЕ экраны с нижней CTA: корзина, создание заказа (шаги
  адрес/доставка/оплата), карточка товара, профиль-редактирование, ЛОВИ
  Бизнес (SZ-007, когда дойдёт) — на iPhone (safe-area) и Android.
- Регресс: e2e/визуальный тест «кнопка полностью кликабельна над таббаром».

### 2.4. Наблюдаемость

- Во время прогона следить за логами core-staging; каждая ошибка — находка в
  журнал (формат SZ-006 §2.4: экран → действие → ошибка → статус).
