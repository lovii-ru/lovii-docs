## 1. Фаза A — спека реферальной связки (предусловие)

Сценарий владельца: «регистрация МСП строго по промокоду, зашитому в
QR-код» — промокод привязывает МСП к ПРЕДСТАВИТЕЛЮ, строится структура
для учёта начислений и доходов.

### 1.1. Спека реферальной связки — v1.0.0 (Super Z, 2026-09-11; на утверждении)

> Источники: BRD §2.4 (2 уровня, без каскада), §3.1–3.5 (формат/генерация/
> коллизии/смена промокода), §4.5 (подписка↔промокод), §5.3 (расчёт по ветке),
> §7.2 (слой 2, 40/40/20), §9.1 (граничные случаи регистрации);
> DATA_MODEL §PoolDistribution (`rep_udid`, `amb_prefix`);
> BRD §359-я строка: rep/amb определяются РЕГИСТРАЦИОННЫМ промокодом МСП.

**1. Формат промокода и QR-обёртка.** Промокод представителя — штатный код
BRD §3.1: `PPXXXX` (2 символа префикса ветки + 4 символа суффикса, алфавит
33 знака без 0/1/I/O). Никакого нового формата не вводим — представитель
как владелец промокода уже определён BRD §2.2. QR-обёртка: QR кодирует
ссылку на заявку точки в app с предзаполненным промокодом —
`https://app.lovii.ru/business/apply?promo=<PPXXXX>` (route SZ-007).
QR генерируется в кабинете представителя (фаза B, экран «Мой QR») из его
текущего активного промокода; перегенерация после смены промокода
(BRD §3.5) — автоматическая, старые QR живут до смены кода, уже
отсканированные заявки не затрагиваются.

**2. Момент привязки.** Поле «Промокод представителя» в форме заявки точки
(шаг 3 SZ-007, `CreatePartnerApplicationAction`) — **обязательное** в
мобильном потоке: валидация `exists,active,owner_is_representative`
(ошибки `PROMO_NOT_FOUND` / `PROMO_INACTIVE` — по BRD §9.1 кейсы 1–2).
Привязка фиксируется в момент **создания заявки** (не апрува): снимок
промокода пишется на заявку и переносится на партнёра при материализации.
Web-заявка из b2b-кабинета (прямой канал компании) остаётся без промокода —
см. п.5. Связь хранится на `lovii_b2b.partners`:
`representative_promo_code` (снимок кода на момент регистрации — начисления
считаются по регистрационному коду, BRD §3.5 «прошлые начисления остаются у
прежнего промокода») и `representative_user_id` (владелец кода на момент
регистрации, nullable FK).

**3. Структура и перепривязка.** Представитель → точки = M1:N, точка
принадлежит ровно одному представителю (прямой уровень 1, BRD §2.4 —
40% только с лично зарегистрированных). Иерархия представитель→амбассадор
уже выражается префиксом кода (`amb_prefix` в PoolDistribution, DATA_MODEL)
— отдельного дерева строить не нужно и запрещено (без каскада).
**Перепривязка точки к другому представителю в MVP не существует**: точка
навсегда закреплена за регистрационным промокодом; разбор конфликтов —
ручная операция владельца (правка записи + аудит-лог). Смена промокода самим
представителем (BRD §3.5, суффикс в рамках ветки) связи точки не рвёт:
начисления идут по актуальному коду владельца связи — при выплате
резолвим `representative_user_id` → его текущий активный код; снимок
остаётся исторической записью.

**4. Учёт для начислений.** Сплит 40/40/20 (BRD §7.2) на транзакции точки:
`rep_udid` = владелец регистрационного промокода точки,
`amb_prefix` = префикс этого кода. Оба резолвятся сервером по
`partners.representative_promo_code` (соответствует BRD «данные хранятся
на стороне сервера и подтягиваются по msp_id», клиент код не передаёт).
Начисления возникают только при активном статусе кода (BRD §4). Таблица
начислений/выплат — контур финтрека (BACKLOG I), вне скоупа этой спеки;
здесь фиксируется только место хранения связи.

**5. Граничные случаи.**
- *Промокод отозван / подписка истекла после привязки* — связь не рвётся,
  точка работает; начисления просто не начисляются, пока код неактивен
  (BRD §4.5).
- *Представитель удалён* — `representative_user_id` не удаляем (nullable,
  `nullOnDelete`); снимок кода остаётся; активный владелец кода отсутствует →
  доля представителя по BRD не начисляется.
- *Точка без представителя* — в мобильном потоке невозможна (поле
  обязательное). Web-канал компании (b2b-кабинет) создаёт партнёра с
  `representative_promo_code = NULL` = «прямая регистрация», 40% остаются
  компании. ✅ **Решено владельцем 2026-09-11 (задача 75)**:
  (1) представитель работает ТОЛЬКО в мобильной версии — web-интерфейс
  представителю не строится (фазы A/B это уже предполагали);
  (2) web-канал компании СОХРАНЁН (рекомендация Super Z и zcode: это
  существующий b2b-кабинет, закрытие = запрет прямых продаж компании;
  если понадобится запрет — это один флаг, скажет владелец).
- *Промокод Основателя `AA…`* — регистрация точки по нему допустима
  (это валидный код ветки Основателя, начисления — Основателю как
  представителю ветки).
- *Самопривязка* (представитель регистрирует свою точку по своему коду) —
  разрешена симметрично BRD edge case 22: получает стандартные 40%.
- *Апрув точки представителем* (гейт витрины SZ-035) — фиксируется
  `partners.representative_approved_at` (слот введён миграцией b2b
  2026-09-11; до фазы B выставляется artisan-командой
  `partner:approve-representative` — ops-инструмент приёмки).

Исходный чек-лист постановки (покрыт §1.1 построчно: п.1→спека п.1,
п.2→п.2, п.3→п.3, п.4→п.4, п.5→п.5):

1. Формат промокода представителя (уже есть в BRD §3 — сверить) и QR-
   обёртка (что в QR: ссылка app + промокод?);
2. Момент привязки: при регистрации заявки точки (шаг 3 SZ-007) — поле
   «промокод представителя» обязательное;
3. Структура: представитель → его точки (M1:N); что происходит при
   «перепривязке»; иерархия представитель→амбассадор (доходы) — по BRD §5
   лестнице;
4. Учёт: где хранится связь для будущих начислений (сплит 40/40/20 —
   DATA_MODEL);
5. Граничные случаи: промокод отозван, представитель удалён, точка без
   представителя (возможно ли по решению владельца 🔶).

## 2. Фаза B — кабинет представителя в app (после утверждения фазы A)

Экраны (сценарий владельца):

1. **Мои точки**: список торговых точек представителя с состояниями (заявка
   / на комплаенсе / апрувнута / активна);
2. **Апрув точки**: карточка заявки точки (данные, ИНН, комплаенс-статус)
   → «Подтвердить точку» (действие представителя);
3. **Отчёты по точкам**: выручка/заказы по каждой точке и сводная;
4. **Контроль подключений**: история подключений, статус комплаенса.

Взаимодействие с SZ-007: заявка точки из «ЛОВИ Бизнес» попадает в кабинет
представителя на апрув; гейт витрины (SZ-035) — после этого апрува.
