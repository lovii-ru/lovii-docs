# SZ-051 — Чистка осиротевших ссылок на медиа (logo_url и фото)

> Статус: **Открыта** (2026-09-18: находка приёмки локального стенда, владелец —
> «добавь обязательно»)
> Приоритет: **P3** (тестовый мерчант; не блокирует пилот, но копит битые картинки)
> Исполнитель: **zcode** · Репо: `lovii-core` (artisan-команда) + разовая правка
> данных staging
> Источник: приёмка 2026-09-18 — у мерчанта 279 «пицца от сс» на staging задан
> `logo_url`, файл по адресу отсутствует (404); локальный стенд показал тот же
> класс проблемы на отсутствовавшем `public/storage` (чинился `storage:link`)

## Контекст

Медиа-поля сущностей (`merchants.logo_url`, `mini_logo_url`, фото позиций) — это
адреса, а не гарантия файла: файл может быть потерян при чистках/переливках
данных, а ссылка остаётся. Витрина и кабинеты показывают битую картинку.
Отдельный класс — легаси-внешние URL (`static.kuper.ru`), их доступность вне
нашей ФС (F-026) и в эту задачу не входит.

## Что сделать

1. Artisan-команда `media:check-orphaned` в `lovii-core`: сверяет медиа-поля
   (на первом проходе: `merchants.logo_url`, `merchants.mini_logo_url`; далее —
   фото позиций) с фактическими файлами `storage/app/public`; по внешним URL —
   HEAD-запрос. Отчёт: сущность, id, поле, url, статус (файла нет / 403 / 404).
2. Режим `--clear`: обнуляет битые ссылки. На staging — только после
   подтверждения владельцем по отчёту; локально — свободно.
3. Прогнать на staging, показать владельцу список, обнулить подтверждённое,
   перезаписать `updated_at` сущностей не требуется (ресурс читает поле на лету).

## Что не делать

- Не удалять файлы из `storage/app/public` — только ссылки в БД.
- Не трогать внешние URL (Kuper и пр.) — только пометить в отчёте.
- Не делать таблицу-реестр медиа — вне MVP (решение владельца 2026-09-18:
  «добавь обязательно» относится к чистке, не к новой сущности).
