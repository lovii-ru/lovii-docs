# T-022 — Пин PHP и базовых образов в CI продуктовых репо: «зелёный с первого раза» как воспроизводимое свойство

> Статус: **Открыта**
> Приоритет: **P1** (гвардия регламента «CI зелёный с первого раза» — T-017 Фаза Г) · Источник: **F-064** — релиз PHP 8.5.11 (24.09) внезапно сломал CI-цепочку `lovii-b2b` и заморозил merge PR #1 (T-017 Фаза В)
> Исполнитель: **zcode** (факт-чек Super Z) · Репо: `lovii-b2b`, `lovii-core`, `lovii-app` (`.github/workflows/*`, Docker-файлы) + `lovii_docs` (session-док, F-064 → Resolved) · Дата постановки: 2026-09-26

## Контекст

F-064: патч-релиз PHP 8.5.11 (вышел 24.09) сломал CI `lovii-b2b` в момент активного PR:
воркеры paratest падают на новой версии, `pint mb_str_functions` требует бинарно-безопасные
`mb_*` (webauthn CborDecoder/CoseKey/Authenticator), базовый Docker-образ `php:8.5.11`
несовместим с pest/paratest. Исполнитель ремонтировал серией из 6 фикс-коммитов за 38 минут
(`a6cbffe`→`f551972`, 26.09 10:48–11:26) — формально запрещённый Фазой Г «фикс-пуш»-паттерн.

Корень: **окружение CI не пиновано** — плавающие теги (`php:8.x`, `latest`, нестабильные
базовые образы) означают, что любой PR в любой продуктовой репо может внезапно покраснеть
из-за внешнего релиза, не связанного с кодом. Требование владельца «каждый коммит зелёный
с первого раза» невыполнимо без воспроизводимого окружения: нельзя гарантировать зелёный
первый прогон, если среда меняется под ногами между коммитами.

## Фазы

**Фаза А — инвентаризация плавающих зависимостей (read-only, 1 session-док):**
1. По всем трём репо: `.github/workflows/*.yml` + `Dockerfile*` + `docker-compose*.yml` +
   `composer.json` (plugin-версии) — выписать каждую плавающую ссылку: теги образов
   (`php:8.x`, `node:xx`, `actions/*` без SHA), `setup-php` без version-pin, composer
   plugins с `*`.
2. Артефакт: таблица «репо → файл:строка → плавающая ссылка → риск» в session-доке.

**Фаза Б — пин окружения (репо за репо, коммит за шаг):**
1. `lovii-b2b`: пин PHP-версии в CI-воркфлоу (job matrix `php-version: ['8.5.10']` или
   эквивалент), пин базового образа Docker на точную версию `php:8.5.10` (уже сделано в
   `4ea22a2` — закрепить в master после merge PR #1), `actions/*` → тегированные версии
   (SHA-пин опционален, решение исполнителя).
2. `lovii-core`: тот же набор.
3. `lovii-app`: пин Node-версии и базовых образов (если есть контейнеризация).
4. Каждое репо: отдельная ветка `chore/pin-ci-env-<repo>`, PR, зелёный CI, мерж. **Не
   пушить в PR-ветки чужих активных PR** (правило F-064.3).

**Фаза В — правило ремонта CI (в канон):**
1. В `WORK_PROTOCOL.md` (§9.1/§9.2 или Фаза-Г-блок T-017 — на усмотрение) добавить пункт:
   «Внешняя поломка CI (релизы upstream, недоступность раннеров) ремонтируется в отдельной
   ветке `chore/ci-repair-*` с отдельным PR; серия фикс-пушей в PR-ветку запрещена».
2. FINDINGS: после merge всех пинов F-064 → Resolved со ссылками на merge-коммиты.

## Что не делать

- Не трогать активный PR `lovii-b2b` #1 (T-017 Фаза В) — сначала его merge, потом пины b2b.
- Не менять версии PHP/образов, на которых сейчас зелёная сборка, «попутно» с другими
  правками: один PR = одно изменение окружения.
- Не поднимать мажорные версии (PHP 8.5 → 8.6 и т.п.) в этой карточке — только пин
  текущих работающих.
- Не пинить через `--ignore-platform-reqs` и подобные обходы.

## Приёмка

1. Таблица плавающих ссылок в session-доке — для всех трёх репо, с `файл:строка`.
2. В каждом репо CI-воркфлоу и Docker содержат точные пины (не плавающие теги) — ссылка
   на merge-коммиты.
3. Тестовый PR-цикл в одном из репо после пинов: зелёный CI с первого прогона.
4. `WORK_PROTOCOL` дополнен правилом ремонта CI; F-064 → Resolved.
5. Гейты канона зелёные перед каждым пушем в `lovii_docs`; session-док на каждый шаг.
