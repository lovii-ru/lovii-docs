## 1. Бага: коллизия id «мерчант vs филиал» — подтверждена

- Страница магазина в app: роут `/stores/:id` → `GET /v1/storefront/info`
  с параметром **`branch_id`** (филиал!). Файлы: `lovii-app/src/modules/
  store-module/api/store-api.ts` (`StoreInfoParams.branch_id`), core
  `ShowStorefrontInfoController` (`branchId`).
- Поиск (индекс Meilisearch `merchants`) ставит в ссылку **`merchant.id`**.
- Пример владельца: мерчант **280** «Пышки & Пончики» → `/stores/280` → открылся
  **филиал 280 = «Дикси, 1я В.О. линия, д.20»** (мерчант 6).
- **Масштаб: коллизия 275/275** — id каждого мерчанта совпадает с id какого-то
  филиала (последовательности в одном диапазоне). Сломан ЛЮБОЙ переход из
  поиска/списков, где в `/stores/` подставляется merchant id.

Что должен ответить ресёрч (до фикса): правильная модель ссылок с учётом
**мультифилиальности** (у мерчанта может быть N филиалов — на какой филиал
вести ссылку из поиска?): варианты — ссылки по branch_id (+карточка мерчанта
со списком филиалов), редирект «merchant → его единственный/выбранный филиал»,
единый слаг-роутинг. Плюс аудит ВСЕХ мест, где merchant id подставляется в
branch-контекст и наоборот (поиск, популярные, каталоги, push/глубокие ссылки,
Telegram-бот заказов, sitemap). Проверить real-поведение: `/stores/1024`

## 2. Ресёрч таксономии (вопрос владельца)

Слова владельца: «у нас могут быть ритейл и МСП торговые точки; ритейл —

рестораны — не понятно; почему одни показываются в каталоге, а другие нет».

Факты на сегодня (карта для ресёрча, не решения):

- `merchants.merchant_type` ∈ {`store`, `restaurant`} — единственная ось типа.
- Витрина: «Популярные магазины» = только `store` (SZ-004 §1); поиск = все типы;
  `merchant_type` нигде больше не отображается пользователю.
- **Два параллельных каталога товаров**: Kuper-ритейл живёт в
  `catalog_products` (индекс `catalog_products`), позиции МСП — в
  `merchant_offers` (индекс `offers`). Это фактический ритейл-vs-МСП разлом,
  существующий в данных, но не формализованный в таксономии.
- Категории: дерево категорий мерчанта (b2b Category) + merchantCategories;
  общего справочника категорий заведений нет.

Ресёрч должен выдать **memo на решение владельца (🔶)** с 2–3 моделями

Для каждой модели: что меняется в core/b2b/app (списки, поиск, фильтры,

### 6.1. Аудит ссылок «поиск → карточка» (merchant id vs branch id)

Роут карточки: `/stores/:id` → `GET /v1/storefront/info?branch_id=:id` — параметр
филиала. Единственная сломанная поверхность — выдача поиска в app; остальные
уже корректны:

| Поверхность (app) | API | Payload | Ссылка в app | Статус |
|---|---|---|---|---|
| Результаты поиска | `/v1/search/merchants` | `id`=merchant, `branch_id` (фикс zcode d3ea9fe) | `CatalogSearchStore.vue`: `store.id` | **✗ сломано** — надо `store.branch_id` |
| «Популярные магазины» (главная) | `/v1/popular-stores`, `/v1/home` | `id`=merchant, `branch.id` | `PopularStorePreview.vue`: `store.branch.id` | ✓ |
| «Рядом» (главная) | `/v1/home` `near_you` | `NearbyBranchResource`: `id`=branch | `NearbyStore.vue`: `store.id` | ✓ |
| Каталог `/stores` | `/v1/stores` | `StoreCardResource` (`@mixin MerchantBranch`): `id`=branch | `CatalogStore.vue`: `store.id` | ✓ |
| Карточка магазина | `/v1/storefront/info` | `branch_id` param | `StoreModule.vue` | ✓ |
| Поиск внутри магазина | `/v1/search/offers?branch_id=` | branch-контекст | `StoreSearch.vue` | ✓ роутинг; **но API 500** (§6.2, находка T-7) |
| Push/глубокие ссылки | — | push-инфраструктуры в core/app нет | — | n/a (нет поверхности) |
| Telegram-бот заказов | — | бота заказов нет (только OTP-боты: `MaxBotLink` scope `telegram:otp`) | — | n/a |
| Sitemap | — | в core/app нет генератора sitemap | — | n/a |

Мультифилиальность: поиск возвращает ОДИН `branch_id` (первый активный филиал —
конвенция фиксa d3ea9fe). У мерчанта с N филиалами пользователь из поиска
попадает на один филиал без выбора — приёмлемо на сейчас (у всех мерчантов,
кроме Kuper-партнёров с сетками, по 1–2 филиала); выбор филиала — пункт плана §6.5.

Живые проверки (staging, curl 2026-09-09):
- `/stores/280` (merchant id) → открылся «Дикси» — подтверждено, было сломано;
- `/stores/1024` (branch «Пышек») → «белы куна 6», карточка правильная ✓ —
  семантика `branch_id` в API работает, коллизия — чисто вопрос ссылок.

### 6.3. Memo таксономии — на решение владельца 🔶

**Факты (проверено кодом/staging):**
- `merchants.merchant_type` ∈ {`store`, `restaurant`} — единственная ось типа;
  Kuper-мерчанты автоматически = `store` (KuperReconciler:230).
- Витрина: `/v1/popular-stores` И `/v1/stores` фильтруют `type=store` —
  рестораны недоступны ни на главной, ни в каталоге; только поиск.
- Пользователю тип нигде не виден (кроме фильтра каталога).
- **Фактический ритейл-vs-МСП разлом в данных**: ритейл живёт в
  `catalog_products` (индекс `catalog_products`, 275 Kuper-мерчантов), МСП — в
  `merchant_offers` (индекс `offers`). Каталоги никогда не пересекаются.
- Категории: дерево категорий мерчанта (b2b) + merchantCategories; единого
  справочника категорий заведений нет.

**Модель A — ось «источник» (рекомендация):**
`merchant_kind` ∈ {`retail`, `local`}; retail = Kuper-ритейл (специализированная
витрина, каталоги поставщиков), local = точки МСП (магазины, рестораны, услуги —
единый поток, деление обычными категориями, не типом).
- + Убирает ложную ось store/restaurant (вопрос владельца «зачем делить?»);
- + Ритейл/МСП уже разделены в данных — модель легализует статус-кво;
- + МСП-поток единый: пекарня и парикмахерская в одном списке с категориями;
- − Миграция: добавить поле, перенести 275 Kuper-мерчантов в `retail`,
  `store`-МСП → `local`; два витринных запроса меняют фильтр; b2b-форма
  меняет поле типа; индексы Meili — новое поле в документах;
- − Влияние на I-5 (гейт verified) — нейтрально (гейт не зависит от типа).

**Модель B — сохранить ось заведения (store/restaurant/…) + разделы на главной:**
- + Минимальные изменения (ничего не переименовывать);
- + Привычная UX-метафора «магазины/еда»;
- − Ось не отвечает на вопрос «почему услуги/салоны не показать» — для
  непродуктовых МСП придётся заводить третий/четвёртый тип (расширение enum
  при каждой новой категории бизнеса);
- − Два каталога товаров (catalog_products vs merchant_offers) ось B не
  объясняет — разлом остаётся неформализованным.

**Модель C — гибрид:** источник (retail/local) + свободные категории заведений
(store/restaurant — просто категория, не тип).
- + Максимум гибкости, будущее-proof (услуги, салоны, курсы — всё МСП-локал);
- − Самая дорогая: миграция типа + справочник категорий + фильтры витрины +
  б2б-редактор категорий.

**Рекомендация Super Z: модель A** (минимальная честная формализация
существующего разлома), с эволюцией в C, когда появятся услуги. Для A нужно
решение владельца только по формулировкам: название витрины ритейла и нужен ли
раздел «Рестораны» внутри local-потока (по категориям — да).

SZ-004 §2.1 («рестораны на главной») разрешается внутри этого решения: при A —
рестораны показываются в local-потоке без отдельного фильтра типа.

## 7. Решение владельца (2026-09-10, канон)

Тезисы владельца (дословно по смыслу):

1. **Витрина и глобальный поиск НЕ зависят от `merchant_type`.** На витрине
   выводятся ВСЕ торговые точки — рестораны, магазины, салоны, выгул собак.
   Текущее поведение «на главной не выводятся рестораны» — ошибка дизайна,
   скрытый фильтр без явного указания недопустим.
2. **`merchant_type` = явный фильтр в UI.** Пользователь сам выбирает раздел:
   «сети-ритейл», «общепит (кафе/рестораны)», «клубы», «услуги» и другие по
   мере появления. Список категорий расширяемый.
3. **Переименовать/добавить категории:** текущие значения переосмыслить
   (`store` → «сети-ритейл», `restaurant` → «общепит»), добавить новые
   (`services` «услуги», `club` «клубы» — значения-кандидаты, точный список —
   при имплементации с владельцем).
4. **Сетевой ритейл заводится автоматически** (импорт, без кабинета — как
   сейчас). В их каталогах нужен фильтр запрещённых к продаже товаров
   (энергетики и пр.) — пересечение с **C-4** (18+/алкоголь), делать вместе.
5. Итог владельца: «отключить зависимость витрины и глобального поиска от
   принадлежности к категории; использовать этот фильтр по-другому».

2. **enum + лейблы:** значения в БД не переименовывать (миграция данных не
   нужна) — переименовать отображаемые лейблы (`store` → «Сети-ритейл»,
   `restaurant` → «Общепит») и ДОБАВИТЬ новые значения (`services`, `club`)

   витрины, на попадание не влияет».
3. **app:** явные фильтры-чипы типов на главной/в каталоге витрины (дизайн

5. **b2b:** NB для партнёра в manual-msp-cycle.md — тип больше не влияет на
   видимость.
6. **C-4** (запрещённые товары в ритейл-каталогах) — отдельная задача,
