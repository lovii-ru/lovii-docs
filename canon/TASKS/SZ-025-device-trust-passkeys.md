## 1. Фаза 1 — Реестр устройств и история входов

- Таблица `trusted_devices` / сессии с привязкой к partner_user: устройство
  (user-agent, отпечаток — честный, без «суперфингерпринтинга»), первое/последнее
  использование, IP-страна;
- Таблица `auth_events`: входы (канал: OTP/passkey), неудачные попытки;
- UI в b2b: раздел **«Безопасность»** — активные сессии («это устройство»),
  история входов, «выйти со всех устройств»;
- Тесты: изоляция между partner_user, корректность «выйти со всех».

## 2. Фаза 2 — Вход по пину на доверенном устройстве (банковский паттерн)

Метод — **WebAuthn / Passkeys (FIDO2)**, отраслевой стандарт (так работают
Сбер/Т-Банк/Apple/Google):

- Секретный ключ генерируется **в устройстве** и никогда его не покидает;
  сервер хранит только публичный ключ. «Пин» — это unlock устройства
  (PIN/Face ID/Touch ID — WebAuthn user verification), коды и пуши не нужны;
- Флоу: первый вход по OTP → предложение «Запомнить это устройство» →
  регистрация passkey → следующие входы с этого устройства: клик → разблокировка
  пином устройства → вход. Полностью без OTP;
- **PWA на десктопе** поддерживает WebAuthn (Chrome/Edge/Safari ≥16.4) —
  сценарий владельца «PWA на компе, вход по пину» покрывается;
- Резервный путь: OTP-код остаётся (новое устройство, passkey удалён);

### 🔶 Политики — РЕШЕНЫ владельцем (2026-09-11)

1. Passkey-устройства: **все зарегистрированные**, список управляется в
   «Безопасности»;
2. Регистрация нового устройства — **OTP обязателен** (подтверждено);
3. Срок доверия: **30 дней, скользящий** (каждый вход продлевает на
   следующие 30).

### Бывшие 🔶 (историк)

1. Сколько устройств могут иметь passkey (все зарегистрированные / одно
   «основное»)? Предложение: все зарегистрированные, список управляется в
   «Безопасности» — владелец сам видит и удаляет;
2. При регистрации нового устройства — OTP обязателен (стандарт) — подтвердить;
3. Срок доверия устройства без активности (например, 180 дней) — предлагается.

## 3. NB

### 5.2. Фаза 1 — Реестр устройств + история входов
- Миграция `2026_09_11_100001_create_partner_security_tables.php`:
  `partner_users.sessions_invalidated_at` (бан-метка), `partner_user_devices`
  (fingerprint = sha256(UA+Accept-Language) — честный, без суперфингерпринтинга;
  platform/last_seen/last_login/trusted_at/revoked_at), `partner_auth_events`
  (append-only, 12 видов событий, канал otp/passkey/dev),
  `partner_passkey_credentials` (фаза 2).
- `PartnerSecurityService`: resolveDevice (upsert + ре-активация при повторном
  входе с отозванного устройства), touch (троттл 5 мин), recordEvent,
  invalidateAllSessions, markSessionLogin (сессионная метка login_at + device).
- Middleware `EnforceSessionIntegrity` (в `authMiddleware` панели после
  Authenticate): сессия, открытая ДО `sessions_invalidated_at`, принудительно
  логаутится с редиректом на вход — работает и на redis-сессиях (не зависит от
  списка сессий). Middleware `TrackPartnerDevice` — обновление last_seen раз в 5 мин
  (атомарный Cache::add-гейт).
- Хук логина: `PartnerAuthService::postLogin` — device + login_success-событие
  + сессионная метка. Семантика «Выйти со всех устройств» — рвёт ВСЕ сеансы,
  включая текущий (однозначно и безопасно, подпись в UI это называет).
- UI: страница **«Безопасность»** (`/panel/{tenant}/security`, группа
  «Безопасность»): устройства («это устройство», отозвано, IP/платформа,
  отозвать), история входов (50 последних событий, цветовая маркировка
  успех/провал), блок «Выйти со всех устройств» с confirm.

### 5.3. Фаза 2 — WebAuthn/Passkeys (собственная реализация, без пакетов)
- Почему без пакетов: asbiin/laravel-webauthn не подтверждён для
  Laravel 13/Livewire 4, а web-auth/webauthn-lib тянет symfony-контур; ядровая
  часть WebAuthn (CBOR + COSE + verify) — ~600 строк и полностью покрывается
  тестами с синтетическим аутентикатором.
- Компоненты: `CborDecoder` (RFC 7049 subset), `CoseKey` (ES256 P-256 + RS256,
  DER-сборка SPKI/подписи, raw r||s тоже принимается), `AuthenticatorData`
  (парсер flags/counter/credential data), `Base64Url`, `WebAuthnService`.
- Политики (по §2, не блокируют): (1) passkeys — на всех зарегистрированных
  устройствах, управление в «Безопасности»; (2) первичная регистрация — только
  после OTP-входа (UI: страница «Безопасность»); (3) срок доверия устройства —
  не ограничен сейчас (🔶 владельцу: 180 дней?); counters — clone-детекция
  включена (ноль-каунтеры по спеке не проверяются).
- Флоу логина: кнопка «Войти по пину (ключ доступа)» на странице входа →
  discoverable credential + userVerification=required (PIN/Face ID/Touch ID) →
  сервер валидирует challenge/origin/rpIdHash/подпись/каунтер → Auth::login →
  редирект в кабинет. Резервный путь — OTP (как было). Challenges одноразовые
  (Cache pull, TTL 10 мин); привязка challenge через challengeKey.
- Приватный ключ не покидает устройство; сервер хранит публичный ключ
  (base64url text — bytea-круговорот PDO/PgSQL хрупок).
