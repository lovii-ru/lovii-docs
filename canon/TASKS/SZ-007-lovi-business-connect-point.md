## 6. Карта 🔶-вопросов для приёмки zcode — как фаза 1 их отложила

Ответ на условие приёмки zcode: «возврат/сумма/тип в форме заявки должны быть
аккуратно отложены, не сшиты молча». Сверка кода фазы 1 (app b79750d +
горячие 2488ba6/cca3489/727fa93/2a784e3, core 86604f3) по всем четырём 🔶 §0.
Сверка-вывод: ни одно из решений §0 не принято молча — код не выходит за
границу «форма + черновики».

| 🔶 | Где могло «сшиться» | Фактическое состояние (якоря) |
|---|---|---|
| 0.1 Возврат платежа | Шаг 4 сценария, финконтур | Шаг 4 не реализован (в разрешённом списке старта его нет): счёт не выдаётся, кнопки «Я оплатил, проверьте» нет. В app/core нет ни refund-логики, ни упоминаний возврата платежа (греп чист; «возврат» в core — только HTTP-идемпотентность заявки). Статусы `invoice_issued`/`awaiting_payment` объявлены в статусной машине миграции как до-верификационные и недостижимы до финконтурной очереди. |
| 0.2 Сумма счёта | Счёт / UI / БД | Суммы нигде нет: в `partner_applications` нет колонки суммы; в UI единственные числа — тарифы лендинга, и те дословно PARAMS §1.3 (`const/business.ts` BUSINESS_TARIFFS) — маркетинг, не сумма счёта. |
| 0.3 Тип деятельности | Маппинг на merchant_type | Значение ходит as-is: форма («последствия типа не применяются на клиенте», BusinessApply) → API → колонка `activity_type` как есть. Единственное место последствий — материализация черновика Merchant: `PartnerActivityType::toMerchantType()` (Еда→restaurant, Товары→store, Услуги→services), задокументирован в enum как нейтральный плейсхолдер до решения владельца по SZ-005 memo; `MerchantType::Services` существует (SZ-005 §7); витрину не затрагивает (видимость = partners.verified_at, гейт I-5). При другом решении владельца меняется один `match()`, сырые данные перечитываемы. |
| 0.4 Промокод | Форма / финконтур | Отсутствует полностью (форма, API, БД) — сценарий v1.0 без промокода подтверждён исполнением. |

Подрешение §1 шаг 3 («решает Super Z по лучшей практике, предложить
владельцу»): валидация ИНН — полный алгоритм ФНС (10/12 цифр + контрольная
цифра), клиентское зеркало серверного правила
`app/Domain/Business/Rules/InnChecksum.php` (`isValidInnChecksum` в
use-business-form.ts). Предлагается владельцу к утверждению; ослабление до
«только длина», если владелец против, — правка одного правила.

Дополнительно к проверке: поток осознанно идёт форма (шаг 3) → ожидание
(шаг 5): заявка держится в `submitted` до финконтурной очереди; поллинг шага 5
честно истекает по бюджету 2 мин с текстом «занимает дольше» (BusinessPending),
без прерывающего лупа и без имитации оплаты.

## 7. Решения владельца (2026-09-11)

1. **Комплайнс-платёж — возвратный** (выбор (б)): платёж возвращается
   партнёру на его реквизиты — банк-получатель тем самым подтверждает
   контрагента. Механику (выплата-возврат на р/с) уточнить у Т-Банк при
   реализации финконтура;
2. **Инсталляционный платёж — возвратный** (коррекция владельца 2026-09-11;
   прежняя структура «промо / годовая» ОТМЕНЕНА): сумма рассчитывается по
   правилу комиссии банка — `canon/PARAMS.md` §5.1; абонентка — по канону
   тарифов (PARAMS §1.3);
3. **Промокод обязателен**: привязка МСП к представителю, построение
   структуры для учёта начислений и доходов. Регистрация МСП строго по
   промокоду, зашитому в QR-код;
4. **Апрув точек — ПРЕДСТАВИТЕЛЕМ**: сценарий мобильного кабинета
   представителя (отчёты по точкам, апрув своих точек, контроль
   подключений) → выделено в SZ-034 (предваряется спекой реферальной
   связки промокод→представитель);
5. Гейт витрины: страница точки с плашкой «скоро» — после апрува
   представителем; товары — после полного апрува (см. SZ-035).
