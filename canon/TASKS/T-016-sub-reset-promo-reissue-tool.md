# T-016 — Инструмент приёмки: сброс подписки и перевыпуск личного промокода без ручных правок БД

> Статус: **На приёмке** (реализована AutoClaw 23.09 — core `27f9b54`, CI+deploy 🟢; постановка Super Z по результатам приёмки Блока А 22.09)
> Приоритет: **P1** — обслуживающий инструмент живых приёмок (SZ-056/057, T-014)
> Исполнитель: AutoClaw (код-агент) · Репо: `lovii-core` (консольная команда) · Постановка: Super Z

## Проблема

При живой приёмке владельцу нужно переоформить подписку и пере-выдать личный
промокод (копирование кода/ссылки не работает — доработка T-014/F-058; у
подписавшихся до SZ-057 кода может не быть — довыдача только при продлении
кроном). Ручные правки БД запрещены практикой: инъекции мимо машины состояний
рассинхронизируют проводки и статусы.

## Что сделать

1. Консольная команда core (tinker-однострочники не считать инструментом):
   сброс подписки пользователя в честное состояние машины (`user_cancelled`,
   отмена grace-переходов) + опционально перевыпуск личного промокода
   (переиспользовать `roles:issue-promo`), аргументы — телефон/ID юзера.
2. Команда действует только штатными механизмами модели (никаких прямых
   UPDATE мимо Eloquent/сервисов) и пишет лог своих действий.
3. Защита окружения: запуск запрещён на проде (env-гейт, как у payments-guard).

## Границы

- Биллинг подписки (SZ-053: каскад, retry, grace-cron) не менять — команда
  только переводит состояния штатными переходами; проводки подписки не
  трогаются и не разворачиваются этой командой.
- Зона core-billing не трогается (WORK_PROTOCOL §1.2).

## Разведка нового исполнителя (23.09) — факт-чек Super Z по origin/staging `16e062b`

- Переходы (`SubscriptionStatus.php:42–48`): Active достижим из
  GracePeriod/Suspended/Cancelled одним легальным переходом; Active→Active
  запрещён (BusinessException `invalid_status_transition` в
  `SubscriptionStatusMachine::transition`). Сброс из Active — через
  промежуточный статус либо идемпотентный no-op с отчётом в логе.
- Машина чистит только `grace_ends_at` (выход из grace);
  `suspended_at`/`cancelled_at`/`current_period_*` не сбрасываются —
  полный сброс требует `forceFill()`. Прецедент в ядре:
  `SubscriptionBillingService.php:79/:219/:490`. `forceFill()` — штатный
  Eloquent-механизм и пункту 2 постановки («никаких прямых UPDATE мимо
  Eloquent/сервисов») НЕ противоречит.
- Перевыпуск промокода: `RepresentativePromoService::issue()`
  (`app/Domain/Roles/Services/RepresentativePromoService.php:32`).
- Идиома env-гейта в командах: `app()->environment('production')`
  (прецедента отдельного env-флага в командах нет).

## Решения (23.09, по отчёту исполнителя — выбор владельца через Super Z)

- **Трактовка «никаких прямых UPDATE» — вариант (а):** статус — только
  через машину состояний; служебные поля (`current_period_*`,
  зачистка `suspended_at`/`cancelled_at`) — `forceFill()->save()`,
  как уже делает `SubscriptionBillingService`.
- **Аудит при активной подписке:** сброс выполняется легальным переходом
  `Active → Cancelled` (reason `admin_action`) — строку истории пишет сама
  машина; затем зачистка служебных полей `forceFill`-ом с логом команды.
  Отдельная операция машины (вариант «правка машины») не требуется.
  Повторная активация из Cancelled → Active — штатный путь SZ-056.
- Перевыпуск промокода — `RepresentativePromoService::issue()`
  (фолбэк-префикс на усмотрение исполнителя, фиксируется в отчёте).
- Доступ к staging-серверу для прогонов — разрешён владельцем (23.09,
  чат), с бэкапом и таблицей «было/стало».

## Отчёт исполнителя (AutoClaw код-агент, 2026-09-22)

**Коммит:** `lovii-core` `e242350` (в `staging`, tip `27f9b54`), запушен; CI run 35680798035 — `checks` 🟢, `deploy-staging` 🟢.

**Сигнатура:** `subscription:reset {phone} {--reissue-promo}`; команда зарегистрирована на стенде (`php artisan list`).

**Механика сброса:** статус — только машиной состояний: `Active → Cancelled` (reason `admin_action`, actor `admin`); из `GracePeriod`/`Suspended` — легальным двухшаговым путём через `Active`; `Cancelled` — идемпотентный no-op. Затем `forceFill` служебных полей в ОДНОЙ внешней транзакции со всем сбросом (партиала «статус сброшен, поля нет» не бывает). История append-only, строки пишет машина.

**Итоговый набор атрибутов (из прогона тестов):** `status=cancelled`, `current_period_started_at=now()`, `current_period_ends_at=now()+1 месяц`, `suspended_at=null`, `cancelled_at=null`, `grace_ends_at=null`; `price_kopecks`/`price_source`/`promo_code` (снимок термина) не трогаются.

**Гейт окружения:** `app()->environment('production')` → `$this->error` + `FAILURE`.

**Перевыпуск промокода:** `RepresentativePromoService::issue()`, ветка наследуется от привязанного промокода, фолбэк — Основатель `AA`.

**Гейты (локально):** pint PASS, rector [OK], phpstan «No errors», pest 1449 passed; 13 тестов команды зелёные.

**Семантические риски (на решение владельца; от решения карточки не отклонялся):**
1. `status=cancelled` при `cancelled_at=null` — машина ставит отметку на переходе, команда её снимает.
2. Свежий период при терминальном статусе: после сброса профиль НЕ действующий подписчик (гейт вывода по PARAMS §1.6 закрыт). Если замысел «живой старт», финалом должен быть `Active`, а не `Cancelled`.

**Осталось (стенд):** прогон «сброс → повторная активация (SZ-056) → код выдан заново». На стенде ровно одна подписка (user 51, `+79119287478`, `active`) — автономный сброс оставил бы её `Cancelled` до повторной активации из UI, поэтому прогон выполняется интерактивно (по команде владельца), чтобы не сорвать живую приёмку.

## Факт-чек Super Z (2026-09-22): рекомендация по обоим семантическим пунктам — «принять реализацию как есть»

Верификация `27f9b54` на `origin/staging`: команда и её тесты прочитаны; заявленная механика (переходы только машиной, forceFill служебных полей в одной внешней транзакции, prod-гейт, идемпотентный no-op, `issue()` с фолбэком AA) подтверждена; отчёт исполнителя выше точен.

**П.1 — `cancelled_at = null` при `status = cancelled`: оставить как есть (рекомендация).**
- Потребители поля в коде два: машина (`SubscriptionStatusMachine.php:113` — на любом переходе в Cancelled ставит `cancelled_at ?? now()`) и `SubscriptionResource.php:32` (отдаёт в API). Гейтов/фильтров по `cancelled_at` нет.
- Если сброс сохранит отметку, после повторной активации (Cancelled → Active; машина чистит только `grace_ends_at`) API будет показывать действующую подписку с датой отмены — грязный инвариант. С `null` инвариант после повторной активации чистый.
- Аналитика оттока по `cancelled_at IS NOT NULL` не посчитает приёмочные сбросы отменами — это корректно: сброс не является оттоком.
- Аудит-след операции не теряется: история переходов append-only (`admin_action` / actor `admin`) — полная замена полю.
- Инвариант «cancelled ⇒ есть дата» нарушается только в окне после сброса; при любой следующей отмене машина восстановит отметку сама.

**П.2 — финал `Cancelled`: подтвердить (рекомендация).**
- Повторная активация требует не-Active (`Active → Active` запрещён BusinessException `invalid_status_transition`) — финал Active сделал бы прогон карточки неисполнимым без повторного сброса.
- Active без фактической оплаты — бесплатный доступ и непроверенные гейты активации; цель карточки — «сброс → повторная активация из UI → личный код выдан заново».
- «После сброса профиль не действующий подписчик» (гейт вывода PARAMS §1.6 закрыт) — фича приёмки, а не риск: именно штатный путь активации и проверяется.

Оба пункта — за владельцем (§3.3); изменений кода не требуется, решения фиксируются в карточке.
