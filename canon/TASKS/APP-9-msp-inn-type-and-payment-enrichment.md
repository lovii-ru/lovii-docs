# APP-9 — тип МСП по ИНН + обогащение карточки компании из верификационной платёжки

> Открыт 09.10 по находке на ПРОДЕ: заявка №2 (ИНН 780725031158) создалась без
> юрданных — DaData вернул пусто, заявка прошла штатной деградацией. Диагностика
> и вердикт владельца в чате 09.10: «оформляй карточку и включай в нее
> обогащение при поступлении платежа… данные из платежки более достоверные, так
> как проверены банком».

## Факты (диагностика 09.10, прод)

- Обогащение заявки — DaData `findById/party` при подаче
  (`CreatePartnerApplicationAction::enrichByInn`); пустой ответ = штатная
  деградация: заявка живёт без юрданных, `dadata_party = NULL`.
- 780725031158 — 12-значный ИНН (формат ИП/физлица), контрольные цифры
  валидны, но записи в ЕГРЮЛ/ЕГРИП нет (DaData: `{"suggestions":[]}`;
  внешние реестры — тоже). Вероятно ИНН самозанятого или опечатка. Форма
  принимает 10 и 12 цифр, не различая тип МСП.
- Матчинг верификационного 1₽ (`MatchIncomingVerificationAction`) проверяет
  код VER-* + сумму + **ИНН плательщика == ИНН заявки**; при неверном ИНН
  платёж не сматчится никогда — заявка зависает в awaiting навсегда и ест
  слот лимита «5 ожидающих».
- Каталог до верификации безопасен: мерчант рождается `pending_moderation`,
  `Active` — только при успешном матче (витрина фильтрует по Active).
- При успешном матче сейчас пишется только `PartnerPayoutAccount`
  (holder_name/inn/account/bank); мерчант НЕ обогащается — если DaData при
  подаче был пуст, наименование/ОГРН не появятся никогда.

## Решение владельца (09.10)

1. **Тип МСП по ИНН**: 10 цифр = юрлицо, 12 = ИП/самозанятый. На форме и в
   заявке показывать тип; для «вне реестра» — предупреждение заявителю до
   отправки и пометка в карточке представителя.
2. **Обогащение из платёжки**: банк передаёт в платеже реквизиты, которые
   у него есть для МСП и её счёта, и они **проверены банком — им приоритет**
   над DaData-данными заявки. При успешном матче верификационного платежа:
   - сверить реквизиты плательщика (PayerName/PayerInn/PayerAccount/PayerBank)
     с данными из `dadata_party`;
   - обогатить карточку компании (merchant: legal_name и др.) данными из
     платёжки, расхождения с DaData — логировать (факт сверки);
   - сырой payload платёжки сохранить (аналог dadata_raw — `payment_raw`).

## Критерий приёмки

1. Заявка с 12-значным ИНН помечена типом «ИП/самозанятый» в UI заявителя и
   представителя; «вне реестра» (DaData пусто) — видимая пометка.
2. Успешный матч верификационного платежа обогащает merchant данными платёжки
   (юрданные заполнены даже при пустом dadata_party) и сохраняет payload.
3. Расхождения DaData ↔ платёжка логируются (warnings с application_id).
4. Тесты: матч с расхождением ИНН плательщика по-прежнему игнорируется;
   успешный матч заполняет юрданные; full gate 🟢.

## Развилки (владельцу)

- Что делать с «вне реестра»: только предупреждение (текущий вердикт) или
  блок отправки заявки? — по умолчанию предупреждение + пометка.
- Маппинг PayerName → legal_name для ИП (там ФИО) — подпись на витрине/чеках
  уточнить при реализации.
