## Контекст (проверено 2026-09-21)

- Зоны доставки уже есть в модели: `merchant_delivery_zones` — `branch_id`, `name`,
  `zone_type` (`radius` | `polygon`), `radius_meters` (int, nullable), `delivery_fee`,
  `free_from_amount`, `min_eta_minutes`, `max_eta_minutes`, `is_active`, `polygon`
  (`geography(Polygon,4326)`, GIST-индекс).
- **UI зон есть только в b2b**: `lovii-b2b/app/Filament/Resources/BranchResource/RelationManagers/DeliveryZonesRelationManager.php`
  (круг/полигон на Яндекс-карте, fee, free_from, ETA; полигон пишется через `ST_GeogFromText`).
  В приложении настроек зон нет вообще.
- **Чекаут использует зоны урезанно**: берётся первая активная зона точки только для
  расчёта стоимости доставки (subtotal ≥ free_from → 0, иначе fee; зоны нет → 0);
  проверки «адрес попадает в зону» НЕТ, `min/max_eta_minutes` не читаются
  (`as-is/08-dostavka-adresa-geo.md`, кандидаты №1–3; это же П-2 в
  `as-is/00-zapusk-chego-ne-hvataet.md`).
- Геокодирование адреса точки на сохранении работает (ядро, `UpdateMspBranchSettingsController`),
  координаты точки и адресов покупателя хранятся в PostGIS (`geography(Point,4326)`), расстояния
  считаются SQL-функциями (`ST_Distance`).
- Тумблеры канала (`delivery_available`/`pickup_available`) — только b2b; на стенде у тестовой
  точки 21.09 оба `false`, из-за чего заказ невозможен (`422 delivery_not_supported`) — важно
  для живых проверок этой задачи.

## Что сделать (решения принимает исполнитель, обоснование — в отчёте)

1. **Базовый радиус доставки из приложения.** В настройках точки владелец МСП задаёт радиус
   доставки в метрах; границы значения — минимум 300 м, максимум 1000 м (подтверждаются как
   параметр платформы в `canon/PARAMS.md` — это дом факта, в карточке число не дублируется).
   Полигональные зоны, заданные в b2b, остаются валидными и работающими — упрощённый экран
   приложения их не создаёт, но и не ломает (поведение описать в отчёте).
   Решить: что именно редактирует приложение — существующую радиусную зону точки или создаёт
   новую; что происходит с точкой, у которой зона задана в b2b полигоном или их несколько.
2. **Не затирать точную настройку b2b.** Полигоны, несколько зон, fee/free_from/ETA — детали
   b2b. Сохранение из приложения не должно молча удалять или ломать чужие зоны: если данных
   больше, чем умеет упрощённый экран — экран обязан это честно показать/не трогать.
3. **Решить статус гео-проверки зоны** (П-2). Либо радиус становится реальной проверкой
   «доставим ли по этому адресу», либо осознанно остаётся отображением/расчётом стоимости.
   Если проверка: описать поведение для адреса вне зоны, для самовывоза, для зон без геометрии
   и совместимость с уже собранными корзинами. Решение и его последствия — в отчёте.
4. **Честная витрина/чекаут**: покупатель не должен видеть «доставим» там, где не доставим
   (см. `PRODUCT_QUALITY_BAR.md` — честные цифры, три состояния экрана).
5. **Тесты и живые проверки**: границы 300/1000 м (в т.ч. попытка выйти за них), точка без зоны,
   точка с полигоном, точка, у которой оба канала выключены.

## Что не делать

- Не менять модель `merchant_delivery_zones` без обоснования (на ней уже работает b2b-редактор).
- Не удалять и не переписывать существующие зоны точек при сохранении из приложения.
- Не вводить вторую параллельную сущность «радиус видимости» рядом с зонами доставки —
  «диапазон видимости» владельца должен лечь в существующую модель (если не ложится —
  сначала вернуть вопрос с обоснованием).
- Не пушить в `staging`/`master` без «го» владельца, не трогать прод.

## Приёмка

- Владелец МСП задаёт радиус доставки с телефона в границах 300–1000 м; значение видно
  покупателю как зона доставки честно; выход за границы невозможен с понятным сообщением.
- Точки с полигонами/несколькими зонами из b2b не пострадали (проверено живьём на стенде).
- Если принято решение о гео-проверке — адрес вне зоны ведёт себя предсказуемо во всех
  поверхностях (витрина, корзина, чекаут, инфо-карточка); если нет — это записано в отчёте
  как осознанно отложенное.
- Тесты core/app зелёные; горячие пути (каталог/чекаут) — стресс-страж на локальном стенде.

## Отчёт исполнителя (21.09, zcode)

**Коммиты (локально, без пуша).** core: `b593af7` гео-проверка зоны (радиус/полигон, новый
`DeliveryZoneResolver` + `DeliveryRadiusPolicy`, `DeliveryQuote`, честные коды отказов),
`f8f9006` радиус из приложения (`UpdateMspBranchSettingsController`, `MspBranchSettingsResource`,
`config/delivery.php`), `b8b2156` тесты (32 новых), `4451e79` session 052. app: `0611aa0`
роли/настройки, `e3557db` чекаут (расстояние + честный отказ), `99eebe6` тесты, `b9c9f29`
session 125. b2b **не менялся** — полигоны/цена/ETA там уже работают.

**Принятые решения.** Зона выбирается по попаданию адреса (радиус — расстояние, полигон —
вхождение); при нескольких подходящих — самая конкретная (наименьшая площадь) → дешевле →
младший id. Fee/free_from — из содержащей зоны (раньше — из первой активной, цена зависела
от порядка строк). Точка с включённой доставкой **без активных зон доставку не принимает**
(зона задаёт ещё и территорию). Адрес вне зоны → новый код `delivery_out_of_zone` с числами и
подсказкой про самовывоз; самовывоз радиусом не ограничен. ETA зоны (мёртвые колонки)
теперь показывается покупателю рядом с расстоянием. Приложение правит **ровно одну** радиусную
зону и не переписывает чужие (полигон/несколько зон/радиус вне 300–1000 м → `422
delivery_zone_managed_in_b2b`, проверка до записи); право — `branch.update_delivery_zones`.
Координаты берутся из БД (пересборка во float давала 2·10⁻⁸ м и ломала границу радиуса).

**Живые проверки (локальный стенд, точка 2, оба канала включены, зона 500 м).** Внутри
радиуса (165 м) → доставка проходит, fee из зоны; ровно 500 м → проходит (граница
включительная); 801 м → `422 delivery_out_of_zone` с текстом «в 801 м, доставляем в радиусе
500 м… доступен самовывоз»; самовывоз на 801 м → заказ №6 создан; доставка на 165 м → заказ
№7 с fee; полигон из b2b → доставка по вхождению, попытка правки радиуса → `422
delivery_zone_managed_in_b2b`; зона выключена → канал недоступен честно. Прежнее состояние
точек сохранено: `lovii-core-sz066/storage/app/sz066-stand-backup-2026-09-21.json`.

**Прогоны.** core: новые файлы 32 passed / 166 assertions (перепроверено AutoCoder'ом
независимо, exit 0), полный набор 1392 passed; `pint`/`phpstan` по изменённым файлам чисто.
app: `yarn test` (format→lint→unit→type-check→build) зелёный, 866 юнитов (было 844);
`roles-msp.test.ts` 105 passed и checkout-тесты 25 passed — перепроверены независимо.

**⚠️ Условия работы (координация).** Параллельная сессия переключила HEAD главного
`~/LOVII/lovii-core` на `feat/platform-cabinets` во время работы, а в приложении правит те же
файлы (`MspBranchSettings.vue`, `roles-msp.test.ts`). Поэтому работа вынесена в отдельные
worktree: `~/LOVII/lovii-core-sz066` и `~/LOVII/lovii-app-sz066` (ветки
`feat/sz066-delivery-radius` от `fix/sz067-branch-working-hours`). Главные деревья не тронуты.
При мерже ветки SZ-066 и `feat/platform-cabinets` конфликтуют в `MspBranchSettings.vue` и
`roles-msp.test.ts`; порядок мержа важен, в `feat/platform-cabinets` нет работы SZ-067.

**Риски и непроверенное.** (1) Точки с `delivery_available = true` и без активных зон
начнут отклонять доставку — перед выкладкой прогнать
`SELECT b.id, b.name FROM merchant_branches b WHERE b.delivery_available AND NOT EXISTS
(SELECT 1 FROM merchant_delivery_zones z WHERE z.branch_id = b.id AND z.is_active);`
(на локальном стенде таких не было). (2) Стресс-страж не гонялся (в preview/place добавлен
1–2 запроса; локальный стенд занят параллельной сессией). (3) UI глазами не проверялся —
браузерного бэкенда в сессии нет; экраны закрыты юнит-тестами и живым API. (4) E2e-тесты
чекаута падают предсуществующим 422 по `offer_id` (воспроизведено на чистом `926d786`;
в гейт `composer test` не входят).

## Дополнение владельца (диктовка 21.09, вечер — канон поведения)

- Зона = **радиус от адреса точки (базовая версия в app: 300 м … 1 км)**; **полигоны
  сохраняем** как детальный инструмент b2b — модель `merchant_delivery_zones` поддерживает
  и радиус, и полигон, и оба типа остаются рабочими (уточнение владельца 21.09, ответ 2:
  «значит делаем полигоны»). Существующие зоны точек не удалять и не конвертировать молча.
- **В интерфейсе важнее расстояние, а не способ задания зоны** (уточнение владельца 21.09,
  ответ 2: «для меня в интерфейсе важнее расстояние до точки, чем способ определения
  расстояния»): покупателю и точке показываем расстояние (до точки / до адреса доставки)
  в понятных единицах, тип зоны (радиус/полигон) — служебная деталь экрана настройки.
- **За радиусом оформить заказ с доставкой НЕЛЬЗЯ; с самовывозом — МОЖНО.**
  Цель — не терять дальних покупателей: поднять средний чек и число заказов.
  Значит гейт радиуса проверяется только для канала «доставка»; канал
  «самовывоз» радиус не ограничивает.
- Экран отказа — честный (урок SZ-036): «точка не доставляет сюда — доступен
  самовывоз», не пустота и не 422 без подсказки.
- Сегодняшняя карточка SZ-070 удалена как дубль — вся задача живёт здесь.
