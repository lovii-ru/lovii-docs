## Канон (уже зафиксирован)

- Юридическая модель: Правообладатель — торговый агент, чек выбивает
  Правообладатель с признаком агента и ИНН Лицензиата как Поставщика
  (`money_flow_public.md` §2.1, Оферта присоединения §12.2.3, Публичная
  оферта §2.6).
- Механика двухчековая: «Предоплата 100%» на поступление оплаты, «Полный
  расчёт» на подтверждение/передачу; чек возврата при отмене.
- Данные: `fiscal_documents` — DATA_MODEL §2.9; пороги/ретраи — PARAMS §11;
  API — API_SPEC §3.14.
- **Состав оплат чека (уточнение 19.10, апрув владельца + юриста,
  отменяет модель 17.10 «одна строка, без маркеров баллов»):**
  «в чеке ровно то, что происходит» (mock-services-docs
  `54fz-agent-scheme/01-verdicts.md` Q3б, selftests F-32/F-33).
  Чек — на полную стоимость заказа; строки оплат: type 1 «безналичными»
  на фактически уплаченную деньгами часть + type 4 «иная форма оплаты /
  встречное предоставление» (тег 1217) на списанные баллы. При 100%
  оплате баллами остаётся одна строка type 4. Цены позиций баллы НЕ
  меняют; начисление кэшбэка в чеке по-прежнему НЕ отражается (Q3в:
  не расчёт по ст. 1.1 54-ФЗ). Реализация: `FiscalDocumentManager::
  paymentsSplit()` (electronic = payment.amount, provision =
  bonus_spent) + `FermaFiscalProvider` (строки с sum=0 отсекаются).
  Налоговый вопрос «двойного налогообложения» транзита — решён вердиктом
  владельца 19.10: **налог МСП платится от суммы, фактически поступившей
  на его счёт** (= доля МСП, 90% от R по PARAMS §1.10); чек на полную
  сумму фиксирует расчёт с покупателем (агентская схема), а не налоговую
  базу Лицензиата; начисление кэшбэка в транзит и пул — не доход МСП.
  (Вопрос юристу №3 из пакета 54fz-agent-scheme закрыт этим вердиктом;
  формальную бумагу юриста можно приложить при боевой Ferma.)
- **База кэшбэка (вердикт владельца 19.10, «кэшбэк на кэшбэк» НЕ решён):**
  кэшбэк начисляется ТОЛЬКО на сумму, оплаченную деньгами пользователя
  (`order.total`, уже за вычетом скидок и списанных баллов); баллы
  кэшбэка не порождают. Реализовано с начала: `buildLines` размечает
  paidTotal от `order.total` (ApplyPromoToOrderAction), 100% баллами →
  кэшбэк 0; прогноз в preview масштабируется на денежную часть (В-8,
  вариант «а»). Проверено живьём: заказ 35 (19.10) — bonus_earned=0 при
  выключенных правилах; заказы 32-33 (тур 18.10) — forecast = accrual.
- **Приёмка новой схемы чеков (19.10, заказ 35):** prepayment (confirmed
  кассой) и full_payment (sent) — amount 160000 = 130000 деньги +
  30000 баллы, payments_split {electronic, provision} → строки type 1 +
  type 4. Исторические чеки заказов 25-34 (12 шт) остались в старом
  формате (одна строка electronic) — уже приняты кассой, НЕ перебивать
  (дубли ФД); новые заказы идут по новой схеме.

## Что реализовать (Фазы 3–4 плана)

   (высокий доступ, audit-log).
3. b2b: раздел «Чеки» по заказам своих точек — база месячного отчёта
   Лицензиату (к 5-му числу, Оферта присоединения §6.4.2).
4. app: квитанция — статус «чек сформирован» + ФД/ФП/ссылка.
5. Приёмка (Фаза 4): мок → тестовый контур Ferma → бой 1₽: чек №1 → сверка
   ФД/ФП (кабинет + «Проверка чеков ФНС») → чек №2 → возврат → негатив
   (ретраи/алерты) → инвариант леджера Σ=0. Каждая боевая операция — по
   явному «го» владельца.

## Дефект staging (2026-10-16) — чек без баллов отвергается кассой (P0)

**Симптом.** Заказ 19 (16.10 15:51, `completed`) остался без чеков: `fiscal_documents`
id 18 (`prepayment`) и 19 (`full_payment`) → `failed`, ошибка «Чек не прошёл проверку
кассы: `receipt.payments[1].sum`», ретраи каждые ~2 мин (`retry_count` 4–5, шум в
логах). В app чека нет: блок fiscal отдаётся только после `confirmed` (`4fbb4504`).

**Доказательство смены поведения.** Заказы 15–17 (07–08.10, касса ещё на встроенном
моке) — чеки `confirmed`; заказы 18 и 19 (16.10, касса на внешнем образе
`mock-services:0.8.0`, `lovii-core#21`) — `failed`. Логи kassa-mock: `sell REJECTED
(validation): receipt.payments[1].sum` при `getToken OK` (авторизация/пароль в
порядке — дело не в доступах).

**Корень — ядро, не мок.** `FermaFiscalProvider.php:141-145` всегда кладёт вторую
строку оплаты `['type'=>4,'sum'=>$payments_split['provision'] ?? 0]`, а
`FiscalDocumentManager::paymentsSplit` (255-266) считает `provision = bonus_spent`; без
списания баллов это `0`, а контракт Ferma требует `sum > 0` на каждую строку. Встроенный
мок валидации не имел — переход на строгий образ баг **вскрыл**, а не создал.

**Критерий приёмки.** Тест «`bonus_spent = 0` → в чеке одна строка оплаты; `> 0` → две»
+ повтор сквозного цикла на стенде: новый заказ → `prepayment` = `confirmed`, в логах
нет `fiscalization.send.alert`, заказ виден с чеком в app.

Готовый минимальный фикс (не отправлять строку оплаты с `sum = 0`) и план проверки —
пробел **I6** в `mock-services-product-release.md` (репозиторий `mock-services-docs`,
внутренняя ИС мока). Зона платёжно-фискальная, исполнитель — zcode.
