## 3. Фазы

### Фаза 1 — core-фундамент (эта задача, ветка от `staging`)
1. **Роли**: таблица ролей профиля (`representative` | `ambassador`; роль
   «МСП» = производная от партнёрства `partner_users`, не отдельная запись) —
   роли совмещаются, одна строка на роль. Назначение амбассадора — вручную
   админом (BRD: создаётся Основателем).
2. **Привязка заявки к представителю**: промокод `PPXXXX` → `partner_applications`
   (связка SZ-034A) + шаг **апрува представителя** в машине статусов
   (`awaiting_rep_approval` между `submitted` и `invoice_issued`; при заявке
   без промокода шаг пропускается → текущий путь не ломается). Эндпоинты
   апрув/отклон — по контракту SZ-034B (`/representative/approvals/*`).
3. **Тариф точки**: атрибут мерчанта (`start|basic|pro`, PARAMS §1.3);
   автопереход Старт→Базовый — командой по порогу 30 000 ₽ (запуск — фаза 3).
4. **Амбассадор-ветка**: закрепление представителей/точек за амбассадором
   (branch-wide, 20% пула), read-API `/api/v1/ambassador/*`: dashboard,
   reps (структура), income (история — честные нули до фазы 3), training
   (статический контент уроков из демо, без LMS).
5. **MSP read-API**: `/api/v1/msp/overview` (товары/остатки/последние заказы
   read-only), `/api/v1/msp/payment` (счёт верификации: сумма из PARAMS-
   параметра, код `VER-*`, реквизиты; выдача счёта — по готовности финконтура).
6. Статусы/числа KPI считаем из реальных данных (заказов почти нет — нули
   валидны); заглушки демо (конверсия views, «46%») не переносим.

### Фаза 2 — app: второй интерфейс
Активная роль в профиле + переключатель («Клиент» ↔ роли, как в демо);
вкладки rep по SZ-034B с UI-каноном из artifacts-спеки (Обзор/Подключение/
Точки/Доход/Профиль); amb (Обзор/Структура/Доход/Обучение); msp-слой
(Заявка/Мой магазин/Платёж/Инструкция); чаты — заглушки.
