# T-023 — Кошелёк PAY и полный финансовый контур: типы транзакций → контур → подписи узлов → админка

> Статус: **В работе** — Фаза A принята 26.09 (PR #13/#15 смержены); **Фаза B принята Super Z 26.09 ночь** (PR #14, merge `132d30c` в staging, отчёт ниже); фоллоу-апы Фазы B: TS-зеркало `ruble_adjustment` (lovii-app) + docblock `cascadeAccounts` — до приёмки Фазы C
> Приоритет: **P1** · Источник: решения владельца 2026-09-26 (прогон №3, пункты №2/№4/№5/№6 — `decisions/decisions-needed.md`)
> Исполнитель: **zcode** · Приёмка: **Super Z** (пофазно, PR за PR) · Репо: `lovii-core` (контур) + `lovii-app` (админка/экран — Фаза D) + `lovii_docs` (каталог типов, session-доки) · Дата постановки: 2026-09-26
> Закрывает: **F-059** («две казны», реализацией Фазы B), фиксирует каскад по **F-067**. Готовит базу под карточку чарджбэка Super Z (**F-050**, отдельная постановка).

## Контекст

Решения владельца 26.09: карта PAY — **всегда баллы**; подписка списывается с PAY
**по умолчанию**, **фоллбэк — бизнес-карта** (№2); кошелёк делаем сейчас, исполнитель
zcode (№4); сначала описать **все типы транзакций** и зафиксировать как типы с деревом
проводок, чтобы любую транзакцию можно было развернуть по её дереву (№5); подпись узла
обязательна на всех транзакциях — основа трассировки происхождения средств (№6).

Проверка Super Z (F-067): код `SubscriptionBillingService::findFundedSource()` каскадом
**business → pay** по леджер-счётам `Domain\Billing\Account` — порядок, обратный
утверждённому владельцем; механизм «PAY по умолчанию → фоллбэк Business» в каноне
отсутствует. Это и есть F-059: карта PAY показывает балльный кошелёк `Core\Wallet`,
а подписка дебетит пустой леджер-счёт → 422 `insufficient_funds` при видимом балансе.

Канон-модель: `PAY_POINTS_MODEL.md` (PAY = баллы `wallets`; Business = рубли),
`FINANCIAL_CONTOUR.md`, `FIN_BALANCE_REFERRAL_BRIEF.md` (два контура: рублёвый ledger +
балловый wallet). Инвариант гейта: `wallets.balance` = Σ earn − Σ spend ± refund/adjustment.

## Фазы

### Фаза A — каталог типов транзакций (канон + код-типы, БЕЗ бизнес-логики)

1. Каталог **всех** типов финансовых транзакций платформы: начисления (кэшбэк, реп/амб
   доли, бонусы), списания (подписка, покупка, конвертация), переводы P2P, выводы,
   корректировки/adjustment, фоллбэк-списания подписки, резерв под чарджбэк-типы
   (поле/место в enum — без реализации, F-050 у Super Z).
2. Для каждого типа зафиксировать: **дерево проводок** (источник → получатель, через
   какие узлы/счета), казну (баллы `wallets` / рубли ledger), инициатора, события,
   признак «влияет на подписку», признак «фоллбэк-операция».
3. Зафиксировать дважды и идентично: документ канона (`FINANCIAL_CONTOUR.md` §«Типы»)
   + единый enum в коде (PHP `enum` в core, TS-типы в app). Любая проводка — только
   через тип из каталога.
4. **СТОП-ГЕЙТ: каталог принимает Super Z до старта Фазы B.** Код контура до приёмки
   каталога не пишется.

### Фаза B — контур кошелька (закрытие F-059/F-067)

1. PAY = баллы; все операции строго через типы из Фазы A.
2. Механизм подписки: списание **по умолчанию с карты PAY** (`Core\Wallet`); при
   недостатке — **фоллбэк на бизнес-карту** (решение №2); факт фоллбэка — отдельный
   тип транзакции в каталоге.
3. Единая точка списания подписки с маршрутом PAY → Business (инверсия текущего
   `findFundedSource` business→pay); user-ledger источник подписки убрать по модели
   PAY_POINTS_MODEL §3.
4. Приёмка: сценарий SZ-056 №9 (422 insufficient_funds при балансе на PAY) — зелёный.

### Приёмка Фазы B — Super Z, 26.09 ночь: ✅ ПРИНЯТО («го» на Фазу C после фоллоу-апов)

**PR `lovii-core#14`** (`t023b-pay-subscription-contour`) — merge `132d30c` в staging
(без CI — F-066, ретроспективный прогон после оживления; локально php -l/pint/phpstan 🟢).

1. **Инверсия каскада** (F-067/F-059): `cascadeAccounts()` отдаёт `[pay_wallet, business…]`;
   цикл берёт первый источник с достаточным балансом, сплита нет — PAY по умолчанию,
   бизнес-карта фоллбэком (решение владельца №2). При недостатке попытка честно пишется
   failed (`insufficient_funds`) и каскад идёт дальше; частичный PAY-баланс не расходуется.
2. **Тип каталога в действии**: проводка кошелька — `subscription_debit` (новый кейс
   `WalletTransactionType`, инкремент 6→7, без переименований; §8.1). Fail-попытки в
   `wallet_transactions` не пишутся — только успешные (§8.4 п.2).
3. **Фоллбэк-маркер**: бизнес-ветка пишет пару ledger-строк `subscription_payment` с
   `meta.fallback=true` (дебет бизнеса + транзит номинала); wallet-ветка маркера не имеет
   (PAY — дефолт, не фоллбэк). Канон §8.1/§8.4 синхронизирован с этой сигнатурой.
4. **Тесты = сценарий SZ-056 №9**: «PAY funded enough — business stays untouched»
   (source=pay_wallet, баланс 0, `subscription_debit` ×1) + новый тест фоллбэка
   (PAY пуст → source=business, `meta->fallback` ×2). Subscription 27 passed; полный
   набор 1550 passed / 2 предсуществующих E2E-падения по офферам (вне скоупа).
5. **Гигиена enum**: `RubleAdjustment` = `ruble_adjustment` (дедуп значения `adjustment`
   между контурами; storage `LedgerEntryType::Adjustment` = `adjustment` — слои различены,
   §8.2 синхронизирован). `FinancialTransactionType::` в коде не используется —
   переименование рантайм-безопасно.

### Фаза C — финансовая безопасность: подписи узлов и разворот по дереву

1. **Подпись узла** для каждой транзакции (узел/счёт, через который прошла операция)
   — по решению №6; основа трассировки происхождения средств.
2. Разворот любой транзакции по её дереву: от точки последнего перевода/вывода до
   корня возникновения средств (API: дерево проводок по id транзакции).

### Фаза D — админка (`lovii-admin`)

1. Список всех операций и транзакций; фильтры: тип, казна, пользователь, период, узел.
2. Разворот транзакции по дереву в UI (потребляет API Фазы C).
3. Экран поиска/аналитик происхождения средств — **вне скоупа** (в последствии,
   решение №6).

## Приёмка Фазы A — Super Z, 2026-09-26: ✅ ПРИНЯТО, СТОП-ГЕЙТ СНЯТ

3. **PR lovii-app#15** (`financial-types.ts` + session-док 134): Points ×8,

## Протокол приёмки Super Z (на каждый PR)

1. Один PR = одна фаза или один тип транзакции из каталога (мелкие атомарные PR).
2. PR ссылается на пункт каталога; типы в коде ≡ типы в каноне (расхождение = возврат).
3. CI зелёный с первого прогона; гейты канона зелёные; тесты покрывают дерево проводок
   каждого типа (включая отрицательные: недостаток средств → фоллбэк → отказ).
4. Фаза B: демонстрация сценария SZ-056 №9 на staging.
5. Фаза C: каждая операция несёт подпись узла (отсутствие = возврат); разворот
   тестовой транзакции по дереву.
6. Фаза D: фильтры + разворот в админке на тестовых данных.
