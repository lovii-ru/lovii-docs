# SZ-077 — Экран «Перевод» в приложении + единый узел переводов (обход невозможен)

> Статус: **На приёмке**
> Приоритет: P1 (решение владельца 25.09: упрощение перевода + «переводы через один узел»)
> Источник: диктовка владельца 2026-09-25 (вечер): «все операции идут через транзитный номинальный
> счёт, с комиссиями или без; без комиссии — сколько пришло, столько ушло»; «переводы — отдельный

## Контекст: что сейчас (проверено по коду 2026-09-25)

- **Узел перевода есть:** `lovii-core/app/Domain/Billing/Services/TransferService.php` — три
  направления: PAY → другому (`execute`), PAY → свой счёт компании (`executePayToBusiness`),
  счёт компании → PAY (`executeBusinessToPay`, 0%). Правила — `config/transfers.php`
  (мин. 100 ₽, макс. 3 000 ₽, резерв 100 ₽, ступени 0,5–3,5%).
- **Эндпоинты:** `GET /account/transfer/quote`, `GET /account/transfer/resolve`,
  `POST /account/transfer` (`lovii-core/routes/api.php`).
- **Транзит:** все ноги идут через `platform_nominal` (SZ-043); комиссия — на счёт оператора
  (`payments.split.operator_partner_id`). Канон: `canon/PAY_POINTS_MODEL.md` §5,
  `canon/FINANCIAL_CONTOUR.md` §5.3/§5.5.
- **Приложение:** экран `ProfileTransfer.vue` (`/profile/wallet/transfer`) — сегменты источника,
  получателя и способа адресации; `destination_type` передаётся явно.
- **Эталон вида:** витрина `#/transfer` (сборка 126, `lovii-demo/js/transfer.js`) — одно поле
  адресата с авто-определением типа, точный авто-расчёт, источник одним выпадающим списком,
  экран успеха.
- **Найденный обход:** `lovii-admin/app/Services/DatabaseWalletService.php` → `adjustBalance()` —
  прямой `wallets.balance += X` + `WalletTransaction(adjustment)` **в обход** узла, лимитов, резерва
  и транзитного номинала.

## Что сделать

### A. Экран «Перевод» в приложении (`lovii-app`)

1. Переписать `ProfileTransfer.vue` по эталону витрины:
   - одно поле «Телефон, карта или промокод»; тип определяется по вводу (**промокод — ровно 6 знаков,
     может быть цифрами или буквами**; телефон — 11 цифр; карта — 13+ цифр);
   - поле «Сумма»; **точный** расчёт ровно по введённой сумме (без подмены); превышение лимита/остатка —
     явным сообщением и блокировкой кнопки;
   - **один выпадающий список источника**: Личный счёт (PAY) · Счёт компании; при «Счёт компании»
     поле получателя скрывается (только себе в PAY, 0%);
   - экран успеха вместо молчаливого возврата: «Сделать ещё перевод» / «На главную».
2. API: `destination` без обязательного `destination_type` — либо клиент определяет тип (как витрина),
   либо ядро определяет по вводу. Решение зафиксировать в отчёте.
3. Один маршрут на экран перевода; дублирующие маршруты/экраны удалить.

### B. Единый узел (`lovii-core`)

4. **Три проверки в момент перевода** (в одной `DB::transaction`, до записи; нарушение → `422`,
   ни одной записи):
   - **балансы** — источник под `lockForUpdate`; PAY: `сумма + комиссия ≤ баланс − 100 ₽`;
     счёт компании: `сумма ≤ баланс`; проверка **под блокировкой**, а не до неё;
   - **дубли** — поле `idempotency_key` + unique-индекс на `account_transfers`; повторный запрос с тем же
     ключом возвращает тот же перевод и не создаёт второй; запрет перевода самому себе;
   - **правила** — `100 ₽ ≤ сумма ≤ 3 000 ₽`, резерв, тариф по ступеням, направление из белого списка,
     получатель найден и не является отправителем.
5. **Инвариант транзита:** по каждому переводу `platform_nominal` в ноль —
   с комиссией `+(сумма+комиссия) − сумма − комиссия = 0`, без комиссии `+сумма − сумма = 0`.
   Добавить тест; расхождение → инцидент P1 (канон `FINANCIAL_CONTOUR.md §5.4`, допуск 0).
6. **Одна точка подписи:** `AccountTransfer` + `WalletTransaction` (transfer/fee) + проводки ledger —
   в одной транзакции и в одном месте (`TransferService`), с `transfer_id` и `split_role` у каждой ноги.
7. **Детектор обхода:** перевод, созданный не через узел, должен **не создавать транзакцию**, а
   возвращать пользователя с ошибкой `transfer_unknown_origin`. Закрепить стражем-тестом: скан
   `lovii-core/app` и `lovii-admin/app` падает, если `AccountTransfer::query()->create` или
   `WalletTransaction::query()->create` с типом transfer/fee встречается вне `TransferService`.

### C. Админка (`lovii-admin`)

8. Закрыть `DatabaseWalletService::adjustBalance()` — удалить либо провести через единый узел
   (с причиной, аудитом и записью в ledger).
9. `TransferSettings` — комиссия **по каждому типу перевода**, а не только min/max/резерв.

### 2. Решения по развилкам карточки

- **`destination_type` необязателен, тип определяет ядро** (`TransferResolver`): буквы → промокод
  (**ровно 6 знаков**), 11 цифр → телефон, 13+ цифр → карта, ровно 6 цифр → промокод. Определённый
  тип уходит в `meta.destination_type`; клиент тип не присылает (параметр принимается для старых сборок).
- **Идемпотентность**: `idempotency_key` (uuid на попытку отправки) + unique-индекс; повтор отдаёт тот
  же перевод, гонка добивается индексом; чужой ключ → `transfer_idempotency_conflict` (409).
- **Единая точка подписи**: `TransferSigningContext` открывает только `TransferService`; модели
  `AccountTransfer` и `WalletTransaction(transfer|fee)` вне окна бросают `transfer_unknown_origin` (422)
  и не создают записи. Закреплено стражем-тестом по скану `lovii-core/app` (и аналогичным по `lovii-admin/app`).
- **Комиссии по типам**: админка правит ставку каждого направления, ядро читает рантайм-оверрайды
  `payment_settings.transfers.commission_*`; пусто — канон (ступени 0,5–3,5% / `business_to_pay` 0%).
- **`adjustBalance` закрыт, а не удалён из продукта**: корректировка осталась, но выполняется ядром
  (кошелёк + история `adjustment` + зеркальная проводка ledger) — иначе поддержка потеряла бы инструмент,
  а кошелёк продолжал бы расходиться с обеспечением.
