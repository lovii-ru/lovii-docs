# T-032 · Карта страниц lovii-app: полная инвентаризация экранов и функционала с постоянными ID

> Статус: **Открыта**. Исполнитель: продукт-агент (zcode).
> Приёмка: фаза A — владельческая приёмка формата (3–5 карточек); финал —
> Приёмка-1 Super Z (факт-чек полноты) → Приёмка-2 владелец.
> **Код приложения не меняется** — задача документационная.
**Связано:** SCREEN_MAP.md (концепт демо, Draft — не источник истины, см. «Границы»),
PRODUCT_QUALITY_BAR.md (места дизайн-прохода), SZ-076 (канон демо), T-031 (промо на
покупательских экранах), REGISTRY.md (регистрация результата).

## Зачем

Хвост точечных правок по app (дизайн-проходы, состояния, багфиксы) адресуется
«по-человечески»: «экран настроек», «шторка профиля», `SettingsSheet.vue` — это
неоднозначно, страницы плодятся (витрина → карточка точки → товар → чекаут →
квитанция; кабинет МСП → мерчант → бренд → точка → каталог; настройки акций,
группы товаров, каналы продаж), и в задачах регулярно возникает вопрос «о какой
именно странице речь». Нужна полная as-is карта всех страниц приложения — включая
вложенные и производные — где каждая страница имеет постоянный уникальный ID.
В дальнейшем любая задача или правка ссылается на ID (`APP-P-014#subscription`),
а не на описание словами.

## ID-схема (постоянные номера — не переиспользуются никогда)

- `APP-P-NNN` — страница (запись маршрутизатора lovii-app). Нумерация сквозная,
  в порядке появления в конфиге роутера.
- `APP-M-NNN` — модальный экран / оверлей без собственного маршрута (модалки,
  sheets, drawers, поповеры-экраны).
- Функциональный блок внутри страницы: якорь `APP-P-NNN#slug` / `APP-M-NNN#slug`
  (например `APP-P-032#promocode-input`).
- Вложенные и производные страницы — обычные `APP-P-NNN` с полем «Родитель» и
  точкой входа (пример: настройки акции → родитель: страница акции; группа
  товаров → родитель: каталог/товары; каналы продаж → родитель: карточка товара).
- Параметризованный маршрут (`/product/:id` и подобные) = **одна** карточка-шаблон
  с разделом «Варианты параметров», а не карточка на каждый инстанс.
- Вкладка = блок `#slug` внутри карточки страницы; отдельный children-маршрут =
  отдельная карточка с «Родителем».
- Удалённая страница: статус `removed` в карточке, ID не переиспользуется.
  Новые страницы получают следующий свободный номер.

## Шаблон карточки страницы (один файл на страницу)

```markdown
# APP-P-014 — <Название>
- Статус: живая / эксперимент / removed
- Маршрут: <path> + name (<файл роутера>:<строка> — file:line привязка)
- Тип: обычная / вложенная (родитель: APP-P-XXX, вход: <кнопка/ссылка/редирект>) / guard-редирект
- Доступ: гость / авторизован / роль / подписка
- Назначение: 1–2 предложения
- Функциональные блоки:
  - #slug — Название: что делает, чем управляет
- Состояния: loading / пусто / ошибка / offline / guest-view
- Зависимости: API-эндпоинты, модули/компоненты/сторы (пути файлов)
- Переходы: → APP-P-XXX (что и откуда ведёт), ← APP-P-YYY (кто сюда входит)
- Сверка: роутер ✓ / код ✓ / UI ✓
```

## Что сделать (метод полноты — 3 прохода + сверка)

1. **Роутер:** разобрать конфиг маршрутизатора lovii-app полностью (children,
   lazy-импорты, meta/guards) → реестр маршрутов; каждая запись = карточка.
2. **Код:** поиск всех переходов и оверлеев (`RouterLink`, `router.push/replace`,
   `useRouter`, `navigate*`, `Modal/Sheet/Drawer/Teleport`, динамические импорты)
   → всё, что не поймал проход 1: модалки, динамические экраны, 404/редиректы,
   страницы-заглушки.
3. **UI:** все пункты меню, таб-бары, списки настроек, кнопки-переходы → каждый
   видимый вход привязать к существующему ID. Попутно ловим переходы в никуда.
4. **Сверка:** таблица «источник → находка → ID / расхождение» в INDEX.md.
   Каждая карточка имеет ≥1 подтверждённый вход; каждый видимый вход указывает
   на существующий ID.

## Результат (DoD)

1. `canon/APP_PAGES/` — новый каталог канона: `_INDEX.md` (карта-оглавление:
   таблица всех ID — ID, название, тип, маршрут, файл; статистика; зафиксированный
   HEAD среза lovii-app; таблица сверки; раздел «Расхождения»; правила сопровождения)
   + один файл на страницу/модалку по шаблону.
2. Правила сопровождения в `_INDEX.md`: как заводить новые страницы (следующий
   свободный номер в той же задаче, которая их добавляет); ID не переиспользуются;
   карточка страницы обновляется тем же пуш-циклом, что и правка страницы.
3. Число карточек страниц = числу записей роутера; расхождения объяснены явно
   (в «Расхождениях», не молча).
4. Каталог зарегистрирован в `REGISTRY.md` (корень, вручную).
5. Гейты канона зелёные: `task_guard`, `doc-canon-check`, `fact_guard`.
6. Отчёт исполнителя в этой карточке: числа (страниц/модалок/расхождений), HEAD
   среза, ссылка на INDEX.

## Фазы

- **A — скелет:** проход 1 (роутер), все страницы с маршрутом + короткое
  описание, INDEX. В конце фазы A — сообщить фактическое число страниц.
  → **Приёмка формата владельцем на 3–5 карточках** до массового заполнения.
- **B — наполнение:** полные блоки/состояния/зависимости по шаблону; проходы 2–3;
  сверка и «Расхождения».
- **C — расхождения:** перечень найденного уходят в отдельные задачи, не здесь.

## Границы

- Код lovii-app (и любых репо) не меняется. Найденные баги/битые переходы —
  строка в «Расхождениях», фиксы — отдельными задачами.
- `SCREEN_MAP.md` не трогать: это концепт демо (Draft, ~16 экранов, до роли-
  дашбордов реального app), исторический артефакт. Источник истины для T-032 —
  только код lovii-app на зафиксированном срезе. Вопрос о судьбе SCREEN_MAP —
  владельцу отдельно, вне этой задачи.
- Карта описывает as-is: что есть на срезе, без пожеланий и рефакторингов.
- Роли/доступы описывать по факту кода (guards/meta), не по ожиданиям.

## Приёмка

- **Фаза A:** владелец смотрит 3–5 карточек на соответствие шаблону и глубине —
  «го» на заполнение остатка.
- **Финал:** Приёмка-1 Super Z — факт-чек полноты двунаправленной выборкой:
  случайные страницы из кода должны находиться в карте, случайные карточки карты
  должны подтверждаться кодом (file:line); сверка числа записей роутера с числом
  карточек. Приёмка-2 владельца — практическая полезность адресации.
