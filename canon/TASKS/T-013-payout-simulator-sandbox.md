# T-013 — Выплаты: свой тестовый контур — модуль выплат и симулятор банковского API (lovii-pay)

> Статус: **Открыта** (2026-09-18 — решение владельца: «платежку выплат можно
> сделать примерно похожим модулем согласно документации — как бы создать свой
> тестовый контур, пока нам не дали тестовый контур от банка, и провести все
> сценарии, подготовиться к полному фин-контуру»)
> Приоритет: **P1** (полоса C — деньги; репетиция реестров выплат до
> получения тестового контура банка — запрос в банк отложен владельцем)
> Исполнитель: zcode · Репо: `lovii-pay` · **Зависимость: каркас T-012**
> Источник: BACKLOG §1 (пункты 1–3 + сверка с банком) + PARAMS §1.6 (вывод
> самозанятым) + FINANCIAL_CONTOUR §5.5 (Правило 3) + документация банка
> по выплатам (версия у владельца; путь в репо — зафиксировать в отчёте)

## Контекст

Реестры выплат МСП («Выручка за (дата)»), вывод без бизнес-карты и сверка с
банком (BACKLOG §1) упираются в отсутствие тестового контура банка — запрос
на API счёта отложен владельцем («пока ещё ждём»). Решение владельца: не
ждать — собрать модуль выплат по документации банка и вмонтировать в него
СИМУЛЯТОР банковского API: свой тестовый контур, на котором прогоняются все
сценарии. Когда банк выдаст тестовый контур — меняем драйвер и ключи,
сценарии те же: подготовка к полному фин-контуру уже будет сделана.

## Что решить

1. **Границы модуля.** Реестр ежедневных выплат (дата, партнёр, счёт, карта,
   сумма; статусы строки: сформирован → отправлен → исполнен / отклонён),
   вывод на карту без бизнес-карты, сверка день-итогов. Развилка: реестр
   собирает lovii-pay (балансы/реквизиты приходят из core подписанным
   вызовом) или core приносит готовый реестр.
2. **Драйвер банка.** Единый контракт «провайдер выплат» + две реализации:
   симулятор (по документации банка — те же эндпоинты, статусы, ошибки) и
   заготовка боевого драйвера. Переключение — конфиг (`driver=simulator|tbank`).
3. **Сценарии симулятора** (минимальный реестр приёмки): успешная выплата;
   отказ банка (нехватка средств на счёте платформы); частичный отказ
   реестра; таймаут/повторная доставка (идемпотентность по ключу выплаты);
   получатель снят с НПД-учёта между формированием и отправкой; лимиты
   суммы; итоговая сверка за день (отправлено vs исполнено, расхождения).
4. **Назначение платежа.** Шаблон «Выручка за (дата)» — параметр реестра
   (BACKLOG §1.2); реквизиты счёта списания — из окружения lovii-pay.
   Развилка: один шаблон для всех или параметризуется типом получателя
   (МСП / самозанятый).
5. **Комиссии вывода самозанятым.** Правила PARAMS §1.6: ≥ 3 000 ₽ — 1%
   (min 100 ₽), платит Компания; < 3 000 ₽ — 30 ₽ флэт, удерживается из
   суммы получателя. Исполняются как есть, в карточке не меняются.
6. **Ledger.** Когда списывается с баланса получателя — при формировании
   реестра или при подтверждении исполнения (развилка); append-only,
   суммы в копейках (FIN_BALANCE_REFERRAL_BRIEF, PRD FR-13.9); Правило 3
   §5.5: минусовый баланс блокирует исходящие.

## На что смотреть (грабли)

- Симулятор НЕ маскируется под боевой: ответы/логи помечены test-mode, на
  тестовом стенде — видимый маркер; боевой драйвер без ключей — fail-fast
  при старте (невозможное состояние).
- Деньги — копейки, округления комиссий — по канону, без собственных правил.
- Идемпотентность: повторный реестр за тот же день/получатель не создаёт
  двойной выплаты; ключ идемпотентности — в отчёте.
- `LedgerEntryType::Payout` объявлен, но не использовался (F-049) — первый
  реальный пользователь; проверить совместимость с ledger core.
- Реквизиты и персональные данные в fixtures — только синтетические.
- Гейты: PHPUnit + phpstan + pint зелёные; в отчёте — sha, таблица сценариев
  с результатами, переключатель driver проверен в обе стороны.

## Что не делать

- Не отправлять реальные платежи: боевой драйвер не включается без решения
  владельца; реальные реквизиты не заливаются.
- Не менять правила BACKLOG §1 и PARAMS §1.6: если по ходу всплыла развилка
  правила — остановиться и поднять владельцу.
- Не трогать гейт №4 и №3 sub-billing (T-011), эквайринг заказов в core.
