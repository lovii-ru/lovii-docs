# T-012 — lovii-pay: каркас фин-сервиса — отдельный репозиторий, сервис и поддомен платёжных ссылок

> Статус: **Открыта** (2026-09-18 — решение владельца: «lovii-pay — это
> фин-контур; я за такое решение; поддомен я бы даже запустил для будущих
> систем оплаты, чтобы ссылку на оплату отправлять»; решение-2 тем же днём:
> имя поддомена — **pay.lovii.ru**)
> Приоритет: **P1** (полоса C — деньги: дом для эквайринга, подписочных
> списаний, ККТ и выплат; без дома фин-код размазан по core)
> Исполнитель: zcode · Репо: **новый `lovii-pay`** (в `lovii-core` — только
> клиент вызова, без секретов)
> Источник: BACKLOG §0.3 полоса C + as-is/04 (эквайринг Т-Банк,
> двухстадийный) + as-is/12 + PARAMS (домены: `app.lovii.ru`, `api.lovii.ru`,
> `lovii.ru`) + SZ-018 (ротация секретов)

## Контекст

Сейчас весь фин-код живёт внутри lovii-core: эквайринг заказов (двухстадийный
Т-Банк), верификационные платежи МСП, далее подписочные списания (№3), потом
ККТ (54-ФЗ) и выплаты. Владелец решил (2026-09-18): lovii-pay — фин-контур
платформы, оформляем его как ОТДЕЛЬНЫЙ репозиторий/сервис и запускаем
поддомен под платёжные ссылки — единую точку входа «ссылка на оплату», куда
лягут текущие и будущие системы оплаты.

Смысл деления: core = продукт (заказы, пользователи, подписки, статусы),
lovii-pay = касса (принять деньги, вернуть, отчитаться). Секреты банка живут
только в lovii-pay, core их не видит; кассу можно править и деплоить, не
трогая витрину; банк-интеграции не валят продукт.

Имя поддомена утверждено владельцем тем же днём: **`pay.lovii.ru`**
(см. развилку 2).

## Что решить

1. **Каркас репозитория.** Развилка: новый чистый Laravel-каркас (тот же
   стек, что core) или скелет, вынесенный из core с вычищенным
   продуктовым доменом. Критерий выбора: минимум кода, который потом
   не придётся выпиливать.
2. **Поддомен и формат ссылок.** Имя поддомена — РЕШЕНО владельцем
   (2026-09-18): **`pay.lovii.ru`** (рядом с `app.lovii.ru` / `api.lovii.ru`
   — PARAMS; после запуска внести в таблицу доменов PARAMS). Формат
   платёжной ссылки — короткий, годный для SMS/пуша (например
   `https://pay.lovii.ru/p/{код}`). Остаются развилки: staging-адрес; TTL
   и одноразовость ссылки; что видит человек по ссылке до и после оплаты.
3. **Контракт core ↔ pay.** Core инициирует платёж → pay возвращает ссылку;
   банк бьёт вебхуком в pay; pay подтверждает core подписанным внутренним
   уведомлением («оплачено»). Развилки: синхронный API с подписью запросов
   (HMAC) + очередь, или только очередь; где истина статуса платежа
   (у pay; в core — зеркало для отображения).
4. **Своё хранилище.** Ожидаемо — своя БД lovii-pay (деньги отдельно от
   контента). Развилка: что именно зеркалится в core для показа
   пользователю и с какой задержкой.
5. **Секреты и окружения.** Ключи Т-Банка / ККТ / выплат — только в
   окружении lovii-pay; ротация по SZ-018; тестовый/боевой контур —
   переключатель драйвера (симулятор — T-013). Развилка: границы внутренней
   сети (подпись запросов, ограничение по IP).
6. **Миграция существующих потоков.** Эквайринг заказов и верификационные
   платежи пока остаются в core. Развилка: lovii-pay стартует ПУСТЫМ
   (каркас + поддомен + один первый поток — например, оплата подписки после
   №3) или сразу принимает существующие потоки. Рекомендация Super Z:
   старт пустым; перенос потоков — отдельные решения по одному.

## На что смотреть (грабли)

- Не дублировать бизнес-логику: машина статусов подписки (SZ-052) и заказы
  остаются в core; lovii-pay — только «взять деньги / вернуть / отчитаться».
- Вебхуки банка: идемпотентность (повторные доставки), проверка подписи
  банка, быстрый 2xx + отложенная обработка.
- Секреты не должны попасть в core `.env`, в репо или логи; в отчёте —
  где живут и как ротируются (связка SZ-018).
- Универсальная ловля `?`-суффиксов (T-010) работает в app на своём домене;
  платёжные ссылки pay-домена не должны конфликтовать с ней и с OTP-ссылками.
- Деплой: отдельный хост/контейнер рядом с core; staging и прод раздельно;
  TLS на поддомене — зафиксировать в отчёте (infra).
- Гейты: PHPUnit + phpstan + pint зелёные в новом репо; в отчёте — sha,
  staging-адрес, лог успешного круга тестовой ссылки.

## Что не делать

- Не переносить существующие оплаты заказов из core в lovii-pay в этой
  карточке (только каркас + поддомен + один поток по развилке 6).
- Не хранить в lovii-pay продуктовые данные (заказы, товары, профили).
- Не включать боевые ключи банков — только тестовые/симулятор до решения
  владельца.
- Не трогать домен подписки №3 (T-011) и гейт №4.

## Приёмка

- Приёмка-1 (Super Z): факт-чек нового репо (каркас, секреты, деплой);
  тестовая платёжная ссылка на staging проходит полный круг: создание →
  оплата → подтверждение в core.
- Приёмка-2 (владелец): имя поддомена, живой прогон ссылки с телефона.
