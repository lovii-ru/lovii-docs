## Фазы

### Фаза A — аудит контура (read-only, session-док)

1. Подтвердить №1 живым кейсом на staging: предпросмотр в админке ≡ фактический набор проводок разворота (Правило 4), включая номинальные зеркала и инбокс; эквайринг-fee не разворачивается (§5.4).
2. Инвентаризация **всех типов операций** чарджбэк-контура (reversal, bank_fee, earn-refund, spend-возврат, частичный разворот, повторный регресс) → **единая таксономия с каталогом T-023 Фазы A** (чарджбэк-типы входят в общий enum, отдельного словаря не плодить).
3. Проверка трассируемости: от `chargeback_logs` по `original_entry_id` до корня средств (meta Правила 5); контурная сверка §5.4 до/после разворота на тестовом заказе.
4. Артефакт: аудит-док в каноне; FINDINGS F-050 → статусы по пунктам.

### Фаза B — запрос решений владельца (2 пункта буквы канона)

- **№2 (dedup fee)**: рекомендация Super Z — дедуп по `payment_id` (Dispute Fee приходит на каждый регресс; заказ #133 — живой кейс). Правило 6 §5.5 уточнить.
- **№5 (spend-баллы)**: рекомендация — при чарджбэке возвращать списанные баллы как при отмене заказа (симметрия §5.3); иначе клиент теряет баллы за мошенническую операцию.
- **№3 (частичный)**: рекомендация — оставить полный разворот (MVP), добавить в UI админки явное предупреждение «частичный регресс разворачивает весь объём ног»; пропорциональный разворот — отдельное решение после MVP.

### Фаза C — код-фиксы core (после решений B + приёмки каталога T-023A)

1. **№4 → разворот с идемпотентностью по `original_entry_id`** (unique: order_id + original_entry_id + type) — устранить тихий пропуск дубль-пар.
2. **№2 → dedup fee по `payment_id`** (при «го» владельца).
3. **№5 → spend-возврат** (при «го» владельца) — через типы каталога, зеркально отмене заказа.
4. **№3 → предупреждение в UI** (сразу); пропорциональный разворот — отдельным решением.
5. Все новые проводки — типы из каталога T-023; в meta резервировать поле **подписи узла** (контракт T-023 Фазы C; если подписи уже в мастере — писать сразу).

### Фаза D — админка (`lovii-admin`, после T-023 Фазы C/D)

1. Таблица чарджбэков: фильтры (период, точка/партнёр, сумма, тип операции, узел).
2. **Разворачивание любой транзакции по дереву** — потребляет API дерева T-023 Фазы C: от чарджбэка до корня возникновения средств (подписи узлов видны в развороте).
3. Подтверждённый предпросмотр (№1) — регресс-тест «предпросмотр ≡ факт» на каждое изменение ядра.

### Фаза E — приёмка (краевые сценарии из правила F-050)

- Заказ с **несколькими платежами** (#133 — реальный кейс staging): два независимых регресса, каждый со своим fee.
- Частичный возврат; отсутствие партнёра; **повторный чарджбэк**; ретрай вебхука банка (идемпотентность end-to-end).
- Контурная сверка §5.4 до/после; демонстрация владельцу: фильтры + развороты по дереву на staging-данных.
