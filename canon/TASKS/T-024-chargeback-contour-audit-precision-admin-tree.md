### Фаза B — запрос решений владельца (2 пункта буквы канона)

- **№2 (dedup fee)**: рекомендация Super Z — дедуп по `payment_id` (Dispute Fee приходит на каждый регресс; заказ #133 — живой кейс). Правило 6 §5.5 уточнить.

- **№3 (частичный)**: рекомендация — оставить полный разворот (MVP), добавить в UI админки явное предупреждение «частичный регресс разворачивает весь объём ног»; пропорциональный разворот — отдельное решение после MVP.

#### Решения владельца — Фаза B (получены 26.09 ночь через owner-канал, дословно)

- **№2 (fee банка)**: «Fee банка — настраивается в момент чарджбэка, уже было реализовано в админке». Механизм остаётся ручным вводом оператора при обработке чарджбэка — нового продукта не требуется. Технический фикс дедупа (`order_id` → `payment_id`: скоупы идемпотентности разъехались с unique журнала — F-050 №2) выполняется в Фазе C как техгигиена, поведение владельца не меняет.
- **№3 (частичный чарджбэк)**: «Нет — лучше начислить потом, чем некорректно закрыть. Закрываем чарджбэк в ноль всегда, чтобы не было коллизий. Необходимые начисления с нужным комментарием из админки — лучший ход». **Политика: разворот — всегда полный, в ноль**; частичные компенсации — штатными adjustment-начислениями из админки с комментарием. Пропорциональный разворот снят с повестки; UI-предупреждение — опциональная страховка, не блокирует.
- **№5 (spend-возврат)**: сначала «Не понимаю, что это» → владельцу направлено разъяснение (при оплате заказа клиент мог заплатить баллами PAY (`spend`); при чарджбэке деньги возвращаются банком, а списанные баллы остаются списанными; готовый механизм `refundSpendForOrder` возвращает их как при отмене заказа). **Ответ владельца (26.09 утро, дословно): «spend возврат — да полный, симметрия с отменой»**. **Политика: spend-возврат при чарджбэке включается — полный, зеркально отмене заказа** (`refundSpendForOrder` + `reason=chargeback`); рекомендация Super Z принята.
- **6a (multi-earn)**: «Возвращать все начисления: всё дерево. Всё должно посчитаться в ноль — сколько начислено, столько списано». **«Го»**: фикс Фазы C — суммировать все earn-строки заказа.
- **6b (отрицательный баланс)**: «Да — важно видеть баланс. Баланс может быть отрицательным, это ещё один триггер для работы в контуре. Фактические деньги на счету в банке, у нас только учёт». **Политика: минус разрешён и видим**; отрицательный баланс — сигнал/триггер для контурной работы; клэмп не вводить.

### Таксономия операций чарджбэк-контура (сверка с каталогом T-023A §8)

| Операция | Казна | Тип в коде | Направление | Идемпотентность | Трассировка (meta) |
|---|---|---|---|---|---|
| Зеркальный разворот ног сплита (+инбокс) | рубли | `chargeback_reversal` | каждой ноге на ТОТ ЖЕ счёт −1×оригинал (обе стороны пары) | pre-check `(order_id, account_id, split_role)` + unique-индекс | `original_entry_id`, `original_type`, `original_amount`, `split_role`, `order_id`, `payment_id`, `chargeback_date` |
| Комиссия банка (Dispute Fee, вводит оператор) | рубли | `chargeback_bank_fee` | счёт Точки → банк (−), split_role=point | dedup **по `order_id`** (дефект №2) | `reason`, `order_id`, `payment_id`, `fee_amount` |
| Возврат earn-кэшбэка | баллы | `refund` (wallet) | `balance -= earn`, строка +amount | dedup по `(order_id, type=refund)` + unique | `reason=chargeback`, `order_id`, `payment_id` |
| Возврат spend-баллов | баллы | — **в чарджбэке НЕ вызывается** (№5); при отмене заказа — `adjustment` из `OrderStatusMachine` | `balance += spent`, строка +amount | unique `(wallet_id, order_id, type)` | `reason=order_cancelled` |
| Журнал обработки | — | `chargeback_logs` | — | unique `(order_id, payment_id)` | `refund_amount` (кумулятивно — F-069), `bank_fee_amount`, admin, meta.source |

Не разворачивается: `acquiring_fee` (§5.4 — банк комиссию эквайринга за чарджбэк не возвращает, сверка поглощает). Разворачиваются 3 типа оригиналов: `order_income`, `pool_share`, `payment_income` — предпросмотр админки берёт ровно эти же типы: **предпросмотр ≡ факт структурно** (№1).

### Каталожные уточнения (внести в §8.1 при Фазе C)

1. `refund` в коде = **зеркало earn** (возврат начисленного кэшбэка), а не «зеркало spend», как записано в §8.1 — описания инвертированы относительно реальности.
2. `adjustment` — не только «ручная корректировка админом»: это также **программный возврат spend** при отмене заказа (`refundSpendForOrder`, `OrderStatusMachine`), `reason` в meta различает. unique `(wallet_id, order_id, type)` держит `refund` под earn-возвратом — поэтому spend-возврат ходит через `adjustment`.

### Дефекты F-050 — итоги аудита

- **№1 — закрыт код-level**: `fetchLegs` без фильтра по знаку, `getReversalPreview` инвертирует все ноги; набор типов совпадает с `REVERSED_TYPES` ядра. Остаток — живой кейс «предпросмотр ≡ факт» на staging (Фаза E).
- **№2 — подтверждён**: dedup fee по `order_id` (`PostChargebackBankFeeAction:40–45`), при том что `chargeback_logs` уникален по `(order_id, payment_id)` — скоупы идемпотентности разъехались. Живой кейс #133.
- **№3 — подтверждён структурно**: ноги ищутся по `order_id` (не payment), API не принимает частичную сумму — любой регресс разворачивает весь заказ.
- **№4 — подтверждён**: pre-check на каждую ногу `(order_id, account_id, split_role)` — дубль-пара тихо не развернётся. Фикс Фазы C: идемпотентность по `original_entry_id`.
- **№5 — подтверждён + найден готовый механизм**: `refundSpendForOrder` уже существует и отлажен (отмена заказа) — фикс Фазы C сводится к вызову в `ProcessChargebackController` + параметризация `reason=chargeback`. Дёшево, симметрия с отменой preserved.

### Новые края (→ F-069)

- **6a. Multi-earn**: `refundEarnForOrder` возвращает только **первый** earn заказа (`->first()`) — при нескольких начислениях кэшбэка часть не вернётся.
- **6b. Отрицательный баланс**: `decrement(balance)` без проверки достаточности — если клиент уже потратил кэшбэк, баланс уходит в минус. Требует политики (разрешить минус / клэмп / долг) — **вопрос владельцу** (Фаза B).
- **6c. Кумулятивный `refund_amount`** в `chargeback_logs`: сумма считается по всем `chargeback_reversal` заказа — при втором чарджбэке (другой платёж) в лог пишется совокупный объём, не дельта. На деньги не влияет (учётная неточность журнала).

### Трассируемость (Правило 5) — что есть / чего не хватает

Есть: разворот → корень по `original_entry_id` (полная цепочка `chargeback_logs → chargeback_reversal → оригинальная нога → payment → вебхук`); fee → заказ/платёж. Не хватает: (а) earn-refund не ссылается на исходную wallet-строку (только по `order_id` — для дерева T-023C добавить `original_wallet_transaction_id`); (б) **подписи узлов нет нигде** — ожидается контракт T-023 Фазы C (§8.4 п.4), в meta резервировать поле с Фазы C этой карточки.

### Методика сверки §5.4 (выполняется на живом заказе, Фаза E)

Снимок балансов всех затронутых счетов до → подтверждение чарджбэка → снимок после: Σ(разворотов) = Σ(order_income+pool_share обе стороны+payment_income) c обратным знаком; acquiring_fee не тронут; wallet: −earn ± spend-возврат; инварианты §5.2/§8.4 п.1 сходятся. Кейс #133 (два платежа) + частичный + повторный.

**Вывод**: контур структурно здоров (атомарная транзакция, двойная идемпотентность, метатрассировка разворота), краевые дефекты №2/№4/№5 точечные и дешёвые в фиксе. Фаза B — запрос решений владельца по №2/№3/№5 + новым 6a/6b.
