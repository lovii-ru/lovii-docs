> Статус: **Открыта** (zcode, 2026-09-11; владелец: «надо сделать контур для баллов,
> куда будут приходить начисления»)
> Приоритет: **P1** — фундамент баллового контура канона (FIN_BALANCE_REFERRAL_BRIEF
> §0.1, решение владельца №1: балловый контур отдельный от рублёвого, 1 балл = 1 ₽)
> Исполнитель: zcode · Репо: `lovii-core` + `lovii-app`
> Гейт: `docker exec lovii-core-app-1 composer test` / `yarn test`
> Источники: FIN_BALANCE_REFERRAL_BRIEF v0.5 (A-1 балловая часть, A-2 триггер),
> FINANCIAL_MODEL §2.5, решения владельца №1/3/8/9, БД staging 2026-09-11

## 1. Факт (проверено по коду core и staging 2026-09-11)

- Каркас живой: `wallets` + `wallet_transactions` (копейки, 1 кошелёк на юзера),
  сервис `LoyaltyService` (earn/spend/validateSpend), API уже есть:
  `GET /api/v1/wallet`, `GET /api/v1/wallet/transactions` (auth).
- **Начисления не приходят**: `LoyaltyService::earnFromOrder()` не вызывается нигде.
  spend подключён в `PlaceOrdersAction` (списание при заказе с баллами).
- `loyalty_rules` пустая (0 строк) → даже при подключении начислять нечем.
- 17 confirmed-платежей в `payments`, wallets = 0 строк: история начислений
  начинается с этой задачи (бэкфилл старых заказов НЕ делаем — они тестовые).
- В enum `WalletTransactionType` есть `Expiration` — против решения №8
  (баллы бессрочные), вывести из употребления.

## 2. Куда приходят начисления (модель контура)

| Операция | Тип проводки | Триггер | MVP |
|:---|:---|:---|:---|
| Кэшбэк за заказ | `earn` | confirmed-платёж (вебхук/GetState Т-Банка) | ✅ |
| Возврат кэшбэка | `refund` | payment → Refunded/Reversed после Confirmed | ✅ |
| Оплата заказа баллами | `spend` | оформление заказа (уже работает) | ✅ есть |
| Корректировка админом | `adjustment` | вручную (SQL/b2b — интерфейс отдельно) | каркас |
| P2P-перевод | earn+spend парой | — | ❌ (нужны лимиты/антифрод EC-38/39, отдельно) |
| Вывод в деньги | spend | — | ❌ (нужны подписка/статусы: Б-3/Г-3) |

Кэшбэк выдаёт платформа по глобальному правилу `loyalty_rules` (MVP).
Конструктор кэшбэка на точке (канон FINANCIAL_MODEL §2.5: % задаёт точка,
комиссия 25% с кэшбэка — точка платит сверху) — **отдельная задача**, рублёвая
сторона той механики появится вместе с пулом 40/40/20 (бриф A-2).

## 3. Правки core

1. **Hook начисления.** `HandleTBankNotificationAction::applyStatus()`: при
   переходе в `Confirmed` (после перевода заказа) → `LoyaltyService::earnFromOrder($order)`.
   Идемпотентность: если по заказу уже есть `earn`-транзакция — не начислять
   повторно (банк ретраит вебхуки; GetState — единственный источник истины).
2. **Возврат.** При `Refunded`/`Reversed` по оплаченному заказу: если кэшбэк был
   начислен — проводка `refund` на ту же сумму (баланс минус, неизменяемый журнал).
3. **Без сгорания (решение №8).** Убрать `Expiration` из enum; `expires_at`
   в БД не трогаем (колонка остаётся, код её не пишет). Тест: earn-проводка живёт.
4. **Инвариант (тесты).** `balance = Σ(wallet_transactions.amount)` после серий
   операций; двойной CONFIRMED → одна earn; Refunded после Confirmed → refund.
5. **Правило на стенде.** Одна строка в `loyalty_rules`: earn 5%, max_spend 100%
   (решение №9: оплатить можно 100% чека баллами; 5% — как в демо/витрине).
   Конфиг платформы, не витринные данные — руками через artisan/SQL на staging,
   b2b-экран для правил — отдельно, не в этой задаче.

## 4. Правки app

- Модуль `balance-module`: экран «Баланс» (остаток крупно + история проводок
  с человекочитаемыми лейблами: «Кэшбэк за заказ #N» / «Оплата заказа #N» /
  «Возврат по заказу #N»), ленивое создание кошелька не нужно — API отдаёт нулевой.
- Роут `/profile/balance` + вход из профиля (строка «Мои баллы» с остатком).
- Дизайн — токены lovii-design; монетка/эмодзи по канону демо (баллы 1:1).
- Пустая история — честный стейт «Баллы появятся после первого оплаченного заказа».

## 5. Гейты и приёмка

- core: composer test зелёный (новые pest-тесты §3.4 + регресс платежей).
- app: `yarn test` зелёный; вручную на staging: заказ с оплатой картой (тестовый
  терминал) → кэшбэк на «Балансе», повторный вебхук без дубля, возврат → refund.
- Приёмка владельцем на app-staging: «Достаточно» = начисление видно в UI после
  живого заказа.

## 6. Вне MVP (не терять)

- P2P-переводы (решение №3 — да, но с лимитами/логом EC-38/39).
- Вывод баллов в деньги (Г-4, канал по legal_status, гейт подписки).
- Конструктор кэшбэка на точке + комиссия 25% (рублёвая механика, с A-2).
- Сверка В-4 «Σ баллов = транзитный счёт» — когда появится транзитный счёт.
- b2b-экран управления `loyalty_rules`.
