> Статус: **На приёмке** (2026-09-09, Super Z; §2.1 заморожена — см. §6); приёмка-1 zcode «Достаточно» по §2.2–2.4 — 2026-09-10 (§7)
> Приоритет: **P1** — блокирует проверку цикла МСП на собственных компаниях владельца
> Источник: запрос владельца («создал всё что надо, но не вижу своего магазина;
> указал адрес как в профиле, чтобы быть первым — не сработало»)
> Исполнитель: Super Z · Репо: `lovii-core` (+ подсказки в `lovii-b2b`) · Гейт: composer test
> Диагноз: zcode, факты проверены на staging 2026-09-09 (см. §1)

## 1. Диагноз (факты, проверено на staging)

Тестовый мерчант владельца: **«Пышки & Пончики»** (id 280, partner 263 ООО
«АТМОСФЕРА»), филиал **«На Белы Куна»** (id 1024, city 13), 2 позиции — обе
`is_active=true, is_available=true`. Meilisearch-индексация работает: документ
280 в индексе `merchants`, поиск «Пышки» находит.

Почему магазина нет на главной витрины («Популярные магазины»,
`ListPopularStoresController` → `GetPopularStoresQuery`):

1. **Главная причина:** запрос фильтрует `merchant_type = 'store'`. У мерчанта
   **`merchant_type = 'restaurant'`** → отфильтрован ВСЕГДА, остальные условия
   выполняются. Адрес/сортировка ни при чём: сортировка главной — по числу
   активных позиций (`offers_count DESC`), адрес на порядок не влияет.
2. **Филиал: `location = POINT(0 0)`** — адрес введён вручную
   (`address_line_manual`), геокодинг не выполнен. В текущем списке не
   участвует, но сломает карту, зоны доставки и любую дистанционную логику.
3. **Справочник городов захламлён: 3 записи про СПб** (`3` «Санкт-Петербург»,
   `13` «Санкт Петербург», + ещё дубль). Автосоздание городов при ручном вводе
   адреса плодит дубли → фильтры «рядом» работают непредсказуемо.
4. UX-пробел b2b: нигде не сказано, что (а) тип мерчанта определяет видимость
   на главной, (б) порядок списка = число позиций, (в) адрес вводить через
   пикер (тогда координаты ставятся сами), а не вручную.

## 2. Задачи

### 2.1. 🔶 Прод-решение владельца (сначала вопрос, потом код)

Рестораны на главной витрины: сейчас показываются только `Store`. Варианты:
отдельный раздел/таб «Рестораны» (тип остаётся), или общий список обоих типов,
или подтипы. **До решения владельца пункт не имплементить.** После решения —
фильтр/раздел на витрине (app + core API).

### 2.2. Гео филиалов: ручной адрес → геокодинг

- При ручном вводе адреса (manual-режим BranchResource) геокодировать
  `address_line` через Яндекс-геокодер (`YANDEX_GEOCODER_API_KEY` уже на
  staging) и заполнять `location`/`city_id`; не получать `POINT(0 0)`.
- Валидация формы: координаты обязательны; (0,0) — невалидное значение.
- Миграция-датафикс: все филиалы с `location = POINT(0 0)` геокодировать по
  `address_line` (отчёт: сколько исправлено, сколько не удалось → список
  админу).

### 2.3. Города: дедупликация и защита

- Датафикс: слить дубли («Санкт Петербург»/«Санкт-Петербург»/др.) в каноничную
  запись, перепривязать `city_id` филиалов и профилей пользователей.
- Защита при создании: нормализация имени (ё/дефисы/регистр) + поиск
  существующего города перед INSERT.

### 2.4. Подсказки в b2b (мелочь, важная)

- У поля типа мерчанта: подпись, где витрина показывает этот тип.
- На форме филиала: «вводи адрес через подсказки — координаты подставятся
  сами; от адреса не зависит порядок в списке, от числа товаров — да».

## 3. Быстрый анблок владельца (без кода, до выполнения SZ-004)

В b2b в карточке мерчанта сменить тип `restaurant` → `store` — магазин
появится в «Популярных магазинах» (фильтр города пройден, 2 позиции активны).
Вернуть `restaurant` можно после решения 🔶 2.1.

## 6. Отчёт исполнителя (Super Z, 2026-09-09)

### 6.1. Что сделано

**§2.2 Гео филиалов** — `lovii-b2b` (4c2ed0a → b1edbea, CI 🟢):
- форвард-геокодинг адреса: `DadataClient::geocodeAddress` (основной, `/suggest/address`)
  + `YandexGeocoderClient::geocodeAddress` (фолбэк); новый сервис `ManualAddressGeocoder`;
- общий concern `BranchResource/Concerns/ResolvesBranchGeo` для create/edit:
  manual-режим с пустыми/нулевыми координатами геокодирует `address_line` и
  заполняет координаты + `city_id` (через `AddressResolver::resolveCity`);
  в обоих режимах (0,0) запрещён — «координаты обязательны»; неразрешимый адрес
  блокирует сохранение. `POINT(0 0)` больше не возникает;
- датафикс существующих `POINT(0 0)` — миграция в core (ниже).

**§2.3 Города** — `lovii-core` (31c943f → b8b2a59, CI):
- `CityNameNormalizer` (display-имя + ключ сравнения; ё/дефисы/регистр/«г.»);
  одинаковые правила в b2b и core;
- миграция `2026_09_10_000001_deduplicate_cities_datafix`: слияние дублей по
  нормализованному ключу; канон = максимум связей (merchant_branches,
  user_addresses, carts), тай-брейк — дефисная орфография, затем старейший;
  перепривязка + удаление; отчёт `cities_dedup_migration_report` в логе;
- миграция `2026_09_10_000002_geocode_zero_location_branches_datafix`: филиалы
  с `location = POINT(0 0)` геокодируются по `address_line` (GeocoderContract),
  city резолвится нормализованно; неразрешимые остаются + отчёт админу
  `branch_zero_location_geocode_report`;
- защита в `KuperReconciler::resolveCity` — нормализованный find-or-create
  с ленивым кешем (первая строка на ключ выигрывает);
- в b2b `AddressResolver::findExisting` добавлен нормализованный поиск в
  пределах страны — «Санкт Петербург»/«санкт-петербург» переиспользуют запись.
