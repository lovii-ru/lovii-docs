## Симптомы (приёмка владельца 22.09)

1. Авторизация с новым номером — работает.
2. Кабинет представителя: взять промокод «для вставки или для ссылки» не
   выходит — на экране ошибка.
3. Промокод представителя введён по памяти в блоке счёта → привязка
   сработала, появилась кнопка оплаты подписки (путь SZ-057 рабочий).
4. Витрина → корзина → оплата: не прошла — «там стоит ссылка на локал хост».
5. Подозрение владельца: настройки локального стенда на staging не заменились
   на стейджинговые после последних мержей.

## Диагноз (проверено по коду)

### Баг A — оплата ведёт на localhost

- App просто открывает `payment.payment_url` из ответа API:
  `CreateOrderSuccess.vue:37–40` и `ProfileOrder.vue:88–91`
  (`openPaymentUrl`) — localhost приходит из ядра.
- Ядро строит Init по системе каналов: `config/payments.php:124–156` —
  каналы `local-mock`/`staging-mock` по умолчанию смотрят на
  `http://tbank-mock:3100/v2` (docker-имя, из браузера владельца
  недоступно); канал `bank-test` захардкожен на
  `https://rest-api-test.tinkoff.ru/v2` сознательно — env-подмена исключена.
  Активный канал: env `PAYMENTS_CHANNEL` ИЛИ запись `tbank_channel` в БД
  `payment_settings` (консоль `/api/v1/payments/console`).
- Мок возвращает `PaymentURL = http://localhost:3100/payment/{id}`:
  `tbank-mock/server.js:28` (`MOCK_PUBLIC_BASE_URL`), `:301`, `:311`.
- Альтернативный кандидат того же симптома: fake-режим —
  `PAYMENTS_FAKE=true` + `PAYMENTS_FAKE_PAYMENT_URL` в `.env` staging
  (дефолт публичный `https://app-staging.lovii.ru/payment/fake`,
  `config/payments.php:62`) — проверить, не подменялся ли при подъёме
  локального стенда.
- Гипотеза владельца согласуется с хронологией: волна 20–21.09 подключала
  tbank-mock и верификацию МСП (as-is, дополнение 22.09); CI-деплои не трогают
  серверный `.env` и БД — локально-стендовые значения пережили мержи.

### Баг B — кабинет представителя: «ошибка сети» вместо честного состояния

- Гейт: `EnsureRepresentative.php:24` — 403 «Представительские инструменты
  недоступны», если нет ни своего выпущенного кода, ни привязанного
  промокода (`User.php:142–146`: `isRepresentative()` = activePromoCode()
  ИЛИ hasBoundPromoCode()).
- App: `RepresentativeProfile.vue:43–46` — любая ошибка API показывается как
  «Профиль недоступен — проблема с сетью» → владелец видит «ошибку», хотя
  сервер честно ответил 403 «ты пока не представитель».
- После привязки промокода (шаг 3 симптомов) `isRepresentative() = true` —
  кабинет должен открыться; в приёмке до этого не дошло.
- Канон G6 (решение владельца 19.09, карточка SZ-061): привязанный промокод =
  доступ к реп/МСП кабинетам с честными пустыми состояниями — это Ф3 и здесь
  НЕ делается; эта карточка чинит только честность сообщения об отказе.

## Что сделать

### A. Платёжный канал staging (P0)

1. Сверить фактическое состояние staging-сервера и отчитаться «было/стало» по
   каждому ключу: `payment_settings.tbank_channel` (tinker), env
   `PAYMENTS_CHANNEL`, `PAYMENTS_FAKE`, `PAYMENTS_FAKE_PAYMENT_URL`,
   `TBANK_API_URL`, `TBANK_SUCCESS_URL`, `TBANK_FAIL_URL`,
   `TBANK_NOTIFICATION_URL` на `/opt/lovii-core-staging`.
2. Вернуть staging в приёмочный режим: канал `bank-test` (тестовый контур
   Т-Банка) или очистка `tbank_channel` (legacy env-путь `payments.tbank.*`).
   Зависимость: тестовый контур требует белый список IP staging-сервера
   (acq_help@tbank.ru) — если его нет, допустим временный мок-канал, но тогда
   `MOCK_PUBLIC_BASE_URL` обязан указывать на доступный извне адрес, и это
   решение фиксируется в отчёте.
3. Защита от повтора (минимум): при Init через мок-канал — предупреждение в
   ответе консоли каналов и в логе, что `PaymentURL` локальный и приёмка из
   браузера невозможна. Более строгий гейт — на усмотрение исполнителя.
4. Контрольный прогон: заказ через витрину staging → Init → оплата в
   тестовом контуре → SuccessURL возвращает на staging → платеж CONFIRMED →
   кэшбек/сплит появились (связка SZ-045/SZ-043 живая).

### B. Честные состояния кабинета представителя (P1)

1. App: различать 403/404 от сетевых сбоев в `RepresentativeProfile.vue`
   (и на соседних ролевых экранах с тем же паттерном catch): 403 → честный
   текст «представительские инструменты появятся после привязки промокода»,
   сеть → текущее сообщение.
2. Проверить оба сценария на staging: (а) новый пользователь без промокода —
   честное состояние, а не «проблема с сетью»; (б) пользователь с привязанным
   промокодом — кабинет открывается, код/ссылка/QR работают (ссылка строится
   от текущего origin: `referral.ts:74–81`).
3. Core: ответ `EnsureRepresentative` должен нести различимый код ошибки
   (access_denied), чтобы app отличал отказ гейта от сетевого сбоя; текст
   сообщения можно уточнить.
