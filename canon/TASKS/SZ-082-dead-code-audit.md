## Анти-ложные-срабатывания (обязательные проверки перед вердиктом)

- Динамические вызовы: строковые имена классов/событий, `config()`,
  `resolve()`, `->route()`, event-шина, Blade-@include переменные.
- artisan-команды, вызываемые из cron/schedule/деплой-скриптов/доков.
- Код, нужный Фазе B других задач (T-020 Фаза В «TxRow/feed.ts» — слить,
  а не удалять; не помечать как мёртвый).
- Публичный API-контур: эндпоинты/ресурсы, которые потребляет клиент —
  сверять с `lovii-app` API-слоем, а не только с grep по core.
- Миграции — исторический контракт БД: миграции не удаляются никогда.

## Ограничения и правила

1. **Фаза A — read-only.** Ни одного удаления/переименования.
2. Working-копии: свежий `git fetch` каждой ветки `staging` (не локальные
   рабочие деревья агентов — там незакоммиченное).
3. ⚠️ Параллельная дизайн-сессия работает в `lovii-app` (ветки
   `audit-fixes-wave2`, SZ-080) — её файлы не считать мёртвыми; выводить
   зоны её работы в отдельный раздел «в работе, не аудитить».
4. Способ поиска — на усмотрение исполнителя (knip/depcheck для app,
   инвертированный grep + phpstan-уровни для core); находку обязан
   подтверждать минимум двумя независимыми проверками.
5. Инструментальные сборщики бандла (vite) — источник истины по JS-дереву:
   сравнить manifest с реальными импортами.

## Что НЕ делать

- Не удалять ничего (Фаза A).
- Не трогать `vendor/`, `node_modules`, миграции, секреты.
- Не делать «улучшений по ходу» — найденное, но живое (дубли, неоптимальности)
  фиксировать отдельным разделом «попутные наблюдения», без правок.
