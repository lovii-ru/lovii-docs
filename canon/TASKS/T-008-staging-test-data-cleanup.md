## Контекст

На staging-БД накопился тестовый мусор, который мешает приёмкам, выгрузкам
и контурным сверкам:

1. **Мусорные гео-адреса** — записи в `user_addresses` без названия
   (`label` NULL/пустой) или с `house = '-'`. Это след бага адресного ввода,
   исправленного в SZ-046 (app `0da6a82`, 2026-09-09): дом проставлялся
   дефисом до фикса, label мог не заполняться.
2. **Тестовый пользователь** `users.id = 57`, телефон `+79000000001` —
   ручные прогоны чекаута/заказов.
3. **Тестовые заказы** `orders.id = 147, 148` этого пользователя.

Пункт 1 финального гайда SZ-045 (SQL-аудит трассируемости по staging-БД)
тоже выигрывает от чистой базы. Доступ к staging-БД из документационной
песочницы Super Z невозможен (нет psql/портов, `DB_HOST` — docker-имя),
поэтому исполнение передаётся zcode. Если доступа нет и у zcode — запросить
у владельца (psql на staging-хосте либо `docker compose exec <db> psql`).

## Что сделать

Порядок жёсткий: блоки скрипта выполняются по номерам 0 → 4, пропуски и
перестановки запрещены.

### Шаг 0. Пре-флайт (блок 0 скрипта, read-only)

Выполнить блок 0 целиком, ничего не менять, зафиксировать результаты — они
понадобятся для пост-проверки: юзер 57, его связи (orders/wallets/
user_addresses), заказы 147/148 с числом проводок по каждому, список
мусорных адресов, контрольные суммы `ledger_entries` и
`wallet_transactions`.

### Шаг 0.5. ⚠️ Сверка актуальности — главное правило задачи

Снимок в разделе «Контекст» снят 2026-09-13 по коду и косвенным признакам;
staging живой — с момента аудита записи могли измениться, исчезнуть или
прибавиться. **Сначала проверь актуальность, потом приступай** (требование
владельца). Перед любым изменяющим блоком сверить блок 0 с ожиданиями:

| Ожидание (снимок 2026-09-13) | Действие при расхождении |
|---|---|
| `users.id = 57` существует, `phone = +79000000001` | СТОП |
| заказы `147, 148` существуют, `user_id = 57` | СТОП |
| мусорные адреса (0.4) есть, состав похож на «Контекст» | СТОП, если их нет вовсе или состав резко иной |
| заказы 147/148 не находятся в живом исполнении (сборка/доставка) | СТОП |

**СТОП означает:** изменяющие блоки 1–3 не выполнять; расхождение
задокументировать в «Отчёте исполнителя», карточку/скрипт актуализировать
отдельным коммитом, доложить владельцу и дождаться подтверждения.
Импровизация «на глаз» запрещена.

Допустимое расхождение одно: **мусора стало больше того же вида** (критерии
скрипта ищут по признакам — пустой `label`/`house = '-'`, а не только по id,
так что новые записи того же рода просто попадут в чистку). Если сомнение —
это СТОП.

### Шаги 1–3. Изменяющие блоки скрипта

- Блок 1 — пометка юзера 57: `name = '[TEST] …'`, без удаления.
- Блок 2 — пометка заказов 147/148 через существующую колонку
  `cancel_reason` (миграция `2026_09_13_100001`), без удаления.
- Блок 3 — удаление мусорных адресов: сухой прогон 3.1 → `DELETE` → сверка
  счётчика с 0.4 → `COMMIT`; при расхождении — `ROLLBACK` и разбор.

### Шаг 4. Пост-проверка (блок 4)

Сверить с записями шага 0: суммы `ledger_entries` / `wallet_transactions`
не изменились ни на единицу; мусорных адресов — 0; юзер помечен; заказы
помечены. Итог сверки — в отчёт.

## Что не делать

- Не трогать **никакие другие** строки бухгалтерии: `ledger_entries` и
  `wallet_transactions` — append-only (`FINANCIAL_CONTOUR` §2.3),
  `DELETE`/`UPDATE` запрещены даже для мусорных заказов; их суммы —
  инвариант сверок §5.4 / SZ-040.
- Не удалять юзера 57 и заказы 147/148: FK `orders.user_id` → `users`,
  `wallet_transactions.order_id` → `orders` (без cascade); история нужна
  контурным сверкам.
- Не менять схему: миграций в задаче нет; никаких новых колонок/флагов —
  пометки только через существующие `users.name` и `orders.cancel_reason`.
- Не выполнять на проде; прод-креды не запрашивать и не копировать. Только
  staging.
- Не трогать код репозиториев и зону SZ-045 (денежное ядро core): у задачи
  нет точек соприкосновения с SZ-045 по файлам.
- Если мусорных адресов в 0.4 вдруг сотни — не удалять пачкой молча: СТОП,
  сверка с владельцем (возможен дефект критерия).
