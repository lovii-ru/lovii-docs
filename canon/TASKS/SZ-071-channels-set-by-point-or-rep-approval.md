## Контекст (проверено 2026-09-21)

- **Точка материализуется в момент ПОДАЧИ заявки**, а не при апруве:
  `CreatePartnerApplicationAction::materializeBranchDraft` создаёт `merchant_branches` сразу
  с `pickup_available = false`, `delivery_available = false`, `working_hours = []`,
  `status = active`, `timezone` = пояс города (после `SZ-067`).
- **Апрув представителя параметров не принимает вообще**: `POST /api/v1/representative/approvals/{application}/verify`
  → `ApprovePartnerApplicationAction` только переводит заявку в `invoice_issued` и ставит
  `rep_approved_at` (и запускает выпуск бизнес-карты). UI репа —
  `lovii-app/src/modules/roles-module/representative/RepresentativeApprovals.vue`.
- **Каналы продаж точки** (`pickup_available` / `delivery_available`) правятся сегодня только
  в b2b (`lovii-b2b/app/Filament/Resources/BranchResource.php`, секция «Операции»); в кабинете
  МСП приложения их нет; чекаут блокирует канал — `CheckoutBuilder.php:82–87`
  (`delivery_not_supported`).
- Следствие, из-за которого вопрос и возник: заявка → апрув → точка на витрине → **заказать
  нельзя, пока кто-то не откроет b2b**. Точка физически не может довести себя до рабочего
  состояния из приложения.

## Что сделать (решения принимает исполнитель, обоснование — в отчёте)

**Канон владельца (21.09, 02:49):** вопрос решается **системно и автоматически**; каналы
настраивает **в первую очередь сам владелец точки**, **в том числе из приложения**. Представитель
при апруве — вспомогательный путь (может предзаполнить), а не обязательная инстанция: сегодня
именно из-за «настроить можно только в b2b» точка застревает в состоянии «заказать нельзя».

1. **Владелец точки управляет каналами сам, включая приложение.** Базовое управление
   (самовывоз / доставка) — в кабинете МСП приложения (объём и оформление — `SZ-068`), в b2b —
   как есть. Право — `branch.update` по действующей матрице ролей (`SZ-038`/`SZ-047`); отдельно
   решить, доступно ли это администратору/сотруднику точки или только владельцу.
2. **Автоматика вместо ручного администрирования.** Точка должна приходить в рабочее состояние
   сама, без похода в b2b: система выводит готовность каналов из фактического состояния точки
   (адрес и координаты, график работы, зона доставки, минимум заказа) и не оставляет её на
   витрине в состоянии «заказать нельзя» без объяснения. Что именно решается автоматически
   (дефолты, авто-включение по заполненности, подсказки в чек-листе запуска
   `lovii-app/src/modules/roles-module/msp/readiness.ts`) — решаешь и обосновываешь; главное —
   владелец точки не должен зависеть от чужого кабинета.
3. **Представитель при апруве (вспомогательно).** Апрув сегодня вообще не принимает параметров
   (`POST /api/v1/representative/approvals/{application}/verify`), а точка материализуется при
   подаче заявки с выключенными каналами. Представитель может предзаполнить каналы и ближайшие
   к ним параметры точки (объём реши и обоснуй, апрув не должен превращаться в длинную форму),
   но этот путь не обязателен: даже без него точка настраивается сама.
4. **Разграничить владение настройкой.** Значения, заданные представителем при апруве, не должны
   молча затирать то, что владелец точки потом изменил сам (и наоборот). Правило разрешения
   конфликта описать явно и покрыть тестом; по умолчанию исходить из того, что **после запуска
   настройка принадлежит точке**.
5. **Тесты и живой прогон**: заявка → апрув (каналы предзаполнены или нет) → точка приходит в
   рабочее состояние и принимает заказ; владелец точки меняет каналы из приложения; точка без
   заполненных базовых данных честно объясняет покупателю, почему заказ невозможен.

## Что не делать

- Не давать представителю править точку ПОСЛЕ апрува: настройка после запуска принадлежит точке
  (если понадобится обратное — отдельное решение владельца).
- Не включать каналы «по умолчанию всем» без обоснования: включённый самовывоз на точке без
  адреса/графика — такое же враньё, как и закрытая круглосуточная точка.
- Не ломать контракт апрува для уже работающих клиентов: обязательные поля не добавлять к
  существующему вызову без версионирования/совместимости.
- Не пушить в `staging`/`master` без «го» владельца, не трогать прод-данные.

## Приёмка

- Владелец точки включает/выключает каналы **из приложения** (и в b2b); заказ проходит по
  указанным каналам — без обязательного похода в чужой кабинет.
- Точка приходит в рабочее состояние автоматически (или честно объясняет, чего не хватает);
  поведение при конфликте «представитель предзаполнил → владелец изменил» описано и
  протестировано.
- Покупатель не видит точку, на которой нельзя заказать, без честного объяснения.
- Тесты core/app зелёные, живой прогон цепочки выполнен, гейты (`pint`/`rector`/`phpstan`,
  `yarn test`) пройдены.
