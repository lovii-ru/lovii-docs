## Контекст (проверено 2026-09-21)

- **Точка материализуется в момент ПОДАЧИ заявки**, а не при апруве:
  `CreatePartnerApplicationAction::materializeBranchDraft` создаёт `merchant_branches` сразу
  с `pickup_available = false`, `delivery_available = false`, `working_hours = []`,
  `status = active`, `timezone` = пояс города (после `SZ-067`).
- **Апрув представителя параметров не принимает вообще**: `POST /api/v1/representative/approvals/{application}/verify`
  → `ApprovePartnerApplicationAction` только переводит заявку в `invoice_issued` и ставит
  `rep_approved_at` (и запускает выпуск бизнес-карты). UI репа —
  `lovii-app/src/modules/roles-module/representative/RepresentativeApprovals.vue`.
- **Каналы продаж точки** (`pickup_available` / `delivery_available`) правятся сегодня только
  в b2b (`lovii-b2b/app/Filament/Resources/BranchResource.php`, секция «Операции»); в кабинете
  МСП приложения их нет; чекаут блокирует канал — `CheckoutBuilder.php:82–87`
  (`delivery_not_supported`).
- Следствие, из-за которого вопрос и возник: заявка → апрув → точка на витрине → **заказать
  нельзя, пока кто-то не откроет b2b**. Точка физически не может довести себя до рабочего
  состояния из приложения.

## Что сделать (решения принимает исполнитель, обоснование — в отчёте)

1. **Точка настраивает свои каналы сама.** Базовое управление (самовывоз / доставка) — в кабинете
   МСП приложения, в объёме и оформлении `SZ-068`; в b2b — как есть. Право — `branch.update`
   по действующей матрице ролей точки (`SZ-038`/`SZ-047`); отдельно решить, доступно ли это
   администратору/сотруднику точки или только владельцу.
2. **Представитель задаёт каналы в момент апрува заявки.** Апрув перестаёт быть «пустой» кнопкой:
   представитель физически договаривается с точкой, поэтому может указать, как точка продаёт
   (самовывоз/доставка), а при необходимости — ближайшие к каналам параметры (что именно —
   реши и обоснуй; не превращай апрув в длинную форму). Технически: параметры апрува в
   контракте эндпоинта + применение к уже созданной точке (`branch_id` есть на заявке).
3. **Разграничить владение настройкой.** Значения, заданные представителем при апруве, не должны
   молча затирать то, что точка потом изменила сама (и наоборот). Правило разрешения конфликта
   («кто последний», или «реп только при апруве, дальше только точка») описать явно и покрыть
   тестом.
4. **Честность состояния витрины.** Точка не должна висеть на витрине в состоянии «заказать
   нельзя» без объяснения покупателю. Варианты (дефолты включены / точка обязана подтвердить /
   витрина честно сообщает) — выбери и обоснуй; учти существующий чек-лист запуска
   (`lovii-app/src/modules/roles-module/msp/readiness.ts`) и `PRODUCT_QUALITY_BAR.md`.
5. **Тесты и живой прогон**: заявка → апрув представителя с указанными каналами → точка на
   витрине принимает заказ по этим каналам; точка сама меняет каналы из кабинета; конфликт
   «реп задал → точка изменила» ведёт себя по принятому правилу.

## Что не делать

- Не давать представителю править точку ПОСЛЕ апрува: настройка после запуска принадлежит точке
  (если понадобится обратное — отдельное решение владельца).
- Не включать каналы «по умолчанию всем» без обоснования: включённый самовывоз на точке без
  адреса/графика — такое же враньё, как и закрытая круглосуточная точка.
- Не ломать контракт апрува для уже работающих клиентов: обязательные поля не добавлять к
  существующему вызову без версионирования/совместимости.
- Не пушить в `staging`/`master` без «го» владельца, не трогать прод-данные.

## Приёмка

- Представитель при апруве указывает каналы — точка появляется на витрине в рабочем состоянии
  (заказ проходит по указанным каналам), без обязательного похода в b2b.
- Точка сама включает/выключает каналы из своего кабинета; поведение при конфликте с апрувом
  описано и протестировано.
- Покупатель не видит точку, на которой нельзя заказать, без честного объяснения.
- Тесты core/app зелёные, живой прогон цепочки выполнен, гейты (`pint`/`rector`/`phpstan`,
  `yarn test`) пройдены.
