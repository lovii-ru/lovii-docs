## Контекст — зачем это Lovii

- У платформы уже есть три **живых** канала с аудиторией и инфраструктурой
  (см. FEATURES §2, треки O/V BACKLOG):
  - **Telegram** — боты otp/orders/support (long-poll воркеры, исходящий через
    прокси 172.17.0.1:3128);
  - **MAX** — бот «Лови» @id7842223709_bot (Bot API, адресация `user_id`,
    OTP-доставка на staging работает);
  - **VK** — сообщество @loviiru (Callback API, сообщения сообщества, посты).
- Аккаунт покупателя Lovii = **номер телефона** (OTP-вход); magic link в бот
  уже сделан (SZ-008). Клиент — PWA `lovii-app` (Vue 3 + TS + Vite + Pinia),
  ходит в core API. Оплата в платформе не подключена (финконтур —
  canon/FINANCIAL_CONTOUR.md, эквайринг Т-Банк готов, верификация через
  спец-счёт).
- **Рабочая гипотеза владельца**: у каждого жителя РФ стоит хотя бы одно из
  этих трёх приложений → мини-апп в хост-мессенджере = витрина Lovii без
  установки чего-либо и без борьбы за инсталлы. Ресёрч должен подтвердить или
  опровергнуть гипотезу фактами и оценить цену входа на каждую платформу.

## Что исследовать — для КАЖДОЙ платформы (VK Mini Apps, MAX Mini Apps, Telegram Mini Apps)

Ответы фиксируются с источниками (URL) и датой доступа; приоритет — официальная
документация разработчика (dev.vk.com, dev.max.ru, core.telegram.org +
core.telegram.org/bots/webapps); сторонние обзоры — с явной пометкой. Доки MAX
молодые и меняются — сомнительное проверяй дважды.

1. **Что это технологически**: формат (web-приложение в webview хоста?), где
   запускается (iOS/Android/десктоп/web-версии хост-приложения), SDK и
   фреймворки (официальные и сообщества: @telegram-apps/sdk, VKUI/@vkontakte/vk-bridge,
   аналоги MAX), совместимость с Vue 3 — можно ли переиспользовать код `lovii-app`.
2. **Как создать и опубликовать**: портал разработчика, кто может создавать
   (физлицо/ИП/юрлицо — что требуется Lovii/АКСИОМЕ), платная ли регистрация
   и размещение, модерация (сроки, причины отказов, ограничения контента),
   каталог/магазин мини-аппов, требования к хостингу (HTTPS, RU-хостинг?).
3. **Как пользователи попадают в мини-апп**: каталог, поиск, прямые ссылки,
   QR, кнопка в боте (menu button / inline), карточка сообщества VK,
   рекламные механики платформы, вирусные механики (шеринг, стори, реферальные
   launch-параметры `start_param`/`startapp`).
4. **Авторизация** (самое важное — детально):
   - что хост передаёт при запуске: подписанные launch-параметры / `initData` /
     аналогично в MAX — какие поля (id, имя, аватар, язык, …), что подписано и
     каким ключом, **точный алгоритм серверной валидации** (для Telegram —
     HMAC-SHA256 по bot token; для VK — sign по app_secret; MAX — по докам),
     чтобы zcode мог факт-чек по криптографии;
   - **автоматическая/тихая авторизация**: что сервер «знает» о пользователе
     при первом открытии без единого клика; можно ли автоматически связать
     личность мини-аппа с Lovii-аккаунтом;
   - **гипотеза тихой связки через бота** (проверить по докам каждого хоста):
     Lovii уже знает соответствие «user бота ↔ телефон» из OTP-диалогов
     (Telegram chat_id, MAX user_id, VK peer_id) → при открытии мини-аппа тем
     же ботом можно отождествить пользователя по его user_id БЕЗ повторного
     OTP. Верно ли понимание модели идентичности (один ли id у бота и
     мини-аппа на платформе), есть ли грабли (мультиаккаунты, приватность);
   - **доступ к номеру телефона** явным способом: запрос контакта
     (`VKWebAppGetPhoneNumber`? request_contact в Telegram? аналог в MAX),
     согласия и ограничения;
   - классический логин-виджет/OAuth, если есть (Telegram Login Widget,
     VK ID) и чем он хуже/лучше launch-параметров.
5. **Стандартные/базовые возможности** платформы: тема (светлая/тёмная),
   viewport/fullscreen, клиентское хранилище, буфер обмена, геолокация,
   сканер QR, контакты, haptics, deep links, закрытие/навигация, попапы,
   orientation, события жизненного цикла.
6. **Уникальные возможности** платформы (то, чего нет у конкурентов): у VK —
   стори/статусы, виджеты сообществ, VK Pay-инфраструктура; у Telegram —
   Stars, inline-режим, Web App в inline-кнопках, TON-экосистема — что
   реально доступно из РФ; у MAX — что есть по докам (молодая платформа:
   зафиксировать, что реально, а что в роадмапе/анонсах).
7. **Уведомления после визита** (критично для статусов заказов): может ли
   мини-апп/бот написать пользователю после закрытия (сообщение бота, push
   через хост, токены пуша)? Ограничения антиспама? Как это состыкуется с
   уже живыми OTP-ботами Lovii.
8. **Платежи**: механизмы каждой платформы (VK Pay/ЮKassa, Telegram Stars и
   Payments 2.0 — что работает в РФ в 2026, MAX — есть ли платежи) и их
   совместимость с финконтуром Lovii (спец-счёт, Т-Банк, верификация
   партнёров). Только факты о механиках; продуктовое решение — 🔶 владельцу.
9. **Ограничения и реалии РФ**: модерация коммерции, 152-ФЗ/ПДн (согласия,
   где хранится), требования к оферте, санкционные ограничения SDK/CDN,
   лимиты и квоты, аналитика (VK Metrika, TG Analytics/статистика ботов,
   MAX — ?).
10. **Симбиоз с существующим**: можно ли мини-апп на каждом хосте прикрепить к
    УЖЕ существующему боту/сообществу Lovii (Telegram: bot → menu button;
    VK: приложение + сообщество @loviiru; MAX: бот → ?), или нужен новый
    объект. Что из этого требует действий владельца во внешних UI.

- **НЕ создавать** никаких ботов, сообществ и мини-аппов во внешних UI —
  кнопки во внешних интерфейсах жмёт только владелец. Всё, что требует
  создания объектов, — в список 🔶 владельцу.
- **НЕ писать код** в lovii-core/lovii-app/b2b/admin и не менять инфраструктуру;
  никакие env/серверные действия.
- **НЕ класть** в канон секреты и токены.
- Не выдавать непроверенное за факт: где доки расходятся с реальностью или
  молчат — пометка «не подтверждено», а не догадка.

### Приёмка zcode (2026-09-10) — «Достаточно» (по исходному скоупу)

Факт-чек (а)–(д) из плана приёмки:

- **(б) Криптография** — подтверждено по первоисточникам:
  - Telegram §1.4 — дословно по core.telegram.org/bots/webapps: data-check-string
    (сортировка, `\n` 0x0A, `key=<value>`), `secret_key = HMAC_SHA256(bot_token,
    "WebAppData")`, hex-сравнение, рекомендация свежести `auth_date`, раздел
    third-party (Ed25519, base64url-подпись) существует;
  - MAX §3.4 — дословно по dev.max.ru/docs/webapps/validation:
    `HMAC-SHA256('WebAppData', BOT_TOKEN)`, сортировка a→z, `launch_params`
    через `\n`, hex-сравнение; состав `WebAppData` (user/chat/ip/query_id/
    auth_date/hash + WebAppPlatform/WebAppVersion) подтверждён;
  - VK §2.4 — первоисточник dev.vk.com JS-SPA (fetch-недоступен с этой машины),
    схема подтверждена вторично (vksdk `vkapps.ParamsVerify`:
    HMAC-SHA256 от client_secret). ⚠️ Уточнение для спеки M-2: у VK `sign`
    в **base64**, у TG/MAX hash в **hex** — валидатору отдельные приведения.
- **(а) URL §8** — core.telegram.org и dev.max.ru живы и ведут на заявленное
  (выборочно); сетевой таймаут core.telegram.org с машины zcode — через
  web-reader, содержимое совпадает.
- **(г) Матрица §4** — пустых ячеек нет; «не подтверждено» всегда с причиной. ✓
- **(д)** Регистрация дока (REGISTRY §2.2, REFERENCE §3.9.14), трек M, BACKLOG
