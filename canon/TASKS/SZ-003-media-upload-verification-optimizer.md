## 1. Бага: «не более 5120 КБ» на файле 680 КБ

**Симптом (владелец):** добавление картинки к категории (b2b, Category →
`image_url`) даёт ошибку «Размер файла изображение должен быть не более
5120 КБ» при файле 680 КБ; воспроизводится «независимо от размера».

**Что известно из анализа zcode:**

- Компонент: `app/Filament/Forms/Components/SquareImageUpload.php` —
  `->maxSize(5 * 1024)` (5120 КБ — текст ошибки его) + `->imageEditor()` +
  `->imageCropAspectRatio('1:1')`. Используется в Category (image_url),
  Merchant (logo/mini_logo), Position.
- Сервер НЕ лимитирует: PHP `upload_max_filesize`/`post_max_size` = 64M,
  nginx `client_max_body_size` = 64M (b2b-staging, проверено 2026-09-09).
- **Серверный нормализатор уже есть**: `App\Domain\Catalog\Services\ImageNormalizer`
  (Imagick; HEIC→JPEG через ffmpeg) — ресайз до 2048px, JPEG q85; вызывается из
  `PublicDiskMediaStorage::store()`.

**Основная гипотеза:** встроенный imageEditor Filament при кропе 1:1
пересобирает картинку на клиенте (canvas) и **перезаливает новый файл**;
экспорт canvas — как правило **PNG без сжатия**, из любого исходника (хоть
680 КБ JPEG) получается файл > 5 МБ. Повторная валидация `maxSize(5120)`
отсекает его **до того, как файл дойдёт до серверного нормализатора**, который
как раз умел бы его уменьшить. Отсюда «независимо от размера».

**Первое дело — подтвердить, не лечить вслепую:** повторить сценарий
(фото ~700 КБ → кроп в редакторе), в devtools замерить размер/формат
второй загрузки (edited variant). Если гипотеза не подтвердится — искать
далее (например, валидация `maxSize` на Livewire-временном файле с иным
размером, mime-отсечение `ACCEPTED_IMAGE_MIME_TYPES`).

## 2. Фикс (минимальный)

Сделать так, чтобы любой реалистичный исходник доходил до серверного
нормализатора. Варианты (выбери по результату проверки, можно комбинировать):

- поднять/убрать `maxSize` на `SquareImageUpload` (нормализатор всё равно
  жмёт до 2048px/q85 — лимит на входе перестаёт быть смысловым);
- включить клиентский ресайз FilePond (`imageResizeMode('cover')` +
  `imageResizeTargetWidth/Height` ≈ 2048) — файл ужимается **до** отправки;
- если редактор умеет — форсировать экспорт кропа в JPEG вместо PNG.

**Критерий баги:** фото ~700 КБ загружается в категорию/позицию/логотип с
телефона и десктопа; кроп 1:1 работает; в хранилище лежит нормализованный
файл.

## 3. Фича: фотооптимизатор (просьба владельца)

Цель владельца: «ограничение на вес файла загружаемого владельцем витрины не
имеет значения — мы сами готовим фото нужного качества для отгрузки
посетителям».

- Серверная основа **уже есть** — `ImageNormalizer`. Дополнить:
  1. тяжёлые PNG-фото конвертировать в JPEG/WebP (сейчас формат входа
     сохраняется как есть; PNG-скриншоты с прозрачностью — оставить PNG);
  2. целевой ориентир: фото 2048px после нормализации ≤ ~300–500 КБ;
  3. логировать исходный/итоговый вес (наблюдаемость экономии).
- Клиентский ресайз (см. §2) — первая ступень сжатия, экономит трафик.
- Прогнать через нормализатор ВСЕ точки входа картинок: SquareImageUpload
  (категории/логотипы) и Position (media) — проверить, что Position использует
  тот же `MediaStorage::store()`.

## 4. Ограничения и NB

- Политику orphan-файлов `SquareImageUpload::context()` (намеренно без

- Мультитенантность: компоненты шарятся между мерчантами — каталог

## 6. Отчёт о реализации (Super Z, 2026-09-09, `f51e233` + `ed0babe`)

**§1 — гипотеза подтверждена кодом Filament v5.5.2 (дистрибутив
`packages/forms/dist/components/file-upload.js`):**

- `saveEditor()` экспортирует кроп как
  `toBlob(cb, rounded ? "image/png" : editingFile.type)` **без quality** —
  PNG-исходник после кропа остаётся **lossless-PNG** и раздувается в разы
  (фото 680 КБ → PNG 4–8 МБ); JPEG — переупаковка ~q0.92;
- кроме того, `imageCropAspectRatio('1:1')` включает transform-on-add
  (`toBlob(canvas, t.type, t.quality)`) — PNG раздувается уже при добавлении
  файла, до всякого редактора;
- `maxSize(5*1024)` отсекал результат **до** `ImageNormalizer` — отсюда
  «независимо от размера». Гипотеза zcode подтверждена, доп. ветки
  (mime-отсечение) не понадобились — `resolveMime()` уже читает canvas-блобы.

**§2 — фикс (SquareImageUpload + PositionResource::media, обе точки):**

- `maxSize 5 МБ → 64 МБ` (зеркало инфраструктурного потолка nginx/PHP; реальный
  гейт веса — серверный нормализатор);
- клиентская первая ступень сжатия: `imageResizeMode('contain')` +
  `imageResizeTargetWidth/Height(2048)` + `imageResizeUpscale(false)` —
  байты ужимаются до отправки; константа 2048 — `ImageNormalizer::MAX_DIMENSION`
  (теперь public), один источник истины;
- контракт `MediaStorage`, биндинг и orphan-политика `context()` не тронуты;
  мульти-контекст (`categories`/`logos`/…) сохранён.

**§3 — фотооптимизатор (`ImageNormalizer`):**

- PNG-политика: с **любой видимой прозрачностью** (проверка
  `getImageChannelRange(ALPHA)`: равномерно-непрозрачный RGBA-канал = opaque)
  остаётся PNG; **тяжёлые** (вход > 200 КБ) **opaque**-PNG-фото конвертируются
  в JPEG, если кандидат реально меньше; лёгкие PNG (логотипы) остаются
  lossless; GIF проходит без изменений (анимация);
- quality-лестница 85/75/65 для JPEG/WebP с целью ≤ 500 КБ на фото ≤ 2048px
  (первый подходящий шаг; ниже 65 не опускаемся — иначе видимые артефакты);
- наблюдаемость: `PublicDiskMediaStorage::store()` логирует
  context/key/source_mime/source_bytes/stored_mime/stored_bytes;
- HEIC→JPEG путь без изменений, теперь тоже через лестницу.

**Тесты (Pest, +4):** тяжёлый opaque-PNG → JPEG (фикстура `plasma:fractal`,
несжимаемый шум); тяжёлый PNG с альфой → остаётся PNG (альфа сохраняется);
гладкое фото 3000×2000 → ≤ 500 КБ и ≤ 2048px; лог веса в store()
(`Log::spy`). Существующий тест «PNG → PNG» остался зелёным (сплошная заливка
= лёгкий PNG). Пинтовый нюанс учтён: байтовые счёты — `mb_strlen($x, '8bit')`
(`mb_str_functions` в pint.json; паттерн как в `SharedKeyEncrypted`).

**NB (прозрачно):**

- Анимированный GIF в Position media теперь проходит через клиентский
  ресайз → становится статичным первым кадром (в SquareImageUpload это было
  и раньше из-за кропа 1:1). Каталожные фото — не GIF-кейс; осознанный трейд-офф.
- Локально в песочнице Pest с Imagick не гоняется (нет ext-imagick; синтакс
  проверен `php -l` 8.5.8) — гейт `composer test` закрыт CI в docker-образе
  (ран 34386647095: checks 🟢, deploy-staging 🟢). Первый прогон поймал ректора
  (ClosureToArrowFunctionRector в лог-тесте) — поправлено в `ed0babe`.
- Владельцу виден новый хинт вместо «До 5 МБ на файл»: «Вес файла значения не
  имеет — фото автоматически сжимается на сервере».
