## 0. Резюме для владельца (2 минуты)

- Гипотеза владельца («у каждого жителя РФ стоит хотя бы одно из трёх хост-приложений,
  мини-апп = витрина Lovii без установки») **подтверждается устройством платформ**:
  все три хоста отдают мини-аппу подписанную идентичность пользователя при запуске,
  а Lovii **уже хранит** связь «user бота ↔ телефон» для всех трёх платформ
  (`max_bot_links` со scope: Telegram-OTP, MAX-OTP, VK-сообщества). Тихая связка
  «открыл мини-апп → уже залогинен» технически возможна на всех трёх хостах
  **без повторного OTP** (§1.4, §2.4, §3.4).
- Цена входа различается радикально. **MAX**: мини-апп прикрепляется к СУЩЕСТВУЮЩЕМУ
  боту за 5 минут, нужен только лицензионный договор в business.max.ru (§3.2).
  **Telegram**: публикация без модерации хоста, прикрепление к @loviiru_bot через
  BotFather (§1.2). **VK**: новый объект «приложение» в панели dev.vk.com +
  обязательная модерация (§2.2).
- Криптография запуска у Telegram и MAX **одна и та же схема** (HMAC-SHA256 с
  ключом `WebAppData` от токена бота) — один PHP-валидатор закроет оба хоста;
  у VK — HMAC-SHA256 по отсортированным `vk_*`-параметрам с защищённым ключом
  приложения (§4).
- Рекомендация: MVP-волна 1 = **MAX + Telegram** (одна кодовая база адаптера),
  волна 2 = **VK** (модерация + новый объект). Платёжные механики хостов
  Lovii не нужны — свой финконтур (Т-Банк) сохраняется без изменений (§5, §6).
- Порядок и скоуп — 🔶 решения владельца (§7); технических блокеров нет.

## 1. Telegram Mini Apps

### 1.1 Технология и совместимость с lovii-app

- Мини-апп = **веб-приложение (HTML/JS/CSS) внутри webview хост-клиента** Telegram
  (iOS/Android/десктоп/web). Запускается из чата бота или по прямой ссылке.
  Источник: core.telegram.org/bots/webapps (дата 2026-09-10).
- Официальный SDK — скрипт `telegram-web-app.js` (`window.Telegram.WebApp`);
 community-обёртки: `@telegram-apps/sdk` (сторонний). Прямой зависимости от фреймворка
  нет — **Vue 3 + Vite подходит как есть**: lovii-app переиспользуется, добавляется
  только хост-адаптер (детект initData, тема, BackButton) и точки входа.
- Тема: `colorScheme` («light»/«dark», CSS-переменная `--tg-color-scheme`) +
  `themeParams`; клиентская навигация: `BackButton`, `MainButton`/`BottomButton`,
  `SettingsButton`; fullscreen (Bot API 8.0), safe-area отдаётся приложению
  (`safeAreaInset`, `contentSafeAreaInset`). Источник: core.telegram.org/bots/webapps.

### 1.2 Как создать и опубликовать

- Создание: объект мини-аппа прикрепляется **к боту** (у Lovii есть: @loviiru_bot).
  В @BotFather: `/newapp` или настройка Menu Button (Bot API 6.0+), «Main Mini App»
  (Bot API 7.8, 2024-07-31) — превью и кнопка запуска прямо в профиле бота.
- **Модерации хоста нет**: Telegram не ревьюит мини-аппы; размещение = HTTPS-хостинг
  где угодно + ссылка в боте. Витрин в духе app store нет — «внутренние витрины и
  подборки» + поиск Telegram (вкладка мини-приложений) — сторонние обзоры:
  media.friflex.com (2026), club.dns-shop.ru (2026). Пометка: систематического
  каталога с модерацией, как у VK, у Telegram нет — попадание в подборки
  не гарантировано.
- Требования к хостингу: HTTPS (обязателен), RU-хостинг не требуется.
- Действия владельца во внешнем UI: настройка кнопки в @BotFather (5 минут).

### 1.3 Как пользователи попадают в мини-апп

- **Кнопка меню бота** (menu button) — основной путь: чат → кнопка «Открыть».
- **Main Mini App** — кнопка/превью в профиле бота (7.8+).
- **Прямая ссылка** `https://t.me/<bot>?startapp[=<param>]` — параметр попадает в
  `start_param` и `tgWebAppStartParam` (Bot API 6.7, 2023-04-21) → диплинки на
  товар/магазин/раздел: `?startapp=branch_1024`. Источник: core.telegram.org/bots/webapps.
- Inline-кнопки `web_app` в сообщениях бота; inline-режим (запрос из любого чата,
  `switchInlineQuery`); **шорткаты на домашний экран** (`addToHomeScreen`,
  `checkHomeScreenStatus`); шеринг `shareMessage`/`shareToStory` (вирусность).
- Реклама: Telegram Ads (через реселлеров, EUR-бюджеты) — вне задачи, фактор попадания.

### 1.4 Авторизация (детально — для факт-чека zcode)

- Хост передаёт `Telegram.WebApp.initData` — **query-string** парами
  `key=value`: `user` (JSON: `id, first_name, last_name, username, language_code,
  photo_url, added_to_attachment_menu, allows_write_to_pm`), `auth_date` (unix),
  `query_id`, `start_param`, `hash`, опционально `chat_type`/`chat_instance`.
- **Точный алгоритм серверной валидации** (цитата по
  core.telegram.org/bots/webapps, раздел «Validating data received via the Mini App»):
  1. `data_check_string` = все поля кроме `hash`, отсортированные по ключу,
     склеенные `\n` (0x0A), в формате `key=<value>`.
  2. `secret_key = HMAC_SHA256(bot_token, "WebAppData")`.
  3. `hex(HMAC_SHA256(data_check_string, secret_key)) == hash` → данные подлинные.
  4. Дополнительно сверять `auth_date` (свежесть) — рекомендация самой доки.
- **Third-party валидация (NEW)**: Telegram публикует Ed25519-публичный ключ;
  `signature` (base64url) проверяется **без бот-токена**, по `bot_id` — полезно,
  если валидацию делает отдельный сервис. Источник: там же, «Validating data for
  Third-Party Use».
- **Тихая авторизация**: после валидации сервер знает `user.id` без единого клика.
  Lovii хранит связь `chat_id ↔ телефон` (MaxBotLink, scope `telegram:otp`) из
  OTP-диалогов @loviiru_bot. **Один ли id у бота и мини-аппа**: да — `initData.user.id`
  это id того же Telegram-аккаунта, что и в чате с ботом (модель идентичности
  Telegram: один аккаунт = один user_id на всех поверхностях). Гипотеза тихой
  связки **подтверждается**: мини-апп на том же боте → матчинг по `user.id` →
  JWT без OTP. Грабли: (а) мультиаккаунты Telegram — привязка по chat_id остаётся
  правильной на каждый аккаунт; (б) пользователь может открыть мини-апп, **не**
  стартовавшего бота — initData всё равно придёт (запуск возможен без `/start`),
  но сообщение ботом такому пользователю не доставится — для авторизации это не
  мешает, для уведомлений — см. §1.7; (в) привязку стоит проверять на свежесть
  (если OTP-связка старше политики — запросить OTP повторно; решение за спекой).
- **Телефон**: `WebApp.requestContact()` (Bot API 6.9, 2023-09-22) — нативное
  подтверждение; контакт (с `phone_number`) приходит **сообщением боту** в чат
  (webhook), не в initData. Прямого чтения телефона из initData нет — так же, как
  мы уже делаем в OTP-боте. Источник: core.telegram.org/bots/webapps (changelog).
- **Login Widget / OAuth**: существует Telegram Login Widget (для сайтов) — для
  мини-аппа избыточен: launch-параметры дают тот же результат с меньшим трением.

### 1.5 Базовые возможности платформы

- Тема/цвета: `colorScheme`, `themeParams`, `setHeaderColor`, `setBackgroundColor`,
  `setBottomBarColor`; viewport: `expand`, `requestFullscreen`/`exitFullscreen` (8.0),
  safe-area (8.0+); кнопки: Back/Main/Bottom/Settings; haptics: `HapticFeedback`.
- Хранилища: `CloudStorage` (6.9), `DeviceStorage` и `SecureStorage` (Bot API 9.0,
  2025-04-11); биометрия: `BiometricManager` (7.2); буфер: `readTextFromClipboard`;
  QR: `showScanQrPopup` (6.4); датчики (NEW): `Accelerometer`, `DeviceOrientation`,
  `Gyroscope`; события жизненного цикла: `activated`/`deactivated`/
  `safeAreaChanged`/`fullscreenChanged`; попапы: `showPopup`/`showAlert`/`showConfirm`;
  `openLink`/`openTelegramLink`; `downloadFile`; закрытие: `close`,
  `enableClosingConfirmation`; `isVersionAtLeast` для фиче-детекта.
  Источник: core.telegram.org/bots/webapps.
- Геолокация/контакты: встроенного гео-API в WebApp нет (браузерное `navigator.geolocation`
  в webview; в iOS требует разрешения) — как у обычного сайта.

### 1.6 Уникальные возможности (чего нет у конкурентов)

- **Inline-режим**: мини-апп/бот доступны из поля ввода любого чата
  (`switchInlineQuery`) — уникальная витрина «в каждом чате».
- **Prepared messages / shareMessage**: нативный шаринг карточек в любой чат и в
  стори (Bot API 9.x) — вирусный контур заказов/рефералок.
- **Stars-экосистема**: подарки, платные рассылки (см. §1.7/§1.8), бусты каналов.
- Home-screen shortcuts поверх PWA-логики; TON/Fragment — вне РФ-контура Lovii.

### 1.7 Уведомления после визита (статусы заказов)

- Механика: **бот пишет в чат** — тот же канал, что наши OTP/заказы. Бот может
  писать пользователю, который **стартовал бота** (`/start`); у Lovii связка уже
  есть (scope `telegram:otp`). Мини-апп может попросить старт: `requestWriteAccess`
  + `requestContact` (6.9), а также вызвать `/start` диплинком.
- Официальные лимиты (core.telegram.org/bots/faq, дата 2026-09-10): 1 сообщение/сек
  на чат (всплески → 429), 20 сообщ/мин в группах, broadcast ≈30 сообщ/сек;
  **paid broadcasts**: до 1000 сообщ/сек, **0.1 Stars за сообщение** сверх бесплатных 30/сек.
- Антиспам: жалобы пользователей → ограничения бота (спам-блок через @SpamBot) —
  практики со стороны сообщества (сторонние источники), официальных квот на
  транзакционные сообщения бота нет. Для Lovii это НЕ риск: заказы = адресные
  уведомления по событию, не рассылки.

### 1.8 Платежи

- **Цифровые товары/услуги** — только через **Telegram Stars** (`openInvoice`,
  Stars-транзакции; telegram.org/blog от 2024-06-06). Вывод — через Fragment/TON:
  для РФ-юрлица непрактично (сторонние обзоры покупки Stars в РФ через посредников:
  vc.ru 2026-06-04 — пометка «сторонний», механика подтверждает трение).
- **Физические товары** — Bot Payments API (Payments 2.0): провайдеры, подключённые
  к Telegram; для РФ в обзорах фигурируют ЮKassa и др.
  (pay.yandex.ru 2026-01-15 — «Mini Apps поддерживают оплату банковскими картами
  и через провайдеров… к примеру, ЮKassa» — пометка «сторонний»; актуальный список
  провайдеров сверить при интеграции).
- **Позиция для Lovii**: платежи платформы НЕ нужны — заказ оплачивается в
  финконтуре Lovii (Т-Банк, спец-счёт; canon/FINANCIAL_CONTOUR.md). Мини-апп =
  витрина и статусы, чекаут завершаем собственным потоком.

### 1.9 Ограничения и реалии РФ

- Telegram доступен в РФ, формальных ограничений на мини-аппы для РФ-бизнеса нет.
- SDK-скрипт `telegram-web-app.js` грузится с telegram.org — при блокировках/деградации
  на стороне клиента нужен self-host скрипта (практика сообщества; пометка «сторонняя»).
- 152-ФЗ: данные пользователя (`user` из initData) обрабатываем на своей стороне —
  основания уже покрываются Политикой ПД Lovii (дополнение формулировки — 🔶 юристу).
- Аналитика: собственные RUM-точки (SZ-008 P-3 `window.__loviiPerf`) работают
  без изменений; Telegram-статистика ботов — базовая.

### 1.10 Симбиоз с существующим Lovii

- Прикрепляем мини-апп к **@loviiru_bot** (menu button + Main Mini App) — новый бот
  не нужен. Orders-бот (@lovii_pay_bot) остаётся в своей роли.
- `start_param` → маршрутизация: `startapp=branch_1024` → витрина филиала,
  `startapp=order_123` → статус заказа (клик из уведомления ведёт точно).
- Действия владельца: только @BotFather. Код: хост-адаптер lovii-app + валидатор core.

## 2. VK Mini Apps

### 2.1 Технология и совместимость с lovii-app

- Мини-апп = **веб-приложение в webview** клиентов VK (iOS/Android/web/desk);
  контейнером может выступать и OK (vk-bridge совместим — apiok.ru, таблица событий).
- Официальные SDK: **`@vkontakte/vk-bridge`** (события/методы нативных возможностей)
  и `@vkontakte/vk-mini-apps-api` (обёртка повыше уровнем); UI-кит **VKUI — React**,
  Lovii его НЕ берёт (Vue 3): используем только vk-bridge — он фреймворк-агностичен.
  Скаффолд `create-vk-mini-app` (Vite-шаблоны; GitHub VKCOM, 2026-09-10).
- Тема: событие `VKWebAppUpdateConfig` (scheme: bright_light/space_gray);
  статус-бар: `VKWebAppSetViewSettings`; типографика/лейаут — по нашей
  дизайн-системе lovii-design (VKUI не обязателен).

### 2.2 Как создать и опубликовать

- Создание: панель dev.vk.com → «Создать приложение» → тип **«Мини-приложение»**;
  привязка к сообществу-автору (@loviiru) — после модерации смена сообщества
  заблокирована **на год** (dev.vk.com/mini-apps/management/information, 2026-09-10).
- **Модерация обязательна** для размещения в каталоге: заявка + критерии
  (дев.доки: dev.vk.com/mini-apps/catalog/moderation и …/catalog/criteria;
  «модераторы проверяют механики, UX, юридическую корректность, соответствие
  платформенным требованиям» — habr.com/doubletapp 2026-03-13, сторонний).
  Сроки модерации публично не зафиксированы — «не подтверждено», планировать
  запас времени.
- **Тестовые домены/версии**: релиз на узкую аудиторию до публикации
  (habr.com 2025-11-05, сторонний) — удобно для staging-версии Lovii.
- Хостинг: HTTPS; RU-хостинг не обязателен; Who-хостит — наш выбор.
- Кто может создавать: юрлицо/ИП — приложение привязывается к сообществу
  Lovii; платной регистрации нет (источники §8).

### 2.3 Как пользователи попадают в мини-апп

- **Каталог приложений VK** (после модерации) + поиск VK (вкладка «Приложения»).
- **Карточка сообщества**: приложение прикрепляется к @loviiru (меню сообщества)
  — органический путь от подписчиков.
- Прямые ссылки `vk.com/app<id>` (и universal links в мобильные клиенты).
- Stories: `VKWebAppShowStoryBox` (шеринг в стори), посты сообщества,
  `VKWebAppShowWallPostBox`; реферальные параметры запуска (`vk_ref`,
  `vk_ref_source`) — источник: dev.vk.com (launch params).
- VK Ads/продвижение — платный контур попадания (вне задачи).

### 2.4 Авторизация (детально — для факт-чека zcode)

- Хост передаёт **подписанные launch-параметры** в URL (`vk_user_id`, `vk_app_id`,
  `vk_is_recommended`, `vk_ref`, `vk_ts`, `sign`, …).
- **Точный алгоритм серверной валидации**: подпись `sign` вычисляется VK
  защищённым ключом доступа приложения («защищённый ключ» из настроек приложения);
  серверная проверка — сортировка `vk_*`-параметров по алфавиту, склейка
  `key=value` парами, **HMAC-SHA256** с защищённым ключом, сравнение с `sign`;
  сверьте `vk_ts` (свежесть) и `vk_app_id`. Источники: dev.vk.com «Подпись
  параметров запуска» (vk.com/ru/…, 2026-09-10 — URL в §8; серверные реализации
  в открытом доступе подтверждают схему: pkg.go.dev/SevereCloud/vksdk,
  swimmwatch.github.io «Compare VK's sign value against an HMAC-SHA256 signature
  built from the received vk_* parameters. Reject stale launches. TTL check»).
- **Тихая авторизация**: после валидации сервер знает `vk_user_id`. Связка с
  Lovii: сообщения сообщества @loviiru (`peer_id`) и OTP-контур VK уже дают
  нам `vk_user_id ↔ телефон` (существующий VKCallbackHandler + трек V).
  **Один ли id**: да — id аккаунта VK един на всех поверхностях (сообщество,
  мини-апп). Гипотеза тихой связки **подтверждается** с оговоркой: писать
  пользователю без `message_allow` нельзя (грабли приватности), на авторизацию
  это не влияет.
- **VK ID** (OAuth-виджет): полноценный вход с подтверждением, но отдельный
  объект VK ID и лишний клик — для мини-аппа избыточен; launch-подпись проще.
  Источник: spark.ru «Сценарии авторизации в VK Mini Apps» 2025-10-15 (сторонний).
- **Телефон**: метод bridge **`VKWebAppGetPhoneNumber`** (iOS/Android; таблица
  совместимости apiok.ru; README VKCOM/vk-mini-apps-api). Нюанс: доступность
  метода для категории приложения/необходимость заявки на разрешение — **не
  подтверждено** по официальной доке (страница метода за JS-SPA), проверить
  в панели при интеграции; фолбэк — `VKWebAppGetPersonalCard` (карточка контактов
  по согласию) и существующий OTP-контур.

### 2.5 Базовые возможности платформы

- vk-bridge: хранилище клиента `VKWebAppStorageSet/Get`; QR `VKWebAppOpenCodeReader`;
  гео `VKWebAppGetGeoData`; контакты `VKWebAppGetPersonalCard`, телефон

## 3. MAX Mini Apps

### 3.1 Технология и совместимость с lovii-app

- Мини-апп = **веб-приложение (HTML/JS/CSS) внутри клиента MAX** (iOS/Android/web —
  платформа отдаёт `WebAppPlatform`, в примере доки значение `web`; десктоп-клиент —
  «не подтверждено» явно, сверить). Ключевое отличие платформы: **мини-аппы живут
  только внутри чат-ботов** — «Мини-приложения работают только внутри чат-ботов
  в MAX и не могут существовать автономно» (dev.max.ru/docs/webapps/introduction,
  2026-09-10).
- Официальный SDK — **MAX Bridge** (`window.WebApp` — API-зеркало Telegram WebApp);
  UI-кит **MAX UI (React)** + FIG-гайдлайн — React НЕ обязателен, Bridge
  фреймворк-агностичен: **Vue 3 lovii-app переиспользуется** (хост-адаптер + Bridge).
- Хостинг: HTTPS; платформа VK Cloud запустила готовый хостинг мини-приложений MAX
  (dev.max.ru/docs/webapps/introduction) — но подойдёт любой HTTPS.
- Тема: соответствует клиенту (светлая/тёмная — детектируется; детальная механика
  theme-параметров в доке Bridge не зафиксирована — «не подтверждено», сверить).

### 3.3 Как пользователи попадают в мини-апп

### 3.4 Авторизация (детально — для факт-чека zcode)

- Хост передаёт **фрагмент URL** (`#`): параметр `WebAppData` (URL-энкод) + служебные
  `WebAppPlatform`, `WebAppVersion`. Внутри `WebAppData`: `user` (JSON: `id,
  first_name, last_name, username, language_code, photo_url`), `chat` (JSON),
  **`ip`** клиента (!), `query_id`, `auth_date`, `hash`. Клиентский доступ:
  `window.WebApp.initData` / `initDataUnsafe` (dev.max.ru/docs/webapps/validation).
- **Точный алгоритм серверной валидации** (цитата по
  dev.max.ru/docs/webapps/validation, раздел «Абстрактная логика проверки»):
  1. Извлечь фрагмент после `#`, распарсить `key=value`; каждый параметр — ровно раз.
  2. Из `WebAppData` извлечь пары; сохранить `hash`, исключить из массива.
  3. URL-декодировать значения; отсортировать по ключам a→z.
  4. `launch_params` = склейка `key1=value1\nkey2=value2`.
  5. `secret_key = HMAC-SHA256('WebAppData', BOT_TOKEN)`.
  6. `hex(HMAC-SHA256(secret_key, launch_params)) == hash` → подлинные данные.
  Схема **идентична Telegram** (vc.ru 2026-03-17: «валидации initData идентичен») —
  один валидатор с константой-ключом на платформу (`WebAppData`) закроет оба хоста.
- **Тихая авторизация**: после валидации сервер знает `user.id`. Lovii хранит
  связь «user_id MAX ↔ телефон» (MaxBotLink, scope max — OTP-бот @id7842223709_bot).
  **Один ли id**: да — `user.id` в `WebAppData` = id аккаунта MAX в диалоге с ботом
  (модель идентичности MAX: один аккаунт = телефонная регистрация). Гипотеза тихой
  связки **подтверждается** — и это самый сильный кейс: регистрация MAX = номер
  телефона (green-api.com: вход в MAX по номеру телефона — сторонний), т.е. id
  платформы фактически привязан к телефону на стороне хоста.
- Грабли: (а) `ip` в подписанных данных — вопрос приватности, в логи не писать;
  (б) мультиаккаунты MAX теоретически возможны — матчинг по нашей таблице связок
  корректно отработает каждый; (в) свежесть `auth_date` — проверять (рекомендация
  зеркально Telegram).
- **Телефон**: `window.WebApp.requestContact()` — «запрашивает номер телефона
  пользователя в модальном окне нативного клиента MAX»; телефон уходит **сообщением
  боту** («Чат-бот получает номер телефона пользователя из сообщения» —
  dev.max.ru/docs-api, механика обмена контактами) — тот же механизм, что наш
  OTP-контур MAX уже использует. Прямого телефона в initData нет.

## 5. Рекомендация: MVP и порядок

1. **Волна 1 — MAX + Telegram (параллельно, одна кодовая база)**:
   - оба хоста: (а) валидация = одна схема HMAC/WebAppData; (б) тихая связка
     «user ↔ телефон» уже в БД Lovii; (в) прикрепление к СУЩЕСТВУЮЩИМ ботам —
     новых объектов мессенджера ноль; (г)Lovii-сценарий «витрина + заказ»
     начинается без установки PWA.
   - MAX добавляет стратегический лот: предустановка в РФ + Цифровой ID (позже).
   - Скоуп MVP (🔶 подтвердить): витрина филиала, карточка товара, корзина/чекаут
     (веб-поток Lovii), статус заказа; вход — тихая связка, фолбэк — OTP в бот.
2. **Волна 2 — VK**: требует карточки приложения + модерации (сроки «не
   подтверждено») и решения о брендинге сообщества (фиксация на год). Даёт
   каталог/стори/Notify — отдельный маркетинговый лот.
3. **Не в MVP**: платежи хостов (финконтур свой), реклама платформ, Цифровой ID,
   NFC-механики.
4. Что даёт каждая платформа Lovii: **витрина каталога и заказ без установки**
   (все три), **статусы заказов в мессенджере** (уже живо ботами; мини-апп
   добавляет UI статуса), **лояльность/рефералка** (шеринг-механики §1.6/§2.6/§3.6),
   **вход b2b-кабинета** (вторая роль, по духу SZ-007 — отдельная спека).

## 6. Карта стыковки с Lovii (архитектурный набросок, без кода)

- **lovii-app** (Vue 3): модуль `mini-app-host` — детект хоста
  (Telegram: `initData`; VK: `vk_*`-параметры; MAX: `WebAppData` в фрагменте) →
  стартовые экраны = существующие маршруты SPA (витрина/товар/корзина/заказы);
  тема/BackButton через хост-адаптер; RUM помечает `host=tg|vk|max`.
- **lovii-core**: новый эндпоинт обмена (чертка API — спека после 🔶-решений,
  например `POST /v1/auth/mini-app/exchange`): payload хоста → серверная валидация
  подписи платформенным драйвером (драйверы: tg / vk / max — конфиг токенов и
  защищённых ключей в env, секреты не в git) → матчинг `max_bot_links`
  (scope `telegram:otp` / `max`, + VK-связка сообщества) по user_id →
  **выдача access-токена Lovii** (как после OTP); нет связи → обычный OTP-флоу
  (запрос кода в бот). Свежесть `auth_date`/`vk_ts` — обязательная проверка.
- **NotificationService** (проект SZ-010 §2): канал `mini-app` не нужен —
  уведомления остаются в ботах (Telegram/MAX) и сообществе (VK); клики пушей
  ведут в PWA, внутри мини-аппа — глубокие экраны по `start_param`/`vk_ref`.
- **Никаких новых сущностей БД**: связка уже хранится в `max_bot_links`
  (расширение scope-семантики — решение на спеке).
- **Действия владельца во внешних UI** (когда дойдёт): BotFather (menu button /
  Main Mini App), business.max.ru (договор + URL в настройках бота), dev.vk.com
  (карточка приложения + модерация).

## 10. Бизнес-кейс по волнам

### 10.1 Что стоит (оценка)

- **Ядро (один раз, W1)**: PHP-валидатор подписей TG+MAX (одна HMAC-схема,
  §4) + exchange-эндпоинт core + env-секреты + хост-адаптер lovii-app
  (детект хоста/тема/BackButton) + CI-прогон. Оценка: 3–5 сессий (zcode
  оценивал вход схожим порядком; сверено — не копировано).
- **VK (W2)**: второй драйвер валидатора (vk_*-HMAC, sign=base64) +
  адаптер-ветки + модерация. Оценка: 2–3 сессии + календарное время
  модерации.
- **Поддержка**: 3 поверхности одного SPA (не три кодовые базы) — cost
  равен «один фронт + N валидаторов».

### 10.2 Когда даёт (зависимость от наполнения)

- Представитель/амбассадор: **сразу после релиза W1** — не зависит от
  ассортимента (воронка точек: QR на точке → заявка SZ-007). Это
  соответствие текущему приоритету владельца.
- Клиентская витрина: при ≥N живых точек с ассортиментом (N — 🔶; ориентир
  «город видит 3+ точки с меню»); сейчас — 31 позиция/1 мерчант = демо.
- МСП-панель: после первой верифицированной точки (цикл SZ-007 работает).

### 10.3 Что теряем, если НЕ делать

- Воронка представителей остаётся ручной (QR ведёт в PWA с ручным вводом
  промокода — трение теряет конверсию на ключевом сегменте); атрибуция
  start_param-ами не работает в PWA-ссылке без хост-обёртки.
- «Витрина без установки» как УТП запуска каталога откладывается;
  конкуренты каталогов в TG/MAX уже витринятся (§8: friflex, dns-shop).
- Позже входить дороже: обмен/валидатор всё равно понадобится, но под
  загрузку, а не под запуск.

### 10.4 Порядок относительно денежных треков

- **I-1 фискализация (ККТ/ОФД) и WL Т-Банка — выше по приоритету**:
  мини-апп W1 не зависит от денег (представительская воронка не требует
  платежей) и может идти параллельно, но ресурсы агента при конфликте —
  в деньги. Рекомендация: W1 после/рядом с I-1 спекой, не вместо.
- Начисления в панели амбассадора — только после I-1 (данные сплитов).
