## 0. Правила ведения бэклога (2026-10-06 — обязательны для всех агентов)

### 0.1 Флоу одной задачи (цикл — без изменений)

```text
1. as-is/<модуль>.md — факты кода (file:line) + кандидаты «не хватает»
2. Владелец: сверка модуля → вердикты в «Сверка владельцем»
3. Решения → файл-дом канона (PARAMS/BRD/FINANCIAL_CONTOUR/…);
   очередь агента → BACKLOG_REVIEW §B
4. Super Z: карточка T-NNN в canon/TASKS/ («что решить» + развилки, без рецептов)
5. Владелец: передаёт ссылку карточки локальному агенту (zcode)
6. zcode: реализация на своей станции → session-док в docs/sessions/ репо
   → отчёт в карточке
7. Приёмка: Приёмка-1 Super Z (факт-чек) → Приёмка-2 владелец →
   Закрыта → archive/tasks/
8. Super Z: актуализация as-is/ и STATUS; гейты зелёные; один пакет = один
   пуш (WORK_PROTOCOL §9.3)
```

### 0.2 Жизненный цикл пункта бэклога (НОВОЕ, 2026-10-06)

1. **Открыт** — пункт в этом файле: цель, критерий приёмки, приоритет,
   исполнитель, «что нужно от владельца» (если блокирует).
2. **В работе** — по пункту открывается карточка в `canon/TASKS/`; в пункте
   остаётся короткая ссылка на карточку. Пункт не превращается в дневник
   прогресса — прогресс живёт в карточке и session-доках.
3. **Закрыт** — пункт УДАЛЯЕТСЯ из этого файла одним коммитом, и в
   `BACKLOG_ARCHIVE.md` добавляется журнальная строка:
   `ID — название — дата закрытия — чем закрыт (коммит/вердикт) — куда ушли артефакты (карточка в archive/tasks/, решение в файл-дом, находка в FINDINGS.md)`.
4. **Каноническое решение владельца**, родившееся в пункте бэклога, в течение
   того же цикла переносится в файл-дом (PARAMS/BRD/FINANCIAL_CONTOUR/…);
   в бэклоге остаётся только открытый остаток. fact-guard-пометки переносятся
   вместе с текстом решения.
5. **Правило чтения:** агент читает этот файл целиком (он тонкий и содержит
   только открытое); для истории пункта — `BACKLOG_ARCHIVE.md`, для фактов —
   файл-дом, для исполнения — карточки `canon/TASKS/` и `archive/tasks/`.
6. **Запреты:** не возвращать закрытые пункты в файл; не вести в пунктах
   переписку и срезы состояния (для этого STATUS.md); не хранить в бэклоге
   канон-таблицы дольше одного цикла (переносить в дом).

      минуты» появляется ДО отправки кода; код фактически не ушёл, форма ввода
      не открылась, альтернативные каналы заблокированы. Гипотезы: (1) клиент
      дёргает лимитируемый эндпоинт при каждом открытии/перерисовке экрана
      (счётчик растёт не по факту `request-code`); (2) лимитер по IP, а не по
      телефону (NAT операторов; известен флейк «OTP-429 между e2e-прогонами»);
      (3) блокировка глобальная вместо пер-канальной — если app ЗНАЕТ, что
      доставка не удалась, нельзя мешать переключить канал. Требуется:
      файл:line лимитера в core, сетевой лог app при открытии экрана, семантика
      счётчика (телефон/IP/девайс), расхождение «счётчик вырос» vs «код не
      отправлен». Результат: as-is-факты + фазировка фикса (счётчик только по
      реальному `request-code`; пер-канальная блокировка; fallback UI при
      известном провале доставки). Причина приоритета: блокирует первое касание
      → прямая потеря новых пользователей. НЕ чинить до вердикта и решения
      ↳ Статус 06.10: базовый фикс (глобальные IP-бакеты) — на staging; прод-промоушен и остаток —
      карточка [`T-036`](TASKS/T-036-otp-429-followup.md) (OTP-429: остаток). Материалы: ресёрч
      [`RES-016`](../artifacts/RES-016-otp-o2-429-research.md); отчёт P0-волны —
      [`EXECUTION-P0`](../artifacts/2026-10-06-arena-prioritization/EXECUTION-P0-2026-10-06.md).
      владельца.
