## 0. Суть модели одним экраном

Твои два принципа ложатся в одну таблицу балансов:

- **Один баланс на один профиль** — человек (телефон в app) имеет ровно один денежный баланс при любых ролях: покупатель, представитель, амбассадор. Роли не плодят кошельки.
- **Один баланс на один ИНН** — юрлицо/ИП партнёра имеет ровно один денежный баланс, даже если у него несколько мерчантов, филиалов и каналов приёма. Разбивки по мерчантам/филиалам/каналам — это **аналитика проводок**, а не отдельные балансы.

Всё движение денег — **журнал проводок (ledger)**, записи только добавляются, баланс = сумма проводок. Это уже канон (`FINANCIAL_CONTOUR` §2.3, §5): инвариант «деньги не создаются и не исчезают», сверка с банком до копейки.

```
Клиент оплатил 1000 ₽ (карта)
  ├─ Точка (ИНН) ....... 900 ₽  → проводка на баланс ИНН (помечена: мерчант, филиал, канал «карта»)
  └─ Пул LOVII ......... 68,40 ₽ (10% − 3,16% банк)
        ├─ Компания ..... 27,36 ₽ (внутренний счёт платформы)
        ├─ Представитель  27,36 ₽ → баланс его ПРОФИЛЯ
        └─ Амбассадор ... 13,68 ₽ → баланс его ПРОФИЛЯ
```

### 0.1. Два контура (решение владельца, 2026-09-11)

- **Финансовый контур (рубли)** — «полное прохождение всех сумм»: платежи заказов, мультирасчёт точке, пул 40/40/20, комиссии, выплаты, верификационные платежи. Каждый рубль прослеживается (инвариант нулевого баланса §5 канона).
- **Балловый контур (кэшбэк клиента)** — начисления и списания кэшбэка, 1 балл = 1 ₽. Это **отдельный** ledger от рублёвого (решение вопроса №1). Пересечения двух контуров ровно три: (а) начисление кэшбэка — сумма остаётся деньгами платформы на транзитном счёте; (б) комиссия 25% с кэшбэка — платит точка в финансовом контуре; (в) вывод баллов в деньги.

**Для клиента:**
- финансовый контур = список платежей по заказам + возвраты (пассивное наблюдение);
- балловый контур = баланс (= Σ операций по кэшбэку, 1:1 к рублю), которым можно: перевести другому клиенту, оплатить заказ полностью/частично, вывести в деньги.

⚠️ Следствие: балловый баланс — **обязательство платформы, обеспеченное деньгами** на транзитном счёте (кэшбэк из чека точка не получает). Поэтому сверка «Σ баллов клиентов = деньги на транзитном счёте» — обязательная часть контурной сверки (В-4).

В коде уже есть `wallets` (earn/spend/refund/adjustment/expiration) — это каркас баллового контура; дополнить переводами P2P, выводом и сверкой.

## 2. Техзадачи

Коды рабочих групп A/Б/В/Г; номера SZ-NNN присвоим при заводе в TASKS (по одной задаче = один файл, как принято). Для каждой: суть → где живёт → гейт.

### Эпик A — Балансный контур (фундамент)

**A-1. Счета и проводки (ledger).**
Два контура — две системы записей (§0.1):
- **Рублёвый (финансовый):** таблицы `accounts` (владелец = `user` ИЛИ `partner/ИНН`; ровно один счёт на владельца, копейки) и `ledger_entries` (append-only: счёт, тип операции, сумма ±, ссылка на источник — заказ/платёж/выплата — и аналитика: `merchant_id`, `branch_id`, канал оплаты, роль в сплите). Баланс в одной транзакции с проводкой (row-lock), тест инварианта `balance = Σ(entries)`, идемпотентность по вебхуку Т-Банка.
- **Балловый (кэшбэк):** каркас уже есть (`wallets` + `wallet_transactions`), дополнить: P2P-переводы между клиентами (с лимитами и логом), операция вывода (списание баллов + ссылка на рублёвую выплату), операция оплаты заказа (списание + ссылка на заказ). **Убрать сгорание**: канон прав — баллы бессрочные, колонку `expires_at` и тип `expiration` вывести из употребления (правка кода). Отдельный инвариант: Σ баллов всех клиентов = деньги платформы на транзитном счёте (сверка В-4, обязательна).

*Гейт:* pest-тесты двойного списания/конкурентности; обе сверки на пустых данных сходятся в 0.
*Закрывает:* «один баланс на профиль», «один баланс на ИНН».

**A-2. Начисление пула 40/40/20 при подтверждённом платеже.**
Триггер — подтверждение оплаты (вебхук уже есть). Канон: `SAGA-2` + BRD §7: пул = 10% − комиссия банка по каналу (карта 3,16% / СБП 0,7% / T-Pay 2,59%, мин 3,49 ₽; **оплата баллами — комиссия банка 0, пул = полные 10%**, решение №9), ROUND_HALF_UP, остаток округления → Компания, сумма долей = пул ровно. Для системы неважно, чем оплатил клиент — расчёты идентичны. Резолв представителя/амбассадора — по регистрационному промокоду точки (сервер, клиент код не передаёт). Проверки активности: подписка представителя истекла → 40% → Компания; амбассадор деактивирован → 20% → Компания (EC-33). Только для МСП-мерчантов с связкой: Kuper-импорт в контур не входит.
*Гейт:* табличные тесты по всем вариациям BRD §9.4 (EC-16…21, 36) + самозанятый/ИП не влияет на сплит (только на вывод).
*Зависимость:* A-1, Б-1.

**A-3. Разбивки и отчёты по счетам.**
API поверх ledger: обороты и остаток по периоду, разрезы — канал оплаты, мерчант, филиал, точка. Потребители: b2b-кабинет партнёра (ИНН), кабинет представителя «Отчёты по точкам» (SZ-034 фаза B), месячный отчёт Лицензиату (I-3 — одним API закрыть оба).
*Гейт:* суммы разрезов сходятся с общим остатком (это же тест A-1).

**A-4. UI баланса.**
App: экран «Баланс» в профиле (остаток + история проводок, фильтры). B2b: страница «Баланс» с фильтрами A-3 + экспорт. Дизайн-токены lovii-design/demo.
*Зависимость:* A-1, A-3.

### Эпик Б — Рефералка

Спека уже написана и ждёт твоего утверждения: `SZ-034` §1.1 (промокод `PPXXXX` в заявке точки из «ЛОВИ Бизнес», снимок кода на `partners.representative_promo_code`, перепривязок в MVP нет, web-заявка без промокода = «прямая» 🔶). **Б-2. Промокоды и статусы представителей/амбассадоров.**

*Гейт:* табличные тесты BRD §9.1 (EC-1…6).
*Зависимость:* Б-1 (связка ссылается на коды).

**Б-3. Подписка представителей + гейт начислений.**
Тарифы 599/199 (BRD §4), оплата с баланса профиля или картой (платёжный контур уже есть), правило: неактивная подписка → начисления уходят Компании (EC-11), подписка НЕ участвует в сплите (EC-35).
*Зависимость:* A-2, Б-2.

**Б-4. Кабинет представителя (экраны).**

### Эпик В — Спец-счёт и верификация (канон FINANCIAL_CONTOUR)

**В-1. Открытие спец-счёта + корпоративное API банка.**
Офлайн-шаг (твой): юрлицо счёта 🔶 (#14), запросить баланс/выписку/вебхуки, mTLS+IP-WL, тарифы РКО. До API — ручной режим администратора.

**В-2. Реестр банковских операций.**
Таблица операций выписки (external_id = идемпотентность, сырой payload, append-only), загрузка: вебхук ускоряет, крон-опрос выписки — источник истины.
*Гейт:* повторная выписка не создаёт дубль.

**В-3. Верификационный платёж партнёра.**
Счёт с назначением `Верификация… Код VER-<partner_id>-<суффикс>` (суффикс уже генерится в заявках), оплата строго с р/с компании, авто-матчинг = код + сверка плательщика (ИНН/счёт) → `verified_at` (гейт витрины уже живой, I-5). Сбои → ручная очередь 🔶 где экран (#18). Самозанятые — отдельный путь 🔶 (#16).
*Зависимость:* В-2; решения #13 (сумма), #15 (оферта), #17 (срок жизни), #19 (возврат 1 ₽ — рекомендация «без возврата»).

**В-4. Система сверк нулевого баланса (обязательна — решение владельца 2026-09-11).**
Главный контроль контура: сумма всех операций по любому счёту и контуру обязана сходиться в ноль. Три уровня из канона §5: парность проводки; ежедневная сверка ledger ↔ выписка (допуск 0 коп); контурная сверка, включая **внутренние балансы A-1 и балловый контур**: Σ баллов всех клиентов = деньги платформы на транзитном счёте, Σ счетов профиля+ИНН объяснима банковскими операциями. Нарушение = P1: алерт в Telegram/MAX (боты уже развёрнуты), блок автоматических исходящих.

### Эпик Г — Выплаты (деньги наружу; модель: pull + дневной реестровый цикл, решение №2)

**Г-1. API выплат Т-Банка (mTLS + IP-WL).**
Подключить канал выплат по реквизитам/реестрам (`lovii-docs/tbank/vyplaty-multisplit.pdf`); тестовые выплаты на свои счета. Мультирасчёт при оплате (deal_id) в модели pull **не нужен**. Ключи mTLS — в `lovii-docs/tbank`, в git не класть.
*Зависимость:* верифицированные партнёры (В-3) — реквизиты ИНН уже в карточке.

**Г-2. Ежедневный финансовый цикл (закрытие дня → выплаты в 10:00).**
Крон-конвейер по финансовому дню. Задержка выплаты на день — **намеренная**: это окно прохождения всех проверок всех транзакций и балансов; если всё ок — реестры уходят на счета.
1. Сверка дня: логи, операции, чеки, квитанции, статусы, транзакции — все операции дня сошлись (сверки В-4 зелёные);
2. Отчёт дня + записи периодической отчётности по всем МСП (в b2b — это I-3);
3. Актуализация БД: старые данные (проводки/логи старше N дней) — в холодное хранение, разгрузка горячей БД (партиционирование ledger);
4. Формирование реестров выплат: в реестр дня попадают получатели, у которых **наступил выбранный период выплат** — база «ежедневно» (весь накопленный баланс), можно выбрать другой период (канон BRD §8.4); самозанятые — по запросу: запрос сегодня → реестр завтра;
5. В 10:00 следующего финансового дня — отправка реестров в банк.
*Гейт:* день с красной сверкой В-4 реестров не формирует (P1-инцидент, ручной разбор).
*Зависимость:* A-1, A-2, В-4, Г-1.

**Г-3. Выплаты по `legal_status` (единый принцип для всех ролей — решение владельца).**
Канон не правим: **период выплат выбирает получатель, база — ежедневно** (BRD §8.4). ИП/ООО (МСП, представитель, амбассадор — не важно): в свой период — весь накопленный баланс, комиссия банка 0,5%, платит Компания. Самозанятый (в любой роли, включая клиента-физика с подпиской представителя): запрос на вывод в любой день → попадает в реестр следующего цикла, 1% мин 30 ₽, при < 3 000 ₽ удержание из суммы. Формулы канон (BRD §8.4). Отрицательный баланс при возврате после вывода — блок новых запросов до погашения (EC-37 🔶). Ошибка банка → retain + повтор в следующем цикле (EC-28).
*Зависимость:* A-1, A-2, Г-2.

**Г-4. Вывод баллов клиента в деньги.**
Операция двух контуров: списание баллов (балловый ledger) + выплата (рублёвый, механизм Г-3). Физик выводит только через статус представителя — активная подписка обязательна, канал по `legal_status` (самозанятый → карта: запрос в любой день → реестр следующего дня; ИП/ООО → по выбранному периоду в дневном реестре). Трата и перевод кэшбэка — без подписки.
*Зависимость:* A-1, Г-3, Б-3 (подписка).

## 3. Порядок работ

```
A-1 (счета+проводки) ─┬─> A-2 (пул 40/40/20) ─> A-3 (отчёты) ─> A-4 (UI)
                      │        ↑
Б-1 (связка) ─> Б-2 (промокоды/статусы) ─> Б-3 (подписка)
В-1 (счёт офлайн) ─> В-2 (выписка) ─> В-3 (верификация) ─> Г-1 (API выплат) ─┐
A-2 + В-4 (сверки) + Г-1 ─> Г-2 (дневной цикл, 10:00) ─> Г-3 (выплаты) ───────┴─> Г-4 (вывод баллов)
```

Минимальный путь к «работающей рефералке на глазах»: **A-1 → Б-1 → Б-2 → A-2 → A-3/A-4** — начисления видны в интерфейсе ещё до реальных денег. Ветка В идёт параллельно (офлайн-шаг В-1 не ждёт кода). Выплаты (Г) — последними: требуют верифицированных партнёров (В-3), API банка (Г-1) и накопленных балансов.

## 4. Что осознанно НЕ входит (не теряем, но отдельно)

- **Фискализация ККТ/ОФД (I-1)** — трек I BACKLOG, агентская модель (Правообладатель бьёт чек), двухчековая механика. Связка с A-2 только через ссылку на платёж.
- Месячный отчёт Лицензиату (I-3) — закрывается задачами A-3 + Г-2 (дневной цикл готовит записи, витрина — b2b).
- Роялти Разработчику, франшизы, события/бонусы статусов, антифрод-мониторинг (лимиты/лог P2P и EC-38/39 — добавить дёшево в A-1/A-2, разбор отдельно).
- Клиентский кэшбэк-конструктор точек (лояльность-домен) — отдельно; целевой счёт ясен: балловый контур (§0.1).
