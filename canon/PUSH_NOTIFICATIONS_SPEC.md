## 1. Матрица сред РФ: где web push работает

Канон реализованного (SZ-010): Web Push / VAPID без внешних сервисов —
это совместимо со всеми средами из колонки «Push» ниже (VAPID — единый
стандарт; разница только в требовании установки и в UX подписки).

| Среда | Push | Требование / источник |
|---|---|---|
| iOS/iPadOS Safari, **PWA установлена** (16.4+) | ✅ | «Add web push to Home Screen web apps in iOS 16.4 or later» — developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers; «…comes support for Web Push and other features for Home Screen web apps» — webkit.org/blog/13878 (16.02.2023). Запрос разрешения — только из жеста пользователя в установленном веб-аппе |
| iOS/iPadOS Safari, обычная вкладка | ❌ | та же пара источников: Home Screen web apps — единственный носитель web push на iOS; в табе Push API не экспонируется |
| Android Chrome | ✅ | Web Push через FCM-транспорт, стандартный flow VAPID; требование: HTTPS, Service Worker (developer.chrome.com/docs/notifications) |
| Android Яндекс.Браузер | 🔶 | Chromium-база: push работает по модели Chrome; официальной вендорской доки по Web Push нет — проверять на реальном устройстве перед продом (§5) |
| Десктоп Chrome/Edge (Chromium) | ✅ | стандартный Web Push + уведомления ОС (developer.chrome.com) |
| Десктоп Safari 16+ (macOS Ventura) | ✅ | «Safari 16 adds support for Web Push to web apps» — webkit.org/blog/13878 |
| Десктоп Firefox | ✅ | Push API поддержан (MDN Push API: browser-compat) |
| WebView мини-аппов VK / Telegram / MAX | ❌ | в вебвью Push API недоступен; каналы уведомлений этих платформ — их собственные боты. Дословно и с URL: MINI_APPS_RESEARCH §6 |
| In-app браузеры соцсетей/мессенджеров | ❌ | та же природа (WebView) — web push не доставляется; покрытие таких пользователей — боты + email |

Вывод для MVP: **пуш — основной канал только для установленных PWA**
(iOS — обязательна установка; Android/десктоп — работают из вкладки, но
установленная PWA надёжнее). Все прочие среды уже покрыты fallback'ами:
Telegram/MAX-боты (живые, OTP-паттерн) и email SZ-009.

## 2. UX согласия (soft-ask)

Принцип: браузерный диалог разрешения — одноразовый и дорогой; показывать
его только после ценного действия пользователя.

1. **Момент запроса** (первый шаг — после первого заказа или после
   сохранения адреса, не по заходу): шит «Получать статусы заказа?» —
   заголовок «Узнавайте о заказе первыми», текст «Мы пришлём пуш, когда
   заказ соберут, отдадут курьеру или отменят. Никакой рекламы без вашего
   согласия (см. „Рассылки и акции")», кнопки «Включить» / «Не сейчас».
2. **iOS-подсказка до запроса**: в установленной PWA — шаг «Установите
   ЛОВИ на главный экран» («Поделиться» → «На экран „Домой"») уже
   реализован в SZ-010 (секция «Уведомления», статус ios-standalone-required).
3. **Отказ**: повторный запрос браузер невозможен (permission denied —
   состояния нет в UI? есть: SZ-010 рисует честную подсказку «разрешите в
   настройках браузера»). Не показывать диалог чаще 1 раза в 2 недели —
   мягкий ритм: событие-триггер → шит.
4. **Управление подпиской**: шит «Настройки» → «Уведомления» (тумблер
   SZ-010 уже в staging). Транзакционные пуши статусов — без согласия по
   SZ-022 (это не маркетинг); промо-пуши — только через
   communication_consents.push (SZ-022, рельсы готовы).

## 3. Канальная матрица «событие × канал» + анти-дубли

Правило анти-дублей: **одно событие — один канал по предпочтению
пользователя**; push > бот > email. Порядок задаётся тем, что у
пользователя реально работает (подписка на push активна → бот/email за
то же событие клиенту не шлём). Для продавца — отдельная аудитория
(B2B-партнёр): push о новом заказе/отмене — в lovii-app (решение
владельца 2026-09-13, v1.1.0) + боты по его выбору; в b2b-кабинете
подписки на push нет.

| Событие (карта групп SZ-010/SZ-009) | Push | TG/MAX-бот | Email | Правило |
|---|---|---|---|---|
| Заказ собран/передан курьеру/в пути/выполнен клиенту | ✅ основной | fallback | fallback | один канал: активная подписка push глушит остальные клиентские каналы |
| Отмена заказа клиенту | ✅ | ✅ | ✅ | критичное — допустимы push + email одновременно (решение 🔶-4) |
| Новый заказ / отмена — продавцу | ✅ в lovii-app (v1.1.0) | ✅ боты | — | пуш продавцу — в мобильном приложении (бизнес-пользователь); в b2b-кабинете пуш-подписки нет (решение владельца 2026-09-13); бот не заменяется |
| Промо/акции клиенту | через consents.push | нет | через consents.email | только по SZ-022-согласиям; пуш без согласия = юридический риск |
| OTP-коды | — | ✅ (max+telegram live) | — | OTP не в пушах (телефон/бот) |

Анти-дубль реализуется на стороне диспетчеров core (уведомления клиенту
о статусе идут всеми включёнными каналами today — это текущее поведение
SZ-009/SZ-010; сведение к «одному каналу по предпочтению» — 🔶-3, код не
писался в этой задаче).

## 4. MVP-приоритизация и 🔶-решения владельца

## 6. Решения владельца 2026-09-21 (уточнение §3–§4)

- 🔶-3 закрыт: **анти-дубль = push-only**. Email-канал уведомлений о статусах
  заказа НЕ используется — почта только для отчётов и документов. Email-листенеры
  статусов (NotifyClientOnOrderStatusChangedByEmail и соседние) глушатся/убираются
  из матрицы (исполнение — SZ-069).
- 🔶-4 закрыт: отмена заказа — только push (email-ноги нет).
- Клиентские пуши управляются **в профиле, per-device** (включено только на тех
  устройствах, где включил пользователь); у МСП — настройка участника кабинета
  + дублер-переключатель в канбане приёма заказов («какие пуши получать на
  данное устройство»); карточка **SZ-069**.
- Пуш нового заказа — со звуком («как у Яндекса»); ограничения платформ
  (Web Push не даёт произвольный звук на iOS) и развилка — в SZ-069.
