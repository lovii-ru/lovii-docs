# TEST_PROFILES — картотека тестовых профилей («актёров») и правила работы с их данными

> Канон с 2026-10-03. Обязателен для агентов и e2e/скрин-съёмки.
> Проблема, которую решает: до сих пор все скрины сняты глазами владельца
> (user 51), онбординг/статусы заявок показывают не то, что видит реальный
> подключающийся. См. `screens-library/REVIEW.md`.

## 1. Механика (уже работает, не изобретать заново)

Staging (`api-staging.lovii.ru`) и dev:

- **Любой новый номер = новый пользователь.** Один цикл:
  `POST /api/v1/auth/send-code {phone, channel:"sms"}` →
  код (см. ниже) → `POST /api/v1/auth/confirm {phone, code}` → Bearer-токен.
- **Код:** универсальный бипас `1234` действует на dev/staging; программно
  надёжнее читать реальный код из дев-эндпоинта `GET /api/v1/dev/otp/last-code?phone=…`
  (включён вместе с `OTP_DEV_BYPASS=true`; на прод роута нет).
- **Лимиты:** `otp-send` 2/мин на телефон (анти-спам). Один прогон = 1–2 отправки;
  повторный прогон раньше минуты = 429 — это штатно, не баг.
- **Реф-ссылки/промокод:** заявка МСП принимает `promo` (6 символов) — указан,
  привязка представителя фиксируется в момент создания заявки; не указан —
  заявка идёт в модерацию платформы. Так проигрываются ветки «с промо/без промо».
- Полное описание цикла в e2e: `lovii-app/e2e/README.md`, `e2e/helpers/api.ts → loginWithOtp`.

**Актёры-разовые (throwaway):** для сценариев, мусорящих данными (заказы,
промо-правила, переводы), актёров из картотеки НЕ использовать — создать
одноразовый профиль `+7900999XXXXX` (та же механика) и очистить его данные
в конце сессии (см. §4).

## 3. Раннер — одна команда вместо подбора методов

```bash
python3 ~/LOVII/tools/stage-actor.py create ACT-01        # создать/залогинить актёра, напечатать токен
python3 ~/LOVII/tools/stage-actor.py login +790099912345  # разовый профиль
python3 ~/LOVII/tools/stage-actor.py list                 # состояние картотеки (актуализирует «Создан»)
```

Раннер идемпотентен: существующий профиль просто логинится (профиль = номер).

## 4. Правила работы с данными (для каждого прохода агента)

1. **Перед съёмкой/сценарием** определить целевое состояние по картотеке:
   есть актёр с таким состоянием — брать его; нет — одноразовый профиль (§2).
2. **Владельческие данные не трогать никогда**: user 51 / Основатель,
   АТМОСФЕРА (точка 1024), прод-стартер-сущности (см. `canon/PROD_STARTER.md`).
   Актёры — только свои данные.
3. **Когда создавать нового:** состояние не покрыто картотекой ИЛИ сценарий
   мутирует данные (заказ, промо, перевод, апрув) — одноразовый профиль.
4. **Когда чистить:** конец сессии = удалить/обнулить созданные за сессию
   сущности одноразовых профилей (заказы → cancel, заявки → reject, промо-правила
   → удалить, корзины → очистить). Актёров картотеки НЕ чистить: их состояние —
   их ценность; если актёр «испачкался», зафиксировать в таблице §2 и
   восстановить состояние до следующей съёмки.
5. **meta.json кадра обязан содержать `profile`** — кто снимал кадр
   (актёр/номер). Библиотека показывает это в подписи версии. Кадры, снятые
   владельцем, в онбординг-ветках считаются временными до пересъёмки актёром.
6. **База данных:** приёмка через `tools/core-tests.sh` (не `docker exec`!);
   ручные правки данных — только в своих актёрах и только через API.

## 5. Связь с библиотекой экранов

- Съёмка новой версии экрана — под актёром, чьё состояние соответствует
  назначению экрана (онбординг — «чистые» актёры, рутинные экраны — наполненные).
- В `screens/<slug>/<vN>/meta.json` поле `profile` — обязательное, формат
  `+79000000013 (ACT-03 msp-pending)`.
- Пересъёмка онбординг-ветки (APP-P-021…024, 044, 045, 052, кабинеты) —
  отдельной задачей по актёрам после создания картотеки.
