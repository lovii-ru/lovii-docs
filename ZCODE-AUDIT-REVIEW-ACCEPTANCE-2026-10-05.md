# Независимая пере-приёмка ответа на AUDIT-ACCEPTANCE

**Для:** zcode, исполнитель Wave 3.
**Проверенный срез:** `origin/main` на `089b4fd`; wrapper содержит изменения из `9a0a268`.
**Назначение:** передать в репозитории результат, который раньше был только в чате. Этот addendum не заменяет `AUDIT-VERDICT-R4-2026-10-05.md` и не переносит `origin/main` в рабочую ветку.

## Вердикт

**Частично принято; полная независимая приёмка остаётся открытой.** Прогресс в пакете есть, но некоторые ключевые утверждения ответа противоречат приложенным артефактам, а несколько проверок требуют live-доступа, которого у аудитора не было. Поэтому заявления о сервере и GitHub Actions ниже не трактуются как независимо подтверждённые.

**Граница проверки:** статический просмотр Git-артефактов. Доступа к SRV и GitHub Actions нет; серверный SHA, ротация/отзыв токенов, состояние runner-контейнеров и результаты живых прогонов независимо не проверялись. Секреты не запрашивались.

## Что блокирует полную приёмку

### 1. A4: проверки не обеспечивают строгий и правильный mapping

В `audit-bundle/infra/lovii-deploy.sh`:

- `tag_one` получает target из `compose config`, а затем отклоняет только перечисленные префиксы (`redis:`, `imresamu/`, `getmeili/`, `node:`, `alpine:`, `docker:`, `library/`; строки 90–101). Это blacklist, не строгий target allowlist: прочие нежелательные либо неожиданные образы не запрещены.
- В app-ветке вызывается `tag_one app app` (строка 106), тогда как `audit-bundle/infra/compose-lovii-app.yml` объявляет сервис `web` (строки 1–15). Для отсутствующего `app` target функция молча пропускает тегирование. Нужен точный mapping к `web` и тест, который доказывает, что именно этому сервису назначается ожидаемый GHCR image.
- Проверка A4 (строки 144–179) сравнивает ID pulled GHCR-образа с ID **любого** image из `docker compose config --images`, а не с образом конкретного ожидаемого сервиса. Это не доказывает mapping «пакет → нужный сервис».
- Проверка расположена после `migrate` и `horizon:terminate` (сопоставить строки 136–142 и 144–179). Следовательно, она происходит до `up`, но не до потенциально изменяющих состояние действий.
- При ошибке любого `docker pull` скрипт переходит к `$DC build --pull` (строки 111–125). Production остаётся не fail-closed / не pull-only: неожиданный pull-failure может привести к сборке на общем хосте.

**Для закрытия:** явная таблица ожидаемых сервисов и образов каждого стека; строгий target allowlist; отказ при пропущенном/дублированном/лишнем mapping; проверка image ID для конкретного target-сервиса до миграций и `up`; fail-closed при pull-failure. Приложить unit-тесты на app=`web`, core=`horizon`, изменённый порядок compose-сервисов, отсутствующие сервисы, чужие targets и отсутствие нужного SHA-образа.

### 2. R-1.9 / R-3.4: артефакт prod-compose не совпадает с заявлением

В `audit-bundle/infra/compose-core-prod.yml:302–304` healthcheck всё ещё содержит `redis-cli -a ${REDIS_PASSWORD}`. `REDISCLI_AUTH` показан для staging, а не для приложенного prod-файла. В ответе сначала сказано, что REDISCLI_AUTH есть в prod-compose (`AUDIT-RESPONSE-ACCEPTANCE:22`), а ниже прямо сказано, что production Redis пока работает со старым healthcheck и изменение применится при следующем recreate (`:76–81`). Это внутреннее противоречие; R-1.9 для production не закрыт.

Тот же prod-compose всё ещё **объявляет** `tbank-mock` под профилем `mock` (`compose-core-prod.yml:373–403`). Наличие профиля само по себе не доказывает, что сервис активен в текущем production, но файл не подтверждает требование о чистом prod-наборе. Нужны точный экспорт с SRV и безопасный вывод фактически применённого `docker compose config --services` с соответствующими файлами/профилями.

Отдельно: SHA `b74a3268…`, ранее приведённый как prod-compose, принадлежит `compose-core-staging.yml`; SHA приложенного `compose-core-prod.yml` — `a3ab5abc…`. Поэтому B7 и parity нельзя принимать без правильного prod-экспорта, хэша и вывода сервисов обоих стеков.

### 3. R-0.4: manifest не включает последний ответ

Коммит `089b4fd` добавляет `AUDIT-RESPONSE-ACCEPTANCE-2026-10-05.md`, но inventory в `audit-bundle/MANIFEST-REDACTED.md` после этого не пересобран: новая запись отсутствует. Там также остаются две записи `.DS_Store`, которых нет в дереве (`./.DS_Store` и `./workflows/.DS_Store`). R-0.4 остаётся открытым до пересборки и сравнения inventory со всеми реально существующими файлами после последней правки.

### 4. A1: ротация зачтена как заявление; ephemeral credential не реализован

Ротация старого PAT засчитывается как заявление владельца, но не как независимая проверка отзыва. Wrapper всё ещё описывает persistent login и план `docker logout` (`lovii-deploy.sh:3–6`); исполняемого `docker logout` в wrapper нет. Нужны реализация/проверка очистки credentials (например, login перед pull и гарантированный logout через trap), а также безопасное подтверждение, что на хосте больше не используется прежняя сохранённая учётка. Секреты в пакет не добавлять.

### 5. R-3.1: наличие runner-контейнеров не подтверждает изоляцию

В `audit-bundle/infra/runners-compose.yml` все runner и все DinD подключены к одной сети `ci-net` (`:19–119`); DinD слушает `tcp://0.0.0.0:2376` при отключённом TLS (`DOCKER_TLS_CERTDIR: ""`). Следовательно, ожидаемое обращение runner к своему daemon не доказывает запрет доступа к соседним daemon. Нужны отдельные сети или равноценная аутентифицированная изоляция, отрицательный тест runner A → dind B, а также pins/digests и ограничения/cleanup. R-3.1 не закрыт.

### 6. B1–B10 и owner-зависимые пункты остаются частичными

Дополнительные выдержки полезны, но ответ не заменяет полный комплект проверяемых артефактов: нужны четыре run ID (core/app/b2b/admin), job-логи и связка каждого run с runner и SHA; один ID core не доказывает все четыре репозитория. Off-site backup и restore-тест по-прежнему не выполнены; первый production-релиз отложен до разрешённого окна. Эти пункты остаются открытыми до фактических доказательств и/или решения владельца.
