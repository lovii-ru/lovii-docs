## 0. TL;DR — вердикт ревизии

**Продуктовых пробоев не найдено.** Staging-контур жив (прямые пробы API 21.09: поиск и витрина отвечают, ошибок 500 нет), тесты трёх репозиториев зелёные в CI, гигиена кода образцовая (реальных TODO — единицы). При этом ревизия нашла **одну сломанную инфраструктурную деталь**, **два устаревших блокера в документации готовности** и **системный дрейф трёх индексов задач** — то есть проблемы сейчас не в продукте, а в связках «деплой» и «документы».

1. **Что не работает прямо сейчас:** в core CI push-триггер мёртв с самой миграции на GitHub (см. §4, находка F-055) — авто-деплой staging не срабатывал ни разу, все деплои core фактически были ручными; колонка `orders.method` не хранится (точность пула по СБП/T-Pay — как «карта»); `OTP_DEV_BYPASS` по умолчанию включён; подсистема выплат появилась в коде, но тестовый контур банка ещё не подключён (T-013 открыта).
2. **Что переделать:** не код, а слои координации — RELEASE_READINESS v0.1 (17.09) уже устарел (два его блокера закрыты кодом), as-is-модули не покрывают волну 18–21.09, три индекса задач расходились с карточками (исправлено этой ревизией), три gemini-резюме владельца лежат в `as-is/` без канонического дома, b2b-спеки заморожены с апреля.
3. **Что делать дальше:** порядок полос владельца (BACKLOG §0 A–D) подтверждается. Поверх него: P0 — фикс одной строки в CI core + RELEASE_READINESS v0.2 + разбор стопки из 37 карточек «На приёмке» (это главный узкий горлышко — см. §6). Вердикт RELEASE_READINESS от 17.09 («не готов к публичным платежам, условно готов к pilot M1») на срез 21.09 **подтверждается**, но условия пилота сократились: выплаты начаты в коде, UI карт LOVII PAY готов и перерос план.

**🚨 Находка №1 — F-055: CI lovii-core не запускается по push с 20 июня.**
`.github/workflows/ci.yml:11` содержит `branches: aster, staging]` — скаляр-строка вместо списка `[master, staging]`. Пиксакс по истории: `aster]` появился в коммите миграции GitLab→GitHub `00eae98` (2026-06-20), затем `39b66be` (2026-09-05, «auto-deploy staging») дописал staging к уже битой строке. Фильтр «aster, staging]» не матчит ни одну ветку → событие push не порождает ни checks, ни auto-deploy-staging. Работают только pull_request (без фильтра веток) и ручной workflow_dispatch. Следствие: **авто-деплой core на staging не срабатывал ни разу за GitHub-эпоху** — вся цепочка «merge в staging → CI → деплой» у core держалась на ручных dispatch. Фикс — одна строка (список веток), плюс контрольный dispatch и сверка, что staging-сервер содержит `70c765e`. Аналогичные триггеры в app и b2b проверены — там списки корректны.

**Остальное, что стоит знать (не блокеры):**

- **e2e вне гейтов.** Core: сьют E2e исключён из `composer test`/покрытия (2 теста, нужен поднятый стек). App: Playwright-сценарии (3 сценария + 4 теста) в CI не запускаются вовсе. Юнит-щит при этом плотный (см. §5) — но «золотой путь» заказа охраняется только юнитами и ручными приёмками.
- **Юнит-тесты app ходят в сеть.** `ProfileModule.test.ts` делает реальные connect-попытки на `::1:3000` (не замокан axios в одном кейсе) — тесты проходят, но среда тестов негерметична.
- **Локальный node_modules app устарел:** пакет `uqr` объявлен в yarn.lock, но отсутствует в локальной установке — один сюит (roles-representative, ~56 кейсов) не собирается локально; в CI (свежий install) зелёный.
- **b2b: статанализ с дырами и без vendor.** PHPStan level=max, но три крупных слоя (Models/Database/Config) исключены; локально тесты не воспроизводимы без composer install.
- **Кросс-стековая связность b2b:** очередь SZ-037 (`NotifyCoreOfOrderStatusTransition`, ретраи 5 с…30 мин) потребляет redis из стека core через external network — работает, но должно быть отражено в схеме окружения и прод-чеклисте (зависимость деплоев, урок F-040).
- **Мелочи app:** опечатка `creatOrder` в публичном методе стора (въела в API), CacheFirst на `static.kuper.ru` в SW-рантайм-кэше (наследие выключенной интеграции, F-026).
- **Живой staging (пробы 21.09):** `/api/v1/search/merchants` → 200; `/api/v1/stores` → 422 (теперь требует параметры гео — ожидаемое поведение после SZ-066/067, а не поломка). Явных 500 нет.
