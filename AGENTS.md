# AGENTS.md — обязательная точка входа для агентов LOVII

Этот файл — **маршрутизатор**, а не копия канона. Он действует для работы в
репозитории `bestdeejay-design/lovii_docs` и задаёт порядок чтения. Подробные
правила находятся в документах, на которые он ссылается.

## 1. Идентичность репозитория и имена

| Идентификатор | Значение | Как использовать |
|---|---|---|
| `REPO_ID` | `bestdeejay-design/lovii_docs` | каноничный GitHub-репозиторий в переходный период |
| `REPO_DIR` | `lovii_docs` | имя checkout/каталога этого репозитория |
| `WORKSPACE_DIR` | `LOVII/lovii-docs` | алиас локального workspace, **не** имя GitHub-репозитория |
| `PUBLIC_REPO` | `axiiom-ru/lovii` | публичное зеркало документов |
| будущий alias | `lovii-docs` | только план миграции, не заменять им текущие имена автоматически |

Не переименовывай GitHub-репозиторий, remote, каталог или ссылки только ради
дефиса. Если речь идёт о `lovii-docs`, сначала выясни, обозначает ли это
workspace-путь, будущий alias или конкретный репозиторий; в документации
подписывай значение явно.

## 2. Обязательный порядок чтения

1. Этот `AGENTS.md`.
2. `DOCS_GUIDELINES.md` — классы документов, файл-дом факта, маршрутизация и
   гейты корпуса.
3. `canon/AGENT.md` — операционный ранбук сопровождения документации.
4. `canon/WORK_PROTOCOL.md` — роли, жизненный цикл задач и передача работы.
5. По контексту задачи: `canon/STATUS.md`, `canon/FINDINGS.md`,
   `canon/BACKLOG.md`, `canon/REFERENCE.md` и конкретная карточка из
   `canon/TASKS/`.
6. Для работы в другом репозитории — сначала соответствующая запись в
   `REGISTRY.md`, затем его локальные `AGENTS.md`/`CLAUDE.md`, session-документы
   и только после этого код.

Если инструкции ниже расходятся с подробным документом, не угадывай: зафиксируй
расхождение в `canon/FINDINGS.md` и следуй более высокому документу из порядка
чтения. Изменение самого правила делается отдельной правкой governance, а не
молчаливой интерпретацией задачи.

## 3. Где хранится какой результат

| Результат | Единственное рабочее место | Не использовать вместо него |
|---|---|---|
| Канонический факт/правило | файл-дом из `DOCS_GUIDELINES.md` §4 (`PARAMS`, `BRD`, контракт и т. п.) | `STATUS`, `BACKLOG`, task-spec, workspace |
| Производное объяснение/карта | соответствующий документ класса B со ссылкой на файл-дом | копия числа или решения без ссылки |
| Постановка и отчёт задачи | `canon/TASKS/<ID>-<slug>.md` до архивации | `STATUS`, `FINDINGS`, workspace |
| Состояние корпуса и общий срез | `canon/STATUS.md` | отчёт исполнителя, backlog |
| Расхождение с кодом/доками | `canon/FINDINGS.md` | скрытая правка в индексе или чате |
| Очередь и решение владельца | `canon/BACKLOG.md` | статус задачи или session-док |
| Карта всех документов/репозиториев | `canon/REFERENCE.md` / `REGISTRY.md` | случайный README |
| Инженерная история исполнения | `docs/sessions/` соответствующего кодового репозитория | `canon/STATUS.md` как единственный отчёт |
| Оперативная работа workspace | `LOVII/lovii-docs/` и его `status.md`/`decisions-needed.md` | канон; workspace не становится SSOT |
| Юридическая публикация | `public/` и зеркало `axiiom-ru/lovii` | `archive/`, task-spec или workspace |

`canon/TASKS/` находится внутри канона только для удобства доступа; сами
карточки — **рабочие артефакты**, не источник продуктовых фактов. Они могут
цитировать критерии с явной ссылкой на канон, но не переопределяют его.

## 4. Жизненный цикл задач

В заголовке карточки допускаются только эти статусы:

- **`Открыта`** — задача выдана, исполнение ещё не началось;
- **`В работе`** — есть исполнитель и зафиксирован фактический прогресс;
- **`На приёмке`** — отчёт/результат заявлены, но обязательная приёмка ещё не
  закрыта;
- **`Закрыта`** — в карточке есть отчёт исполнителя, обязательные вердикты
  приёмки и зафиксированные коммиты/результаты;
- **`Заменена`** — работу продолжает другая карточка; причина и её ID обязательны;
- **`Отменена`** — владелец отменил работу; причина обязательна.

`Реализация выполнена`, `Ресёрч выполнен`, `Выдана`, `ждёт приёмки` и
`Фаза 1 — принята` — это описания, но не статусы. Их можно оставить в пояснении
после канонического статуса, но не вместо него.

Переход в `Закрыта` требует минимум: `Отчёт исполнителя`, приёмка независимой
стороной с вердиктом `Достаточно`, второй обязательный вердикт по
`WORK_PROTOCOL.md` и ссылку на коммит/результат. После этого карточка переносится
через `git mv` в `archive/tasks/`; ID не переиспользуется. Незавершённая фаза
остаётся `В работе` или `На приёмке` и получает отдельную карточку/ссылку, а не
маскируется статусом `Закрыта`.

## 5. Имена карточек и устранение дублей

- Имя файла и первый заголовок должны начинаться с одного и того же ID:
  `T-NNN`, `SZ-NNN` или, при нормализации коллизии, `SZ-NNNB`.
- Суффикс `B` — часть ID, а не комментарий к названию. Например,
  `SZ-013B-storefront-search-section.md` и заголовок `# SZ-013B — ...`.
- Активные ID уникальны; ID архивной карточки нельзя занимать снова.
- `SZ-013` сохраняется за привязкой позиции к филиалу, storefront-поиск получает
  `SZ-013B`. `SZ-041` сохраняется за балансами personal/company, банковский
  редизайн получает `SZ-041B`.
- Для `SZ-030`–`SZ-033` ID в заголовках и внутренних ссылках должен совпадать с
  именем файла; старые `SZ-025`–`SZ-028` в этих четырёх карточках не являются
  текущими ID.

## 6. Рабочий цикл агента

1. Классифицируй запрос: канон, производный документ, задача, приёмка, индекс,
   workspace или код в другом репозитории.
2. Найди файл-дом и прочитай текущий срез `STATUS`/`FINDINGS`/`BACKLOG`.
3. Сначала установи или проверь правило; только затем меняй корпус. Не
   архивируй старые карточки по одному слову «выполнено».
4. Правь минимальный набор файлов, обновляй ссылки и индексы в той же серии.
5. В отдельном независимом проходе проверь результат: task/governance-гейт,
   ссылки, статусы, имена и факт-guard. Самопроверка исполнителя не заменяет
   независимую проверку.
6. Обнови `STATUS.md` текущим срезом. `BACKLOG` отражает очередь и решения, а
   не заменяет task-report; `FINDINGS` отражает только находки и их решения.

## 7. Запрещённые действия

- Не редактировать код продуктовых репозиториев из этого checkout вместо работы
  в репозитории из `REGISTRY.md`.
- Не редактировать первоисточник договора Т-Банка и не коммитить секреты.
- Не превращать workspace-документ, chat или session-заметку в канонический
  факт без записи в файл-дом.
- Не использовать `scripts/gen_registry.py`: он deprecated и может перезаписать
  ручной `REGISTRY.md`.
- Не создавать живые markdown-ссылки на `archive/`; для истории достаточно
  текста или inline-кода с пояснением.
- Не выполнять массовое переименование `lovii-docs` ↔ `lovii_docs` без отдельного
  решения о миграции.

## 8. Обязательные локальные проверки

Перед отчётом и перед коммитом запускай из корня репозитория:

```bash
python3 scripts/task_guard.py
python3 scripts/doc-canon-check.py --strict
bash scripts/fact-guard.sh
bash scripts/sync-public.sh --dry-run
git diff --check
```

Красный результат любого структурного гейта требует
исправления или явной записи находки, а не blanket-исключения. После этого
сделай независимый повторный проход и доложи: изменённые файлы, перенесённые
карточки, оставшиеся открытые задачи и результаты всех проверок.
