## 1. Зачем этот устав

Корпус документации вырос до ~35 рабочих документов, и один и тот же факт (комиссия, тариф, сплит, роль, палитра) оказался записан в нескольких файлах. Внешний аудит зафиксировал результат: ~40 расхождений, из них 7 критических, — и это не «случайные ошибки», а математически неизбежное следствие дублирования. Пока число живёт в четырёх местах, рассинхрон — вопрос только времени, а сверка канонов вручную съедает дни работы — человеческой и машинной.

Введём рабочую метрику: **стоимость изменения факта = число файлов, в которых он записан**. Смотрите на FACT_MAP §11 — вы сами это задокументировали: изменение комиссии требует правки 4 файлов, тарифов — 3, ролей — 3. Цель этого устава — довести стоимость изменения любого факта до **ровно одного файла**, а контроль целостности передать машине, а не человеку и не следующему аудиту.

**Главный закон (SSOT — Single Source of Truth):**

> У каждого факта ровно один дом. Все остальные документы ссылаются на дом, а не пересказывают его содержимое.

Следствия из закона:

- Если значение встречается в двух файлах — это **дефект**, даже если значения сегодня совпадают. Совпадение — временное состояние, которое разъедется при первой же правке.
- Рассинхрон ловит **скрипт** (`fact-guard.sh`, §9) при каждом коммите, а не человек «вторые сутки» и не внешний аудит раз в полгода.
- Новый документ появляется **только** через гейт §7 — иначе корпус снова начнёт расти.

## 2. Структура репозитория

### 2.1 Что это за репозиторий

`bestdeejay-design/lovii_docs` — приватный репозиторий документации платформы LOVII.
Checkout называется `lovii_docs`; workspace-алиас `LOVII/lovii-docs` не является
именем GitHub-репозитория. В репозитории живут канон, производные документы,
рабочие task-specs и артефакты. В публичный репозиторий `axiiom-ru/lovii`
(GitHub Pages) при пуше в `main` автоматически попадают четыре файла из
`public/` и корневой `README.md`; `canon/`, задачи и архив не публикуются.
Переименование slug `lovii_docs` в будущий alias `lovii-docs` — отдельная
миграция, не выполняемая этим уставом.

| `public/` | **канон публикации (C)** | 4 публичных документа: `Публичная_оферта.md`, `Оферта_присоединения.md`, `money_flow_public.md`, `Политика_обработки_ПД.md` |

### 2.4 Быстрый старт (локально)

```bash
# 1. Клонировать приватный репозиторий
git clone git@github.com:bestdeejay-design/lovii_docs.git
cd lovii_docs

# 2. Рабочие правки канона — в canon/
# 3. Публикация в публичный репо происходит автоматически при пуше в main
#    (см. DEV_GUIDE.md). Локально проверить решения можно:
bash scripts/sync-public.sh --dry-run
# 4. При F-051 (пуш в приватный репо недоступен) — публикация в рабочее
#    зеркало-хаб lovii-ru/lovii-docs (единственный живой пуш-путь на GitHub):
git remote add mirror git@github.com-lovii-ru:lovii-ru/lovii-docs.git
bash scripts/fact-guard.sh && python3 scripts/task_guard.py && python3 scripts/doc-canon-check.py --strict
git push mirror main
#    При возврате доступа догнать origin: git pull mirror main && git push origin main
```

### 2.5 Рабочие правила (топ-6)

1. **Канон правится в `canon/`.** Только файлы из `public/` и `README.md` попадают в публичный репо.
2. **Публичные документы — в `public/`.** Они заморожены (класс C) и обновляются только при изменении внешних условий.
3. **Источник истины по комиссиям** — договор Т-Банка (класс C). Не редактировать.
4. **Версия канона важна.** Скрипт публикации сравнивает версию в источнике с опубликованной: выше — публикуем как есть, равна и тело изменилось — авто-бамп, ниже — защита от понижения (пропуск).
5. **Не пушь вручную в `axiiom-ru/lovii`.** Публикация — только через `sync-public.sh` из `lovii_docs`.
6. **Меняя состав или статус — обнови `REFERENCE.md` и `REGISTRY.md`.**
   `.omo/doc-manifest.json` локальный/игнорируемый и в свежем клоне может
   отсутствовать; не запускай deprecated `scripts/gen_registry.py`.

## 3. Классы документов и рабочих артефактов

Каждый документ корпуса принадлежит одному классу. Класс определяет, можно ли
в нём хранить факты и как его править. `canon/TASKS/` физически находится в
`canon/`, но относится к отдельному рабочему классу W, а не к канону фактов.

| Класс | Что это | Может содержать факты? | Как правится | Примеры |
|---|---|---|:---:|---|
| **A. Канон-источник** | единственный дом фактов своего домена (§4) | да — это его работа | по протоколу §6 | `PARAMS.md`, `BRD.md`, `DATA_MODEL.md`, `DESIGN.md` |
| **B. Производный** | нарратив, гайды, карты, спецификации | **нет** — только ссылки на канон | свободно, но без значений | `VISION.md`, `PRD.md`, `ARCHITECTURE.md`, `SCREEN_MAP.md`, `FACT_MAP.md` |
| **C. Артефакт (заморожен)** | внешние/юридические/подписанные документы | да, но это снепшот внешнего мира | только при изменении внешних условий; новой версией файла | 4 файла `public/`, договор Т-Банк, анкета, чеки, презентации |
| **D. Архив** | устаревшие версии, дубли и закрытые карточки | никогда | никто; при помещении — баннер §10.3 | `archive/*` |
| **W. Рабочий артефакт** | постановка, отчёт, приёмка, session/workspace-оперативка | может цитировать факт со ссылкой, но не переопределяет его | по `WORK_PROTOCOL.md`; после закрытия — архив | `canon/TASKS/`, `docs/sessions/`, workspace |

Правила классов:

- **Класс A:** изменение факта выполняется только здесь. Каждому канону — строка в карте §4 и поле «Канон для:» в шапке (§10.1).
- **Класс B:** хранит ссылки вида «канон: `PARAMS.md` §1.1». При конфликте с каноном производный файл чинится **удалением копии** (замена на ссылку), а не правкой числа под канон — правленая копия устареет снова.
- **Класс C:** самодостаточен по требованиям внешнего мира (юристы, банк, публикация). Наша иерархия его только читает. Обновление — правкой на месте для публикуемых документов либо новой версией для подписанных документов.
- **Класс D:** в первой строке — баннер устаревания §10.3. Живые Markdown-ссылки на архивные файлы запрещены.
- **Класс W:** хранит ход работы, а не новый источник истины. Отчёт исполнителя и приёмка остаются в карточке; общий итог коротко отражается в `STATUS.md`. Для task-specs структурный гейт — `scripts/task_guard.py`.

Правила чтения карты:

1. Производный документ, содержащий **значение** из домена N — дефект, ловится `fact-guard.sh` (§9).
2. Появился **новый тип факта** (новый домен) — сначала строка в этой карте, потом файл. Порядок обратный — запрещён.
3. Карта канона — часть `DOCS_GUIDELINES.md`; изменения карты — отдельный коммит с пометкой владельца.
4. Карточка задачи не может переопределить дом факта. Она хранит постановку,
   отчёт и приёмку; общий срез и очередь ссылаются на неё.
5. `STATUS`, `FINDINGS`, `BACKLOG` и workspace не взаимозаменяемы: каждый
   используется только для назначения из таблицы маршрутизации.

## 5. Правило ссылок и white-list

### 5.1 Два допустимых вида упоминания факта

**Вид 1 — жёсткая ссылка (по умолчанию, для всех производных документов):**

> Нагрузка на точку фиксируется в каноне параметров — `PARAMS.md` §1.1.

Числа в тексте нет. Значение не может устареть, потому что его нет.

**Вид 2 — копия с якорем (только для файлов из white-list карты §4):**

> Нагрузка на точку — 10% *(канон: `PARAMS.md` §1.1)*

Число есть, но рядом — явный якорь на дом. Это привилегия, а не право: white-list закрыт, расширяется только решением владельца отдельным коммитом.

**Запрещённый вид (то, что породило 40 находок аудита):** число без якоря — «Комиссия платформы 10%…» посреди нарратива. Это неуправляемая копия.

### 5.2 Правила white-list

1. White-list каждого домена перечислен в карте §4 и зашит в `scripts/fact-guard.sh` (§9). Всё, что вне списка, при коммите падает CI.
2. Файл из white-list обязан нести якорь канона рядом с каждым скопированным значением (Вид 2).
3. При изменении факта в каноне версии `minor` и выше — white-list-копии обновляются **в том же коммите** (см. §6, шаг 4). Сегодня таких файлов максимум два — это приемлемая ручная работа, зафиксированная явно.
4. Цель — **сокращать** white-list. Добавление файла в white-list = осознанное решение владельца с обоснованием в коммит-сообщении.

### 5.3 Ограничение честности

Некоторые файлы **обязаны** содержать значения: машиночитаемый контракт
(`openapi.yaml`), тест-кейсы, публичный лендинг (`README.md`) и публичные
документы. Устав не запрещает это — он делает список таких мест явным,
закрытым и проверяемым машиной. Task-specs в `canon/TASKS/` могут цитировать
числовые критерии для исполнения, но это рабочие артефакты: их структура и
статусы проверяются `task_guard.py`, а источник каждого факта должен быть
указан в карточке. Они не расширяют white-list канона.

## 6. Протокол изменения факта

Триггер: любое изменение домена из карты §4 — новая комиссия, тариф, порог, роль, домен, токен, срок.

```text
Шаг 1. Открой карту канона (§4) → найди файл-дом → правь ТОЛЬКО там.
Шаг 2. Подними версию файла-дома (patch/minor/major — правила AGENT.md, Фаза 4).
Шаг 3. Прогони fact-guard:  bash scripts/fact-guard.sh
        Красный вывод = где-то осталась копия старого/нового значения.
        Копия сносится (замена ссылкой, Вид 1), НЕ правится под новое значение.
Шаг 4. Если домен имеет white-list-исключения (README, money_flow_public) —
        обнови их в том же коммите.
Шаг 5. Обнови карточку файла в REFERENCE.md §4, если менялась структура.
Шаг 6. Один коммит:  docs: <домен>: суть (канон + производные)
```

Чего в протоколе **нет**: обхода производных файлов с правкой чисел. Если хочется «обновить число в PRD» — стоп. В PRD числа быть не должно: правьте ссылку, а если значение там действительно необходимо — оформите white-list-исключение осознанно, через владельца.

## 7. Гейт создания нового документа

Страх «дальше будет больше доков» закрывается гейтом: новый `.md` создаётся только после семи вопросов. Если на любой вопрос нет ответа — файл не создаётся.

| # | Вопрос | Проверка |
|---|---|---|
| 1 | Какой **единственный** вопрос отвечает новый документ? | Сформулировать в заголовке файла |
| 2 | Уже есть документ с этим вопросом? | Поиск по `REFERENCE.md` §4. Есть → правим существующий, не создаём новый |
| 3 | Его класс? | §3. Класс A требует новой строки в карте §4 |
| 4 | Какие факты он будет содержать? | Только своего домена или ссылки; task-spec может цитировать критерий, но указывает источник и не становится домом (§3/W) |
| 5 | Что он поглощает? | Правило «1 вход — 1 выход» (ниже) |
| 6 | Карточка добавлена? | `REFERENCE.md` §4 + `REGISTRY.md`/манифест, если меняется состав |
| 7 | Шапка по шаблону? | §10.1 |

**Правило «1 вход — 1 выход»:** число живых канонических и производных
документов в `canon/` не растёт без поглощения или архивации существующего.
`canon/TASKS/` — рабочий каталог W и не входит в счётчик документов. Текущий
счётчик и исключения ведёт `STATUS.md`; фиксированное старое число из
исторической консолидации не является целью.

> **Исключения состава:** `canon/FINDINGS.md`, `canon/WORK_PROTOCOL.md`,
> `canon/MINI_APPS_RESEARCH.md` и `canon/PUSH_NOTIFICATIONS_SPEC.md` уже
> существуют как отдельные документы по решениям владельца. Это не разрешение
> создавать новые дубли: перед новым документом всё равно проходят семь
> вопросов и правило «1 вход — 1 выход».

**Нейминг:** канон и производные документы используют понятные стабильные
имена без дат и версий; публичные юридические документы сохраняют русские
имена. Карточка задачи называется `T-NNN-<slug>.md`, `SZ-NNN-<slug>.md` или
`SZ-NNNB-<slug>.md` при нормализации дубля; первый H1 обязан повторять тот же
ID. ID не переиспользуются после архивации.

### 7.1 Гейт task-spec

Новая карточка создаётся только после проверки:

1. ID отсутствует среди активных и архивных карточек;
2. направление (`T-*` или `SZ-*`), исполнитель и целевой репозиторий понятны;
3. файл-дом канонических фактов указан, а рабочая карточка не объявляет себя
   этим домом;
4. есть стоп-лист, проверяемые критерии и план отчёта;
5. в `STATUS`/`BACKLOG` добавляется короткая ссылка без копирования отчёта;
6. после создания проходят `python3 scripts/task_guard.py` и link-check.

При коллизии ID выбирается сохранённая карточка только по явному решению;
вторая получает новый суффикс-ID, а все ссылки и заголовок обновляются в одной
серии.

## 8. Порядок уборки и изменения корпуса

Уборка выполняется только после согласования правил, а затем отдельным
проходом проверяется другим агентом. Не считать старые карточки актуальными
только по их возрасту или словам «выполнено».

1. Зафиксировать маршрутизацию и имена в `AGENTS.md`, этом уставе,
   `canon/AGENT.md` и `canon/WORK_PROTOCOL.md`.
2. Провести структурную проверку task-specs: ID, H1, статусы, дубли,
   обязательные отчёт/приёмку и ссылки. Для нормализации дубля использовать
   новый ID с суффиксом `B`, не переиспользовать старый ID.
3. Исправить пути и индексы (`STATUS`, `BACKLOG`, `REFERENCE`, `TASKS/README`),
   не превращая историческую запись в живую задачу.
4. Переносить в `archive/tasks/` только карточки, для которых в самой карточке
   есть обязательные основания закрытия. В текущем проходе это только
   бесспорно закрытые `T-005`, `T-006`, `T-007`.
5. Добавить архивный баннер и запрет живых ссылок на архив.
6. Выполнить `task_guard`, `doc-canon-check`, `fact-guard`, dry-run публикации,
   затем повторить весь набор в независимом проходе и обновить `STATUS`.

Это не разрешение на механическую архивацию остальных карточек. Каждая новая
архивация требует отдельного подтверждаемого отчёта и приёмки.

## 9. Автоматизация: fact-guard и CI

### 9.1 Скрипты проверок

- `scripts/fact-guard.sh` ловит копии канонических числовых параметров вне
  закрытого white-list. Каталог `canon/TASKS/` намеренно не сканируется этим
  guard: task-spec обязан цитировать критерий, но не является домом факта;
  его ID, статусы и ссылки проверяет `scripts/task_guard.py`.
- Строковое исключение `<!-- fact-guard: allow -->` допускается только рядом с
  конкретным white-list-значением и объяснением. File-level blanket-allow для
  корпуса запрещён.
- `scripts/doc-canon-check.py --strict` проверяет старые факты, версии и
  битые относительные ссылки на `.md`. Историческая строка может получить
  точный inline-маркер `doc-canon: historical`; общий пропуск корпуса запрещён.
- `scripts/task_guard.py` проверяет соответствие ID filename/H1, уникальность
  активных и архивных IDs, статусы, баннеры и живые ссылки на архив.

Exit 1 любого из этих гейтов означает, что результат не принят. Список не
считается «нормой на будущее»: его исправляют, либо оформляют узкое
документированное исключение с источником и причиной.

### 9.2 CI-задание

Workflow `.github/workflows/fact-guard.yml` запускает все три проверки на
изменениях корпуса и скриптов:

```yaml
- run: python3 scripts/task_guard.py
- run: python3 scripts/doc-canon-check.py --strict
- run: bash scripts/fact-guard.sh
```

### 9.3 Проверка ссылок

`doc-canon-check.py --strict` проверяет относительные ссылки на `.md`, а
`task_guard.py` дополнительно запрещает живые Markdown-ссылки на `archive/`.
Ссылки на активные карточки допустимы и должны вести на существующий файл.

## 10. Шаблоны и терминология

### 10.1 Шапка документа

Канон (класс A):

```markdown
# <ИМЯ>.md — <вопрос документа>

**Версия:** x.y.z
**Дата:** YYYY-MM-DD
**Статус:** Канон — источник истины по <домен из карты §4>
**Канон для:** <перечень доменов>
**Владелец:** <роль>
```

Производный (класс B):

```markdown
# <ИМЯ>.md — <вопрос документа>

**Дата сверки:** YYYY-MM-DD
**Статус:** Производный — значений не хранит
**Источники истины:** `PARAMS.md`, `BRD.md`
```

### 10.2 Терминология (канон — `PARAMS.md` §Термины)

| Пишем | Не пишем | Комментарий |
|---|---|---|
| **МСП (точка)** | «Партнёр», «партнёр-точка» в тех-доках | Аудит: дрейф «Партнёр» vs «МСП/ТСП». Финальное слово за владельцем — но ровно одно написание |
| **LOVII** / платформа LOVII | «Лови 2.0», «Платформа Лови» в живых доках | «Лови 2.0» — история из чатов |
| **АО «Т-Банк»** | «Тинькофф», «Т-Банк» без формы | |
| **ООО «АКСИОМА»** | «АО „Аксиома“» | Как в договоре |
| **Компания** | «платформа», «LOVII» в контексте сплитов | В сплитах «Компания» = LOVII (ООО «АКСИОМА») |
| **Представитель / Мэр / Губернатор / Амбассадор** | «цифровой мэр», «региональный менеджер» | Лестница v2; «цифровые мэры» — только в цитатах PDF |
| **2 990 ₽/мес**, **6,84%** | «2990р», «6.84%» в русском тексте | Единицы всегда; запятая в русском тексте, точка — в JSON/коде |

### 10.3 Баннеры

Архив (класс D, первой строкой файла):

```markdown
> ⚠️ **АРХИВ.** Карточка закрыта и не является текущим источником требований; сохранена только для истории.
```

Замороженный артефакт (класс C, первой строкой файла):

```markdown
> 🔒 ВНЕШНИЙ АРТЕФАКТ (класс C). Подписан/опубликован. Не редактировать; обновление — новой версией файла.
```

## 11. Связь с инструкциями агентов

Корневой `AGENTS.md` — обязательный router и не дублирует этот устав.
`canon/AGENT.md` описывает операционные режимы, проверки и коммит-гейт.
`canon/WORK_PROTOCOL.md` описывает роли, task-specs, приёмку и архивирование.
Если агент обнаружил противоречие между этими документами, он сначала
фиксирует его в `canon/FINDINGS.md`, а не выбирает удобную формулировку молча.

Короткий `CLAUDE.md` существует только как указатель на корневой `AGENTS.md`.
