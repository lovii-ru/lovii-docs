## Назначение

Партнёр сам задаёт кэшбэк магазину (процент по умолчанию) и выделяет группы товаров своим процентом.
Сегодня в `lovii-core` правило глобальное (`LoyaltyService` берёт `first()` из активных), партнёр им не управляет.

## 2. Цель конструктора (MVP, «самое простое»)

Две настраиваемые сущности на стороне партнёра:

1. **Кэшбэк по умолчанию** — один процент на магазин (мерчант).
2. **Группы товаров** — именованные наборы, каждому свой процент (переопределяет умолчание).

Всё остальное (сегменты клиентов, уровни, акции по расписанию) — фазы 2–3.

## 3. Модель данных (миграции в `lovii-core`, схема `public`)

### 3.1 Расширение `loyalty_rules`

| Поле | Тип | Смысл |
|---|---|---|
| `merchant_id` | bigint NULL, FK → merchants | NULL = платформенное правило (глобальное) |
| `group_id` | bigint NULL, FK → loyalty_product_groups | NULL = правило «весь магазин» (умолчание) |
| `priority` | smallint, default 0 | разрешение пересечений (выше = приоритетнее) |

`name`, `earn_percent`, `max_spend_percent`, `is_active`, `starts_at`, `ends_at` — **без изменений** (контракт `LoyaltyService` сохраняется).

Партиальный unique-индекс: одно активное правило «по умолчанию» на мерчанта —
`UNIQUE (merchant_id) WHERE group_id IS NULL AND is_active`.

### 3.2 `loyalty_product_groups`

| Поле | Тип |
|---|---|
| `id` | bigint PK |
| `merchant_id` | bigint FK → merchants (NOT NULL) |
| `name` | string |
| `is_active` | bool, default true |
| `sort_order` | smallint, default 0 |
| `timestamps` | |

### 3.3 Состав группы — два пивота (FK-целостность вместо полиморфизма)

- `loyalty_group_categories` — `group_id` FK, `catalog_category_id` FK, unique(group_id, category_id)
- `loyalty_group_products` — `group_id` FK, `catalog_product_id` FK, unique(group_id, product_id)

Индексы под обратный матчинг при оформлении заказа: `(catalog_category_id)`, `(catalog_product_id)`.

> Альтернатива — одна полиморфная таблица `target_type/target_id`. Отклонено: без FK на цель; чистка «висячих» ссылок ложится на приложение. При FK-пивотах целостность держит БД.

## 4. Алгоритм начисления (замена линейного правила)

Резолвинг — **один раз на заказ**, без N+1 в request path (требование `AGENTS.md`, страж SZ-060):

1. **1 запрос** — активные правила мерчанта + платформенное:
   `loyalty_rules WHERE is_active AND (merchant_id = M OR merchant_id IS NULL) AND окно дат`.
2. **2 запроса** — карты состава групп мерчанта: категория → группа, товар → группа.
3. Для каждой позиции: группа = **товар**, иначе **категория**, иначе `null`.
   Процент = правило этой группы → правило «по умолчанию» мерчанта → платформенное → 0.
4. `earned = Σ round(item.total_price * pct / 100)`, пишется в `orders.bonus_earned`.
5. Идемпотентность и возвраты — **не трогаем**: контракт `wallet_transactions (wallet_id, order_id, type)` остаётся.

Приоритет разрешения (при пересечениях): `товар > категория > умолчание магазина > платформенное`.

`validateSpend` (потолок списания) берёт `max_spend_percent` из правила «по умолчанию» мерчанта, фолбэк — платформенное. Потолок списания задаёт **платформа**, не партнёр.

## 5. UX кабинета — mobile-first

Новая группа навигации `NavigationGroup::Loyalty` («Лояльность») в `lovii-b2b` и **страница-конструктор**, а не таблица CRUD:

- **Кэшбэк по умолчанию** — процент (слайдер + инпут), тумблер, период.
- **Группы товаров** — список; у каждой: имя, %, счётчик товаров, тумблер. Внутри: имя, %, пикер категорий (переиспользуем существующий `CategoryTreeSelect`) и пикер товаров.
- **Предпросмотр покупателя** — карточка товара с бейджем «Кэшбэк N%».
- **Стоимость программы** — честная оценка: при обороте X, % Y → расход из доли точки + комиссия 25%. Без выдуманных цифр (требование `PRODUCT_QUALITY_BAR` §1).

Мобильные требования (`PRODUCT_QUALITY_BAR` §1): mobile-first 390px+, тап-таргеты ≥44px, три состояния (загрузка/пусто/ошибка), липкая кнопка сохранения, без широких таблиц (стек вместо grid).

Переключение между магазинами партнёра — по существующему паттерну табов (`ListCategories::getTabs`).

## 6. Что видит покупатель

**Фаза 1 (без изменений app):** начисление уже видно в ленте баллов (`wallet/transactions`, комментарий «Кэшбэк за заказ №N»). Расширяем комментарий именем правила для прозрачности.

**Фаза 2 (app):** в каталоге/карточке товара — поле `cashback_percent` из API и бейдж «Кэшбэк N%»; в чекауте — «Начислим N баллов».

## 7. Guardrails платформы

- Потолок `earn_percent` — в настройках админки (рядом с `PlatformOrderSetting` / `payment_settings`); партнёр не может его превысить.
- `max_spend_percent` — фиксирует платформа.
- Предупреждение о пересечении групп (какой процент применится) до сохранения.
- Кэшбэк финансирует точка → показываем прогноз стоимости.

## 8. Тесты и гейты

- **core:** unit на резолвинг (приоритеты, пересечения, окна дат, фолбэки, пустые группы), идемпотентность earn/refund сохраняется.
- **b2b:** cross-tenant regression — партнёр A не видит/не правит группы и правила мерчантов партнёра B (обязателен по докстрингу `ScopedToCurrentPartnerViaMerchant`).
- Гейты: `docker exec lovii-core-app-1 composer test`, `docker exec lovii-b2b-app-1 composer test`.
- Проверка на данных: заказ по товару из группы и вне её → корректная сумма `bonus_earned`.
