## 2. Инварианты (нарушение = баг с приоритетом P0)

1. Все деньги — целые копейки (`*_minor`), баллы — целые; округление только `floor`; никаких float в расчётах.
2. `paid_money + points_redeemed × 100 + Σ discounts == gross_total` для каждого чека.
3. Суммарная скидка класса «цена» ≤ `max_total_discount_pct` от `gross_total`; суммарный merchant-кэшбэк ≤ `max_merchant_cashback_pct` от базы.
4. Движок детерминирован: `quote(campaigns, context, state, now)` без обращений к часам/ГСЧ; случайность — из `sha256(order_id:campaign_id)`.
5. `commit` идемпотентен по `order_id`; повтор возвращает тот же результат с `idempotent: true` без побочных эффектов.
6. Каждое начисление/списание — проводка в `ledger_entries` с уникальным `idempotency_key`; `Σ point_lots.amount_left == баланс`.
7. Опубликованная версия кампании неизменяема; правки создают новую версию.
8. Клиент в holdout не получает ни применения, ни отображения кампании.
9. Клиент никогда не видит причины `skipped` внутренних ограничений (holdout, бюджет) — только нейтральные формулировки из [06 §4](06-ui-spec.md).
10. Ни один вызов Runtime API не блокирует оплату при недоступности Loyalty (деградация — [08 §6](08-integrations.md)).

## 3. Как добавить или изменить механику

1. Прочитай раздел LM-NN в [02](02-mechanics-catalog.md); если требуется новое действие/поле условия — сначала PR в `campaign.schema.json` + [03](03-rules-engine.md) (+ `engine.js` и golden-кейсы), затем реализация.
2. Создай шаблон `templates/lm-NN-<mechanic>`: `params_schema` (JSON Schema, поля с `title`/`description` на русском — из них генерируется форма мастера), `defaults(ctx)`, `compile(params) → Spec`, `estimate(params, stats)`, `preview(params)`.
3. Добавь пример `examples/campaigns/lm-NN-<name>.json` и ≥ 3 golden-кейса `examples/testcases/lm-NN-*.json` (позитивный, ограничение/лимит, стекинг с другой механикой).
4. Убедись, что `compile(defaults)` проходит валидатор Spec и golden-раннер.
5. Обнови таблицу тарифов и приоритетов в [02 §1](02-mechanics-catalog.md), если менялись.

## 4. Соглашения

- Язык кода — по стеку проекта; язык всех пользовательских текстов, комментариев в Spec (`content.*`) и документов — русский. Идентификаторы (поля Spec, коды ошибок, события) — английские, как в контрактах.
- Коды ошибок — только из [05 §6](05-api.md); новые — добавлять туда и в `openapi.yaml`.
- Тайм-зона — локации (`schedule.timezone`), не сервера и не клиента.
- Никаких ПДн в логах и событиях; `customer_id` — псевдоним.
- Форматы вывода в интерфейсе: `1 250 ₽`, `+60 баллов`, `−15 %` (неразрывные пробелы, типографские знаки) — см. [06 §4.5](06-ui-spec.md).
- Тесты называются по ID задачи: `E1-T4_bundle_cheapest_free`.

## 5. Как проверять себя

```bash
# Валидность контрактов
node -e "JSON.parse(require('fs').readFileSync('schema/campaign.schema.json'))"
npx --yes @redocly/cli lint schema/openapi.yaml            # или swagger-cli validate
psql -f schema/schema.sql                                   # на пустой БД

# Примеры кампаний против схемы (любой валидатор JSON Schema 2020-12)
npx --yes ajv-cli validate -s schema/campaign.schema.json -d "examples/campaigns/*.json" --spec=draft2020

# Golden-кейсы на референсном движке
node examples/run-golden.mjs
```

Целевая реализация обязана выдавать те же результаты на golden-кейсах (сравнение по канонизированному JSON без `quote_id`, `expires_at`, `spec_hash`).

## 6. Чего не делать

- Не добавлять механику как «особый случай» в конвейер — только через Spec-действия и шаблон.
- Не хранить вычисленные скидки в каталоге товаров; цены на витрине — всегда «цена + бейдж», расчёт в quote.
- Не менять поведение округления/порядка стекинга без обновления golden-кейсов и раздела [03 §5](03-rules-engine.md).
- Не показывать ТСП персональные данные клиентов сверх маскированного телефона.
- Не отправлять уведомления напрямую — только события `notify` в подсистему уведомлений.
- Не использовать `Math.random`/`now()` внутри движка.
