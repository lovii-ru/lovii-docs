        Статус: черновик 1.0 для реализации · Дата: сентябрь 2026 · Владелец: продукт LOVII (ООО «Аксиома»)

        Конструктор лояльности — модуль платформы LOVII, который позволяет микро- и малому бизнесу (ТСП) за 5 минут с телефона включить проверенные механики роста продаж: порог чека «до подарка осталось…», конструктор кэшбэка, штампы N+1, счастливые часы, промокоды, реферал, возврат уснувших клиентов и другие — с расчётом на кассе через QR-оплату LOVII, честной оценкой эффекта (holdout-группа) и понятной стоимостью.

        Пакет написан так, чтобы ИИ-агенты могли реализовать решение без дополнительных уточнений: продуктовые требования + формальные контракты (JSON Schema правил, OpenAPI, DDL PostgreSQL) + примеры кампаний + golden-тесты + референсный движок + план задач.

        Стек

        Контракты стек-агностичны. Рекомендации, согласованные с существующей платформой LOVII (см. docs/SRS-main/SRS-v2.md):

        Слой Рекомендация Обязательно
        Движок правил Чистый модуль без I/O (TypeScript/Go/Python/Java — по стеку платформы) детерминизм, golden-тесты
        Хранилище PostgreSQL 15+ (schema.sql), Redis для кэша активных кампаний и счётчиков транзакционный леджер
        API REST по openapi.yaml; события — Kafka/NATS/Redis Streams через outbox идемпотентность, HMAC вебхуки
        Кабинет ТСП и клиент Vanilla JS PWA в стиле текущего приложения LOVII (hash-роутинг, дизайн-токены 06 §1) a11y AA, RU
        Аналитика Дневные агрегаты в PostgreSQL; события в аналитическое хранилище без ПДн holdout

        Ключевые решения (кратко)

        • Одна модель для всех механик. Каждая механика — шаблон, который компилируется в декларативную Spec (trigger → conditions → actions + schedule, audience, limits, stacking). Движок не знает про «штампы» или «кэшбэк» как особые случаи.
        • Два класса эффектов. «Цена» (скидки, подарки, абонементы) применяется до оплаты; «награда» (баллы, штампы, купоны) — после, на базе оплаченных денег. Порядок и стекинг фиксированы (03 §5).
        • Баллы — лоты. Промо-баллы ТСП живут в лотах со сроком и источником финансирования; базовые баллы платформы не сгорают. Списание — FIFO: сначала промо ТСП, потом остальные, потом базовые.
        • Честная аналитика. 10 % клиентов — контрольная группа; эффект = разница с контролем; стоимость показывается всегда.
        • MVP = 9 механик (LM-01, 03, 04, 05, 06, 10, 11, 13, 14) через QR-оплату без кассовой интеграции; кассы, наборы, уровни, абонементы, челленджи, кросс-промо, день рождения, розыгрыши, сертификаты, отзывы — V2.

        Статус: Draft v1.0 · Дата: 2026-09-22 · Владелец: продукт LOVII (ООО «Аксиома») Часть пакета docs/lovii-loyalty-constructor/ — см. README

        1. Зачем

        LOVII — SaaS-инфраструктура локальной экономики для микро- и малого бизнеса (ТСП): цифровая витрина района, кошелёк LOVII PAY (1 балл = 1 ₽), оплата по QR, базовый кэшбэк баллами у всех точек, роли «Торговая точка / Представитель / Амбасадор».

        Сегодня платформа даёт ТСП единую программу лояльности (базовый кэшбэк, статусы PAY / PASS / VIP, «спец-скидки у МСП», «Приведи друга»). Но у владельца кофейни, пекарни или салона нет инструмента, чтобы самому управлять стимулами: поднять чек, вернуть «уснувших» клиентов, разогнать частоту визитов, продвинуть новый товар.

        Конструктор лояльности — модуль кабинета «ЛОВИ Бизнес», в котором ТСП за 5 минут без программиста собирает из готовых механик собственные акции поверх базовой программы LOVII, а платформа исполняет их на кассе/в QR-оплате, показывает клиентам в приложении и считает эффект.

        1.1 Продуктовая гипотеза

        Если дать ТСП 3–5 проверенных механик с шаблонами «в один клик», подсказками и честной аналитикой эффекта, то средний чек у активных точек вырастет на 8–15 %, частота визитов — на 10–20 %, а доля ТСП на тарифе PRO — до 30 % (цель зрелой локации из стратегии LOVII).

        1.2 Как это связано с экономикой LOVII

        Элемент LOVII Роль в конструкторе
        Базовый кэшбэк (2,5–5 % от чека, финансируется из комиссии платформы) Не настраивается ТСП. Конструктор работает поверх него
        Баллы 1:1, «баллы не сгорают» Базовые баллы бессрочны. Промо-баллы ТСП (бонусы кампаний) могут иметь срок — отдельные «лоты» в кошельке
        Счёт LOVII BUSINESS Источник финансирования всех стимулов ТСП (повышенный кэшбэк, скидки, подарки) — списывается при коммите чека
        Статусы PAY / PASS / VIP Доступны как аудитория кампаний («особый % для VIP»)
        Гео-изоляция локаций Кампании и аналитика живут внутри локации; кросс-промо — только между точками одного района
        SaaS PRO (2 990 ₽/мес) Расширенные механики и аналитика — драйвер апселла тарифа
        Роль «Представитель» Помогает ТСП настроить первую кампанию; видит эффект по своим точкам

        2.2 Jobs-to-be-Done ТСП

        1. Увеличить чек: «Когда клиент уже покупает, я хочу подтолкнуть его добавить ещё позицию, чтобы вырос средний чек без потери маржи».
        2. Увеличить частоту: «Хочу, чтобы клиент возвращался чаще и предпочитал меня соседям».
        3. Привлечь новых: «Хочу, чтобы существующие клиенты приводили друзей, а соседние точки — своих клиентов ко мне».
        4. Вернуть уснувших: «Хочу автоматически напоминать о себе тем, кто пропал».
        5. Распродать/продвинуть: «Хочу быстро продвинуть конкретный товар/время (вечер, будни)».
        6. Понимать эффект: «Хочу видеть в рублях, что акция принесла и сколько стоила».

        3. Цели и метрики продукта

        3.1 North Star

        Инкрементальная выручка ТСП, созданная кампаниями конструктора (₽/мес по локации), при стоимости стимулов ≤ 35 % от инкремента.

        3.2 Метрики успеха (пилот 3 локации, 90 дней)

        Метрика База Цель пилота
        Доля ТСП с ≥ 1 активной кампанией 0 % ≥ 60 %
        Время создания первой кампании (медиана) — ≤ 5 мин
        Средний чек у ТСП с механиками «чек ↑» x +8–15 %
        Частота визитов клиентов-участников (30 дней) y +10–20 %
        Возврат «уснувших» (win-back, 30 дней после триггера) ~3 % ≥ 10 %
        Доля ТСП на PRO — ≥ 20 % среди пользователей конструктора
        Стоимость стимулов / инкрементальная выручка — ≤ 35 %
        NPS ТСП по модулю — ≥ 40

        4. Принципы продукта

        1. Шаблон вместо конструктора «с нуля». Пользователь выбирает цель («Поднять чек»), получает 2–3 готовые механики с предзаполненными параметрами под свою категорию бизнеса и правит 1–3 поля.
        2. Честная экономика на экране. Каждая настройка показывает прогноз стоимости («≈ 4 200 ₽/мес при текущем трафике») и подсказку «безопасной» зоны параметров по марже.
        3. Одна модель — много механик. Все механики компилируются в единую спецификацию кампании (DSL), исполняемую одним движком. Новая механика = новый шаблон + тесты, а не новый код в кассе.
        4. Клиенту понятно за 2 секунды. Любая акция сводится к одной строке + прогресс-бару: «До бесплатного кофе — 2 штампа», «До подарка — 150 ₽».
        5. Детерминизм и аудит. Одинаковый чек + одинаковые кампании = одинаковый результат. Каждый применённый стимул привязан к версии кампании.
        6. Мобильно-первый. Кабинет ТСП используется с телефона за стойкой; всё — в стиле текущей PWA LOVII.
        7. Не ломаем базу LOVII. Базовый кэшбэк, статусы и кошелёк — платформенные; конструктор добавляет, а не переопределяет.

        5. Границы (Scope)

        5.1 В объёме (MVP → V2)

        • Каталог механик (16 шт., приоритизация в 02-mechanics-catalog.md).
        • Движок правил (quote / commit / reverse), леджер промо-баллов с лотами и сроком.
        • Кабинет ТСП: галерея механик, мастер настройки, предпросмотр, список кампаний, аналитика.
        • Клиентские поверхности в приложении LOVII: бейджи на витрине, прогресс на экране оплаты, штампы, купоны, «Акции рядом».
        • Экран кассира (QR/POS): применённые стимулы + подсказка апселла.
        • События и вебхуки для внешних касс и уведомлений.
        • Аналитика с контрольной группой (holdout).

        5.2 Вне объёма (сейчас)

        • Изменение базовой экономики баллов LOVII (ставка платформенного кэшбэка, вывод на карту).
        • Полноценная CDP/CRM с произвольными рассылками (используем существующий канал push/e-mail с согласием).
        • Программы лояльности федеральных сетей и коалиции вне района.
        • Учёт и налоговый учёт ТСП (только экспорт данных).

        6. Глоссарий

        Термин Определение
        ТСП / Точка Торгово-сервисное предприятие, подключённое к LOVII (кофейня, салон, магазин…)
        Локация / Район Гео-изолированная единица платформы (напр., «Тверской»). Кампании не пересекают границы локации
        Клиент Пользователь приложения LOVII с кошельком LOVII PAY
        Балл Единица кошелька, 1 балл = 1 ₽. Базовые — от платформы, бессрочные. Промо — от ТСП по кампании, могут иметь срок
        Лот Порция баллов с общим источником и сроком действия; списываются FIFO по сроку
        Механика Тип стимула (кэшбэк, штампы, порог чека…), описанный шаблоном с параметрами
        Кампания Настроенный экземпляр механики у конкретного ТСП со сроком, аудиторией, лимитами и бюджетом
        Спецификация (Spec) JSON-описание кампании в едином DSL (schema/campaign.schema.json)
        Версия кампании Неизменяемый снимок Spec; любое изменение опубликованной кампании создаёт новую версию
        Quote Предварительный расчёт стимулов для корзины без списаний (предпросмотр на кассе/в приложении)
        Commit Фиксация стимулов после успешной оплаты (идемпотентно по order_id)
        Reverse Откат стимулов при возврате/отмене (полный или частичный)
        Стекинг Правила совместного применения нескольких кампаний к одному чеку
        Holdout Контрольная группа клиентов, к которым кампания не применяется, для оценки инкремента
        Финансирование (funding) Источник стоимости стимула: platform (базовый кэшбэк) или merchant (счёт LOVII BUSINESS)
        Статус Уровень клиента в платформе: PAY / PASS / VIP (платформенный)
        Уровень (tier) Уровень клиента у конкретного ТСП (механика LM-07, задаётся точкой)

        LM-01 · Порог чека («До подарка осталось …»)

        Цель: средний чек ↑ · Приоритет: MVP · Сложность: S · Тариф: Free

        Суть. При сумме чека от порога X клиент получает награду: промо-баллы, скидку, подарок-товар. Главное — не сама награда, а прогресс-бар «до подарка осталось 150 ₽» на витрине, в корзине и на кассе. Работает на психологии «почти достиг» (goal-gradient).

        Как видит клиент. В карточке точки: бейдж «От 500 ₽ — +100 баллов». В корзине / на экране QR-оплаты: полоса прогресса и подсказка «Добавьте круассан 164 ₽ — и получите +100 баллов». После оплаты: «+100 промо-баллов до 29.09».

        Параметры ТСП.

        Параметр Тип По умолчанию Безопасный диапазон Подсказка
        Порог threshold ₽ 1,3 × средний чек точки 1,2–1,6 × средний чек «Ваш средний чек 320 ₽ — ставим 450 ₽»
        Тип награды reward.type enum points points / discount / free_item Баллы дешевле скидки: часть не потратят
        Размер награды ₽ или % 10–15 % от порога ≤ 20 % порога Показать прогноз стоимости
        Срок промо-баллов ttl_days дни 14 7–30 Короткий срок = быстрее вернётся
        Многоступенчатость steps[] список 1 ступень до 3 «500 → +50, 1000 → +150»
        Учитывать скидки bool после скидок — Порог считается по сумме к оплате деньгами

        Пример. Кофейня «Daily», средний чек 320 ₽: порог 450 ₽ → +60 промо-баллов на 14 дней. Ожидаемо 25–35 % чеков «дотягиваются», из них половина — инкрементально.

        Best practices. - Порог на 20–60 % выше медианного чека; при большем разрыве клиенты игнорируют. - Подсказка должна называть конкретный товар с ценой ≥ остатка (движок сам подбирает самый дешёвый подходящий из каталога точки). - Баллы со сроком 7–14 дней дают вторую покупку; бессрочные — нет. - Не сочетать с глубокими скидками того же чека (стекинг exclusive внутри группы basket_reward).

        Метрики. Доля чеков ≥ порога (до/после), средний чек участников vs holdout, стоимость награды на инкрементальный рубль, доля потраченных промо-баллов.

        Антифрод. Лимит 1–3 срабатывания на клиента в день; порог по сумме, оплаченной деньгами (не баллами); возврат чека → откат награды.

        DSL. trigger: purchase · conditions: basket.paid_money >= threshold · actions: accrue_points|discount|free_item · hints: threshold_progress. Пример: examples/campaigns/lm-01-threshold.json.

        LM-02 · Наборы и комбо

        Цель: чек ↑ и маржа (продажа высокомаржинальных позиций в связке) · Приоритет: V2 · Сложность: M · Тариф: PRO

        Суть. «Кофе + круассан = 349 ₽ вместо 384» или «Любые 3 позиции из группы — −15 %». Набор — это правило на состав корзины, а не отдельный SKU (не требует перезаводить номенклатуру).

        Как видит клиент. Карточки товаров с меткой «В комбо»; в корзине — «Добавьте круассан — и набор станет дешевле на 35 ₽»; на кассе — авто-применение.

        Параметры. Состав (группы SKU/категорий с количеством), тип цены (фикс. цена набора / % скидки / скидка на самый дешёвый), макс. количество наборов в чеке, расписание.

        Пример. Пекарня «Слойка»: «Пирожок + напиток = 199 ₽» в 8:00–11:00.

        Best practices. Комбинировать «якорь» (то, за чем пришли) с высокомаржинальным дополнением; скидка 10–15 % от суммы компонентов; максимум 3–4 активных комбо.

        Метрики. Attach rate дополнений, маржа чека, доля чеков с комбо.

        Антифрод. Не применяется к возвратам частично (при возврате компонента — пересчёт набора).

        DSL. conditions: basket.matches_bundle(groups) · actions: discount(scope: bundle, mode: fixed_price|percent|cheapest_free) · hints: bundle_missing_component. Пример: lm-02-bundle.json.

        LM-03 · Апселл на кассе («Добавьте за …»)

        Цель: чек ↑ · Приоритет: MVP · Сложность: S · Тариф: Free

        Суть. Если в корзине есть товар-триггер (или сумма ≥ X), клиенту и кассиру показывается предложение добавить конкретную позицию по спеццене. Классика фастфуда, доступная микробизнесу.

        Как видит клиент. На экране оплаты: карточка «Чизкейк за 199 ₽ вместо 320 — только с кофе» с кнопкой «Добавить». Кассир видит ту же подсказку в интерфейсе QR/POS.

        Параметры. Триггер (категория/SKU/сумма), товар-предложение, спеццена или скидка, лимит 1 на чек, расписание, аудитория.

        Пример. Бургерная «Гриль»: к любому бургеру — картофель за 79 ₽ вместо 129.

        Best practices. Одна подсказка на чек; спеццена не ниже себестоимости + 20 %; менять предложение раз в 2–4 недели; текст в императиве («Добавьте»).

        Метрики. Take rate (принятие предложения), прирост чека на принявших, маржа.

        Антифрод. Спеццена применяется только в чеке с триггером; лимит 1 шт.

        DSL. conditions: basket.contains(trigger) · actions: offer_item(sku, special_price, max_qty 1) — реализуется как discount(scope: item, sku, to_price) + hints: addon_offer. Пример: lm-03-addon.json.

        Группа B · Конструктор кэшбэка

        LM-04 · Конструктор кэшбэка

        Цель: частота и чек · Приоритет: MVP · Сложность: M · Тариф: Free (плоский %) / PRO (категории, лестница, статусы)

        Суть. ТСП настраивает повышенный кэшбэк промо-баллами поверх базового платформенного. Четыре режима, комбинируемых в одной кампании:

        Режим Что задаёт ТСП Когда использовать
        flat единый % на весь чек «Просто больше, чем у соседей»
        by_category % по категориям/SKU (напр., десерты 10 %, кофе 3 %) Продвижение маржинальных групп
        ladder лестница по сумме чека: 300 ₽ → 3 %, 600 → 5 %, 1000 → 8 % Рост чека («больше — выгоднее»)
        by_status надбавка по статусу LOVII (PAY +0, PASS +2 %, VIP +4 %) или уровню точки (LM-07) Удержание лучших клиентов

        Общие настройки: потолок начисления на чек (cap_per_order), срок промо-баллов (ttl_days), база начисления (paid_money — на сумму, оплаченную деньгами, по умолчанию; total — на всю сумму), округление (floor), бюджет кампании.

        Как видит клиент. На витрине «+7 % баллами» рядом с базовым «1:1»; в карточке товара — «+16 ₽ баллами»; на экране оплаты — «Вернётся 46 ₽ (базовые 12 + от точки 34)»; в кошельке — отдельный лот с датой сгорания.

        Параметры (ключевые).

        Параметр По умолчанию Диапазон Подсказка по марже
        percent (flat) 5 % 2–15 % «При марже 60 % безопасно до 10 %»
        ladder.steps 3 ступени 2–4 Шаг ≈ 0,5 × средний чек
        cap_per_order 300 ₽ 100–1000 Защита от крупных чеков
        ttl_days 30 7–90 Короче = быстрее возврат, но выше «раздражение»
        accrue_on paid_money paid_money / total Не начислять на часть, оплаченную баллами

        Пример. Салон «Красота»: by_category — уход 10 %, стрижка 3 %, TTL 45 дней (интервал визита ~5 недель).

        Best practices. - Промо-кэшбэк ≥ 5 % заметен; < 3 % — нет (при базовом 2,5–5 %). - Ставить TTL ≈ 1,5 × типичного интервала визита. - Лестницу делать «крутой» на последней ступени (3 → 5 → 8 %). - Показывать прогноз «ожидаемая стоимость/мес = оборот × % × ожидаемое использование (60–80 %)».

        Метрики. Средний чек, частота (30/60 дней), стоимость начислений, redemption rate промо-лотов, breakage (сгорело), инкремент vs holdout.

        Антифрод. Не начислять на чеки, оплаченные баллами более чем на N %; лимит начислений на клиента/день; исключение сотрудников точки (список телефонов персонала).

        DSL. trigger: purchase · actions: accrue_points(percent|ladder|by_category|by_status, cap, ttl_days, funding: merchant). Примеры: lm-04-cashback-flat.json, lm-04-cashback-ladder.json, lm-04-cashback-category.json.

        LM-05 · Счастливые часы и расписание

        Цель: сгладить спрос (утро/вечер/будни), уменьшить списания · Приоритет: MVP · Сложность: S · Тариф: Free

        Суть. Любое действие (скидка, повышенный кэшбэк, множитель ×2) действует только в заданные окна времени. Технически — это schedule.windows[] у любой кампании, но как отдельный шаблон продаётся понятнее: «Вечерняя выпечка −30 % после 19:00», «×2 баллы по будням до 12:00».

        Как видит клиент. Бейдж с таймером «−30 % до закрытия · 2 ч»; в ленте «Акции рядом» (как в текущей демо-витрине).

        Параметры. Окна (дни недели + интервалы), действие (discount % / points multiplier / points %), категории/SKU, дата начала/окончания, показывать ли таймер.

        Пример. Пекарня «Слойка»: ежедневно 19:00–21:00, выпечка −30 % (списания вместо утилизации).

        Best practices. Окно ≥ 2 ч; таймер «до конца акции» повышает конверсию; не более 2 расписаний на точку одновременно; для «мёртвых» часов — множители баллов дешевле скидок.

        Метрики. Выручка в окне до/после, доля списаний, каннибализация (сдвиг покупок из соседних часов).

        Антифрод. Время — серверное, часовой пояс локации; «пробитие задним числом» запрещено (commit не позже 15 мин после quote).

        DSL. schedule.windows[{days, from, to}] + actions: discount|accrue_points(multiplier). Пример: lm-05-happy-hours.json.

        Группа C · Частота и удержание

        LM-06 · Штампы N+1 («Каждый 6-й кофе бесплатно»)

        Цель: частота и удержание · Приоритет: MVP · Сложность: M · Тариф: Free

        Суть. Цифровая карточка штампов: за каждую покупку из целевой группы — штамп; при N штампах — награда (бесплатный товар из группы, скидка, баллы). Самая понятная механика для кофеен, пекарен, моек, маникюра.

        Как видит клиент. Виджет с кружочками «●●●●○○ — ещё 2 до бесплатного капучино» в карточке точки, на экране оплаты и в кошельке. Награда применяется автоматически в следующем подходящем чеке (или по кнопке «Использовать»).

        Параметры.

        Параметр По умолчанию Диапазон Подсказка
        Целевая группа (SKU/категория) напиток — Штамп только за целевую группу
        Штампов до награды target 6 4–10 5–8 оптимально; > 10 — бросают
        Штампов за чек max_per_order 1 1–3 1 = за визит; 3 = за количество
        Мин. интервал между штампами 2 ч 0–24 ч Защита от дробления чека
        Награда самый дешёвый из группы бесплатно free_item / discount / points
        Стартовый бонус «уже 1 штамп» вкл — Endowed progress: +20–30 % к завершению
        Срок жизни карточки 90 дней без покупок 30–365 Сброс при неактивности

        Пример. Кофейня «Daily»: 6-й напиток бесплатно, старт с 1 штампа, макс 1 штамп/чек, 2 ч между штампами.

        Best practices. Давать первый штамп «в подарок» при вступлении; показывать прогресс на каждом чеке; награда — товар, а не скидка (воспринимаемая ценность выше стоимости); срок карточки — 60–90 дней.

        Метрики. Completion rate карточек, среднее время до завершения, частота визитов участников vs holdout, стоимость награды / инкремент.

        Антифрод. 1 штамп на чек по умолчанию; минимальный интервал; штамп только при оплате деньгами ≥ мин. суммы; откат штампа при возврате.

        DSL. trigger: purchase · conditions: basket.contains(group) · actions: stamp(card_id, count); завершение карточки — системное событие stamp_card.completed → actions: free_item|discount|accrue_points. Пример: lm-06-stamps.json.

        LM-07 · Уровни точки (Bronze / Silver / Gold)

        Цель: удержание лучших клиентов, LTV · Приоритет: V2 · Сложность: M · Тариф: PRO

        Суть. Уровень клиента у конкретной точки по скользящему окну (визиты или сумма за 90 дней). Уровень даёт постоянные привилегии: повышенный %, приоритетная запись, «секретное меню». Не путать со статусами платформы PAY / PASS / VIP — те платформенные, эти — точки.

        Как видит клиент. «Silver · до Gold ещё 3 визита» в карточке точки; привилегии списком; уведомление о повышении/риске понижения.

        Параметры. Метрика (visits_90d | spent_90d), пороги уровней, привилегии уровня (кэшбэк %, скидка, доступ к товарам), период пересчёта (ежедневно), «мягкое понижение» (понижение не раньше чем через 30 дней после предупреждения).

        Пример. Салон: Bronze (0–1 визит/90 дн) 0 %, Silver (2–3) +3 %, Gold (4+) +7 % и приоритетная запись.

        Best practices. 3 уровня максимум; верхний — достижим для 10–15 % клиентов; привилегии не только денежные; предупреждать о понижении за 14 дней.

        Метрики. Распределение по уровням, retention по уровням, миграция между уровнями, стоимость привилегий.

        Антифрод. Метрика — по оплаченным деньгами чекам; возвраты уменьшают счётчик.

        DSL. Системный триггер tier.recalculated (планировщик) + customer.tier как поле условий в других кампаниях (напр., LM-04 by_status). Пример: lm-07-tiers.json.

        LM-08 · Абонемент / подписка

        Цель: предоплата (кэш сейчас), гарантированная частота · Приоритет: V2 · Сложность: L · Тариф: PRO

        Суть. Клиент покупает пакет единиц («10 капучино за 1 800 ₽») или период («безлимит бассейн, месяц») и списывает их у точки через QR. Продажа через приложение LOVII, оплата с LOVII PAY / картой.

        Как видит клиент. Карточка абонемента в кошельке: «Осталось 7 из 10 · до 20.10»; на кассе — «Списать 1 из абонемента».

        Параметры. Тип (units | period), состав (SKU/группа), цена, кол-во единиц/длительность, срок действия, лимит в день, автопродление (V2+), возможность подарить.

        Пример. Кофейня: 10 напитков за 1 800 ₽ (скидка 18 %), срок 60 дней, 2 в день.

        Best practices. Скидка 15–25 % к розничной цене; срок 1,5–2 месяца; показывать «выгоду» в рублях; продажа «в подарок».

        Метрики. Продажи абонементов, utilization (доля использованных единиц), breakage, повторные покупки абонемента.

        Антифрод. Списание только в присутствии (динамический QR); лимит в день; привязка к клиенту.

        DSL. Отдельная сущность subscription_plans / subscriptions; в чеке — actions: redeem_subscription_unit с приоритетом выше скидок. Пример: lm-08-subscription.json.

        LM-09 · Челленджи и серии

        Цель: частота, вовлечение · Приоритет: V2 · Сложность: M · Тариф: PRO

        Суть. Ограниченная по времени цель с прогрессом и наградой: «3 визита за 7 дней → 300 баллов», «Попробуй 3 разных десерта в сентябре», «Серия: 4 недели подряд по визиту». Лежит поверх штампов, но с дедлайном и разнообразием условий.

        Как видит клиент. Карточка челленджа с прогрессом и таймером; пуш при 1 шаге до цели.

        Параметры. Условие прогресса (визиты / сумма / уникальные SKU / дни подряд), цель, окно (дней), награда, аудитория, лимит участия.

        Пример. «Утренний ритуал»: 5 покупок до 11:00 за 14 дней → бесплатный завтрак.

        Best practices. Цель на 30–50 % выше обычного поведения сегмента; окно 7–14 дней; 1–2 активных челленджа на точку; напоминание за 48 ч до конца.

        Метрики. Участие, completion rate, прирост визитов участников за окно и после.

        Антифрод. Уникальность визита = отдельный чек с интервалом ≥ 2 ч; оплата деньгами ≥ мин. суммы.

        DSL. trigger: purchase → actions: challenge_progress(challenge_id, +1|+amount); событие challenge.completed → награда. Пример: lm-09-challenge.json.

        Группа D · Привлечение

        LM-10 · Приветственный бонус

        Цель: конверсия первого визита во второй · Приоритет: MVP · Сложность: S · Тариф: Free

        Суть. За первую покупку у точки — промо-баллы со сроком (или купон на второй визит). Задача бонуса — второй визит, поэтому срок короткий.

        Как видит клиент. На витрине: «Новым — +150 баллов за первую покупку»; после чека: «+150 промо-баллов до 06.10 — потратьте в следующий раз».

        Параметры. Размер (₽ или % от чека), мин. чек, TTL (7–14 дней), форма (баллы / купон на 2-й визит).

        Пример. «У дома»: +100 баллов за первую покупку от 300 ₽, TTL 10 дней.

        Best practices. Размер 20–40 % среднего чека; TTL ≤ 14 дней; сочетать с LM-06 (первый штамп в подарок).

        Метрики. Конверсия 1-й → 2-й визит в 30 дней (vs holdout), стоимость привлечённого возвращения.

        Антифрод. «Первая покупка» = первый оплаченный деньгами чек у точки; один бонус на клиента навсегда; исключение сотрудников.

        DSL. trigger: purchase · conditions: customer.orders_at_merchant == 0, basket.paid_money >= min · actions: accrue_points(fixed, ttl) · limits.per_customer.total = 1. Пример: lm-10-welcome.json.

        LM-11 · Реферал точки («Приведи друга»)

        Цель: новые клиенты по рекомендации · Приоритет: MVP · Сложность: M · Тариф: Free

        Суть. Клиент делится ссылкой/QR точки; друг делает квалифицирующую покупку (≥ мин. чек, деньгами) — оба получают награду. Платформа уже имеет «Приведи друга» (+200 ₽) и «Приведи МСП»; механика точки — локальный слой поверх, финансируемый ТСП.

        Как видит клиент. Кнопка «Пригласить друга — вам обоим по 200 баллов» в карточке точки; экран со ссылкой/QR; статус приглашений («Марат — ждём первую покупку»).

        Параметры. Награда пригласившему / другу (₽, баллы, купон), мин. чек друга, лимит приглашений/мес, срок действия приглашения (30 дней), выплата сразу или после 2-й покупки друга.

        Пример. «Клуб Сила»: другу — пробное занятие −50 %, пригласившему — 500 баллов после покупки абонемента другом.

        Best practices. Двусторонняя награда; выплата после квалификации (не за регистрацию); напоминание другу через 3 дня; лимит 10–20 приглашений/мес.

        Метрики. K-фактор (приглашения × конверсия), CAC по каналу, retention приглашённых.

        Антифрод. Один телефон/устройство/платёжный источник — один друг; запрет самореферала (совпадение device_id / карты оплаты); задержка выплаты 24 ч на случай возврата; velocity-лимиты.

        DSL. trigger: referral.qualified (системное событие после commit чека друга с referral_code) · actions: accrue_points(to: referrer), accrue_points|coupon_issue(to: referee). Пример: lm-11-referral.json.

        LM-12 · Кросс-промо соседей

        Цель: новые клиенты из трафика соседних точек района · Приоритет: V2 · Сложность: M · Тариф: PRO (обеим сторонам достаточно одной PRO)

        Суть. Уникальное преимущество LOVII как районной экосистемы: после покупки в точке A клиент получает купон в точку B (и/или наоборот). Пары формируются по приглашению между ТСП внутри локации; кто финансирует награду — задаётся в соглашении (обычно принимающая сторона B).

        Как видит клиент. После оплаты в пекарне: «Подарок от соседей: −15 % на кофе в „Daily“ до воскресенья, 1 мин пешком». В кошельке — купон с картой/расстоянием.

        Параметры. Партнёр (из списка точек района), направление (A→B, B→A, обе), купон (скидка/баллы/товар), условия выдачи (мин. чек, категория), срок купона (3–7 дней), лимит выдач/день, кто платит.

        Пример. «Слойка» ↔ «Daily»: взаимные купоны −15 % на 5 дней, финансирует получающая сторона.

        Best practices. Пары с непересекающимся ассортиментом и близостью ≤ 5 мин пешком; купон короткий (≤ 7 дней); показывать расстояние; ограничивать 1 купон/клиент/неделя.

        Метрики. Выдано → активировано → использовано (funnel), новые клиенты у B, взаимность потоков.

        Антифрод. Купон персональный, одноразовый, привязан к клиенту; использование только в чеке с оплатой деньгами.

        DSL. trigger: purchase (merchant A) · actions: coupon_issue(campaign_of_B, to: customer, ttl); у B — купонная кампания LM-13 с issuer: partner. Пример: lm-12-cross-promo.json.

        LM-13 · Промокоды и купоны

        Цель: перевести офлайн-трафик (флаеры, QR на витрине, соцсети) в измеримые покупки; персональные предложения · Приоритет: MVP · Сложность: S · Тариф: Free

        Суть. Код (публичный МИЯ15 или персональный одноразовый) даёт скидку/баллы/товар при выполнении условий. Купон — выданный клиенту экземпляр (виден в кошельке, применяется в 1 тап). Является «транспортом» для наград других механик (LM-11, LM-12, LM-14, LM-15).

        Как видит клиент. Поле «Промокод» на экране оплаты; «Мои купоны» в кошельке с таймером; авто-предложение применить подходящий купон.

        Параметры. Тип кода (публичный / персональный / пакет одноразовых), награда, условия (мин. чек, категории, первый визит), срок, лимиты (всего, на клиента), каналы (печать QR, ссылка).

        Пример. Суши «Мия»: МИЯ15 — −15 % на сеты до 23:00, 1 раз на клиента.

        Best practices. Коды короткие и произносимые; персональные — с ограниченным сроком; всегда мерить «использовано/выдано»; для флаеров — QR-ссылка с кодом внутри.

        Метрики. Выдано / активировано / использовано, выручка по коду, новые клиенты по коду.

        Антифрод. Rate-limit ввода кодов (5/мин на клиента), контрольная сумма в персональных кодах, одноразовость, запрет комбинирования с другими купонами (stacking.exclusive: coupon).

        DSL. trigger: purchase · conditions: coupon.valid(code) · actions: discount|accrue_points|free_item · limits. Пример: lm-13-coupon.json.

        Группа E · Реактивация и личные поводы

        LM-14 · Win-back (реактивация уснувших)

        Цель: вернуть клиентов, переставших ходить · Приоритет: MVP · Сложность: M · Тариф: Free

        Суть. Планировщик ежедневно находит клиентов точки без покупок N дней и выдаёт им ограниченный по сроку стимул (промо-баллы/купон) + уведомление (с согласия). Каскад: 30 дней → мягкий, 60 → сильнее, 90 → последний.

        Как видит клиент. Пуш «Мы скучаем: 200 баллов в „Daily“ до воскресенья»; купон в кошельке; бейдж на карточке точки.

        Параметры. Порог неактивности (дней), ступени каскада, стимул на ступень, TTL (5–7 дней), канал (push / e-mail / только в приложении), исключить клиентов с < K покупок (не были «своими»), холдаут %.

        Пример. Салон: 45 дней без визита → 300 баллов на уход, TTL 10 дней; 90 дней → −20 % купон.

        Best practices. Порог = 1,5–2 × медианного интервала визита клиента (персонально), а не константа; стимул растёт по ступеням; только для клиентов с ≥ 2 покупками; всегда holdout 10 % для честной оценки.

        Метрики. Вернувшиеся за 30 дней (vs holdout), стоимость возврата, LTV после возврата.

        Антифрод. Один стимул на ступень; сброс каскада после покупки; стимул привязан к клиенту.

        DSL. trigger: inactivity (scheduler, days_since_last_purchase >= N) · actions: accrue_points(fixed, ttl)|coupon_issue, notify. Пример: lm-14-winback.json.

        LM-15 · День рождения и личные даты

        Цель: повод для визита, эмоциональная лояльность · Приоритет: V2 · Сложность: S · Тариф: Free

        Суть. За N дней до даты (день рождения из профиля LOVII, с согласия; «годовщина первой покупки») клиент получает подарок с окном действия ±7 дней.

        Как видит клиент. «С днём рождения! Десерт в подарок до 30.09» — купон в кошельке и пуш.

        Параметры. Событие (birthday / anniversary), за сколько дней (3–7), окно (7–14), подарок (товар/баллы/скидка), мин. чек для подарка-товара.

        Пример. Кофейня: десерт в подарок к любому напитку в неделю дня рождения.

        Best practices. Подарок-товар вместо скидки; окно неделя; напоминание за 2 дня до конца окна.

        Метрики. Использование подарка, чек визита с подарком, визиты в окне vs обычно.

        Антифрод. Дата рождения меняется не чаще раза в год и только через поддержку после первого использования; один подарок в год.

        DSL. trigger: birthday (scheduler) · actions: coupon_issue(free_item, ttl), notify. Пример: lm-15-birthday.json.

        Группа F · Вовлечение и подарки

        LM-16 · Мгновенный выигрыш (колесо / скретч)

        Цель: вовлечение, рост чека до порога · Приоритет: V2 · Сложность: M · Тариф: PRO

        Суть. После чека ≥ X клиент крутит колесо в приложении и получает случайную награду из таблицы с вероятностями (включая «утешительную»). Стимулирует дотягивать чек и открывать приложение после оплаты.

        Как видит клиент. Экран «Крутите колесо» после оплаты; результат сразу в кошельке.

        Параметры. Мин. чек, таблица призов (награда, вероятность, лимит в день), 1 попытка/чек, период.

        Пример. Бургерная: чек от 700 ₽ → 60 % «+50 баллов», 30 % «соус в подарок», 9 % «−20 % на следующий», 1 % «бургер бесплатно» (лимит 2/день).

        Best practices. Ожидаемая стоимость призов 3–6 % от порога; всегда есть выигрыш (без «пусто»); крупный приз лимитирован; честная и опубликованная вероятность (см. compliance о стимулирующих мероприятиях).

        Метрики. Участие, средний чек участников, стоимость призов, повторные визиты.

        Антифрод. Розыгрыш на сервере с детерминированным seed (order_id), 1 попытка/чек, лимиты призов.

        DSL. trigger: purchase · conditions: basket.paid_money >= X · actions: random_reward(table, seed: order_id). Пример: lm-16-instant-win.json.

        LM-17 · Подарочные сертификаты

        Цель: предоплата, новые клиенты через дарителей · Приоритет: V2 · Сложность: L · Тариф: PRO

        Суть. Клиент покупает электронный сертификат точки на сумму (или на услугу), дарит ссылкой/QR; получатель оплачивает им покупки у точки. Баланс сертификата — отдельный инструмент, не баллы.

        Как видит клиент. «Подарить сертификат» в карточке точки; у получателя — карточка сертификата в кошельке с остатком.

        Параметры. Номиналы, срок действия (по закону — см. compliance), дизайн, частичное использование, возможность доплаты.

        Пример. Салон: сертификаты 2 000 / 3 000 / 5 000 ₽, срок 12 месяцев.

        Best practices. Продажа перед праздниками, персональные обложки, напоминание получателю за 30 дней до конца срока.

        Метрики. Продажи, погашение, breakage, доля новых клиентов среди получателей, доплата сверх номинала.

        Антифрод / compliance. Погашение только через commit чека; юр. режим сертификата (аванс) — см. 09.

        DSL. Сущности gift_cards; в чеке — payment_instruments: gift_card до расчёта наград; начисление кэшбэка на часть, оплаченную сертификатом, — по настройке. Пример: lm-17-gift-card.json.

        LM-18 · Отзывы за баллы

        Цель: отзывы и фото для витрины, обратная связь · Приоритет: V2 · Сложность: S · Тариф: Free

        Суть. После подтверждённой покупки клиент оставляет отзыв (текст/фото/оценка) и получает промо-баллы. Отзыв публикуется в карточке точки после модерации.

        Как видит клиент. Через 1–3 ч после оплаты: «Как вам? Оцените и получите 30 баллов».

        Параметры. Награда (баллы), требования (мин. длина / фото), лимит 1 отзыв на чек и N в месяц, модерация (авто/ручная), окно после покупки (72 ч).

        Пример. Цветы «Бутон»: 50 баллов за отзыв с фото букета.

        Best practices. Награда за факт отзыва, а не за оценку (иначе — искажение); показывать отзывы в витрине; отвечать на негатив в кабинете.

        Метрики. Доля чеков с отзывом, средняя оценка, конверсия витрины у точек с отзывами.

        Антифрод. Только по подтверждённому чеку; 1 на чек; антиспам-модерация; лимит в месяц.

        DSL. trigger: review.approved · actions: accrue_points(fixed, ttl). Пример: lm-18-review.json.

        Приложение A · Подсказки по маржинальности (для экрана настройки)

        Формула «безопасной» ставки стимула, показываемая ТСП:

        max_incentive_pct ≈ margin_pct × 0.35

        где margin_pct — валовая маржа категории (ТСП указывает в настройках или выбирает пресет: кофе 65 %, выпечка 55 %, продукты 25 %, услуги красоты 60 %, фитнес 70 %). Прогноз стоимости кампании за месяц:

        cost_month ≈ eligible_turnover_month × incentive_pct × expected_redemption

        expected_redemption: баллы 0,6–0,8; скидка 1,0; товар-подарок — по себестоимости.

        1. Архитектурная идея

         Шаблон механики (LM-xx)          Спецификация кампании (Spec, JSON)         Движок
 ┌──────────────────────┐  compile  ┌───────────────────────────────┐  quote/commit  ┌────────────┐
 │ params_schema (форма)│ ────────► │ trigger + conditions + actions│ ─────────────► │ детерминир.│
 │ defaults, hints      │           │ schedule, audience, limits    │                │ расчёт     │
 └──────────────────────┘           └───────────────────────────────┘                └────────────┘
        • Шаблон знает про UI (какие поля показать) и про «умолчания под категорию бизнеса». Он чистой функцией compile(params) → spec превращается в Spec.
        • Spec — единственное, что исполняет движок. Движок ничего не знает про «штампы» или «порог чека» как про сущности — только про триггеры, условия и действия.
        • Версия Spec неизменяема. Любое изменение опубликованной кампании = новая версия.

        Следствие для агентов: новая механика = новый шаблон (params_schema + compile + предпросмотр + golden-тесты). Код движка меняется только при появлении нового типа действия или поля условия.

        2. Единицы и точность

        Величина Представление Правило
        Деньги целое, копейки (amount_minor) Никаких float
        Баллы целое, баллы (1 балл = 1 ₽) Дробные баллы не существуют
        Проценты число с ≤ 2 знаками (7, 7.5) Хранить как percent_bp (базисные пункты, 750) в БД; в Spec допускается 7.5
        Время ISO-8601 с зоной; расчёт в часовом поясе локации context.now задаёт сервер, не клиент

        Округление:

        money_pct(amount_minor, percent)   = floor(amount_minor × percent / 100)        // копейки
points_pct(amount_minor, percent)  = floor(amount_minor × percent / 10000)      // баллы (₽)
points_from_minor(amount_minor)    = floor(amount_minor / 100)

        Всегда floor (в пользу ТСП), кроме скидок к клиенту типа to_price, где цена задана явно.

        5. Алгоритм расчёта (quote)

        5.1 Порядок стадий

        0. normalize     цены/кол-ва → minor, gross_total
1. select        активные по статусу, расписанию, аудитории, holdout, лимитам, бюджету, триггеру
2. class PRICE   redeem_subscription_unit → discount(item/bundle/to_price/free_item) → discount(basket)
                 условия считаются на gross-корзине; стекинг по группам (§5.2)
3. REDEEM        списание баллов клиента: min(redeem_points, balance, after_discounts × max_points_share_pct)
                 → paid_money = after_discounts − redeemed × 100
4. class REWARD  условия считаются на paid_money / after_discounts; действия accrue_points, stamp,
                 challenge_progress, random_reward, coupon_issue, notify; стекинг по группам
                 (notify попадает в applied с action_type "notify" и в notifications; cost_minor = 0)
5. platform      базовый кэшбэк платформы (системная кампания, всегда, funding: platform) на paid_money
6. hints         подсказки: до порога, недостающий компонент набора, апселл, штампы, уровень
7. explain       для каждой кандидат-кампании — applied | skipped(reason)
8. result        quote_id (TTL 15 мин), резерв бюджета/лимитов

        Причины skipped (строки reason в explain):

        Причина Когда
        schedule вне starts_at…ends_at
        window вне окон schedule.windows (день недели/время в TZ кампании)
        audience сегмент/статус/уровень клиента не подходит
        staff_excluded audience.exclude_staff и customer.is_staff
        guest customer = null: наградные действия (баллы, штампы, купоны, розыгрыш) недоступны гостю; ценовые действия гостю применяются
        holdout клиент в контрольной группе (см. ниже)
        limit_per_customer, limit_total, budget исчерпаны лимиты/бюджет (counters, uses_total, budget_used_*)
        coupon_required кампания привязана к промокоду (trigger.params.coupon или условие coupon.*), а код не введён; если у клиента есть неиспользованный купон — добавляется hint coupon_available
        coupon_invalid код введён, но не подходит (не найден, чужой, просрочен, использован, не для этой точки)
        condition:<idx> не выполнено условие с индексом idx (первое непройденное)
        stacking:<group>:<winner_id> в exclusive-группе уже победила кампания winner_id
        stamp_interval штамп по карте ставился менее min_interval_minutes назад (защита от дробления чека)
        cap достигнут потолок (max_merchant_cashback_points, max_total_discount_pct, cap действия) — начислять/скидывать больше нечего
        no_effect кампания подходит, но действие не дало эффекта на этот чек (нет подходящих позиций, 0 баллов после округления)

        Контрольная группа (holdout). Принадлежность детерминирована и не зависит от времени: bucket = uint32(sha256(customer_id + ":" + campaign_id)[0:8]) mod 100; клиент в holdout, если bucket < audience.holdout_pct. Один и тот же клиент может быть в holdout одной кампании и вне holdout другой; при смене holdout_pct группа расширяется/сужается монотонно (бакеты не перемешиваются). Кампания в holdout не применяется, не даёт подсказок и не показывается на витрине, но фиксируется в explain и в статистике (holdout_orders, holdout_revenue_minor) для атрибуции эффекта (07 §2).

        5.2 Стекинг

        • У каждой кампании — stacking.group (строка) и mode (exclusive | stackable).
        • Внутри стадии кандидаты сортируются по priority ↓, затем published_at ↑.
        • В группе с exclusive применяется только первая подходящая кампания; остальные получают skipped: stacking.
        • stackable применяются все, но действуют потолки из настроек ТСП (loyalty_settings):
        • max_total_discount_pct (по умолчанию 30 %) — суммарная скидка класса «цена» от gross;
        • max_merchant_cashback_pct (20 %) — суммарный % промо-кэшбэка ТСП;
        • max_coupons_per_order (1);
        • на одну товарную позицию — одно действие to_price|cheapest_free|free_item (побеждает приоритет).
        • Группы по умолчанию (из шаблонов): item_price (LM-02, LM-03, LM-08), basket_discount (LM-05 со скидкой, LM-13), cashback (LM-04, LM-05 с множителем — stackable), bonus (LM-01, LM-10, LM-16 — exclusive), stamp (stackable), coupon_out (LM-12 — stackable, ≤ 1 на партнёра), platform_base (системная).
        • Купоны: 1 на чек; купон исключает другие кампании своей группы; купон не блокирует кэшбэк, если в купоне не указано stacking.blocks: ["cashback"].

        5.3 База начисления

        accrue_on в настройках точки: paid_money (по умолчанию — не начислять на часть чека, оплаченную баллами) или total (after_discounts). Для eligible_amount — сумма позиций по filter пропорционально уменьшается на долю скидок/списаний: eligible × after_discounts / gross.

        5.4 Порог и прогресс (hints)

        Для каждой кампании с условием basket.paid_money >= T (или after_discounts), не выполнившимся:

        remaining = T − current
if remaining <= max(0.4 × T, 30000): hint { type: "threshold_progress", campaign_id, remaining_minor,
   suggested_item: cheapest(catalog where price_minor >= remaining && !in_basket) }

        Для stamp: hint { type: "stamps", card, count, target, remaining }. Для bundle: missing_component. Для addon: addon_offer { sku, special_price_minor } (показывается, пока позиция не добавлена). Для tiers: tier_progress.

        5.5 Списание баллов (REDEEM)

        • Порядок лотов: сначала промо-лоты этой точки по ближайшему сроку, затем промо-лоты района/платформы по сроку, затем базовые (бессрочные).
        • Ограничение: max_points_share_pct точки (по умолчанию 50 %; платформа может задать минимум, напр., ≥ 30 %, чтобы баллы оставались ликвидными).
        • На экране оплаты клиент видит, какие лоты спишутся и что «сгорит раньше».

        6. Commit и Reverse

        6.1 Commit (после успешной оплаты)

        Вход: order_id, quote_id (опц.), payment { method, paid_money_minor, paid_points }, idempotency_key = order_id.

        1. Если quote_id жив (≤ 15 мин) и сумма оплаты равна quote.paid_money — применяются зафиксированные в quote версии кампаний и результаты класса «цена». Класс «награда» пересчитывается на тех же версиях (учёт лимитов на момент commit).
        2. Если quote нет/истёк — полный пересчёт на текущих активных версиях; ответ помечается recomputed: true.
        3. В одной транзакции: проверка/инкремент счётчиков лимитов и бюджета (SELECT … FOR UPDATE), записи леджера (лоты, проводки), штампы/челленджи, купоны, applied_rewards, событие в outbox.
        4. Повторный commit с тем же order_id → тот же ответ (идемпотентность), без повторных проводок.
        5. Если бюджет исчерпан между quote и commit — награда всё равно применяется (quote — обещание клиенту), кампания переходит в paused_budget, перерасход логируется.

        6.2 Reverse (возврат / отмена)

        Вход: order_id, refund { full: bool, amount_minor, items[] }.

        • Полный: снять начисленные баллы с лотов (если лот частично потрачен — списать с базового баланса, допускается отрицательный баланс до max_negative_points = 500, иначе создаётся запись debt и следующее начисление гасит долг); вернуть списанные баллы (в тот же тип лота); снять штампы/прогресс; аннулировать неиспользованные выданные купоны; уменьшить счётчики и бюджет.
        • Частичный: ratio = amount_minor / paid_money_minor; баллы к снятию floor(accrued × ratio); штамп снимается, если возвращена позиция-основание; скидки класса «цена» не пересчитываются (возврат по факту оплаченной цены).
        • Reverse идемпотентен по (order_id, refund_id).

        7. Планировщик (триггеры по времени)

        Задача Периодичность Идемпотентность
        inactivity (LM-14) ежедневно 10:00 локации (campaign_id, customer_id, step)
        birthday (LM-15) ежедневно (campaign_id, customer_id, year)
        tier_recalculated (LM-07) ежедневно 03:00 по дате
        Истечение лотов ежечасно по lot_id
        Истечение карточек штампов / купонов / quote-резервов ежечасно по id
        Напоминания «сгорает через 3 дня» ежедневно (lot_id)
        Агрегаты статистики campaign_stats_daily ежечасно инкрементально по (campaign_id, date)

        Пуш-уведомления отправляются только при наличии согласия (customer.consents.promo_push), с частотным лимитом 2 промо-пуша/нед на клиента по локации.

        8. Компиляция шаблонов

        Каждый шаблон регистрируется объектом (референс — /demo/app/loyalty-constructor/templates.js):

        Расширения JSON Schema для генератора формы (все начинаются с x-):

        Ключ Значение Смысл

        Названия товаров/партнёров для заголовков шаблон не знает — кабинет передаёт их в params (offer_name, partner_name, plan_name) рядом с идентификаторами.

        9. Симуляция для кабинета ТСП

        POST /loyalty/simulate { spec | campaign_id, context } — тот же движок, но без резервов и записи; explain всегда включён; допускается now из запроса (для проверки расписаний). Кабинет использует симуляцию в предпросмотре: «Чек 420 ₽ → без награды, до подарка 30 ₽; чек 740 ₽ → +60 баллов».

        10. Инварианты (проверяются тестами)

        1. sum(discounts) ≤ gross_total × max_total_discount_pct и ≤ gross_total.
        2. paid_money + redeemed_points × 100 + discounts = gross_total.
        3. Баллы никогда не начисляются на сумму, оплаченную баллами, при accrue_on = paid_money.
        4. Один и тот же вход при одних и тех же версиях кампаний даёт байт-в-байт одинаковый результат (кроме quote_id/времени).
        5. Commit идемпотентен; reverse(commit(x)) возвращает счётчики/бюджет к исходным.
        6. Кампания в holdout для клиента никогда не применяется, но всегда попадает в explain.
        7. Промо-лот со сроком списывается раньше бессрочного.
        8. Действие класса «цена» не может сделать цену позиции отрицательной; free_item требует наличия позиции в корзине или добавляет её с ценой 0 (по add_if_missing).

        2. Сущности

        2.1 Настройки точки — loyalty_settings

        Одна строка на ТСП. Хранит категорию бизнеса и маржу (для подсказок), политику начисления (accrue_on), потолки стекинга (max_total_discount_pct, max_merchant_cashback_pct, max_points_share_pct, max_coupons_per_order), список сотрудников (staff_customer_ids), признак тарифа PRO.

        2.2 Кампании — campaigns + campaign_versions

        • campaigns — изменяемая «шапка»: статус, бюджет (budget_total / used / reserved), счётчик использований, current_version.
        • campaign_versions — неизменяемые снимки Spec (триггер запрещает UPDATE/DELETE). spec_hash — sha256 канонического JSON для детерминированных тестов и дедупликации.
        • Публикация: INSERT campaign_versions (version = current_version + 1) + UPDATE campaigns SET current_version, status='active' в одной транзакции.
        • Системные кампании (is_system = true, напр. platform_base) принадлежат платформе, merchant_id = служебный.
        • partner_merchant_id — для кросс-промо: кампания хранится у выдающей стороны, coupons.redeemer_merchant_id указывает на принимающую.

        2.3 Профиль клиента у точки — customer_profiles

        Материализованные метрики клиента в контексте конкретного ТСП: orders_total, last_purchase_at, visits_30d, spent_90d_minor, median_interval_days (для персонального win-back), tier, segments[], winback_step, is_staff. Обновляется синхронно при commit/reverse (счётчики) и ночным воркером (скользящие окна, сегменты, RFM, уровни).

        Системные сегменты (пересчёт ежедневно):

        Код Правило
        new orders_total = 0 или первая покупка < 14 дней
        regular visits_90d >= 3
        sleeping days_since_last_purchase >= max(30, 1.5 × median_interval_days) и orders_total >= 2
        vip_platform статус LOVII = VIP
        top10 верхние 10 % по spent_90d_minor у точки

        2.4 Леджер — accounts, point_lots, ledger_entries, point_debts

        Двойная запись. Каждая проводка дебетует один счёт и кредитует другой:

        Операция Дебет Кредит kind
        Начисление промо-баллов ТСП merchant_funding (₽, копейки) customer_points accrual
        Начисление базового кэшбэка platform_funding customer_points accrual
        Списание баллов в оплату customer_points points_liability (обязательства перед ТСП, погашаемые расчётами) redemption
        Сгорание лота customer_points merchant_funding / platform_funding (возврат источнику) expiry
        Возврат чека: снятие начисленного customer_points источник reversal_accrual
        Возврат чека: возврат списанного points_liability customer_points reversal_redemption

        Инвариант: accounts.balance(customer_points) = Σ point_lots.amount_left (проверяется ночной сверкой).

        Лоты. Любое начисление создаёт лот: funding, merchant_id (чьи промо-баллы), expires_at (NULL = бессрочные базовые), campaign_id/version, order_id. Списание — FIFO: сначала лоты этой точки с ближайшим сроком, затем прочие срочные, затем бессрочные (см. 03 §5.5). Частичный индекс point_lots_fifo_idx обслуживает выбор.

        Долги. Если при возврате начисленные баллы уже потрачены и базового баланса не хватает — создаётся point_debts, следующее начисление гасит долг проводкой debt_settle.

        Идемпотентность. ledger_entries.idempotency_key уникален: "{order_id}:{campaign_id}:{action_index}:{kind}" (для reverse — с refund_id).

        2.5 Заказы и атрибуция — loyalty_orders, quotes, applied_rewards, campaign_counters

        • quotes — результат предрасчёта с TTL 15 мин и зафиксированными версиями кампаний; reserved_minor резервирует бюджет (снимается при commit/истечении).
        • loyalty_orders — снимок чека в терминах лояльности (gross, discounts, points_redeemed, paid_money, items), статус quoted → committed → (partially_)reversed, holdout_campaigns[] — какие кампании не применились из-за контрольной группы (нужно для честного A/B).
        • applied_rewards — по строке на каждое применённое действие с campaign_version, стоимостью для бюджета и details (выпавший приз, sku подарка, лот).
        • campaign_counters — счётчики «на клиента за период» (period_key: 2026-09-22 / 2026-W39 / 2026-09 / all), инкремент под FOR UPDATE в транзакции commit.

        2.6 Штампы и челленджи — stamp_cards, stamp_events, challenge_progress

        • Одна карточка на (campaign, card_code, customer); pending_reward — карточка заполнена, награда ждёт следующего подходящего чека или кнопки «Использовать».
        • stamp_events — журнал ±1 для возвратов и аудита.
        • challenge_progress — прогресс в окне; seen_keys — уникальные sku / номера недель для метрик unique_sku, streak_weeks.

        2.7 Купоны и рефералы — coupons, referrals

        • Купон всегда ссылается на кампанию погашения (redeem_campaign_id, обычно mechanic = coupon) и опционально на кампанию выдачи (issued_by_campaign_id: win-back, birthday, cross-promo). Публичный код — строка без customer_id с max_uses; персональный — с customer_id, max_uses = 1.
        • referrals фиксирует воронку invited → registered → qualified → rewarded; reject_reason — антифрод.

        2.8 Абонементы и сертификаты — subscription_plans, subscriptions, subscription_redemptions, gift_cards, gift_card_transactions

        Отдельные инструменты предоплаты. В расчёте чека абонемент участвует действием redeem_subscription_unit (класс «цена», первым), сертификат — как платёжный инструмент до расчёта наград (см. 03 §5).

        2.9 Партнёрства — partnerships

        Соглашение двух ТСП одной локации для кросс-промо: направление, кто финансирует, лимиты. Кампании LM-12 создаются только при status = active.

        2.10 События, аудит, статистика — outbox_events, audit_log, campaign_stats_daily

        • Outbox-паттерн: события пишутся в той же транзакции, публикуются воркером (Kafka/NATS/webhooks).
        • audit_log — кто/что/когда изменил (кампании, настройки, ручные начисления).
        • campaign_stats_daily — инкрементальные агрегаты для дашбордов, включая holdout-метрики и воронку подсказок (hints_shown → hints_converted).

        2.11 Согласия — customer_consents

        Зеркало платформенных согласий по локации: promo_push, promo_email, birthday_use. Планировщик уведомлений читает только отсюда.

        3. Гео-изоляция и производительность

        • Все таблицы имеют location_id. Рекомендуется партиционирование по location_id (LIST) для ledger_entries, loyalty_orders, applied_rewards, point_lots, outbox_events и RLS-политики app.location_id для сервисных ролей.
        • Горячие чтения quote: активные кампании точки (кэш в Redis, инвалидация по событию campaign.published/paused), профиль клиента (customer_profiles PK), лоты клиента (частичный индекс), счётчики (campaign_counters PK).
        • Цель: quote ≤ 150 мс p95 при 20 активных кампаниях и 30 позициях в чеке.
        • ledger_entries — append-only; ретеншн ≥ 5 лет (бухгалтерская сверка); архив в холодное хранилище по годам.

        4. Миграции и версионирование данных

        • Миграции — только вперёд, с IF NOT EXISTS; версия схемы в loyalty.schema_migrations.
        • Изменение формата Spec → новое значение spec_version; движок поддерживает N и N−1; миграция версий кампаний не выполняется (старые версии остаются исполняемыми до завершения кампаний).
        • Справочник механик/шаблонов не хранится в БД (код + тесты), кроме включения по тарифам (loyalty_settings.pro_plan).

        5. Примеры запросов

        Баланс и ближайшее сгорание клиента:

        SELECT balance, base_balance, promo_balance, next_expiry
FROM loyalty.customer_points_balance

        Лоты для списания (FIFO с приоритетом точки):

FROM loyalty.point_lots

WHERE p.merchant_id = $1
  AND p.orders_total >= 2
  AND p.last_purchase_at < now() - make_interval(days => GREATEST(30, CEIL(1.5 * COALESCE(p.median_interval_days, 30)))::int)
  AND p.winback_step = 0

        6. Совместимость с текущей платформой LOVII

        • Кошелёк LOVII PAY уже показывает операции «Кэшбек · Пекарня „Слойка“», «Бонус „Приведи друга“», «Оплата баллами». Runtime API добавляет к этим операциям поле lot (метка, срок) и campaign (название), чтобы история операций объясняла источник.
        • Экран статуса (PAY / PASS / VIP) остаётся платформенным; customer.status доступен кампаниям как аудитория.
        • Существующие акции витрины («Слойка с вишней −30 % ежедневно до 20:00», «Пицца 2×1 по выходным», «−15 % на сеты по промокоду МИЯ15») выражаются механиками LM-05, LM-02/LM-06 и LM-13 соответственно — при миграции их следует пересоздать как кампании, чтобы получить учёт и аналитику.

        3.3 Мастер настройки #/biz/loyalty/new/{template}

        Общий каркас: шапка с шагами (1–4), прогресс, кнопки «Назад / Далее», справа (desktop) или снизу (mobile, сворачиваемая панель) — живой предпросмотр: карточка для клиента + мини-симуляция чека.

        Шаг 1 · Параметры — форма из params_schema шаблона. Компоненты: слайдер с полем ввода (порог, %), сегментированный контроль (тип награды), выбор категорий/товаров (чипы из каталога точки), степпер (штампы), таблица ступеней (лестница). Под каждым ключевым полем — подсказка: «Ваш средний чек 320 ₽. Рекомендуем 420–500 ₽». Индикатор риска по марже: зелёный/жёлтый/красный.

        Шаг 2 · Аудитория и время — «Все клиенты / Новые / Постоянные / Уснувшие / Статус PASS·VIP»; расписание: «Всегда» или окна (дни недели чипами + время); даты начала/окончания; тумблер «Контрольная группа 10 % для честной оценки» (вкл. по умолчанию, с пояснением).

        Шаг 3 · Лимиты и бюджет — «На одного клиента: 1 раз в день», «Бюджет на месяц: 5 000 ₽ (авто-пауза)», «Не начислять сотрудникам» (вкл.). Прогноз: «≈ 70 чеков/мес пересекут порог → ≈ 4 200 ₽».

        Шаг 4 · Предпросмотр и публикация — карточка клиента (витрина), экран оплаты с прогрессом, пуш-текст (если включён), условия текстом (content.terms, редактируемые), симулятор «Чек 420 ₽ → …, чек 740 ₽ → …». Кнопки: «Опубликовать», «Сохранить черновик», «Запланировать с даты».

        Валидация: серверная (compile → 422 с details[].path) отображается у полей; публикация недоступна без PRO для PRO-механик (карточка «Доступно в PRO» с апселлом).

        ↑ к оглавлению

        2. Определения

        Метрика Формула Примечание
        Средний чек Σ paid_money + Σ points_redeemed×100 / чеков Считаем «валовую» стоимость покупки; отдельно — деньгами
        Частота (30 д) чеков клиента за 30 дней по customer_profiles.visits_30d
        Повторные (repeat rate) доля клиентов с ≥ 2 чеками за 30 дней
        Возврат уснувших доля sleeping, сделавших чек в 30 дней после триггера win-back сравнить с holdout
        Новые по каналу клиенты с 1-й покупкой, атрибутированные рефералу/купону/кросс-промо first-touch
        Стоимость стимулов Σ discount_minor + Σ points_issued(merchant)×100×expected_redemption + Σ free_item cost expected_redemption — фактический по точке за 90 дней, стартово 0,7
        Фактическая стоимость баллов Σ points_redeemed_from(lots кампании) известна с лагом
        Breakage points_expired / points_issued цель 15–35 % для промо-лотов
        Обязательства (liability) Σ point_lots.amount_left промо-лотов точки показывать в ₽ и «ожидаемо к использованию»
        Инкрементальная выручка (metric_participants − metric_holdout) × N_participants см. §3
        ROI кампании (инкрементальная маржа − стоимость) / стоимость, маржа = выручка × margin_pct
        Конверсия подсказки hints_converted / hints_shown «добавили предложенный товар в течение сессии»
        Completion rate штампов завершённых карточек / начатых
        Redemption купонов использовано / выдано по кампании выдачи и по кампании погашения
        K-фактор рефералов приглашений на клиента × конверсия в квалифицированную покупку

        3. Атрибуция: контрольная группа (holdout)

        1. При публикации кампании каждому клиенту детерминированно назначается группа: hash(customer_id + campaign_id) mod 100 < holdout_pct → контроль. Назначение стабильно для всех версий кампании.
        2. Для клиентов контроля движок не применяет кампанию (и не показывает подсказки/бейджи), но записывает loyalty_orders.holdout_campaigns[] и campaign_stats_daily.holdout_*.
        3. Эффект = разница метрик между участниками и контролем за одинаковый период: - средний чек: avg_check_participants / avg_check_holdout − 1; - частота: visits_30d_participants / visits_30d_holdout − 1; - win-back: returned_participants − returned_holdout (п.п.).
        4. Уровень уверенности показывается словами: low (< 100 чеков в контроле), medium (100–500), high (> 500) — плюс интервал (bootstrap 1 000 итераций, ночной джоб). Не показываем p-value ТСП; в API отдаём confidence.
        5. По умолчанию holdout_pct = 10; ТСП может отключить (0) с предупреждением «эффект будет оценкой без контроля». Для механик с публичной офертой (расписание LM-05 на витрине) holdout не применяется — там оцениваем «до/после» по окнам времени.
        6. При нескольких активных кампаниях контрольные группы независимы (разные хэши) — оценка каждой кампании частично захватывает эффект других; в сводке точки показываем суммарный инкремент по «глобальному» holdout 5 % (клиенты, к которым не применяется ни одна кампания точки) — настройка платформы.

        4. Дашборды

        4.1 ТСП · Обзор (30/90 дней)

        Средний чек (участники vs контроль), повторные покупки, выручка по кампаниям, стоимость и ROI, обязательства по баллам, топ-3 подсказки по конверсии, рекомендации «Что запустить» (правила §6).

        4.2 ТСП · Кампания

        4.3 Представитель · Мои точки

        Таблица точек: активных кампаний, инкремент, стоимость, «нет ни одной кампании» (сигнал к действию).

        4.4 Владелец платформы · Локация

        Доля ТСП с кампаниями, суммарный инкремент по локации, распределение механик, обязательства по промо-баллам локации, доля PRO, фрод-алерты.

        5. Отчёты и экспорт

        2. Поток QR-оплаты (MVP, без кассы)

        1. Клиент открывает точку в приложении, собирает корзину (или кассир — на своём экране, корзина синхронизируется по order_id).
        2. Приложение вызывает POST /loyalty/quote при каждом изменении корзины (debounce 300 мс), показывает прогресс/подсказки/списание.
        3. Кассир показывает динамический QR точки (TOTP-токен, ротация 30 с) или клиент сканирует статический QR точки — токен подтверждает физическое присутствие (антифрод для штампов/чек-инов).
        4. LOVII Pay создаёт платёж на paid_money_minor и резервирует points_redeemed.
        5. После успешной оплаты LOVII Pay вызывает POST /loyalty/commit (Idempotency-Key = order_id), получает лоты к начислению и списанию; отражает операции в истории кошелька с меткой кампании.
        6. Приложение получает событие loyalty.order.committed (WebSocket/poll) → PostPaySheet.
        7. Возврат инициируется кассиром в кабинете → LOVII Pay → POST /loyalty/reverse.

        Тайминги: quote ≤ 150 мс p95; commit ≤ 300 мс p95; если Loyalty недоступен на commit — платёжный сервис ставит commit в очередь повторов (до 24 ч), клиенту показывается «начисление в обработке».

        • Средний чек, распределение чеков по суммам и часам, маржа по категории (задаётся ТСП или пресет) — входы для estimate() шаблонов.

        8. Фискализация и 54-ФЗ (для кассовых адаптеров)

        • Скидки класса «цена» и оплата промо-баллами ТСП отражаются в чеке как скидка на позиции (цена позиции уменьшается; сумма чека = оплачено деньгами). Распределение скидки чека по позициям — пропорционально стоимости (правило адаптера, детерминированное).
        • Оплата базовыми баллами платформы (1 балл = 1 ₽ с возможностью вывода) с точки зрения ТСП — способ расчёта, который платформа компенсирует ТСП при взаиморасчётах; юридическая квалификация (скидка / оплата третьим лицом / зачёт) — предмет платформенного договора с ТСП, см. 09 §4. Адаптер должен поддерживать оба режима: «баллы как скидка» и «баллы как безналичная оплата (зачёт предоплаты)».
        • Подарочный сертификат: продажа — чек с признаком «аванс/предоплата», погашение — «зачёт аванса».
        • Абонемент: продажа — предоплата за N единиц; списание единицы — чек на 0 ₽ с зачётом аванса либо отсутствие чека (если единица уже фискализирована при продаже) — уточнить у ОФД/бухгалтера ТСП, адаптер конфигурируем.

        Хранение Леджер и версии кампаний ≥ 5 лет; quotes 30 дней; события 1 год политика ретеншна

        2. Безопасность

        • AuthN/AuthZ: JWT платформы; проверка владения merchantId (или связи представитель→точка); Runtime — сервисные токены с scope loyalty:runtime и привязкой к location_id; клиентские вызовы — customer_id только из токена.
        • RLS по локации на всех таблицах; сервис выставляет app.location_id на соединении.
        • Секреты: HMAC-ключи вебхуков, TOTP-семена QR точек — в секрет-хранилище, ротация 90 дней.
        • Аудит: любое изменение кампаний/настроек, ручные начисления, экспорт данных — в audit_log с актором, IP, до/после.
        • Ручные начисления: лимит 2 000 баллов/день на точку и 500 на клиента, обязательный комментарий, уведомление владельцу точки.
        • Ввод кодов: rate-limit 5/мин на клиента и 60/мин на точку; персональные коды с контрольным символом (Luhn/Base32 + checksum), длина ≥ 8.
        • Экспорт: клиентские данные для ТСП — только маскированный телефон и агрегаты; полный телефон недоступен ТСП (закон 152-ФЗ, минимизация).
        • Защита API: схема-валидация всех входов (JSON Schema), лимиты размера корзины (≤ 200 позиций), защита от переполнения сумм (BIGINT, проверки ≥ 0).
        • Зависимости: SCA (Trivy/Aikido), SAST в CI — как в стандартах платформы.

        2. Инварианты (нарушение = баг с приоритетом P0)

        1. Все деньги — целые копейки (*_minor), баллы — целые; округление только floor; никаких float в расчётах.
        2. paid_money + points_redeemed × 100 + Σ discounts == gross_total для каждого чека.
        3. Суммарная скидка класса «цена» ≤ max_total_discount_pct от gross_total; суммарный merchant-кэшбэк ≤ max_merchant_cashback_pct от базы.
        4. Движок детерминирован: quote(campaigns, context, state, now) без обращений к часам/ГСЧ; случайность — из sha256(order_id:campaign_id).
        5. commit идемпотентен по order_id; повтор возвращает тот же результат с idempotent: true без побочных эффектов.
        6. Каждое начисление/списание — проводка в ledger_entries с уникальным idempotency_key; Σ point_lots.amount_left == баланс.
        7. Опубликованная версия кампании неизменяема; правки создают новую версию.
        8. Клиент в holdout не получает ни применения, ни отображения кампании.
        9. Клиент никогда не видит причины skipped внутренних ограничений (holdout, бюджет) — только нейтральные формулировки из 06 §4.
        10. Ни один вызов Runtime API не блокирует оплату при недоступности Loyalty (деградация — 08 §6).

        3. Как добавить или изменить механику

        1. Прочитай раздел LM-NN в 02; если требуется новое действие/поле условия — сначала PR в campaign.schema.json + 03 (+ engine.js и golden-кейсы), затем реализация.
        2. Создай шаблон templates/lm-NN-<mechanic>: params_schema (JSON Schema, поля с title/description на русском — из них генерируется форма мастера), defaults(ctx), compile(params) → Spec, estimate(params, stats), preview(params).

        6. Чего не делать

        • Не добавлять механику как «особый случай» в конвейер — только через Spec-действия и шаблон.
        • Не хранить вычисленные скидки в каталоге товаров; цены на витрине — всегда «цена + бейдж», расчёт в quote.
        • Не менять поведение округления/порядка стекинга без обновления golden-кейсов и раздела 03 §5.
        • Не показывать ТСП персональные данные клиентов сверх маскированного телефона.
        • Не отправлять уведомления напрямую — только события notify в подсистему уведомлений.
        • Не использовать Math.random/now() внутри движка.
