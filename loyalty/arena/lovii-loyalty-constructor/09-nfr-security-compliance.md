## 1. Нефункциональные требования

| Область | Требование | Как проверяем |
|---|---|---|
| Производительность | `quote` ≤ 150 мс p95, ≤ 400 мс p99 при 20 активных кампаниях и 30 позициях; `commit` ≤ 300 мс p95; `simulate` ≤ 500 мс | k6: 200 rps на локацию, 30 мин soak |
| Пропускная способность | 500 ТСП × 20 чеков/день = 10 000 commit/день на старте; проектировать на ×50 | нагрузочный тест |
| Доступность | 99,5 % (как у платформы), RTO 4 ч, RPO 15 мин; деградация без Loyalty не блокирует оплату | chaos-тест: отключение сервиса при оплате |

| Детерминизм | Одинаковый вход → одинаковый результат (golden-тесты) | CI |
| Идемпотентность | commit/reverse/manual по ключу, окно ≥ 30 дней | тесты повторов |
| Масштабирование | Stateless-сервис; горячие данные в Redis (активные кампании, счётчики с write-through); партиции по локации | |

| Хранение | Леджер и версии кампаний ≥ 5 лет; quotes 30 дней; события 1 год | политика ретеншна |

## 2. Безопасность

- **AuthN/AuthZ**: JWT платформы; проверка владения `merchantId` (или связи представитель→точка); Runtime — сервисные токены с scope `loyalty:runtime` и привязкой к `location_id`; клиентские вызовы — `customer_id` только из токена.
- **RLS по локации** на всех таблицах; сервис выставляет `app.location_id` на соединении.
- **Секреты**: HMAC-ключи вебхуков, TOTP-семена QR точек — в секрет-хранилище, ротация 90 дней.
- **Аудит**: любое изменение кампаний/настроек, ручные начисления, экспорт данных — в `audit_log` с актором, IP, до/после.
- **Ручные начисления**: лимит 2 000 баллов/день на точку и 500 на клиента, обязательный комментарий, уведомление владельцу точки.
- **Ввод кодов**: rate-limit 5/мин на клиента и 60/мин на точку; персональные коды с контрольным символом (Luhn/Base32 + checksum), длина ≥ 8.
- **Экспорт**: клиентские данные для ТСП — только маскированный телефон и агрегаты; полный телефон недоступен ТСП (закон 152-ФЗ, минимизация).
- **Защита API**: схема-валидация всех входов (JSON Schema), лимиты размера корзины (≤ 200 позиций), защита от переполнения сумм (BIGINT, проверки ≥ 0).
- **Зависимости**: SCA (Trivy/Aikido), SAST в CI — как в стандартах платформы.

## 3. Антифрод

### 3.1 Модель угроз

| Угроза | Вектор | Контроль |
|---|---|---|
| Самоначисление персоналом | Кассир проводит чеки «на себя» / друзей | `is_staff` исключение; алерт при > 3 начислениях на одного клиента в смену; анализ доли чеков одного клиента |
| Дробление чека | Один визит → несколько чеков ради штампов/порогов | `min_interval_minutes` между штампами; лимит срабатываний/день; порог по сумме одного чека |
| Реферальные кольца | Фейковые аккаунты, самореферал | Совпадение device_id / платёжного источника / IP-подсети; квалификация только по оплате деньгами ≥ мин. чека; задержка выплаты 24 ч; velocity ≤ 3 приглашений/день; ML-скор (V2) |
| Перебор промокодов | Автоматизированный ввод | Rate-limit, CAPTCHA после 5 ошибок, коды с checksum, блокировка на 30 мин |
| Возвратный фрод | Оплата → награда → возврат | Полный/частичный reverse с clawback; долг баллов; лимит отрицательного баланса; алерт при > 2 возвратов/мес у клиента |
| Оплата баллами → кэш-аут | Списание баллов и возврат деньгами | Возврат всегда в исходном виде (баллы → баллы) |
| Подмена времени/места | Чек-ин без присутствия, «счастливые часы» задним числом | Серверное время; динамический QR (TOTP 30 с); commit ≤ 15 мин после quote |
| Сговор ТСП-партнёров | Кросс-промо для вывода бюджета партнёра | Лимиты выдач/день, симметрия потоков, ручная модерация партнёрств представителем |
| Исчерпание бюджета конкурентами | Массовые покупки ради подарков | Лимиты на клиента; бюджет дневной; авто-пауза |

### 3.2 Скоринг и действия

`risk_score` клиента у точки (0–100) по признакам: доля чеков с наградами, интервалы между чеками, возвраты, совпадения устройств, географическая согласованность. Пороги: ≥ 60 — награды класса «бонус» откладываются на 24 ч (soft hold), ≥ 85 — только базовый кэшбэк платформы, кейс в очередь модерации. Все решения логируются и объяснимы (список сработавших правил).

## 4. Compliance (требует подтверждения юристом платформы)

| Тема | Требование / риск | Реализация |
|---|---|---|
| **152-ФЗ (ПДн)** | Минимизация, согласие на промо-коммуникации, цель обработки | Движок хранит `customer_id`; ТСП видит маскированный телефон; согласия из платформы; DPIA для сегментации и win-back; право на удаление — обезличивание профилей и леджера (замена `customer_id` на токен) |
| **54-ФЗ (ККТ)** | Корректное отражение скидок/баллов/авансов в чеках | Режимы адаптера «баллы = скидка» / «баллы = зачёт предоплаты»; сертификаты и абонементы — авансовые чеки ([08 §8](08-integrations.md)) |
| **Договор платформа–ТСП** | Финансирование промо-баллов ТСП, компенсация базовых баллов, порядок взаиморасчётов, возвраты | Оферта ТСП + приложение «Правила программы лояльности точки» (генерируется из `content.terms`) |
| **Правила для клиента** | Публичность условий каждой акции: срок, условия, ограничения | `content.terms` обязателен при публикации; страница «Условия» доступна из карточки акции |
| **38-ФЗ «О рекламе», ст. 9** | Стимулирующие мероприятия (в т.ч. розыгрыши LM-16): в рекламе указывать сроки, источник информации об организаторе, правилах, количестве призов | Для LM-16 автоматически формируется страница правил; пуши о розыгрыше содержат ссылку |
| **Маркировка интернет-рекламы** | Промо-рассылки о товарах ТСП пользователям платформы могут трактоваться как реклама | Решение юриста: перечень сообщений, требующих маркировки/учёта; технически — поле `is_ad` у шаблона уведомления |
| **Лотереи (138-ФЗ)** | Механика LM-16 не должна требовать платы за участие сверх покупки и не быть лотереей | Участие — только по факту покупки, без доп. платы; отсутствие «пусто»; правила опубликованы |
| **НДФЛ на бонусы** | Доходы физлиц в виде баллов по программам лояльности освобождены при условиях п. 68 ст. 217 НК РФ (публичная оферта, не сотрудники и т. д.) | Условия программы — публичная оферта; исключение сотрудников; крупные разовые призы (LM-16) — лимит стоимости, консультация по налогам |
| **Подарочные сертификаты** | Судебная практика: неиспользованный аванс подлежит возврату по требованию потребителя; «сгорание» рискованно | Срок — как срок действия оферты; остаток возвращается по заявлению; UI не обещает «сгорит» |
| **Защита прав потребителей** | Скидка/подарок не могут быть отозваны после оплаты; условия не меняются задним числом | Неизменяемые версии; quote — обещание; изменения действуют вперёд |
| **Антимонопольные / недобросовестная конкуренция** | Кросс-промо и «спец-скидки» не должны содержать ложных сравнений | Тексты `content.*` проходят авто-проверку запрещённых формулировок («самый дешёвый», «лучший») |
| **Финансовая отчётность ТСП** | Обязательства по выданным промо-баллам | Экспорт реестра лотов и погашений; показатель liability в кабинете |

## 5. Приватность по умолчанию

- Сегменты и win-back считаются внутри локации; данные клиента одной точки не видны другой (кросс-промо передаёт только факт выдачи купона, без истории покупок).
- Дата рождения используется только при `birthday_use = true`; движок получает `birthday_in_days`, а не дату.
- Логи не содержат телефонов/имён; `order_id` и `customer_id` — псевдонимы.
- Ретеншн профиля точки — 3 года после последней покупки, затем обезличивание.
