## Фаза 1 — Выбор платформы фискализации (решение владельца, Ч-1)

Что делаем: собираю сравнительную записку на 2 варианта, владелец решает.

- **Вариант А (рекомендация): Т-Банк «Онлайн-чеки».** Чеки через Receipt
  поверх Init (эквайринг уже Т-Банк: карта/T-Pay/СБП). Плюсы: один договор
  и один кабинет, минимальная интеграция, тестовый контур уже есть.
  Минусы: привязка к одному банку, тарифы чеков — сверить.
- **Вариант Б: отдельная облачная ККТ + ОФД** (АТОЛ Онлайн, и т.п.).
  Плюсы: независимость от банка, гибкость. Минусы: второй договор,
  отдельная интеграция, отдельный кабинет/мониторинг.
- **Юр. блок (параллельно, у юриста/бухгалтера — НЕ на агенте):** сверить
  агентскую схему: чек Правообладателя с признаком агента, ИНН Лицензиата
  как Поставщика; систему налогообложения в чеке (УСН?); предмет расчёта
  («услуги агента» vs «товар» — критично для ФФД); кто и что указывается
  в чеке при кэшбэке баллами (оплата баллами = снижение суммы наличными?
  — развилка, зафиксировать в PARAMS).
- Что нужно от владельца: вердикт А/Б + договор/тарифы; от юриста — подтверждение
  реквизитов чека.

Гейт Фазы 1: выбор зафиксирован в PARAMS, реквизиты чека утверждены юристом.

## Фаза 2 — Спека и канон (Super Z + владелец, без кода)

- Карточка `T-038-fiscalization-54fz` в canon/TASKS: «что решить» без рецептов.
- Канон-решения в файл-дома (DATA_MODEL/API_SPEC/PARAMS):
  - таблица `fiscal_documents`: order_id, payment_id, вид
    (prepayment/full/refund), сумма, ФД/ФП/фд-дата, статус
    (pending/sent/confirmed/failed), текст ошибки, счётчик ретраев;
  - триггер чека №1 «Предоплата 100%» — payment confirmed
    (HandleTBankNotificationAction);
  - триггер чека №2 «Полный расчёт» — развилка владельца: на `ready`
    (собран/передан) или `completed`; для доставки и самовывоза момент
    может различаться — зафиксировать канон;
  - чек возврата: отмена заказа до выдачи, возврат платежа, чарджбэк;
  - связь с леджером: узел «внешний чек» по образцу `external:bank`, Σ инвариант
    не ломается; чек — обязательство отчётности, не движение денег;
  - очередь/ретраи: чеки — асинхронно (Horizon), повтор по экспоненте,
    алерт при 3+ неудачах;
  - идемпотентность: один вид чека на платёж/заказ — unique-индекс.
- Что нужно от владельца: утвердить развилку «момент передачи» и правила
  кэшбэка в чеке.

Гейт Фазы 2: карточка + канон-правки закоммичены, факт-чек Super Z зелёный.

## Фаза 3 — Реализация (агент, core + admin + b2b, всё на фича-ветках)

- core: миграция + модель + `FiscalDocumentManager` + интерфейс провайдера
  + `TBankReceiptProvider` (или `AtolProvider` — по Фазе 1); триггеры в
  существующие точки (payment confirmed, OrderStatusMachine); ретраи;
  internal API для админки.
- admin: реестр фискальных документов (фильтры по статусу/заказу), страница
  документа, ручной «перезапуск» упавшего чека (право под высоким доступом).
- b2b: Лицензиат видит чеки по своим заказам (ссылка/реквизиты ФД) — база
  для месячного отчёта.
- app: квитанция (Ч-4) — сверить с money_flow §2.2: что уже есть с Т-029,
  добавить статус «чек сформирован» и реквизиты.
- Гейт: полный локальный гейт core через `tools/core-tests.sh`, unit на
  идемпотентность и оба триггера, приёмка на staging с мок-провайдером

Гейт Фазы 3: staging зелёный, сквозняк «заказ → оплата → чек №1 → ready →

## Фаза 4 — Боевая приёмка на 1₽ (самый осторожный шаг)

По канону Т-Банка (как 22.09): боевой терминал, СВОИ деньги, минимальные суммы.

1. Сначала тестовый контур платформы чеков (если есть test env — только он).
2. Затем бой на 1₽: заказ 1₽ → оплата своей картой → чек №1 → сверка ФД/ФП
   в кабинете банка/ОФД и в приложении «Проверка чеков ФНС» → передача →
   чек №2 → сверка. 
3. Возврат: отмена заказа → чек возврата → сверка.
4. Негатив: отключить провайдера → убедиться в ретраях/алерте → восстановить.
5. Сверка инварианта леджера Σ=0 после всех операций.
- Каждая боевой операция — по явному «го»; чек-реквизиты фиксируем в
  session-доке (доказательства приёмки).
- Гейт Фазы 4: чек №1, №2 и возврат реально зарегистрированы в ФНС,
  инвариант цел. Откат: `PAYMENTS_ENABLED=false` / обратный SHA-деплой.
