## Источник очереди

Ревизия владельца 2026-09-20 вечер / 2026-09-21 ночь: прогон сценариев на локальном
стенде, найденные нестыковки кабинета МСП. Решения владельца по каждому пункту
зафиксированы дословно в шапке соответствующей карточки.

## Обязательный старт (до первой правки)

1. **Скачать актуальную версию с GitHub** — работать по свежему клону, не по локальному
   состоянию чужой машины. Репозитории: `lovii-tech/lovii-core`, `lovii-tech/lovii-app`,
   `lovii-tech/lovii-b2b`, `lovii-tech/lovii-admin`; документация — `lovii-ru/lovii-docs`.
   Точка интеграции — ветка `staging`; фича-ветка от `staging`.
2. **Проверить, что всё на месте**: каждая карточка содержит снимок фактов с путями к коду
   на 2026-09-21. Пути и `file:line` могли сместиться — перепроверь по актуальному коду.
   Расхождение карточки с кодом — не импровизировать: зафиксировать в
   `lovii_docs/canon/FINDINGS.md` и вернуть вопрос на уточнение (`WORK_PROTOCOL.md` §2).
3. **Локальный стенд** и входы — по чек-листу `HANDOFF-2026-09-20-evening.md` (корень воркспейса)
   (docker compose → миграции b2b/admin → `stand-bootstrap.sh` → смоук; входы и грабли там же).
   ⚠️ Тесты ядра — только `bash ~/LOVII/tools/core-tests.sh <путь>`: прямой `pest`/`composer test`
   при закэшированном конфиге делает `migrate:fresh` по живой базе.
4. Правило владельца о сценариях (канон выпрямления маршрутов): найдена нестыковка —
   исполнитель чинит **маршрут целиком** (кто → куда → каким действием) и проверяет цепочку
   живьём, а не латает одну точку.

## Зависимости и порядок

- **SZ-067** — блокер и уже начат: фикс реализован локально (описание и evidence в карточке),
  в GitHub не отправлен. Делать первым: остальные пункты правят те же экраны и данные.
- **SZ-068** — рамочная задача: фиксирует «базовый набор» и границу app/b2b; её выводы
  нужны SZ-063/064/065/066, поэтому решать её стоит параллельно, но не дублировать их работу.
- **SZ-063** и **SZ-064** независимы друг от друга, но обе трогают кабинет МСП и модель точки.
- **SZ-065** (каналы товара) должен быть согласован с **SZ-066** (канал + радиус) и с моделью
  из **SZ-064** (товар × точка).
- Один агент ведёт задачу вертикально по всем затронутым репо (правило
  «Параллельные сессии» корневого `CLAUDE.md`); в `staging` в один момент пушит один агент.

## Гейты и передача

- app: `yarn test` (format → lint → unit → type-check → build), при затрагивании сценариев —
  e2e (`E2E_TARGET=staging yarn test:e2e:scenarios` для стенда).
- core/b2b/admin: `composer test` (для core на локальном стенде — только `tools/core-tests.sh`).
- Горячие пути (каталог/корзина/чекаут/кошелёк/поиск/лояльность/пул) — стресс-страж
  `lovii-app/scripts/stress/` на локальном стенде, сравнение с базлайном; всплеск
  `db.slow_requests` в `laravel.log` = регресс.
- Мерж: фича → `staging` (авто-деплой, приёмка владельца на стенде) → `master`
  (прод **только вручную**: `gh workflow run ci.yml --repo lovii-tech/<repo> --ref master`).
  **Пуш в `staging`/`master` — только после явного «го» владельца.**
- Каждая карточка закрывается по протоколу: отчёт исполнителя → Приёмка-1 → Приёмка-2
  (`Достаточно` / `Доработка: <пункты>`), затем `git mv` в `archive/tasks/`.
