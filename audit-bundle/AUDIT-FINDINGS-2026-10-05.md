## 0. TL;DR

Пайплайн для команды из двух человек сделан аккуратно: forced-command wrapper,
environment'ы GitHub, health-check'и, heredoc-ловушки задокументированы, docs-only
скип починен дважды (F-075/F-076) с разбором. Но **заявленная модель угроз не

не бэкапится по расписанию (A-4). Это три P0. Хорошая новость: правильный
механизм (gostiny-deploy + pull образов из registry) **уже написан** — надо
перевести на него 4 LOVII-репо, а не изобретать новый.

Отдельно: сам пакет аудита дефектен в трёх местах (§1) — часть заявленного
аудита (B-4, staging-стек) неверифицируема.

## 2. Находки по существу — P0

### A-1. `DEPLOY_SSH_KEY` даёт произвольный shell, а не forced-command (P0)
**Факт из workflow'ов:** все 8 deploy-job'ов делают
`ssh … "…bash -s" <<'ENDSSH'` — на сервер уезжает произвольный скрипт и
исполняется. Если бы ключ был заперт `command=…/gostiny-deploy,restrict`,
wrapper прочитал бы `SSH_ORIGINAL_COMMAND = "DEPLOY_PATH=… bash -s"` и ответил
`DENY usage: deploy <stack>`. Значит **CI-ключ — это полный shell от `deploy`**
на машине с прод-БД, .env и mTLS банка. Это прямо противоречит INFRA-CONTEXT
(«gostiny-deploy ограничивает CI-ключи») и делает B-2 оптимистичнее реальности.

Цепочка атаки: доступ к секрету `DEPLOY_SSH_KEY` (любой admin репо, любой job
на раннере, утечка из логов) → shell → `docker exec` в прод-контейнеры, чтение
.env, mTLS-ключей Т-Банка.

**Фикс:** перевести LOVII-деплой на уже существующий паттерн gostiny-deploy:
1. Деплой-логику из heredoc'ов (fetch/reset/build/migrate/up/health) перенести
   в версионируемый скрипт на сервере (расширить gostiny-deploy подкомандами
   `deploy <stack> <ref>`, он уже умеет ref).
2. В `authorized_keys`: `command="/usr/local/bin/gostiny-deploy",restrict` для
   CI-ключа. Workflow сводится к `ssh deploy@host 'deploy lovii-core <sha>'`.
3. Отдельный ключ на окружение (см. A-11).

**Цена:** низкая-средняя: скрипт уже на 80 % написан, heredoc'и и так
продублированы 8 раз — выносить их в одно место давно пора.

### A-2. Раннеры = root-эквивалент на прод-хосте (P0, подтверждает и усиливает B-1)
Job'ы бегут от `deploy` с доступом к host docker daemon (workflow'ы свободно
делают `docker run -v …`). Доступ к docker.sock == root на хосте
(`docker run -v /:/host …`). Усиления относительно B-1:

- **`pull_request`-триггер включён** и уходит на тот же раннер: код PR
  исполняется (build Dockerfile, тесты) *до* ревью. Для org из 2 админов риск
  «свой» минимален, но любой скомпрометированный аккаунт/токен участника — это
  немедленный RCE на прод-хосте без единого аппрува.
- **Четыре раннера делят одного пользователя** `/home/deploy` — job репо X
  читает `_work`, кэши и файлы репо Y, включая `~/.ssh/deploy_key` (см. A-3).
- **Общий docker daemon с продом** — отдельный вектор A-9.

**Фикс (порядок внедрения):**
1. Срочно (день): `pull_request` переключить на `ubuntu-latest` (или снять
   триггер) — self-hosted оставить только для push в защищённые ветки:
   `runs-on: ${{ github.event_name == 'pull_request' && 'ubuntu-latest' || vars.CI_RUNNER || 'ubuntu-latest' }}`.
2. Неделя: раннеры — в контейнеры (официальный `actions/runner` image или
   `myoung34/github-runner`), по одному пользователю/контейнеру на репо, без
   монтирования host docker.sock; docker для сборок — **отдельный dind** или
   rootless dockerd с собственным graph-root. Прод-стеки раннерам не видны.
3. Деплой из раннера — только `ssh` на forced-command (A-1): раннер больше не
   должен уметь трогать прод напрямую, даже находясь на той же железке.

**Цена:** средняя (совпадает с оценкой B-1); кэши buildx переезжают в volume
dind — одноразовая потеря кэша.

### A-3. Приватный деплой-ключ остаётся на диске раннера навсегда (P0)
`echo "${{ secrets.DEPLOY_SSH_KEY }}" > ~/.ssh/deploy_key` на self-hosted
раннере пишет ключ в **постоянный** `/home/deploy/.ssh/deploy_key` и никто его
не удаляет. Итог: ключ, дающий shell (A-1), лежит в открытом виде на диске
между запусками, читаем любым job'ом любого из 4 репо и любым, кто получил
`deploy`-доступ. GitHub Secrets тут уже не защита.

**Фикс:** (а) минимум — шаг `if: always(): shred -u ~/.ssh/deploy_key`;
(б) правильно — `ssh-agent` в памяти job'а (ключ не касается диска);
(в) по-настоящему — после A-1 ценность ключа падает до «может вызвать деплой»,
и это перестаёт быть P0. **Цена:** минимальная, сделать сегодня.

### A-4. Прод-БД денежного леджера без автоматического бэкапа (P0 — повышение B-5 с P1)
По крону бэкапится только staging (04:17), на **тот же диск**; прод — «дампы
вручную», тоже локально. Для системы с леджером и выплатами это не P1:
единственный диск = единая точка потери и денег, и доказательной базы
(Σ ног = 0 нечем будет восстановить). Отказ диска, шифровальщик, попавший через
A-1/A-2, или `rm -rf` ошибкой — и бизнес закончился.

**Фикс:**
1. Ночной `pg_dump -Fc` прод-БД + `wal-g`/`pgbackrest`, если нужен PITR
   (для леджера — нужен).
2. Off-site: S3-совместимое хранилище с **object lock / immutability** и
   lifecycle (атакующий с хоста не должен мочь удалить бэкапы — ключ только на
   запись, без delete).
3. В бэкап-набор добавить: `.env` обоих контуров (шифрованно, напр. `age`),
   mTLS-сертификаты Т-Банка, volume `storage`, конфиги caddy.
4. Ежемесячный restore-тест на staging + проверка `ledger:tree` на
   восстановленной базе — это естественный критерий успешности restore.

**Цена:** низкая (скрипт + bucket), ценность максимальная во всём списке.

## 3. Находки — P1 / P2 / P3

### A-5. Деплой уезжает не тем кодом, что тестировался (P1)
Сервер делает `git reset --hard origin/${DEPLOY_BRANCH}` — то есть деплоится
**вершина ветки на момент деплоя**, а не SHA, прошедший checks. Пуш в staging
во время работы checks предыдущего пуша → задеплоится непроверенный коммит
(TOCTOU). В lovii-core `PUSH_AFTER=${{ github.sha }}` уже передаётся, но
используется только для docs-diff; в app/b2b/admin SHA не передаётся вовсе.
**Фикс:** передать `DEPLOY_SHA='${{ github.sha }}'` во всех 4 репо и делать
`git reset --hard "$DEPLOY_SHA"` (fallback на origin/branch для ручных
запусков). Правка ×8 мест (ещё аргумент за вынос скрипта, A-1).

### A-6. `cancel-in-progress: true` может убить деплой посреди миграций (P1)
`concurrency: ci-${{ github.ref }}` + cancel действует на **весь** workflow,
включая deploy-job'ы. Второй пуш в `staging` отменяет первый run — возможно,
между `migrate --force` и `up -d`: схема новая, контейнеры старые, стенд лежит.
Для production риск ниже (ручной запуск), но тот же.
**Фикс:** у deploy-job'ов собственная группа:
`concurrency: { group: deploy-${{ github.ref }}, cancel-in-progress: false }`
(job-level concurrency перекрывает workflow-level). Checks пусть отменяются.

### A-7. `StrictHostKeyChecking=no` обнуляет проверку хоста (P1)
`ssh-keyscan` наполняет known_hosts (сам по себе TOFU, да ещё с `2>/dev/null`),
после чего `-o StrictHostKeyChecking=no` разрешает **любой** ключ хоста. MITM
по пути раннер→SRV отдаёт атакующему и приватный ключ не отдаст, но весь
heredoc-скрипт и секреты окружения — да, и подменит исполняемое.
**Фикс:** публичный host key SRV положить в repo variable (он не секрет),
писать его в known_hosts и убрать оба костыля; минимум —
`-o StrictHostKeyChecking=accept-new` без keyscan.

### A-8. Actions без SHA-пина, workflow без `permissions:` (P1, подтверждает B-3)
Подтверждаю B-3 целиком. Дополнение: ни в одном workflow нет блока
`permissions:` — GITHUB_TOKEN получает дефолтные права на self-hosted раннере.
**Фикс:** `permissions: { contents: read }` на верхнем уровне всех 4 файлов +
пин `actions/checkout`, `docker/setup-buildx-action`, `docker/build-push-action`,
`actions/cache` по полному SHA (dependabot/renovate умеют обновлять пины).

### A-9. Общий docker daemon: CI может отравить прод-образы и кэш (P1)
CI-образы (`lovii-ci-php:ci`) — **мутабельные теги на том же демоне**, где
живут прод-образы `lovii-core/app` и выполняется прод-`build --pull`. Любой
job (в т.ч. из PR, см. A-2) может: перетегировать/подменить локальный образ,
отравить build-cache слоёв (следующий прод-build молча возьмёт отравленный
слой из кэша), устроить DoS (диск/память демона — лимиты compose не спасают от
`docker run` из CI). Это самостоятельный вектор даже после изоляции раннеров.
**Фикс:** тот же, что A-2 п.2 (отдельный dockerd для CI) + прод-сборку увести
с хоста целиком (A-10): прод-демон тогда только `pull` подписанных образов.

### A-10. Нет артефакта и нет отката (P1, расширяет B-7)
Образы собираются **на прод-хосте при каждом деплое** без SHA-тегов:
нет воспроизводимости (база `php:8.5-fpm-alpine` плавает — сами же поймали
дрейф в b2b ArchTest), нет мгновенного отката, build-отказ = несостоявшийся
деплой (случай 05.10 с rpc EOF), build жрёт CPU/RAM прод-машины под нагрузкой.
Health-check при провале делает `exit 1` и оставляет прод как есть — откат
руками.
**Фикс (целевая схема, механика уже наполовину есть в gostiny-deploy):**
1. CI собирает образ **один раз** в job'е checks, тегает `ghcr.io/...:<sha>`,
   пушит в GHCR.
2. Деплой = `ssh deploy@host 'deploy lovii-core <sha>'` → wrapper делает
   `docker login --password-stdin` (уже умеет), `compose pull`, `up -d`.
3. Откат = `deploy lovii-core <предыдущий sha>` — секунды, без сборки.
4. В compose `image: ghcr.io/...:${TAG}`; retry на build в CI (2-3 попытки
   с backoff) закрывает транзиентные отказы из B-7.
**Цена:** средняя; это самый большой по пользе рефакторинг после P0.

### A-11. Один ключ и плоские секреты на оба окружения (P1)
`DEPLOY_SSH_KEY/HOST/USER` — общие секреты репозитория: staging-деплой владеет
тем же ключом, что продовый. Environment'ы `staging`/`production` объявлены,
но хранят только `DEPLOY_PATH`.
**Фикс:** (1) отдельная пара ключей на окружение, секреты перенести в
environment secrets; (2) на environment `production` включить **required
reviewers** (второй админ подтверждает прод-деплой — бесплатный four-eyes) и
deployment branch policy = только `master`; (3) после A-1 ключи дополнительно
различаются параметром стека в forced-command (закрывает B-2 для CI-ключей).

### A-12. Миграции применяются к живому проду до переключения контейнеров (P2)
`migrate --force` выполняется из нового образа, пока работают старые
контейнеры: несовместимая миграция (drop/rename колонки) кладёт прод на окно
между migrate и `up -d`, а при провале health-check'а новая схема остаётся со
старым... вернее, уже новым кодом — короче, отката схемы нет вообще.
**Фикс:** дисциплина expand/contract (деструктивные изменения только отдельным
релизом) — записать в правила; pre-migration dump (связать с A-4: дамп перед
каждым прод-migrate — дёшево); `php artisan migrate --pretend` в checks как
смок.

### A-13. tbank-mock живёт в прод-compose (P2)
Профиль `mock` выключен по умолчанию — хорошо, но одна переменная
`COMPOSE_PROFILES=mock` в прод-.env поднимает мок-банк **с публичным
caddy-маршрутом** `mock-pay-staging.lovii.ru` из прод-стека, в сети прода.
Плюс мок = `node:22-alpine` с кодом через volume — непроверяемый снапшот.
**Фикс:** вынести мок в `docker-compose.staging-extras.yml`, который прод
физически не читает; мок-домен привязать к staging-стеку.

### A-14. Admin: деплой гейтится фактически только линтером (P2, подтверждает B-6)
PHPStan, type-coverage и **все тесты** — `continue-on-error`. «needs: checks»
выглядит как гейт, но пропускает красные тесты в прод. Подтверждаю B-6;
добавлю: b2b-карантины (`wip-webauthn`, `sz025-quarantine`, порог 66) — тот же
долг в мягкой форме, нужен тикет с дедлайном на возврат к 70 и снятие
карантинов, иначе «временное» станет архитектурой.

### A-15. Пароль Redis в argv healthcheck'а (P3)
`redis-cli -a ${REDIS_PASSWORD} ping` светит пароль в `docker inspect` и в
процесс-листе. **Фикс:** `REDISCLI_AUTH` env + `redis-cli ping`, или
`redis-cli --no-auth-warning -a "$REDISCLI_AUTH"`. Мелочь, но бесплатная.

### A-16. Раннеры: nohup-из-крона вместо супервизора (P3, подтверждает B-9)
Подтверждаю B-9. Уточнение фикса: `./svc.sh install deploy` у официального
раннера сам генерирует systemd-юнит; либо `systemd --user` + 
`loginctl enable-linger deploy`. После контейнеризации (A-2) — `restart: always`
решает то же самое.

### A-17. Аудит-трейл пишется, но не читается (P3, подтверждает B-10)
Подтверждаю. Дополнение: после A-1 лог gostiny-deploy станет **единственной**
точкой всех деплоев — месячная сводка сведётся к `grep OK /var/log/gostiny-deploy.log`.
Добавить в сводку: `last`/`journalctl _COMM=sshd` по ключам (кто логинился
интерактивно) и diff `authorized_keys` против ACCESS-MATRIX.

### A-18. gostiny-deploy: REF_RE пропускает ref, начинающийся с `-` (P2)
*(добавлено при контрольной перепроверке)* `REF_RE='^[A-Za-z0-9._/-]+$'`
допускает значения вида `-b`, `--detach`, `--orphan` — они уходят в
`git checkout --quiet --force "$ref"` как **опции**, а не ref. Эксплуатация
ограничена (вызывающий и так авторизован деплоить), но при расширении wrapper'а
на LOVII (A-1) это станет единственной линией обороны.
**Фикс:** `REF_RE='^[A-Za-z0-9][A-Za-z0-9._/-]*$'` + аналогично запретить
ведущий `-`/`.` в NAME_RE; в идеале — `git rev-parse --verify "refs/…"` перед
checkout.

Пропуски BASELINE (не упомянуто, найдено аудитом): A-3 (ключ на диске раннера),
A-5 (деплой не того SHA), A-6 (cancel посреди миграций), A-7 (StrictHostKeyChecking=no),
A-11 (один ключ на оба окружения), A-12 (миграции без отката), A-13 (мок в прод-compose).

## 5. Ответы на вопросы владельца

1. **Изоляция раннеров без потери деплой-механики** — да: раннеры в контейнеры
   с отдельным dind (A-2), деплой через forced-command `deploy <stack> <sha>`
   (A-1) + образы из GHCR (A-10). Механика даже упрощается: heredoc'и исчезают.
2. **Разделение прав deploy прод/staging** — отдельный ключ на окружение в
   environment secrets, каждый заперт `command=…gostiny-deploy --only=<stack>`,
   required reviewers на production (A-11). Отдельный unix-юзер на контур —
   следующий шаг, но ключи+wrapper дают 80 % эффекта дёшево.
3. **Достаточна ли схема секретов** — GitHub Secrets + .env приемлемы для
   этого масштаба, НО: ключ сейчас оседает на диске раннера (A-3), один на оба
   окружения (A-11), а .env/mTLS не входят в бэкап (A-4). Закрыть эти три —
   и Vault пока не нужен.
4. **docker-socket-proxy / docker.sock** — по gateway вердикт невозможен, файл
   пуст (M-1). По раннерам: доступ к host-сокету = root, см. A-2/A-9 — убирать,
   а не ограничивать.
5. **Бэкапы** — не хватает: прод-БД по расписанию, off-site с immutability,
   PITR для леджера, .env+mTLS+storage в наборе, restore-тест с `ledger:tree`
   (A-4).
6. **Идемпотентность/откат** — `git reset --hard` ещё и деплоит не тот SHA
   (A-5); отката нет ни у кода (A-10 — нужны SHA-теги в registry), ни у схемы
   (A-12 — expand/contract + pre-migrate dump). cancel-in-progress может
   прервать деплой посередине (A-6).
