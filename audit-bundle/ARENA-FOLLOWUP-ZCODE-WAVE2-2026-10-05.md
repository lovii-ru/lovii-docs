# ARENA FOLLOW-UP — вопросы и критерии приёмки Волны 2 для zcode

**Дата:** 2026-10-05
**Адресат:** zcode, исполнитель
**Основание:** `EXECUTION-WAVE2-2026-10-05.md`, `ARENA-INBOX-2026-10-05.md`,
`AUDIT-RESPONSE-ZCODE-R2-2026-10-05.md`, `AUDIT-CONTROL-2026-10-05.md`.

## 1. Цель и границы

Это узкий follow-up к отчёту Волны 2, а не повтор аудита A-1…A-18 и не новое
задание на перестройку инфраструктуры. Цель — отделить заявленное исполнение
от проверяемых доказательств, закрыть только R-2.1…R-2.5 и явно назвать
блокеры, которые требуют решения владельца.

**Не запускать production-деплой специально ради аудита.** Проверку боевого
пути выполнить на следующем разрешённом владельцем production-релизе. Не
передавать в этот пакет ключи, пароли, содержимое `.env`, дампы БД или иные
секреты.

## 2. Текущая оценка по имеющимся материалам

| Рекомендация | Что заявлено в отчёте | Статус приёмки Арены |
|---|---|---|
| R-2.1 forced-command | Wrapper и ключи с ограничением по окружению; отрицательные проверки и четыре staging-деплоя | **Принять для staging по отчёту;** исходник wrapper и post-Wave2 workflow в пакете отсутствуют, production-путь ещё не проверен |
| R-2.2 prod-бэкап | Локальный `pg_dump -Fc`, retention 7 | **Частично; P0 открыт.** Off-site-копии и restore-теста нет |
| R-2.3 ключи по окружениям | Отдельные staging/production ключи и GitHub Environment secrets; старые CI-ключи удалены | **Частично.** Требование production approval не закрыто; есть зафиксированный HTTP 422 для required reviewers. Остаются неограниченные интерактивные/сторонние SSH-ключи |
| R-2.4 pre-migrate dump | Dump перед production-миграциями; ошибка dump должна останавливать деплой | **Заявлено выполненным;** нужны безопасная проверка ветки отказа и доказательство из исходника |
| R-2.5 env-parity | Ежедневный скрипт и лог; первый прогон нашёл различия | **В работе/на проверке.** Не приложены отрицательный тест и разбор найденных различий |

Здесь «не подтверждено в пакете» не означает «не сделано»: это означает, что
независимо повторить проверку по текущим файлам нельзя.

## 3. Вопросы zcode и проверяемые результаты

### R-2.1 — forced-command и фактическая конфигурация

**Вопросы**

1. Можно ли приложить санитизированный снимок `/home/deploy/bin/lovii-deploy`
   и четырёх workflow после Волны 2? Укажите SHA/версию каждого снимка и
   подтвердите, что экспорт соответствует файлам на сервере и в GitHub.
2. Укажите GitHub Actions run ID (или ссылки) по четырём staging-деплоям,
   SHA, который запускался, SHA на стенде после деплоя и результат wrapper-лога
   `START/OK`. Секреты и содержимое ключей не прикладывать.
3. Подтвердите, что парсер `SSH_ORIGINAL_COMMAND` не выполняет переданные
   аргументы через `eval`/shell-интерпретацию и отклоняет лишние аргументы,
   кавычки/метасимволы, ведущий `-`, неизвестный стек и несовпадение scope.
   Какие проверки уже запускались и каков их результат?
4. Как будет зафиксирована первая production-проверка без отдельного
   тестового деплоя: какой сигнал подтвердит scope production-ключа, ожидаемый
   SHA, pre-migrate dump и health-check на следующем разрешённом релизе?

**Достаточный результат**

- В пакете есть санитизированный wrapper и актуальные workflow, совпадающие
  с задекларированным исполнением.
- Для staging сохранены проверяемые run ID/SHA и результаты положительных и
  отрицательных тестов; production-путь помечен «ожидает следующего
  разрешённого релиза», пока его не проверили.
- Не публикуются приватные ключи, секреты, адреса, дампы или значения `.env`.

**Достижимость:** исходники, run ID и обезличенные логи можно приложить без
production-изменений. Боевой тест — только вместе с обычным владельческим
релизом.

### R-2.2 — off-site-бэкап и восстановление

**Вопросы**

1. Какой именно ввод нужен от владельца для off-site: bucket, регион,
   retention/object-lock-политика и write-only учётные данные? Назовите только
   требуемые параметры; секрет передавать исключительно через утверждённый
   защищённый канал, не в GitHub-репозиторий и не в этот пакет.
2. После получения ресурса: как будет доказано, что ночной dump действительно
   попал off-site и его целостность проверена? Где будет сигнал об ошибке
   cron/upload?
3. Когда и на каком непроизводственном стенде провести restore-тест? Как
   зафиксировать успешное восстановление и проверку `ledger:tree`, не помещая
   данные БД в audit-bundle?

**Достаточный результат**

- Копия актуального production dump доступна вне SRV, с оговорёнными
  write-only правами, retention и защитой от удаления/перезаписи.
- Restore-тест завершён на staging/изолированном контуре; дата, итог и
  проверка леджера зафиксированы без чувствительных данных.
- Пока bucket или ключ не предоставлены, R-2.2 остаётся **частичным P0**;
  локальный бэкап продолжает работать и не выдаётся за off-site-защиту.

**Зависимость:** создание bucket/выдача доступа — решение и действие владельца;
настройка, проверка и restore-тест — достижимая работа zcode после этого.

### R-2.3 — approval для production и оставшиеся SSH-доступы

**Вопросы**

1. Подтверждается ли, что HTTP 422 по required reviewers блокирует и
   production Environment в этих репозиториях? В текущем отчёте перенесённые
   secrets описаны, но production approval/замена этому гейту — нет.
2. Если GitHub-plan не позволяет required reviewers, какой вариант выносится
   владельцу на выбор: изменение плана или иной контролируемый production
   запуск, при котором production-ключ не доступен staging и не выдаётся
   обычному CI без согласованного контроля? До решения владельца не менять
   способ production-деплоя.
3. В `authorized_keys` после удаления CI-ключей остаются четыре ключа без
   forced-command (два интерактивных и два `turokserials`, согласно
   `ARENA-INBOX §3`). Для каждого достаточно дать владельцу fingerprint/комментарий
   (без приватной части), назначение, владельца доступа и предложенное действие:
   ограничить wrapper'ом, удалить либо явно принять как исключение. Их не
   удалять без разрешения владельца.

**Достаточный результат**

- Staging-ключ не может вызвать production-стек; production-ключ не
  предоставляется staging-job.
- В отчёте прямо указано одно из двух: production approval настроен и
  проверен либо он **заблокирован**, а владелец выбрал и принял конкретную
  альтернативу/риск.
- Для всех оставшихся shell-ключей есть владельческое решение; до него они
  считаются открытым доступом, а не частью закрытого R-2.3.

**Достижимость:** проверка границ ключей и инвентаризация выполнимы сейчас.
Выбор плана и принятие остаточного риска принадлежат владельцу.

### R-2.4 — pre-migrate dump

**Вопросы**

1. Приложите санитизированный фрагмент wrapper с порядком «dump → migrate» и
   укажите каталог/права/правило хранения дампов.
2. Проверялся ли безопасно сценарий ошибки `pg_dump`? Нужен тест на staging
   или с подменённой командой, который доказывает: ошибка dump останавливает
   процесс до вызова `migrate` и `up`.
3. На первом будущем production-релизе подтвердите запись pre-migrate dump и
   совпадение задеплоенного SHA с SHA workflow.

**Достаточный результат:** есть тест, где ошибка dump приводит к abort до
миграции; успешная ветка сохраняет dump с ограниченными правами. Production
подтверждение добавляется только после следующего разрешённого релиза.

**Достижимость:** отказной сценарий можно проверить вне production сейчас;
боевую ветку — при обычном релизе.

### R-2.5 — env-parity

**Вопросы**

1. Дайте список найденных имён ключей по каждому стеку и классификацию:
   обязательный, опциональный с default, намеренно различающийся между
   production/staging. Значения секретов не нужны. Отдельно разберите
   `APP_PORT`, `SESSION_DOMAIN`, `CORE_NETWORK`, `IMAGE_PREFIX` и число
   отсутствующих ключей в admin.
2. Проверьте sentinel-сценарий на временных fixture-файлах: отсутствующий
   ключ должен обнаруживаться; не удаляйте ключ из живого `.env` ради теста.
3. Подтвердите, что cron/лог не раскрывают значения `.env`, и укажите, как
   владелец узнает о новой разнице. Само сравнение имён ключей не проверяет,
   что значение задано верно — это ограничение следует явно оставить в отчёте.

**Достаточный результат:** есть классифицированный baseline без неразобранных
production-расхождений и воспроизводимый тест обнаружения отсутствующего
ключа; лог содержит только имя стека/ключа и статус проверки.

**Достижимость:** fixture-тест и классификация доступны сейчас; исправление
самих live-конфигов — только после подтверждения, что конкретный ключ там
действительно обязателен.

## 4. Что можно сделать сейчас, а что зависит от владельца

| Работа | Кто может выполнить | Условие |
|---|---|---|
| Экспортировать wrapper/workflow, приложить run ID/SHA и санитизированные доказательства | zcode | Без доступа к секретам в отчёте |
| Проверить parser-deny cases, abort при ошибке pre-migrate dump и env-parity на fixture | zcode | Без production-изменений |
| Классифицировать оставшиеся SSH-ключи и env-различия | zcode; решение по доступам — владелец | Не удалять ключи и не менять live `.env` без разрешения |
| Provision off-site bucket/доступа | владелец | Требуется безопасно передать доступ zcode |
| Выбрать production approval/альтернативный контроль | владелец | Зафиксировать блокер 422 и остаточный риск |
| Проверить новый путь в production | zcode + владелец | Только на следующем разрешённом production-релизе |

## 5. Граница этой приёмки

Этот документ не закрывает и не переводит в работу другую волну. Изоляция
раннеров R-3.1, root-правка старого `gostiny-deploy` R-1.8, экспорт gateway
R-0.1/B-4 и GHCR/rollback R-3.2 остаются отдельными открытыми пунктами.
Их нельзя считать выполненными на основании Волны 2.

## 6. Формат ответа zcode

По каждому R-2.1…R-2.5 ответить одной строкой статуса (`готово`, `частично`,
`заблокировано`, `ожидает production-релиза`) и приложить:

- путь/версию проверяемого артефакта;
- CI run ID и SHA либо ссылку на безопасный тест;
- результат относительно критерия из §3;
- оставшийся шаг, ответственного и зависимость от владельца.

После этого можно вынести приёмку по каждому пункту отдельно. До получения
этого ответа общий статус — **Волна 2 частично выполнена; R-2.2 и часть R-2.3
не закрыты, production-проверка R-2.1/R-2.4 ожидает следующего разрешённого
релиза**.
