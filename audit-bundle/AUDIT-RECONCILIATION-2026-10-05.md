# AUDIT-RECONCILIATION — финальная сверка аудита (2026-10-05)

Стороны: внешний аудитор (arena) ↔ исполнитель (zcode).
Вход: `AUDIT-FINDINGS` + `AUDIT-CONTROL` (arena) ↔ `AUDIT-VERDICT-ZCODE`
(zcode, с живой проверкой §4 на SRV). Этот документ — **итоговое согласованное
состояние**; при расхождении с тремя предыдущими верен этот файл.

## 1. Итог: разногласий не осталось

18/18 находок согласованы. Обе поправки zcode **принимаются аудитором**:

- **Z-1 принята → M-1 переформулирована:** gateway-файл не «пуст», а
  **нечитаем пользователю deploy** (`/opt/gateway` root:root) — экспорт молча
  отдал 0 байт. Приоритет и действие не меняются: R-0.1 выполняется
  root-сессией владельца, вердикт по B-4 по-прежнему отложен до этого.
  NB: этот случай — точная иллюстрация, зачем нужен R-0.4: sha256-манифест
  при сборке пакета ловит класс ошибок «экспорт молча отдал пустоту»
  (`e3b0c442…` = хэш пустого ввода, детектится автоматически).
- **Z-2 принята → M-2/A-13 переквалифицированы:** один compose-файл на оба
  контура — осознанный дизайн (подтверждено md5 на SRV + COMPOSE_PROFILES
  только в staging-.env). M-2 из «дефекта пакета» становится «README пакета
  должен документировать дизайн» (правка R-0.2 сужается до строки в README).
  R-3.4 (мок в staging-extras) сохраняется со статусом **hardening, не фикс
  ошибки**: барьер «одна env-переменная до публичного мок-банка в прод-сети»
  остаётся тонким.

Живая проверка zcode закрыла оба условных статуса §1 CONTROL:
A-1 — подтверждён **наблюдением** (`authorized_keys`: LOVII-ключи без
`command=`), статус ⚠️→✅; A-3 — ключ на диске найден (✅); A-4, A-18 — ✅.

## 2. Ответ на оговорку zcode по R-1.7 (PR → ubuntu-latest при пустом биллинге)

Оговорка справедлива: при исчерпанных минутах R-1.7 в исходном виде = PR
вечно в Queued. Но оставлять PR-код на прод-раннере тоже нельзя (вектор A-2).
Согласованное решение — заменить R-1.7 на **R-1.7b**:

**R-1.7b | P1 | все 4 ci.yml:** PR-джобы остаются на self-hosted, но
заворачиваются в environment с required reviewer:
```yaml
  checks:
    environment: ${{ github.event_name == 'pull_request' && 'ci-selfhosted' || '' }}
```
GitHub Environment `ci-selfhosted` (×4 репо): required reviewers = второй
админ. Эффект: код PR **не исполняется на SRV, пока второй человек не нажал
Approve**, посмотрев diff. Минуты не тратятся, CI на PR сохраняется,
four-eyes появляется именно там, где раньше был RCE-вектор.
- Fallback, если аппрувы мешают потоку: убрать `pull_request`-триггер целиком
  (страховкой остаётся полный checks на push в staging) — хуже, но честнее
  «очереди навсегда».
- Целевое состояние неизменно: R-3.1 (sandbox-раннер в контейнере без
  docker.sock) снимает и аппрувы, и риск; после него environment-гейт можно
  убрать.

## 3. Свежие F-079/F-080 как эмпирическое подтверждение аудита (+1 рекомендация)

- **F-079** (карантин SZ-025 месяц прятал насквозь сломанный WebAuthn) — это
  ровно сценарий A-14/R-3.3: «временный» continue-on-error/карантин становится
  хранилищем прод-багов. Подтверждает требование: карантин — только с тикетом
  и дедлайном.
- **F-080** (`INTERNAL_ADMIN_SECRET` отсутствовал в прод-.env ~5 месяцев,
  джобы молча 401-ились) — класс дыр, который текущий план не закрывал.
  Добавляется рекомендация:

**R-2.5 | P2 | SRV + репо | env-parity check:** скрипт сравнения **ключей**
(не значений) `.env` между `.env.example` ↔ prod ↔ staging для всех стеков:
`comm -3 <(ключи example) <(ключи prod)` по каждому `/opt/*/.env`; запуск —
крон раз в сутки с алертом в TG/лог + обязательный шаг в чек-листе релиза,
вводящего новую переменную («в оба стенда + обе стороны моста», как в уроке
F-080). Done: искусственно удалённая переменная детектится за ≤24 ч.
