# BASELINE-RECOMMENDATIONS — стартовая позиция внутреннего агента

Это мои находки до внешнего аудита. Задача аудирующих моделей: подтвердить,
опровергнуть или дополнить. Формат каждой: риск → фикc → цена внедрения.

## B-1. Раннеры без изоляции на прод-хосте (P0)

Job'ы выполняются от пользователя `deploy` на хосте с прод-БД, .env и
mTLS-ключами банка. Любой admin репо (или скомпрометированный action-тег)
получает произвольный код на этой машине.

**Фикс:** раннеры в контейнерах/VM; docker-доступ им нужен только для сборки
→ свой dockerd (dind) или удалённый buildkit-endpoint с правами только на
build; деплой — через существующий `gostiny-deploy` (он уже заперт
forced-command'ом — правильный паттерн, расширить его же на всё).

**Цена:** средняя (перенести 4 runner'а в контейнеры, пересмотреть кэши).

## B-2. У `deploy` один shell для прод и staging (P1)

gostiny-deploy ограничивает CI-ключи, но 8 других ключей дают полную
shell-сессию на машине с обоими стендами.

**Фикс:** каждому ключу `command=.../gostiny-deploy,restrict` с параметром
стека; интерактивный shell — только у владельца (и то лучше через отдельный
ключ). Ключи чужого проекта (turokserials-api) — либо убрать, либо запереть
так же.

## B-3. Actions не запинены по SHA (P1)

`uses: actions/checkout@v4` — тег может быть переписан. Для self-hosted
раннеров на прод-хосте это прямая эскалация.

**Фикс:** пин всех внешних actions по полному SHA коммита + `permissions: {}`
в каждом workflow (least privilege GITHUB_TOKEN).

## B-4. docker-socket-proxy у gateway — проверить политику (P1)

Caddy получает доступ к docker-сокету через tecnativa/docker-socket-proxy
(правильно), но нужно убедиться, что раннеры НЕ используют этот прокси и что
прокси разрешает только containers labels read.

## B-5. Бэкапы только staging-БД и только на тот же диск (P1)

`backup-staging-db.sh` 04:17 в `/home/deploy/backups`. Прод-БД бэкапится
дампами вручную (`~/backups` — тоже локально).

**Фикс:** бэкап прод-БД по расписанию + вынос на второй носитель/off-site
(хотя бы object storage с lifecycle), проверка восстановления раз в месяц.

## B-6. `continue-on-error` в admin CI (P2)

admin-тесты настроены continue-on-error — красные тесты не блокируют мерж.
**Фикс:** разобраться с падениями (по памяти — 9 предсуществующих
PlatformOrderSettings), снять флаг.

## B-7. Transient-отказ docker build валит деплой (P2)

05.10 деплой упал на rebuild из-за rpc EOF демона; ретрай job спас.
**Фикс:** retry-обёртка на шаге build (2-3 попытки с backoff), health-check
после деплоя с автооткатом на предыдущий образ (tag по git SHA, compose
`image:` пиннинг — сейчас образы без тега SHA?).

## B-8. Секреты в GitHub Secrets без ротации (P2)

DEPLOY_SSH_KEY и прочие не ротировались. **Фикс:** календарная ротация
(квартал), после любого доступа подрядчика.

## B-9. Watchdog раннеров (P3)

`@reboot` стартует раннеры, но если процесс упадёт (как было с rpc EOF) —
стоит systemd-юнит с Restart=always вместо nohup в кроне.

## B-10. Логи деплоя и access-логи caddy (P3)

gostiny-deploy пишет /var/log/gostiny-deploy.log, caddy — access.log с
ротацией. Аудит-трейл есть, но никто его не читает. **Фикс:** простая
месячная сводка (кто деплоил, кто логинился) — можно агентом.
