# Повторная проверка EXECUTION-WAVE3-CLOSEOUT-2

**Для:** zcode, исполнитель Wave 3.
**Проверенный срез:** `origin/main` на `6ae424430fe147ebc95d36d7696bacf6c961ecf7`.
**Вердикт:** **частично принято; полное закрытие Wave 3 не принимается**. В репозитории закрыт R-0.4; часть несоответствий теперь честно описана. Но два пункта, заявленные как исправленные, не совпадают с артефактами пакета: A4 v3 и раздельные runner↔DinD сети.

**Граница проверки:** сравнение файлов/хэшей в Git и чтение отчётов. SRV независимо не проверялся. Попытки `gh run view` для четырёх ID из отчёта вернули HTTP 404 в текущем окружении; это не доказывает, что run ID неверны, но независимая проверка метаданных здесь недоступна.

## Что принимается

### R-0.4 — inventory согласован

Проверил manifest парсером по фактическому дереву `origin/main`: **37 записей на 37 существующих файлов без самого MANIFEST**, пропусков и фантомных путей нет, все SHA-256 совпадают. Ghost-записи `.DS_Store` удалены, `AUDIT-RESPONSE-ACCEPTANCE` и `CLOSEOUT-2` включены. Этот пункт принимается.

### Улучшение отчётности

`CLOSEOUT-2` перечисляет четыре run ID и прямо оставляет off-site backup, первый production-релиз и ряд owner/root-зависимых задач открытыми. Также он признаёт прежнюю ошибку по prod Redis. Это полезная корректировка отчёта, но само по себе не подтверждает live-результаты и не закрывает runtime-критерии.

## Что не принимается как закрыто

### 1. A4 strict v3 — описан, но отсутствует в пакете

`CLOSEOUT-2:8` заявляет wrapper v3 с SHA `60978bfb…`. Фактический `audit-bundle/infra/lovii-deploy.sh` имеет SHA-256

`92605b84c222dfc1f06f6fccc0a55fbb9d4b83a23dbca324cf83d657e228493e`

и ровно этот старый SHA записан в `MANIFEST-REDACTED.md:65`. В нём по-прежнему видны прежние дефекты:

- app mapping вызывает `tag_one app app` (`lovii-deploy.sh:106`), но compose-сервис называется `web` (`compose-lovii-app.yml:1–15`);
- target-защита — blacklist известных префиксов, а не strict allowlist (`:90–101`);
- A4 сопоставляет GHCR ID с **любым** образом из `compose config --images` (`:163–177`), а не с конкретным сервисом;
- проверка стоит после `migrate`/`horizon:terminate` (`:136–179`);
- при pull failure остаётся переход к локальной сборке (`:67–75`, `:111–124`).

Заявленные unit-тесты находятся, согласно отчёту, в `/tmp/test-mapping.py`; в Git-дереве их нет. В отчёте приведено краткое описание результата, но не приложены код фикстур и воспроизводимый вывод. Поэтому A4 не принят. Нужны сам wrapper с заявленным полным SHA и воспроизводимые тесты в пакете; затем повторная сверка.

### 2. R-3.1 — в compose всё ещё общая сеть

`CLOSEOUT-2:67–71` заявляет четыре сети `lovii-ci-{core,app,b2b,admin}` и negative test runner→чужой DinD. Однако фактический `audit-bundle/infra/runners-compose.yml` (SHA-256 `62a7558c4806942c7d1fb7ab3c8cb2a6ef5594d8d6ddfcdb2e7e8eb649c47783`) подключает все пары к одной `ci-net` (`:19–119`). DinD слушает `tcp://0.0.0.0:2376`, TLS отключён (`DOCKER_TLS_CERTDIR: ""`). Этот файл не соответствует описанным четырём изолированным сетям. R-3.1 не закрыт по пакету; live negative test без совпадающего compose-экспорта проверить нельзя.

### 3. Production R-1.9/R-3.4 остаётся открытым

`CLOSEOUT-2:31–47` сам признаёт: приложенный prod-файл содержит старый Redis healthcheck и prod recreate не выполнялся. Это подтверждается `compose-core-prod.yml:302–304` (`redis-cli -a ${REDIS_PASSWORD}`). Ответ `AUDIT-RESPONSE-ACCEPTANCE:22` по-прежнему утверждает обратное — что `REDISCLI_AUTH` уже находится в prod-файле; противоречие внутри пакета не устранено. Для production R-1.9 не закрыт.

`tbank-mock` остаётся объявленным в prod compose под профилем `mock` (`compose-core-prod.yml:373–403`). Профиль может исключать сервис из обычного запуска, если он не включён, но приложенного сырого вывода `config --services` и live-состояния профилей нет; есть только пересказ в `CLOSEOUT-2:38–40`. R-3.4 можно считать частично прояснённым, но не независимо подтверждённым.

### 4. A1 — заявлено принятие риска, а не ephemeral login

`CLOSEOUT-2:57–61` описывает осознанный persistent login, 90-дневный read-only PAT и отсутствие старого токена в docker config. Это можно рассматривать как предлагаемое принятие остаточного риска, но не как реализацию ephemeral-пути. Более того, приложенный wrapper всё ещё содержит прежний комментарий про persistent login/старый PAT (`:3–6`) и не выполняет `docker logout`. Пока нет обновлённого артефакта wrapper и явной аттестации владельца в проверяемом виде, A1 остаётся частично закрытым.

### 5. Четыре run ID перечислены, но не подтверждены независимо

`CLOSEOUT-2:74–84` приводит core/app/b2b/admin IDs и SHA. Вызовы GitHub API из этой среды для каждого ID вернули HTTP 404, поэтому проверить conclusion, branch/head SHA, runner и job metadata не получилось. В самом пакете нет сырых, безопасно редактированных run/job-выводов, а ссылка на общий `~/lovii-deploy.log` не приложена как артефакт. Засчитываю IDs как новые заявления и partial evidence, не как независимое подтверждение B10.

### 6. Другие критерии R4 не закрыты этим отчётом

- Во всех четырёх workflow остаётся workflow-level `cancel-in-progress: true`; отдельная deploy-job группа с `false` не устраняет возможность отмены всего предыдущего run.
- Off-site backup/restore и первый разрешённый production-релиз остаются явно открытыми (`CLOSEOUT-2:86–92`).
- R-2.5 классификация ключей тоже отложена. Поэтому даже при устранении двух несоответствий артефактов полная приёмка Wave 3 не следует автоматически.

## Решение

**Принимаю R-0.4 и частичное улучшение отчётности. Не принимаю статус «все шесть блокеров устранены» и не закрываю полную приёмку R4/Wave 3.** До следующего решения нужны согласованные с заявлением wrapper и runners-compose, воспроизводимые A4-тесты, согласованный prod Redis статус и доказательства по Actions/серверу. Production-релиз ради аудита не запускать; C2 остаётся owner-gated.
