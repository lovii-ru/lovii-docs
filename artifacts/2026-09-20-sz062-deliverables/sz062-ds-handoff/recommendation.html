LOVII · разбор размера CSS

Можно ли 3804 строки свести к 500?

Короткий ответ: да — но не на всю витрину. 500 строк — это нормальная цель для ядра дизайн-системы, а не для экранного CSS продукта. Ниже почему, и как масштабироваться без роста правил.

01Ключевое различие: ДС ≠ экранный CSS

Сейчас в одном файле смешаны две разные сущности:

Ядро дизайн-системы

  • Токены (цвет/радиус/тень/типографика) — уже есть, ~250 строк.
  • Примитивы и компоненты: кнопка, чип, карточка, поле, бейдж, список.
  • Масштабируется бесконечно за счёт вариантов и токенов.
  • Цель 500 строк — вот сюда и она реалистична.

Экранный (продуктовый) CSS

  • Витрина: десятки экранов (главная, точка, товар, корзина, заказы, кошелёк, адреса, настройки, дашборды 5 ролей, кабинеты, чаты, МСП).
  • ~1700 правил — это число уникальных визуальных узлов, а не «дубли».
  • Сворачивается только двумя путями: переиспользование компонентов и утилиты.
Физика CSS. Токены дают бесконечную вариативность при постоянном числе правил. Компоненты дают масштаб за счёт переиспользования. Но каждый новый уникальный визуальный узел всё равно стоит нескольких правил. «500 строк и ни строки больше при росте продукта» возможно только если все экраны собираются из одних и тех же компонентов.

То есть реалистичная цель: ядро ~500 строк, а витрина — тонкий слой поверх него (в идеале максимум — утилиты + layout-клей). Полностью 500 на всё — только при радикальном переходе к утилитам (Tailwind-подход), но это переносит сложность в разметку (сотни классов в HTML) — не факт, что вам это нужно.

03Как масштабироваться без роста правил

Комбинирование вместо новых правил:

МеханикаЧто даётПример
Токены (custom properties)темы/бренд без новых правил--lv-card, --lv-line
Компонент + варианты10 вида кнопки = 1 правило + модификаторы.btn + [data-variant=ghost|solid]
Комбинация на местеновый экран = существующие компоненты<div class="card"><button class="btn">
Минимум утилитlayout-клей без новых сущностей.stack, .row, .grid-2
@layerпорядок каскада без !importanttokens→base→components→utilities
Что уже сделано в эту сторону: 206 сырых значений теней/радиусов сведены в токены; тени карточек — единый --lv-shadow-soft; границы — --lv-line (единая на тему). То есть «параметризация» уже началась, и это самый масштабируемый путь.

04Что предлагаю сделать

  1. Зафиксировать «компоненты» в каноне: карточка, кнопка, чип, поле, бейдж, строка-список, KPI — по одному правилу + варианты. Экранные стили тогда ссылаются на них.
  2. Витрина оставляет себе только раскладку экранов (grid/flex/отступы) и редкие исключения.
  3. Ограничить вариативность контуров 3 токенами (line / line-2 / strong) + активные (pink/tiffany).
  4. Слойность через @layer, чтобы не плодить «патчи».

Порядок безопасный: идём по экранам, меняем бесшумно (замерами и скриншотами), правило-за-правилом переводим на компоненты.
