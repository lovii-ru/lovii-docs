### 1.3 `partners_inn_digits_unique` — вопрос закрыт (не 🔴)

Проверено по всем слоям: миграции core/b2b/admin — индекса нет; артефакты
T-027 (`2026-09-28-t027-partner-inn-dedupe-deliverables/`) — нет; снимок
staging-схемы (`artifacts/db-schema-analysis.md`, 13.09) — нет. Источник фразы
в карточке — пересказ памяти: «уникальность по нормализованному ИНН». Фактически
инвариант «одно юрлицо — один ИНН» держится **в коде**: `PartnerInnGuard`
(`core/app/Domain/Business/Support/PartnerInnGuard.php:18-30`) нормализует ИНН
до цифр (`preg_replace('/\D+/','')`), берёт transaction-level advisory lock
и находит старейшего партнёра по ИНН любого состояния верификации. Комментарий
там же фиксирует решение T-027 (владелец, 28.09): **полный уникальный индекс
на ИНН сознательно не включается, пока не сведены исторические дубли** — это
не забытая миграция, а отложенный фазовый шаг. Вывод: отдельную «аварийную»
задачу-миграцию заводить не нужно; переключение полного unique на ИНН входит
пунктом в фазировку (§5, Фаза A, гейт «дубли сведены»), актуальность живой БД
сверится при регенерации `db-schema-analysis.md` по снимку 30.09 (уже в очереди
zcode).

## 2. Матрица покрытия сущностей: «сущность × политика × retention»

Инвентарь: 64 create-миграции core + 12 b2b (срез 30.09). Классы политики:
**T** — tombstone (soft-delete по канону каталога); **D** — деактивация →
анонимизация по retention; **H** — анти-фрод реестр HMAC-хэшей; **A** —
анонимизация/сокращение ПИИ по retention (каркас остаётся); **F** — финансовый/
аудит контур: append-only, не трогаем никогда (канон T-023); **X** — техническое,
короткий TTL.

## 3. Юридический слой (ограничения и развилки, не юрзаключение)

> Формат — как просила карточка: якоря и следствия для политики; юрблоки Б-серии
> остаются владельцу. Веб-верификация якорей — 30.09 (consultant.ru, kontur,
> glavkniga).

### 3.1 Верифицированные якоря

1. **Бухгалтерия — 5 лет.** Первичные документы, регистры, отчётность — не
   менее 5 лет после отчётного года (402-ФЗ, ст. 29). Для налоговых целей —
   минимум 4 года (НК РФ, ст. 23 пп. 8 п. 1). Следствие: финансовый каркас
   (класс F) не может быть зачищен «по просьбе пользователя» раньше этих сроков.
2. **Кассовые/фискальные данные — 5 лет** (54-ФЗ контур: чеки, сведения о
   расчётах). Следствие: payments/orders — класс F.
3. **«Право на забвение» — поправка к карточке и RES-012.** Статья о забвении —
   это **ст. 10.3 149-ФЗ «Об информации»** (обязанности оператора **поисковой
   системы**), а не 152-ФЗ. К нашей задаче она почти не относится: нас она
   касается только как источников выдачи. Для оператора ПДн релевантен режим
   **ст. 21 152-ФЗ**: при достижении цели обработки / отзыве согласия оператор
   обязан уничтожить ПДн в срок не более 30 дней (продление — до 30 дней),
   и ст. 19 (обязанность хранить/уничтожать по срокам). Следствие для карточки
   SZ-084: формулировку «152-ФЗ „право на забвение"» в разделе «Что НЕ входит»
   уточнить: юркарта Б-серии — про режим уничтожения ПДн по 152-ФЗ (ст. 21) и
   отдельно — про поисковое забвение (149-ФЗ ст. 10.3), если возникнет.
4. **Обезличивание — методика есть.** Требования и методы обезличивания ПДн —
   Приказ Роскомнадзора от 05.09.2013 № 179 (обезличить = нельзя восстановить
   личность без доп. информации). Наши purge-методы (обнуление ПИИ + подмена
   телефона) ей соответствуют по духу; формализованный разбор — на юркарту.
5. **AML-контур.** 115-ФЗ напрямую платформе может не применяться, но
   требования банков-партнёров/эквайера по срокам хранения данных операций
   транслируются договорами — ещё один довод за класс F «не трогаем 5 лет».

### 3.2 Следствия для политики (таблица retention-классов)

| Класс | Данные | Предложение срока | Основание |
|---|---|---|---|
| ПИИ профиля | ФИО, телефон→`deleted_{id}`, адреса | 30 дней после деактивации | уже реализовано (purge); ст. 21 152-ФЗ 30-дневный режим совместим |
| Технические | devices, push, сессии, логи | 90 дней неактивности | практика, не закон |
| Анти-фрод хэши | HMAC телефона/кода/ИНН | 180 дней | переводыпуск номеров операторами; false-positive окно (RES-012 §7.3) |
| Каркас юрлица/мерчанта | строка без ПИИ | 365 дней | операционная память (споры, повторные подключения) |
| Финансовый каркас | F-класс | 5 лет | 402-ФЗ/54-ФЗ/НК РФ |

Итоговое ограничение: развилка №1 карточки («30/90/180/365») должна решаться
**по классам**, а не одним числом — единый срок либо нарушит statutory-минимумы,
либо затянет ПИИ-зачистку до бессмысленности.

| 8 | Удаление профиля при активной подписке (SZ-053) | запрет до отмены подписки / отмена автоматически с финальным списанием |
| 9 | Слитые дубли ИНН (T-027): tombstone дубля со ссылкой `merged_into` | отдельный статус / обычный tombstone + ссылка |
| 10 | `loyalty_rules` без merchant_id: правило переживает мерчант | деактивировать правила по категориям удалённого мерчанта / оставить глобально |
| 11 | Формулировка «удалено навсегда» в UI до деплоя retention-процесса | писать точный срок («данные будут удалены через N дней») / «навсегда» только после Фазы D |

Развилка 11 — прямое следствие продуктового стандарта: «не обещать того, что
код не делает» (`canon/PRODUCT_QUALITY_BAR.md` §1).

## 5. Фазировка (предложение к карточке)

**Фаза A — политика + каркас (core).** Таблица журнала зачистки (append-only,
канал SZ-048-прецедент); реестр HMAC-хэшей идентификаторов (класс H из §2) +
сервис нормализации (E.164 телефона — как в `PartnerInnGuard` для ИНН);
tombstone для `partners` (deleted_at + причина + кто) и partner-пользователей;
миграция-инвентаризация: partial-индексы «живых» ключей по матрице §2; включение
полного unique на ИНН — гейт «дубли сведены» (T-027 сверка живой БД).
Гейт: миграции идемпотентны, гейты репо зелёные, сводка индексов сверена со
снимком `db-schema-analysis.md`.

**Фаза B — core-сервис удаления + internal API + admin/b2b-поверхности.**
Единый сервис: tombstone-переход + каскады (мерчант → точки/витрины/правила по
канону T-025; развязка амбассадора) + запись в журнал; internal-эндпоинты по
прецеденту `routes/internal.php` (409 при живых зависимостях — как
`cannot_force_delete`); admin: header-actions в Filament + точечное разрешение
в Shield (операторы); b2b: те же действия для владельца юрлица.
Гейт: каждое удаление оставляет строку в журнале (тест), Shield для остальных
по-прежнему false.

**Фаза C — app «удалить аккаунт» (самообслуживание).** Профиль → деактивация
(существующий `status=deactivated`), честный экран «что исчезнет / что
останется» (заказы покупателя, стат. сроки), развилка №4 про баланс,
формулировка срока по развилке №11; уведомления email/MAX-боты.
Гейт: скрин-тест PQB §0, три состояния, визуальная приёмка владельцем.

**Фаза D — retention-процесс + журнал.** Универсальный runner поверх
`users:purge-deactivated` (классы §3.2, dry-run/apply/снимок/undo — прецедент
T-027), расписание (nightly, без пересечений), TTL-сверка реестра хэшей,
мониторинг/алерт по отказам. Гейт: прогон на staging-данных, отчёт владельцу,
после него — развилка №11 разрешается в «навсегда».

Зависимости: решения владельца по развилкам 1-11 (Фаза A); T-027 MERGE-состояние
(гейт ИНН); SZ-048 (канал журнала — дожать или взять таблицу); F-072 (пересечение
с брошенными чекаутами в Фазе D); дизайн-проход demo-канона для Фазы C.

## 6. Продуктовый стандарт: тексты и места дизайн-прохода

Сверено с `canon/PRODUCT_QUALITY_BAR.md` (§0 скрин-тест, §1 DoD, §2 ресёрчи).
Места, требующие дизайн-прохода до реализации Фаз B/C:

1. **app, профиль** — `SettingsSheet.vue` (низ профиля, рядом с «Выход» —
   решение владельца 15.09 о месте выхода): точка входа «Удалить аккаунт»,
   экран подтверждения, пустое состояние после удаления.
2. **Экран подтверждения** — честный текст «что исчезнет / что останется»
   (исчезает: профиль, адреса, баллы — развилка №4; остаётся: история заказов
   в финконтуре со statutory-сроками), ввод-подтверждение, состояние ошибки.
3. **b2b** — `EditMerchant.php`/`EditBranch.php` header-actions сейчас пустые:
   каноничное место кнопок удаления с подтверждением и перечнем каскада
   («гасятся точки и витрины»).
4. **admin** — `MerchantResource`/`MerchantBranchResource`: кнопка + гранулярные
   политики (сейчас false — точечно включаем операторам).
5. **Пустые состояния после удаления** — «пустое — приглашение, не тупик» (PQB §1):
   для витрин покупателя, у которых исчез товар/точка.
6. **Уведомления** (email SZ-009, боты SZ-010/MAX) — тексты о деактивации и
   зачистке; тон PQB (кратко, без канцелярита, никаких «навсегда» раньше Фазы D).
