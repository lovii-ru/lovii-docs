## 1. Канон навигации: «контекст одного юрлица»

**МСП = юрлицо (ИНН)** — формулировка владельца. Один кабинет, в шапке —
контекст текущего юрлица; переключение — один тап. Отдельные кабинеты на каждое
юрлицо отклонены (администратора «на всё» не назначить, экраны размножаются).

Референс практик (нативный паттерн): СберБизнес / Т-Бизнес — переключение
компаний чипом в шапке → шит со списком; маркетплейс-кабинеты — выбор магазина.
Человек знает этот жест без обучения.

### 1.1 Шапка

```
┌──────────────────────────────────────────┐
│ [ООО «АТМОСФЕРА» · ИНН …6839 ▾]   кабинет│  ← тап → шит «Мои юрлица»
└──────────────────────────────────────────┘
   Обзор | Заказы | Каталог | Настройки | Команда
```

Шит «Мои юрлица» — карточки: название, ИНН, статус верификации,
«N брендов · M точек»; последняя строка — «Добавить юрлицо» → существующая
заявка (ИНН → счёт 1 ₽ → верификация, `POST /business/applications` — уже работает).

Умолчание: последнее активное юрлицо хранится локально. У владельца одного
юрлица переключатель не требует ни одного лишнего действия.

### 1.2 Разделы внутри юрлица (нижний бар — состав не меняется)

| Раздел | Контекст | Что меняется |
|---|---|---|
| Обзор | юрлицо | + блок «Бренды и точки» юрлица (карточки) с CTA «+ Бренд» / «+ Точка»; рабочая точка выбирается только из точек этого юрлица |
| Заказы | точка | как сейчас, точки только выбранного юрлица |
| Каталог | бренд (+ точка для наличия) | бывший «Товары» → дерево категорий + товары (§3) |
| Настройки | точка | как сейчас (график, мин. сумма, карточка магазина) |
| Команда | юрлицо → бренд → точки | как сделано 2026-09-17 (бренд → точки → роль → телефон) |

### 1.3 Сценарии (проверка «нативности»)

- **Переключить юрлицо**: тап по шапке → карточка юрлица. 1 действие.
- **Добавить юрлицо**: шапка → «Добавить юрлицо» → заявка с ИНН. Есть.
- **Добавить бренд**: Обзор → «+ Бренд» → название + логотип. (API — Ф2, SZ-050.)
- **Добавить точку**: карточка бренда → «+ Точка» → адрес, график. (API — Ф2.)
- **Пригласить сотрудника**: Команда → бренд → точки → роль → телефон. Готово.
- **Завести товар**: Каталог → категория → «+ Товар» → название + цена. (Ф3.)
- **Пустое юрлицо** (пример: АКСИОМА): Обзор = «Здесь пока нет брендов» +
  «+ Бренд». Никаких тупиков.

## 3. Каталог (номенклатура) с вложенными категориями

Модель данных **уже готова** — шаблон не нужен, каталог = данные, не схема:

- `catalog_categories` — **parent_id** (любая глубина), принадлежат мерчанту;
- `catalog_products` — товары бренда (название, цена, картинка);
- `merchant_offers` — позиции точки (цена/наличие точки) → товар каталога;
- `offer_modifier_groups` — модификаторы (как в iiko);
- `integration_entity_mappings` — готовый механизм внешних импортов
  (1,4 млн строк Kuper): внешний id ↔ внутренний.

### 3.1 Экран (ограничение мобильного: drill-down вместо длинного дерева)

```
Каталог (бренда)            Каталог › Напитки
┌──────────────────────┐    ┌──────────────────────┐
│ ‹ Категории     [+ ] │    │ ‹ Напитки       [+ ] │
│ ▸ Напитки        12  │    │  ▸ Кофе          5   │
│ ▸ Выпечка         7  │    │  ▸ Чай           3   │
│ ▸ Десерты          4 │    │  ▸ Лимонады      4   │
│ …                    │    │  ────────────────    │
│ [ + Товар ]          │    │  Капучино     250 ₽  │
└──────────────────────┘    │  Латте        280 ₽  │
                            └──────────────────────┘
```

- Вход в раздел — список корневых категорий; тап — провал внутрь (подкатегории
  + товары), «‹» — назад. Глубина любая, комфортно — 2–3 уровня.
- «+» в шапке экрана — создать категорию/подкатегорию (bottom sheet: название).
- «+ Товар» — bottom sheet: название + цена (обязательно), описание/фото
  (опционально) — «жёстких требований к логике» нет, поля не блокируют.
- Управление категорией/товаром: свайп/кнопка — переименовать, скрыть,
  перенести (выбор категории). Удаление — только если пусто.

### 3.2 iiko-готовность (Ф4, после включения интеграций)

Импорт апсертит те же сущности по external_id через `integration_entity_mappings`
(уже обкатано на Kuper): группы iiko → категории (parent_id), продукты →
`catalog_products`, цены → офферы точек. **Правило совместного владения**:
синхронизация перезаписывает структуру и цены, локальные флаги (скрыт,
наличие, фото) не трогает — «управлять и просматривать» остаётся у владельца
и после автосоздания каталога.

## 4. Фазы (SZ-050)

| Фаза | Что | Репо | Оценка объёма |
|---|---|---|---|
| **Ф1** | Свитчер юрлиц в шапке + фильтрация разделов + пустые состояния. Ядро почти не нужно (partner_id в обзоре уже есть, f2a4f06) | app | средняя |
| **Ф2** | Создание бренда и точки из приложения: `POST /msp/merchants`, `POST /msp/branches` (права `merchant.create`/`branch.create` уже в матрице) + CTA на Обзоре. Поглощает SZ-049 | core + app | средняя |
| **Ф3** | Каталог: API категорий для app (вложенные, права `category.*` есть) + экран-дерево + товары | core + app | большая |
| **Ф4** | iiko-импорт (после `INTEGRATIONS_ENABLED`): воркер + маппинги + правило §3.2 | core | большая, отдельная задача |

Порядок согласован с зависимостями: Ф1 делает переключение нативным сразу,
Ф2 закрывает «добавить мерчантов/филиалы», Ф3 — номенклатура, Ф4 — автоматизация.
