- **Основной баг закрыт по существу:** отказ больше не занимает слот лимита (подтверждено тестом и кодом), повторная подача по той же точке правит прежнюю заявку.

## 1. Отказ и слот лимита: правда ли «до — не освобождал, после — освобождает»

  `RejectPartnerApplicationAction.php:41` → `PartnerDraftOwnership.php:30-31` (`setStatus(..., 'revoked')`) → членство уходит из `status='active'` → счётчик падает.

### 1.1. Не сломает ли `release()` сценарий, где заявка затем доходит до `verified`

- `release()` **не трогает** партнёра с `verified_at != NULL` — прямой guard: `PartnerDraftOwnership.php:50` (`if (! $partner instanceof Partner || $partner->verified_at !== null) return;`). Это же защищает SZ‑050 (там `partner_id` указывает на **верифицированного** партнёра, `CreatePartnerApplicationAction.php:335-380`).
- Пути к `verified` после `Failed`:
  - `MatchIncomingVerificationAction` — фильтр статусов `invoice_issued/awaiting_payment/verifying` (`MatchIncomingVerificationAction.php:42-44`), `Failed` не проходит → недостижимо.
  - `ConfirmVerificationPaymentSentController` — те же статусы → недостижимо.
  - `VerifyPartnerAction` (админ по `partner_id`) — **статус заявки не проверяет**: берёт «последнюю заявку не из [Verified,Failed,Expired]», а если такой нет — `$application = null`, и всё равно ставит `partners.verified_at` (`VerifyPartnerAction.php:49-70`).
- **Следствие (не блокер, но несогласованность):** после отказа (членство `revoked`, заявка `Failed`) админское `VerifyPartnerAction` может довести этого партнёра до `verified`. Тогда: партнёр verified (точка на витрине), а членство владельца `revoked` → кабинет владельца точку не покажет (`ShowMspOverviewController.php:55` фильтрует `status='active'`). До правки членство оставалось `active`, т.е. поведение изменилось.

## 2. Регрессии от правки

### 2.1. `reopen()` обходит `assertUnverifiedPartnerCap()` и ветку SZ‑050 — ЛОМАЕТ ли сценарий «новый бренд под подтверждённым юрлицом»

**Порядок в `execute()` (подтверждено по коду):**
1. `existing` (до‑верификационные статусы) → `CreatePartnerApplicationAction.php:83-93`;
2. `reopenable` (pre‑verification + `Failed`/`Expired`) → `:103-112`, ветка `reopen()` → `:114-119`;
3. SZ‑050 `findOwnedVerifiedPartnerByInn` / `attachBrandToVerifiedPartner` → `:132-140`;
4. `assertUnverifiedPartnerCap()` → `:142`;
5. создание новой заявки → `:154+`.

Т.е. `reopen()` действительно стоит **раньше** SZ‑050 и лимита. Вердикт — **регрессии подтверждены:**

**(a) Обход SZ‑050 (реально достижимо).**
Сценарий: у пользователя есть `Failed`-заявка по точке X (ИНН И, адрес A) → её черновик-партнёр **не верифицирован**. Позже пользователь оформляет **другую** точку Y (ИНН И, адрес B) и доводит её до `verified` (или ИНН И уже верифицирован через b2b-кабинет). Теперь повторная подача точки X:
- до правки: `existing` (нет), SZ‑050 → `attachBrandToVerifiedPartner` → заявка сразу `Verified`, мерчант `Active`, без апрува представителя;
- после правки: `reopenable` (Failed по X) → `reopen()` → переиспользован **неверифицированный** черновик X, статус обратно в `Submitted/AwaitingRepApproval`, нужен апрув представителя заново.
Поведение изменилось, и оно противоречит правилу SZ‑050 «одно юрлицо — один партнёр». Требуется решение продукта: что старше — «одна точка = одна заявка» или «один ИНН = одно юрлицо».

**(b) Обход лимита cap → можно превысить 5.**
`reopen()` не вызывает `assertUnverifiedPartnerCap()`. Сам по себе `reopen` новых партнёров не плодит, **но** комбинация даёт обход:
1. 5 неверифицированных партнёров (count = 5).
2. Отказ по одной точке → `release()` → count = 4.
3. Пользователь подаёт **новую** точку → count = 5 (слот занят).
4. Повторная подача отклонённой точки → `reopen()` → `restore()` → count = **6** (> cap 5).
До правки шаг 4 упёрся бы в лимит (count после отказа был бы 5). Логика подтверждена; тестом не покрыто. Инвариант «≤5 неверифицированных» нарушаем.

### 2.2. Повторная подача переиспользует `partner_id/merchant_id/branch_id`, если они NULL

**Вердикт: подтверждённая дыра (среды без b2b / сбой материализации).**
- `materializePartnerDraft()` при недоступной схеме b2b возвращает `null` (`CreatePartnerApplicationAction.php:491-497`) — заявка живёт с `partner_id=NULL`.
- `reopen()` (`:410-438`) `partner_id/merchant_id/branch_id` **не трогает и не материализует**; `syncDraftName()` тихо выходит при `merchant_id=NULL` (`:446-451`); `PartnerDraftOwnership::restore()` при `partner_id=NULL` — no‑op (`PartnerDraftOwnership.php:42-44`).
- Итог: если при первом сабмите черновик партнёра не материализовался, повторная подача **никогда** его не создаст (в отличие от обычной ветки, где партнёр/мерчант/филиал создаются). Мерчант при первом сабмите создаётся безусловно (`:190-206`), поэтому `merchant_id`, как правило, уже есть; а вот `partner_id` может остаться NULL навсегда → точку нельзя верифицировать платёжным контуром.

### 2.3. Повторная подача того же ИНН+адреса для заявки в статусе `verified`

**Вердикт: реопен НЕ срабатывает; поведение — как до правки и НЕ закрыто.**
- `Verified` не входит ни в `isPreVerification()`, ни в `isReopenable()` (`PartnerApplicationStatus.php:60-77`).
- Значит поток уходит в SZ‑050 → `attachBrandToVerifiedPartner` создаёт **новую** заявку + новый мерчант (`Active`) + новый филиал под тем же подтверждённым партнёром.
- При этом `identity_key` в этой ветке **не пишется** (см. 5.2) → каждая повторная подача даёт новый дубль и заявку с `identity_key=NULL`. Инвариант «одна точка — одна заявка» для verified/ново-бренд пути не выполняется.

### 2.4. Легаси-фолбэк по `inn` при пустом `identity_key` — склейка разных адресов

**Вердикт: риск есть, но ограничен бэкфиллом.**
- Условие OR: `where('identity_key',$identityKey)->orWhere(fn($q) => $q->whereNull('identity_key')->where('inn',$inn))` (`CreatePartnerApplicationAction.php:85-92` и `:105-112`). Для строк с NULL-ключом матчинг только по ИНН, **без адреса** → возможна склейка двух разных точек одной организации.
- Но миграция бэкфиллит существующие строки тем же правилом (`2026_09_27_120000_…:31-45`), поэтому основная масса старых строк получает ключ. NULL остаются только у: (i) строк, созданных в окне «код задеплоен — миграция не выполнена»; (ii) строк ветки SZ‑050 (всегда NULL — но они `Verified`, и для `reopen` не подходят; для `existing` тоже, т.к. не pre‑verification).
- Вывод: склейка реально возможна лишь в узком окне/при не выполненном бэкфилле.

### 2.5. `reopen()` меняет `status` обратно — нарушение инвариантов?

Проверены потребители статуса (grep по `PartnerApplicationStatus::`):
- `ListApprovalsController` — очередь `awaiting_rep_approval` (`:20-23`): переоткрытая заявка с промокодом снова появится у представителя — **ожидаемо**.
- `VerifyPartnerAction` — исключает `Failed/Expired/Verified` — согласовано.
- `MatchIncomingVerificationAction` — только `invoice_issued/awaiting_payment/verifying` — согласовано.
- `DistributeOrderPoolAction::resolveRepresentativeUserIdRaw` — фильтр `rep_approved_at NOT NULL AND rep_rejected_at NULL` по `branch_id` (`:405-415`); `reopen()` сбрасывает оба в `null` (`:428-430`) → атрибуция комиссий не «прилипнет» к переоткрытой заявке — **согласовано**.
- Ручной админ-очереди по `Failed/Expired` в ядре **нет** (grep: `Expired` вообще нигде не устанавливается, `Failed` ставит только `RejectPartnerApplicationAction`).
- Аудита/истории смены статуса заявки в ядре нет → переоткрытие **не оставляет следа** (ни audit, ни отдельной записи). Это не поломка инварианта, но потеря observability.

**Вердикт: явных нарушений инвариантов не найдено; наблюдение про отсутствие следа переоткрытия.**

## 3. Риск ложных склеек в ключе идентичности

Ключ = `sha256(innKey | placeKey)` (`PartnerApplicationIdentity::forApplication`). **ИНН входит в ключ** — это снимает часть опасений:

- **Два разных МСП в одном здании:** НЕ склеятся — у них разный ИНН → разный `innKey`. (Опасение не подтверждается.)
- **Внутри одного ИНН** две разные точки с одинаковой нормализованной строкой адреса → склеятся в одну. Реальный, но узкий риск (одна организация, два павильона с идентичным адресом).
- **Округление координат до 4 знаков** — подтверждено эмпирически: `55.75584 → 55.7558`. Шаг ≈ 11 м по широте и ≈ 6–7 м по долготе (Москва). Две точки ближе ~11 м → один ключ.
- **`city_name=NULL` при заполненном адресе:** `placeKey` даёт `'addr:—|адрес'` (проверено). Это не склейка, а **расщепление**: если между подачами `city_name` то есть, то нет — ключи разные → дубль.
- **Наличие/отсутствие координат:** `geo:…` vs `addr:…` → разные ключи → расщепление одной точки при расхождении формата (карта vs ручной ввод).

**Критично: нормализация адреса не покрывает часть кейсов, заявленных в docblock.** Проверено запуском самой функции:
```
ул. Белы Куна, 4к1            => [белы куна 4к1]
Белы Куна 4 к 1               => [белы куна 4 1]
```
Docblock (`PartnerApplicationIdentity.php:40-43`) утверждает, что эти две записи дают **один** ключ. Фактически — **разные**. Причина: `\bк\b` не вырезает «к» внутри «4к1» (между цифрой и буквой нет границы слова). → расщепление → дубль → съеденный слот. Это прямо подрывает цель правки для адресной ветки.

## 5. Что правка НЕ закрывает

1. **Ключ не глобальный / кросс-пользовательский случай.** Все поиски фильтруют `where('user_id', $user->id)` (`:84`, `:104`). Второй пользователь по той же физической точке создаёт **нового** партнёра и новую заявку. Глобальной уникальности «точка → одна заявка» нет.
2. **`identity_key` не заполняется в ветке SZ‑050** (`attachBrandToVerifiedPartner`, `:343-363` — поля `identity_key` нет). Все заявки «новый бренд под подтверждённым юрлицом» получают `NULL`-ключ.
3. **Нет уникального индекса.** Миграция добавляет `->nullable()->index()`, НЕ unique (`2026_09_27_120000_…:25`, комментарий прямо объясняет: дубли ещё не сведены). БД‑гарантии нет.
4. **Рассинхрон branch/merchant при правке.** `reopen()` обновляет `address_line/city_name/city_id/lat/lon` и `name`, но **не** обновляет `merchant_branches` (адрес/location/город) и не меняет `merchant_type`/статус. Меняется только имя мерчанта (`syncDraftName`, `:446-451`). Филиал остаётся на старом адресе/координатах.
5. **При `reopen()` не пишется `partner_offer_acceptances`.** `recordOfferAcceptance()` вызывается только в двух create-ветках (`:186`, `:365`); при переоткрытии согласия/оферты повторно не фиксируются (до правки повторная подача создавала новую заявку → новую запись согласия).
6. **Статус членства `'revoked'` — не каноничный для b2b.** Канон lovii_b2b: `'active'` / `'suspended'` (`MspTeamActions.php:123-125`, `AcceptMspInvitationController.php:66`); значение `'revoked'` в кодовой базе как статус членства нигде больше не встречается. Ограничения CHECK в миграции b2b нет (`lovii-b2b/…/2026_04_16_100003_create_partner_memberships_table.php:23` — `string default 'active'`), поэтому запись пройдёт, но это введение нового доменного значения без согласования; b2b/админ-представления про него не знают.
7. **`release()`/`restore()` не оставляют аудит-следов.** Обновление идёт mass-update'ом через query-builder (`PartnerDraftOwnership.php:53-57`) → события модели не срабатывают → в `partner_audit_logs` ничего не пишется.
8. **Не выполнено сведение дублей.** Комментарий миграции ссылается на «шесть отклонённых заявок на адрес “Белы Куйа 4к1”»; уникальность отложена «на потом» — т.е. исторические дубли не разобраны.
