# Задача: одна и та же заявка съедает лимиты при повторных отказах

## Запрос владельца (дословно)
«у нас я так понимаю проблема: одна и та же заявка занимает место в лимитах, если ей отклонить 5 раз.
я думаю что так как это по факту просто отмена, она не должна создавать новую заявку а менять статус прежней.
то есть каждая заявка для каждой точки или мсп — уникальны по набору параметров
и это одна заявка а не пять или какое то другое количество»

## Что уже установлено на этапе разведки (mainline, требует подтверждения)
Репозиторий `~/LOVII/lovii-core`:

1. `app/Domain/Business/Actions/CreatePartnerApplicationAction.php`
   - идемпотентность есть, но **только по паре `user_id` + `inn`** и только пока статус `isPreVerification()`
     (Draft, Submitted, AwaitingRepApproval, InvoiceIssued, AwaitingPayment);
   - строки 44, 360 — проверка лимита `hasReachedUnverifiedOwnedCap()` (422 `partner_application_cap_reached`).
2. `app/Domain/Business/Enums/PartnerApplicationStatus.php:67-71` — `isFinal()` = Verified, Failed, Expired,
   с комментарием: **«Финальные статусы: повторная подача с тем же ИНН создаёт новую заявку»**.
   → после отказа дедупликация по ИНН не срабатывает ⇒ баг воспроизводится.
3. `app/Models/B2b/PartnerUser.php:47,79` — `MAX_UNVERIFIED_OWNED_PARTNERS = 5`;
   `countUnverifiedOwnedPartners()` считает **Partner** (verified_at IS NULL + активная owner-membership),
   а не заявки ⇒ каждый повторный проход материализует нового партнёра-черновика и занимает слот.
4. `app/Domain/Business/Actions/RejectPartnerApplicationAction.php:25-29` — ставит только `status = Failed`,
   материализованные черновики (Partner/Merchant/Branch) не откатываются.
5. Миграция `2026_09_10_100001_create_partner_applications_table.php` — уникальных индексов нет
   (индексы по `status`, `partner_id`, `user_id+created_at`), БД дубли не запрещает.

Вывод предварительный: **владелец прав**. Нужна модель «заявка = сущность точки, отказ = её состояние».

## Целевая модель (на подтверждение по итогам расследования)
- Заявка уникальна по набору параметров точки; повторная подача **обновляет** прежнюю запись,
  а не создаёт новую (сброс статуса в `submitted`, обновление изменённых полей).
- Отказ/истечение = состояние заявки, а не потеря слота: лимит неверифицированных
  не должен расходоваться одинаковой точкой дважды.
- Уникальность закрепляется на уровне БД (уникальный индекс по ключу идентичности),
  чтобы гонки и старые клиенты не могли породить дубль.
