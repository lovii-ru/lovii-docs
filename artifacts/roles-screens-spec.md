# Lovii — Спецификация экранов ролей: Представитель, Амбасадор, МСП

> Документ для агента: что показывать на каждом экране, какие данные,
> какие API-вызовы, бизнес-логика, edge-cases. Основа — lovii-demo (dash.js),
> прод-реализация будет в lovii-app (Vue 3 + TS + Pinia).

> **⚠️ Корректировки по канону (SZ-038, zcode, 2026-09-11).** Спека выведена из демо,
> часть его допущений противоречит канону и уже построенному. Исправлено по месту, сводка:
> 1. Роли **совмещаются** (BRD §2.4, PRD FR-1.1), один баланс на профиль — не «одна роль на пользователя».
> 2. Коды приглашения — промокод `PPXXXX` (BRD §3.1, SZ-034 фаза A принята), не `REP-ГОРОД-042`/`AMB-ГОРОД-777`.
> 3. Верификационный платёж — по канону: код `VER-<partner_id>-<суффикс>`, платёж **с р/с компании**,
>    сумма **1 ₽** (решение владельца 2026-09-11, PARAMS §5.1), платёж возвратный.
> 4. Статус-машина заявки — реальная из SZ-007 фазы 1 (`partner_applications`), не демо-набор lead/pending_rep/catalog/payment/ready.
> 5. Витрина: hidden → teaser (после апрува представителя) → active (после верификации) — гейт SZ-035; «видна в каталоге до платежа» убрано.
> 6. Формулы доходов демо — плейсхолдеры: реальная база = пул 10% чека минус эквайринг, сплит 40/40/20, гейты подписки представителя 599/199 ₽ (BRD §7.2, FIN_BALANCE_REFERRAL_BRIEF A-2).
> 7. Scope (решение владельца 2026-09-11): МСП в app = мобильный слой (заявка/статус/платёж/обзор read-only), управление каталогом остаётся в b2b; чаты — отложены, вкладки-заглушки.
> 8. Rep-часть реализуется совместно со SZ-034B (кабинет представителя, `/api/v1/representative/*`); этот файл — UI-канон по демо.

## Общая архитектура ролей

```
Покупатель (lovii-app) ← основной пользователь
├── Представитель (Rep) — подключает и обслуживает торговые точки
├── Амбасадор (Amb) — управляет структурой представителей
└── МСП (Partner) — владелец точки, управляет каталогом
```

**Роли совмещаются** (BRD §2.4, PRD FR-1.1): один профиль может быть одновременно
МСП + Представитель, Амбассадор + МСП и т.д.; деньги — один баланс на профиль
(FIN_BALANCE_REFERRAL_BRIEF). В интерфейсе — активная роль; переключение через
экран профиля (как в demo: кнопка «Клиент»).

**Финансовая модель (канон BRD §7.2 / PARAMS §1.3):**
- Пул платформы: 10% от чека **минус эквайринг** (карта 3,16% / СБП 0,7% / T-Pay 2,59% мин 3,49 ₽ — FIN_BALANCE_REFERRAL_BRIEF A-2)
- Сплит пула: Компания 40% / Представитель 40% / Амбассадор 20%
- Представитель: 40% только с **лично подключённых** точек; гейт — активная подписка 599/199 ₽ (истекла → доля уходит Компании)
- Амбассадор: 20% branch-wide со всей ветки; деактивация амбассадора → доля уходит Компании
- Подписка точки: 0 ₽ (Старт), 0 ₽ (Базовый), 2 990 ₽/мес (Про)

### Экран: Подключение (`rep/connect`)

**Hero-секция (ink-gradient):**
- Заголовок: «QR-подключение МСП»
- Подзаголовок: «Один понятный маршрут для владельца точки»
- Глаголы: 0 ₽ старт, 3 дня запуск, 90/10 сплит
- QR-код (генерируется из invite code)

**Промокод представителя**: `PPXXXX` — 4 символа, алфавит 33 (BRD §3.1, PRD FR-13.1,
SZ-034 фаза A). QR ведёт на `https://app.lovii.ru/business/apply?promo=<PPXXXX>`.
Перепривязок нет.

**Stepper статуса заявки** (реальная машина `partner_applications`, SZ-007 фаза 1,
+ шаг апрува представителя из SZ-038):
1. ИНН и карточка (draft → submitted)
2. Апрув представителя (awaiting_rep_approval)
3. Счёт на верификацию (invoice_issued → awaiting_payment)
4. Верификация платёжом с р/с (verifying; витрина teaser)
5. Продажи включены (verified; витрина active)

**Сценарий подключения (пошагово, по канону):**
1. Представитель показывает QR с промокодом PPXXXX
2. Владелец сканирует → `/business/apply?promo=PPXXXX` (форма SZ-007 фазы 1)
3. Владелец вводит ИНН (DaData-проверка) → создаётся заявка + drafts merchant/branch/partner
4. Добавляет карточку: название, адрес, описание, фото
5. Представитель апрувит → витрина teaser (видна с заглушкой, SZ-035)
6. Владелец оплачивает счёт верификации **с р/с компании** (код VER-*, сумма 🔶
   PARAMS §5.1); после матчинга — возврат на реквизиты (механика возврата
   уточняется у Т-Банка) → витрина active
7. Владелец ведёт каталог в b2b-кабинете (Filament); в app — обзор read-only

**Очередь заявок:**
- Показывает текущую заявку (если есть)
- Юрлицо, канал связи, адрес, описание
- Кнопки: «Апрув: показать в каталоге» / «Вернуть на правку»

### Статусы заявки (stepper)

Статусы = enum `PartnerApplicationStatus` (SZ-007 фаза 1, уже в системе):
`draft → submitted → invoice_issued → awaiting_payment → verifying → verified | failed | expired`.
Шаг «апрув представителя» (`awaiting_rep_approval`) добавляется SZ-038 фазой 1
(промокод → представитель → апрув перед выставлением счёта).

| Этап | Что видит МСП | Витрина (SZ-035) |
|------|---------------|------------------|
| `draft`/`submitted` | Форма + «отправлено, ждём апрув представителя» | hidden |
| awaiting_rep_approval | «Представитель проверяет карточку» | hidden |
| `invoice_issued`/`awaiting_payment` | Счёт: сумма, код VER-*, реквизиты | teaser |
| `verifying` | «Платёж получен, проверяем» | teaser |
| `verified` | Всё готово, переход в b2b-кабинет | active |
| `failed`/`expired` | Честная ошибка + как исправить | hidden |

### Экран: Платёж (`msp/pay`)

**Pay-card (канон FINANCIAL_CONTOUR §3 / PARAMS §5.1):**

## Edge-cases и нюансы

1. **Точка в статусе waiting**: не показывает доход, GMV = «—»
2. **Нет активных точек**: KPI показывает 0, конверсия = 0%
3. **Нет представителей у амбасадора**: структура пуста, средний доход = 0
4. **Заявка МСП в draft**: точка не видна в каталоге
5. **Верификационный платёж**: сумма **1 ₽** (решение владельца 2026-09-11;
   покрытие комиссии — PARAMS §5.1), код VER-*, плательщик = компания заявки;
   матчинг по коду И плательщику (финконтур §3.1)
6. **Возврат**: платёж возвратный (решение 2026-09-11); механика уточняется
   у Т-Банка — без обещания «автоматически/мгновенно»
7. **Ранг «Губернатор»**: максимальный, прогресс = 100%
8. **Чаты**: непрочитанные считаются по всем чатам роли
9. **Промокод PPXXXX**: уникален на представителя (алфавит 33, BRD §3.1); перепривязок нет (SZ-034 фаза A)
10. **Тариф точки**: в проде из БД; автопереход Старт→Базовый при превышении 30 000 ₽ (PARAMS §1.3)
