# Задача для zcode: одно ИНН — одно юрлицо (дубли партнёров при подаче заявки)

**Тип:** дефект правила + дефект данных. **Приоритет:** высокий (блокирует приёмку стартового дампа на стенде).
**Основа:** ветка `staging` (tip `164a90ce` на момент постановки).
**Выгрузка:** по действующему регламенту — `lovii_docs/canon/CI_RUNNERS_SELFHOSTED.md` (CI/CD на self-hosted раннерах, действует с 27.09.2026).

## 2. Что нужно найти (root cause)

Подтвердить или опровергнуть по коду, с цитатами файлов и строк:

1. `app/Domain/Business/Actions/CreatePartnerApplicationAction.php` — правило ИНН применяется **только к подтверждённым** юрлицам (методы `findOwnedVerifiedPartnerByInn` и `attachBrandToVerifiedPartner`). Для неподтверждённого юрлица путь уходит в `materializePartnerDraft`, который безусловно создаёт нового партнёра и членство владельца. Это основной подозреваемый.
2. `app/Infrastructure/Integrations/Kuper/Reconcilers/PartnerProvisioner.php` — тот же паттерн создания партнёра без дедупликации по ИНН. Проверить, может ли он быть вторым источником дублей (в том числе по расписанию/очереди).
3. Есть ли где-либо дедупликация или уникальность по ИНН: индексы, `firstOrCreate`, доменные проверки. Ожидание — нет ни одной. Подтвердить выборкой из `information_schema`/`pg_indexes` и грепом по коду.
4. Почему оба юрлица названы «АКСИОМА», хотя заявка и точка — «Пышка»: имя юрлицу присваивается обогащением по ИНН, бренд теряется. Зафиксировать отдельным выводом (не чинить в этой задаче, но описать).

## 3. Что нужно сделать

**Обязательное:**

1. **Красный тест первым.** Воспроизвести дефект тестом, который падает до правки: подача заявки по ИНН, у которого уже есть неподтверждённое юрлицо, не должна создавать второго партнёра.
2. **Правило:** одно юрлицо — один партнёр по нормализованному ИНН, **независимо от подтверждения**. Несколько точек и брендов живут под одним юрлицом.
3. **Закрыть все пути создания партнёра**, а не только путь заявки — иначе дубли вернутся через провижининг.
4. **Гонка:** две одновременные подачи с одним ИНН не должны дать двух партнёров.
5. **Чужой ИНН:** если ИНН уже принадлежит другому пользователю — это не дубль, а конфликт владения. Поведение заявки должно быть предсказуемым; чужое юрлицо переиспользовать нельзя.
6. **Тесты** на всё перечисленное. Локальный гейт зелёный, стиль и типы чистые.

**Учесть уже сделанное, не переделывать вслепую:**

- Ветка **`t027-application-identity`** (коммит `c18137ac`, от `staging`, **не опубликована**). Модель владельца, которую она реализует: заявка живёт по своему идентификатору, повторная подача правит ту же заявку; лимит пяти считается **по заявкам пользователя, ожидающим подтверждения** (статусы `submitted`, `awaiting_rep_approval`, `invoice_issued`, `awaiting_payment`, `verifying`), а не по партнёрам и не по ИНН. Тесты ветки: 18 зелёных в наборе заявок, 216 в смежных кабинетах.
- Независимый разбор этой ветки закрыл обход лимита при переоткрытии и перехват правила ИНН; **открытые хвосты**: нормализация «4к1» против «4 к 1», синхронизация точки при смене адреса, повторная подача по уже подтверждённой точке, отсутствие истории смены статусов заявки, и главное — **уникальный индекс включать нельзя, пока не сведены исторические дубли**.
- Решение по ветке за владельцем. По умолчанию: новая ветка от `staging`, наработки t027 перенести осознанно, а не вслепую.

**Данные:**

- Подготовить сведение **существующих** дублей: какой партнёр остаётся, куда переносятся членства, точки и заявки. Никаких удалений без `WHERE`; скрипт идемпотентный, обратимый, с логом изменений.
- После сведения — предложить уникальный индекс по нормализованному ИНН и объяснить, почему он безопасен.

## 4. Выгрузка на staging

Канонический документ: `lovii_docs/canon/CI_RUNNERS_SELFHOSTED.md` (действует с 27.09.2026; пока не сбросится лимит GitHub Actions). Порядок:

1. **Локальный гейт до пуша** (`tools/lovii-php-tests.sh core` и прочее по затронутым репозиториям). Он первая линия, CI — вторая.
2. **Пуш в `staging`** → проверки на раннерах `gostiny-ci-*` → **автодеплой стенда** (git reset + build + migrate + up + health-check).
3. **Смотреть прогон:** `gh run list --branch staging --limit 1`, затем `gh run watch <id> --exit-status`. Пуш создаёт новый прогон — старый id не переиспользовать.
4. **Приёмка стенда:** на сервере `curl -s https://api-staging.lovii.ru/healthz` (с машины владельца внешний curl может таймаутить).
5. **Прод — только вручную:** `gh workflow run ci.yml --ref master`.
6. **Откат:** штатный GitHub Revert плохого коммита → пуш в `staging` → стенд откатится сам. Аварийно, мимо CI: в `/opt/lovii-<repo>-staging` — `git fetch origin && git reset --hard origin/staging@{1}` + build + up.
7. **Если раннер offline/завис** — доложить владельцу и принимать по-старинке: локальный гейт + ручной деплой по SSH.

## 5. Ловушки (уже стоили инцидента — не повторять)

- **Тесты — только санкционированным раннером:** `~/LOVII/tools/lovii-php-tests.sh core|admin|b2b`. Прямой запуск тестов из этого репозитория один раз ушёл в живую локальную базу и `migrate:fresh` стёр схему стенда.
- Миграции на живой локальной базе не гонять. `migrate:fresh` по базе `laravel` = потеря данных стенда.
- **Не трогать основной чекаут `~/LOVII/lovii-core`** — там ветка `ci-self-hosted-runner` с чужими незакоммиченными правками. Работать в отдельном worktree от `staging`.
- Канон-документы правит только владелец.
- Публикация — только по явной команде владельца; после выгрузки доложить id прогона и результат проверки.
