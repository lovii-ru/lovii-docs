## Контекст

Решение владельца: **VK — следующий OTP-канал доставки** платформы. Заглушки
(sms/whatsapp/vkontakte/call) уже скрыты из списка каналов (`4d544ed`); VK
возвращается в список только как полноценно работающий канал — «Скоро»-состояние
для VK не требуется, канал делаем до показа покупателю.

Что уже есть у владельца (док-заготовка в воркспейсе; **СЕКРЕТЫ В КАНОН И РЕПО НЕ
КОПИРОВАТЬ** — устав, факт-guard; секреты живут в локальном файле и .env стейджинга):

- сообщество `vk.ru/loviiru` (публичная страница), group_id — в локальном доке
  (`/Users/best/LOVII/OTP codes VK .md`; для конфига предложить env `VK_GROUP_ID`);
- **токен сообщества создан** (право «доступ к сообщениям сообщества») — строка в том
  же локальном доке; на staging попадёт через env (внесёт zcode, SSH);
- **строка подтверждения Callback** — выдана VK при попытке привязать URL
  `https://app-staging.lovii.ru/vk/callback` (там же); пока сервер не отвечает —
  подтверждение не завершено, владелец ждёт нашей готовности;
- черновик шагов владельца из дока: включить «Сообщения сообщества» → Callback API
  (события `message_new` / `message_allow` / `message_deny`, версия API 5.199 в
  заготовке — сверить актуальную) → пользователь заходит по `vk.me/loviiru` и пишет
  первым → приходит `message_allow` → сохраняем vk_user_id → `messages.send` с кодом;
  ошибка 901 = «нет разрешения на сообщения» → фолбэк.

Рабочий прецедент в коде — **Telegram-канал** (session 014/016–017): привязка
(`MaxBotLink` scope `telegram:otp`), ответ `send-code` `telegram_link_required` +
deeplink, экран привязки в lovii-app, `TelegramSender` (код первой строкой, inline
copy_text), long-poll воркеры (F-030). VK-флоу должен лечь в те же интерфейсы
(`OtpSenderContract`, контракт `*_link_required`, экран привязки в клиенте).

## Что сделать

1. **Верификация механики по официальной документации VK (dev.vk.com, актуальная
   версия API; цифры из заготовки владельца не принимать на веру):**
   - `messages.send` от имени сообщества (peer_id = vk_user_id): формат, права
     токена сообщества, коды ошибок 901/902 и их обработка;
   - события Callback API `message_allow` / `message_deny` / `message_new`:
     payload, handshake подтверждения URL (type=confirmation → вернуть строку),
     опциональный `secret_key` и его проверка, формат ответа сервера;
   - лимиты: частота отправки сообществом, ограничения на пользователя, квоты токена;
   - **альтернатива inbound: Callback API vs Community Long Poll**
     (`messages.getLongPollServer`) — сравнить надёжность на нашем РФ-хостинге
     (прецедент F-030: входящие вебхуки Telegram заблокированы сетью; VK — другая
     сеть, но класс риска тот же). Дать рекомендацию с обоснованием; финальное
     решение — владельца;
   - краткая юр. заметка: является ли подписка на сообщения сообщества
     (`message_allow`) достаточным согласием для доставки кода (не юр. заключение,
     пометка для владельца).
2. **Продуктовый флоу по образцу Telegram:** экран входа → VK → `send-code` →
   привязки нет → ответ `vk_link_required` + deeplink (`vk.me/loviiru`) →
   пользователь пишет сообществу → `message_allow` → сервер сохраняет привязку
   (сравнить: переиспользование `MaxBotLink` со scope `vk:otp` vs отдельная модель —
   предложить) → повторный `send-code` → `messages.send` с кодом → 901 → снова
   `vk_link_required`. Описать состояния, таймауты привязки, throttle
   (`throttle:otp-send` уже есть), поведение `message_deny`.
3. **Спека-фаза «VK»** в `lovii-core/docs/specs/otp-delivery-channels.md` (по образцу
   фазы Telegram): компоненты (`VKSender`, публичный контроллер callback, обработчик
   событий, клиент VK API с таймаутами), env-ключи (предложить имена:
   `VK_COMMUNITY_TOKEN`, `VK_GROUP_ID`, `VK_CALLBACK_CONFIRMATION`,
   `VK_CALLBACK_SECRET`, `VK_API_VERSION`, `OTP_VK_ENABLED`), маршрут
   (`POST /api/v1/vk/callback` — вне auth, с проверкой confirmation/secret),
   миграции/модель привязки, тесты (unit+feature по образцу `TelegramOtpAuthTest`),
   план деплоя и включения канала в список (`AllChannelsStrategy` + флаг).
4. **T-задача(и) для zcode** по шаблону WORK_PROTOCOL §4 — самодостаточные (файлы,
   шаги, гейты, критерий приёмки, стоп-листы): (а) реализация VK-канала кодом и
   тестами; (б) настройка стейджинга: env через SSH (zcode), коннективити-чек
   `api.vk.com` из контейнера core-staging (исходящий) и достижимость
   `app-staging.lovii.ru` для Callback VK (входящий, внешняя проверка), live-план.
5. **Чек-лист владельца** (кнопки VK UI, точные URL разделов — в спеке): порядок
   координации «сначала деплой обработчика callback → потом вписать URL в
   настройках сообщества → VK шлёт confirmation → сервер отвечает строкой →
   Подтвердить/Сохранить»; где включить «Сообщения сообщества»; где задать
   `secret_key`; что владелец сообщает zcode после каждого шага.
6. **Канон:** FEATURES §2 (VK — в работе), BACKLOG трек V (актуализировать по
   итогам), REGISTRY/срез STATUS в той же серии, fact-guard 🟢, CI lovii_docs 🟢.

  CI/деплой не триггерят).
- Сервер (SSH), env стенда, сетевые проверки из контейнера — zcode, не Super Z:
  если изысканию нужна проверка с сервера — пометить в T-задаче/отчёте, zcode

## Отчёт исполнителя

**Super Z, 2026-09-09 — задача выполнена, канон синхронизирован (срез STATUS, задача 32).**

1. **Верификация механики (п.1 постановки) — выполнена по официальным источникам:**
   машинночитаемая схема **VKCOM/vk-api-schema (v=5.199)** — official, сверяется с
   dev.vk.com; факты в спеке §7.1:
   - `messages.send` — `access_token_type: [user, group]`: токен сообщества работает;
     параметры `peer_id`, `random_id` (антидубль, обязателен), `group_id`;
   - ошибки: **901** (нет разрешения → привязка), **902** (приватность → канал
     недоступен пользователю, не ретраим), 6/914/15/200; лимит токена сообщества —
     **20 req/s** (dev.vk.com), пользовательский 3 req/s не используем;
   - Callback API: handshake — на `type=confirmation` сервер отвечает **сырой строкой**
     (не JSON); `secret` в каждом событии (если задан); `event_id` — дедуп;
   - события `message_new` / `message_allow` / `message_deny` подтверждены схемой
     (payload в карточке F-038 и спеке §7.1);
   - **`ref`/`ref_source` подтверждены схемой** у входящих сообщений: привязка по
     `https://vk.me/<screen>?ref=<binding_token>` работает по образцу Telegram
     (UUIDv4 36 симв. влезает в лимит ref ≤100) — fallback «код привязки»
     зарезервирован, не реализуем (§7.3);
   - версия: схема master = **5.199** — заготовка владельца совпала (не устарела);
     политика VK с 01.12.2024: Callback/LongPoll <5.81 не поддерживаются.
2. **Решение Callback vs Long Poll (п.1) — рекомендация: Callback API** (§7.4):
   F-030 был блокировкой Telegram-специфичной (РФ-сеть режет и inbound, и outbound к
   api.telegram.org; VK — российская сеть, MAX API с того же хоста доступен),
   воркеры не нужны, строка подтверждения уже получена. Long Poll (`getLongPollServer`
   подтверждён схемой, token: group) — задокументированный fallback с тем же
   обработчиком. **Финальное решение — владелец** (открытый вопрос №5 спеки §12).
3. **Спека (п.3) — фаза «§7 VK»** в `otp-delivery-channels.md` v1.1: lovii-core
   коммиты `a2f62ed` + `465a2e3` (docs-only, CI не триггерят); session-док 019.
   Дизайн-уточнение: VK появляется в списке клиента только при заданном токене
   (условная запись в `AllChannelsStrategy` — философия `4d544ed`/F-037),
   «Скоро»-бейдж для VK не вводится.
4. **Ловушка для zcode — F-038:** `max_bot_links.phone` UNIQUE без scope бота —
   один телефон не может держать привязки двух ботов; в T-002 включена миграция
   `unique(bot, phone)`. Заодно: безкодовый сценарий VK невозможен (VK не передаёт
   телефон), статус-поллинг не нужен — код доставляется сразу после привязки.
5. **T-задачи (п.4) — созданы, самодостаточны, порядок выдачи:**
   [`T-002-vk-otp-channel-core`](T-002-vk-otp-channel-core.md) (реализация + тесты,
   гейты pint/pest, session 020) → [`T-003-vk-otp-channel-app`](T-003-vk-otp-channel-app.md)
   (клиент: `vk_link_required`/`vk_deeplink`, иконка IconVk уже есть) →

6. **Чек-лист владельца (п.5) — в T-004 шаги 4–6** (и спека §7.7): URL в настройках
