## Контекст

F-024: на карточке товара витрины блок КБЖУ скрыт, потому что данные не
заполняются (M-СП-партнёрам некогда). Владелец: помочь партнёрам — придумать
способ «считать» КБЖУ и подставлять автоматически там, где человек не заполнил.

## Что сделать (ресёрч + спека, без имплементации)

1. **Источники данных**: открытые базы (Open Food Facts, FoodData Central,
   РФ-справочники Химсостава Скурихина), Kuper-импорт (есть ли нутриенты в
   `catalog_products`/payload уже?), усреднённые значения по типовым позициям
   меню (блюда общепита).
2. **Механика подстановки**: по штрихкоду (barcode уже в модели позиции?) →
   по названию/категории с нормализацией; пометка «примерное значение» в UI;
   партнёр может перезаписать (его данные приоритетны всегда).
3. **UX b2b**: где показывать партнёру подставленное (бейдж «авто»?), как
   выглядит «заполнить вручную vs оставить авто»; массовое применение.
4. **Витрина**: условия возврата блока КБЖУ на карточку (только при наличии
   данных; дисклеймер «средние значения»).
5. **Риски**: юридические (неточная нутрициология — дисклеймер), качество
   источников, объём ручной верификации.
6. Спека в этот файл: варианты + рекомендация + оценка; решение владельца 🔶.

## Что НЕ делать

- НЕ имплементить; НЕ трогать карточку витрины; НЕ грузить Kuper-пайплайн.

## Ресёрч + спека — v1.0.0 (Super Z, 2026-09-11; КОД НЕ ПИСАЛСЯ)

### 1. Текущее состояние кода (проверено)

- `merchant_offers.barcode` (string nullable) — **штрихкод уже в модели**,
  но Kuper-импорт его не заполняет (payload оффера: sku/retailer/store/
  taxon/price/stock — нутриентов и barcode в Kuper-API payload нет).
- `catalog_products.attributes` (jsonb) — сейчас human_volume/volume/
  volume_type/price_type; сюда же ляжет nutrition-блок (или отдельные
  колонки — 🔶 п.7.1).
- B2b-кабинет: полей КБЖУ нет вообще (ни в схеме, ни в Filament-форме) —
  рельсы заполнения создаёт эта спека.
- F-024: витринный блок КБЖУ скрыт при отсутствии данных — механика
  «показывать только при наличии» уже есть, возвращать блок будем
  наполнением.

### 2. Источники данных (3 варианта + гибрид)

| Источник | Покрытие | Качество | Цена/лицензия | Стык |
|---|---|---|---|---|
| **Open Food Facts** (OFF) | упакованные товары, штрихкоды, ~3 млн продуктов | среднее (краудсорс), для РФ — неровное | ODbL/CC-BY-SA, бесплатно, атрибуция обязательна | REST v2 по barcode: `https://world.openfoodfacts.org/api/v2/product/{barcode}.json` |
| **FoodData Central** (USDA) | продуктовый состав США, SR Legacy/Foundation | высокое, но американские рецепты | public domain, бесплатно | REST по названию (FDC API key бесплатный) |
| **Скурихин «Химический состав»** (СКФО РФ) | сырьё и типовые блюда общепита | эталон для РФ, но это справочник-книга | издание, не API — оцифровка таблиц вручную/одноразово | локальная таблица ~500–800 позиций |
| Kuper-пайплайн | нутриентов в payload НЕТ | — | — | стыка нет (п.1) |

**Рекомендация: гибрид по типу товара** —
- **упакованные товары** (Еда-ритейл): barcode → OFF; miss → название+
  бренд+объём с нормализацией; miss → «заполните вручную»;
- **блюда общепита** (Еда-кафе): категория+название → локальная таблица
  типовых позиций (Скурихин-основа, ~позиций под меню МСП: салаты/супы/
  горячее/выпечка/кофе…). Это закрывает самую частую боль МСП «я не знаю
  КБЖУ своего супа» усреднёнными эталонными значениями;
- непродовольственные (Товары/Услуги): КБЖУ не подставлять никогда
  (урок F-024: «жирность 2,5 на букете» недопустим — гейт по
  merchant_type=restaurant/Еда).

### 3. Механика подстановки

1. **Триггер**: партнёр сохранил товар с пустым КБЖУ → queued-job
   автозаполнения (не в веб-запросе); перезапуск при переименовании товара.
2. **Приоритет данных железно такой**: manual (партнёр) > verified-auto
   (админ подтвердил) > auto (подставлено) > нет. Перезапись партнёром —
   всегда, source меняется на manual, авто-значение уходит в историю.
3. **Матчинг**: (а) barcode exact; (б) name+brand нормализованный
   (lowercase, ё→е, стоп-слова объёма) → exact/совпадение ≥ порога
   (fuzzy 0.9 — 🔶 п.7.2, начать с exact-only, фолбэк «нет»);
   (в) общепит: нормализованное название → таблица типовых позиций
   (+синонимы: «Цезарь» ≡ «Салат Цезарь с курицей»).
4. **Provenance обязателен**: каждая подстановка пишет источник
   (off_id/fdc_id/skurikhin_code), дату, версию — для аудита и «почему так».
5. **Массовое применение**: b2b-команда «заполнить КБЖУ автоматически» для
   всех незаполненных товаров точки с превью-отчётом (сколько найдено/
   пропущено) до применения — 🔶 п.7.3 (рекомендация: сначала превью,
   применение кнопкой).

### 4. UX b2b

- Заполненное авто: значения видны + бейдж «авто» (цвет tertiary) + тултип
  «средние значения из открытых источников, источник: …»;
- Кнопки: «Оставить как есть» (значения остаются авто) / «Изменить»
  (партнёр правит → manual, бейдж исчезает);
- В списке товаров: колонка-индикатор «КБЖУ: ✓ / авто / —» + фильтр «без
  КБЖУ» для точечного заполнения;
- Онбординг-подсказка: «Не знаете КБЖУ? Мы подставим средние значения —
  вы сможете исправить».

### 5. Витрина

- Блок КБЖУ возвращается на карточку **только** при наличии хоть одного
  нутриента (сейчас так и скрыт — рельсы не меняются);
- Для auto-значений — дисклеймер «средние значения» мелким шрифтом под
  блоком; для manual — без дисклеймера;
- Непродовольственные merchant_type — блок не показывается (гейт уже
  описан в F-024 фикс-плане).

### 6. Риски

- **Юридические**: подставленное среднее ≠ данные производителя — дисклеймер
  обязателен; в оферту МСП добавить пункт «ответственность за
  нутрициологическую точность — на партнёре»; для детских/диетических
  категорий авто-подстановку не давать вообще (список 🔶 п.7.4);
- **Качество OFF по РФ**: у части SKU пусто/устарело — метрика покрытия
  после пилота (ожидание: 40–60% упакованных по barcode; остальное — ручное);
- **Скурихин-таблица**: одноразовая оцифровка ~500–800 позиций (1–2 дня
  ручной работы) — нужен исполнитель, 🔶 п.7.5;
- **Лицензия OFF**: атрибуция на витрине/в оферте (ODbL) — маленький, но
  обязательный хвост.

### 7. Решения владельца 🔶

1. Хранение нутриентов: jsonb в `catalog_products.attributes` (рекомендую —
   гибкая схема per 100 г/мл + порция) vs отдельные колонки;
2. Порог fuzzy-матчинга: начать с exact-only (рекомендую для пилота) vs 0.9;
3. Массовое автозаполнение: превью+кнопка (рекомендую) vs сразу;
4. Категории-исключения для авто-подстановки (детское/диетическое) — список;
5. Кто оцифровывает таблицу Скурихина и когда (блокер для общепит-ветки);
6. Пилотный объём: одна точка-ресторан + один продуктовый магазин.

**Вердикты владельца (чат, 2026-09-13):**

1. ✅ jsonb в `catalog_products.attributes` — по рекомендации спеки;
2. ✅ exact-only для пилота (fuzzy 0.9 — кандидат на вторую итерацию);
3. ✅ массовое заполнение: превью-отчёт + кнопка применения;
4. ✅ решено иначе, чем «словарь исключений» из спеки: детскому/диетическому
   авто-подстановка не применяется вовсе — заполнение на усмотрение
   продавца (вручную). При реализации — гейт по категории, без ручного
   ведения списка;
5. ✅ снято владельцем 2026-09-13: действующих партнёров-общепита нет —
   оцифровка Скурихина не нужна сейчас; вернуться при онбординге первых
   ресторанов (тогда же — исполнитель и срок ручного переноса);
6. ✅ снято владельцем 2026-09-13: «пилот на реальных точках» неприменим —
   действующих точек нет; при старте реализации роль пилота естественно
   сыграют первые живые партнёры.

**Итог (2026-09-13):** задача ресёрча выполнена полностью; реализация
(вне объёма этой карточки — по стоп-листу код не писался) отложена

решения пп.1–4 остаются зафиксированным базисом будущей спеки

**Оценка**: рельсы+модель+job ~2–3 сессии; OFF-интеграция ~1 сессия;
